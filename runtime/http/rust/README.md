# Rust HTTP runtime

Shared runtime crate for Rust REST APIs generated by `superschematic`.

This crate provides:

- Request context structure used by generated handlers, with the caller
  (`principal`) on a route that needs one, the calling service
  (`service_caller`), and the end user's token to forward (`bearer_token`)
- `ApiError` and `error_response`: a refusal as an RFC 9457 problem
  (`application/problem+json`), with `details` and `errors` members, and
  the response headers it carries (`with_header`)
- `request_ids`: the middleware the generated router runs around every
  route, which settles the request's id (`X-Request-ID` or a fresh UUID),
  echoes it in `x-request-id`, adds it to a problem body and marks every
  response `no-store`
- `json_body` and `query_values`: a request's body as JSON whatever its
  `Content-Type` (none when empty), and its query's keys and values, with a
  failure as an `ApiError`
- `ParamSpec`: how the generated router decodes one path, query or body
  argument, as the TypeScript runtime's `params.ts` does, refusing a value
  with a 400 whose `details` name it
- `input`, `required_input` and `input_refusal`: an operation's input
  parsed by its type's generated `parse_<type>`, with undeclared keys
  refused and field errors in the problem's `errors`; `body_fields` and
  `operation_response`, the body object scalar arguments come from and the
  result in the success envelope
- `schema`: the schema runtime crate the generated types crates validate
  with, re-exported so a parameter spec and an input parse share its types
- `RouterOptions`, `openapi_router`: the OpenAPI document and its RapiDoc
  page a generated router serves
- `Authenticator` and `Principal`: how a service tells the router who the
  caller is, and the dotted-path permission rule (`has_any_permission`)
- `ServiceAuthenticator` and `ServiceCaller` (D37): which deployable is
  calling, from a JWT in `Service-Authorization`. `JwtServiceAuthenticator`
  verifies RS256, ES256 and EdDSA tokens against a `ServiceAuthConfig`,
  with static keys or a JWKS it caches per URL
- `RouteControls`: a route's `@rateLimit`, `@bodyLimit`, service step
  (`@requireService`, `@allowService`), permission check and `@timeout`,
  applied with `route_layer` in that order
- Service credential sources for a calling service, each a `TokenSource`:
  `GoogleIdTokenSource` (Cloud Run), `TokenFileSource` (a Kubernetes
  projected token) and `SignedKeySource` (an edge's Ed25519 key)
- What a server in a stack reads, opens and logs through, below

Signatures are checked with `ring`. The optional `http-client` feature adds
`HttpFetcher` (reqwest, native-tls), the default JWKS fetcher of
`JwtServiceAuthenticator` and HTTP client of `GoogleIdTokenSource`. Without
it, a service passes its own `KeyFetcher` or `HttpGetter`.

## Running in a stack (D57)

A generated Rust server in a stack reads its configuration from the
environment, opens its databases, calls other APIs with a service
credential and logs JSON lines, through these pieces, the twins of the Go
and TypeScript runtimes' (D51):

- `stackconfig`, with no feature: the readers of the fields an API's edges
  derive (section 3.4 of `docs/stack-model.md`), each from one variable per
  member, `<field>_<MEMBER>`. `load_database` reads `<field>_URL`, or
  `<field>_CLOUD_SQL_INSTANCE`, `_DATABASE` and `_USER`, as a `Database`
  (`Url` or `CloudSql`); `load_service` the callee's `<field>_URL` and its
  `<field>_CREDENTIAL_*`, as a `Service`; `load_bucket` `<field>_NAME` and
  `<field>_ENDPOINT`; `load_callers` the indexed `<field>_ISSUERS_*`, as the
  `ServiceAuthConfig` `JwtServiceAuthenticator` takes; and `load_cors`
  `<field>_ORIGINS`. Each refuses what Go's refuses, with its messages, all
  of a field's in one `StackConfigError`, and has a `_from` twin over a map.
  `runtime/http/testdata/stackconfig_parity.json` holds the three runtimes
  to one encoding; `tests/stackconfig_parity.rs` runs every vector. An
  API's identity config, `<API>_IDENTITY`, is the JSON `identity::Config`
  reads.
- Credential sources: `stackconfig::credential_source` turns a `Service`'s
  credential into the `TokenSource` it names: `GoogleIdTokenSource` for
  `google-id-token` (with the `http-client` feature), `TokenFileSource`
  for `token-file`, and `SignedKeySource` for `signed-token`, signing as
  the issuer for the audience. A generated SDK's `ServiceTokenSource` is
  the same type, so its `ServiceCredential` is
  `{ token: credential_source(c)?, headers: c.header_names() }`.
- The `postgres` feature's `postgres` module: `connect(&Database)` opens a
  `deadpool-postgres` pool, which connects when first used, and
  `ping(&Pool)` is the `SELECT 1` a server's `/readyz` makes. A URL
  connects as it says, its `sslmode` read as libpq reads it: `disable` is
  no TLS, `prefer` encrypts when the server offers TLS and `require`
  always, neither verifying the certificate, and `verify-ca` and
  `verify-full` verify it against the system's roots. A
  Cloud SQL instance connects over the Unix socket Cloud Run mounts,
  `/cloudsql/<connection name>`, without TLS, as its IAM database user,
  with an OAuth access token from the metadata server
  (`GCE_METADATA_HOST` honoured) as the password, fetched for each new
  connection. The module re-exports `deadpool_postgres` and
  `tokio_postgres`. With `identity-postgres` too, `identity::PostgresPool`
  runs the identity store over the same pool.
- The `logging` feature's `logging` module: `init_json(stack, server)`
  installs a `tracing-subscriber` layer writing one JSON object per line on
  stdout at `info`, with the TypeScript `createLogger`'s members: `level`,
  `time` (RFC 3339 in UTC, to the millisecond) and `msg` first, then
  `stack` and `server`, the fields of the spans the event is in (`api`, in
  an `api_span(api)`), and the event's own.

The Postgres tests run on the database
`SUPERSCHEMATIC_POSTGRES_TEST_DATABASE_URL` names, and skip without one;
`SUPERSCHEMATIC_POSTGRES_TEST_TLS=1` says it offers TLS with a certificate
the system's roots do not sign:

```
cargo test --features postgres,identity-postgres,identity-sqlite,logging
```

## Identity (D50)

The optional `identity` feature adds the `identity` module, the Rust runtime
of the core user model. It does what the Go runtime's
`runtime/http/go/identity` does, held to the shared vectors
(`runtime/http/testdata/identity_parity.json`, whose harness
`runtime/http/testdata/README.md` states):

- `identity::Config`: the identity config's JSON, read strictly, with its
  defaults and rules
- argon2id passwords as PHC strings (`hash_password`, `verify_password` and
  its rehash decision, `check_password` for `Auth.Password`), session tokens
  (`new_token`, `hash_token`), the credential on a request
  (`extract_credential`), the session cookie (`Config::session_cookie`,
  `Config::clear_cookie`), the cross-origin check (`check_cross_origin`,
  Go's `net/http.CrossOriginProtection`) and the credentialed `CorsLayer`
- permission names, a principal's permissions, the grant rule and
  capabilities over the router's operation table (`Route::of` an
  `OperationInfo`)
- `Store` and `SqlStore`, built from the schema's identity descriptor (the
  generated types' `IDENTITY_DESCRIPTOR`), which runs its SQL through a
  `Client`: `TokioPostgres` with `identity-postgres`, `Rusqlite` with
  `identity-sqlite`, or a binding of the service's own (a pool, another
  driver). The store parses logins, display names and keys with the scalar
  catalog the service passes as `Scalars`, superscalar's registry in a
  generated crate, since this crate does not link the scalar crate
- `Service`, every session and administration operation with the Go
  runtime's statuses and problem codes; `Service::handler` and
  `Service::routes`, the axum handlers of `ir/identity_routes.go`; and
  `IdentityAuthenticator`, the router's `Authenticator`, so `admit`,
  `RouteControls` and `OperationInfo::admit` work unchanged

A password hash runs on tokio's blocking pool, so the service needs a tokio
runtime. The store and route tests run on SQLite, and on Postgres too with
`identity-postgres` and the database `SUPERSCHEMATIC_IDENTITY_TEST_DATABASE_URL`
names:

```
cargo test --features identity-postgres,identity-sqlite
```
