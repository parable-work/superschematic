# Rust HTTP runtime

Shared runtime crate for Rust REST APIs generated by `superschematic`.

This crate provides:

- Request context structure used by generated handlers, with the caller
  (`principal`) on a route that needs one, the calling service
  (`service_caller`), and the end user's token to forward (`bearer_token`)
- `ApiError` and `error_response`: a refusal as an RFC 9457 problem
  (`application/problem+json`), with `details` and `errors` members, and
  the response headers it carries (`with_header`)
- `request_ids`: the middleware the generated router runs around every
  route, which settles the request's id (`X-Request-ID` or a fresh UUID),
  echoes it in `x-request-id`, adds it to a problem body and marks every
  response `no-store`
- `json_body` and `query_values`: a request's body as JSON whatever its
  `Content-Type` (none when empty), and its query's keys and values, with a
  failure as an `ApiError`
- `ParamSpec`: how the generated router decodes one path, query or body
  argument, as the TypeScript runtime's `params.ts` does, refusing a value
  with a 400 whose `details` name it
- `page`: the page of a `@paginated` operation (D60). `PageSpec::query`
  reads `cursor` and `limit` from the query with a parameter's 400s,
  `PageSpec::request` and `PageSpec::check` hold a request an in-process
  caller built to the route's spec, `Cursor::encode` and `Cursor::decode`
  write and read a position as the unpadded base64url of its JSON, the
  encoder's error a 500 for a key no router reads back, and
  `Page::from_rows` keeps `limit` of the `limit + 1` rows an
  implementation read and sets `next`, or returns that error. A sorted
  operation's spec is `PageSpec::new(2, 5).sorted(SortSpec::new("sort",
  &["name", "sku"], "name"))` (D60, amended): `query` reads its `Sort` as
  sent, `sorted_request` from a form's values, and `check` holds it to the
  spec's values; `PageSpec::unbind` fills the default in and unbinds the
  cursor (`Cursor::unbind`), and `Page::bind` binds the `next`
  (`Cursor::bind`) to the base64url of `{"sort":"-placedAt","key":K}`. The
  router's decode and an in-process call each unbind once and bind once,
  and a cursor sent with another sort is the 400 `SORTED_CURSOR_DETAIL`.
  `tests/page_parity.rs` runs `runtime/http/testdata/page_parity.json`
- `input`, `required_input` and `input_refusal`: an operation's input
  parsed by its type's generated `parse_<type>`, with undeclared keys
  refused and field errors in the problem's `errors`; `body_fields` and
  `operation_response`, the body object scalar arguments come from and the
  result in the success envelope
- `schema`: the schema runtime crate the generated types crates validate
  with, re-exported so a parameter spec and an input parse share its types
- `RouterOptions`, `openapi_router`: the OpenAPI document and its RapiDoc
  page a generated router serves, and the `RateLimits` registry its routes
  take their limiters from (`rate_limits`, a new one by default). Options
  compare their registry by identity, so a clone is equal to its original
  and two `RouterOptions::default()` are not
- `Authenticator` and `Principal`: how a service tells the router who the
  caller is, and the dotted-path permission rule (`has_any_permission`)
- `ServiceAuthenticator` and `ServiceCaller` (D37): which deployable is
  calling, from a JWT in `Service-Authorization`. `JwtServiceAuthenticator`
  verifies RS256, ES256 and EdDSA tokens against a `ServiceAuthConfig`,
  with static keys or a JWKS it caches per URL
- `RouteControls`: a route's `@rateLimit`, `@bodyLimit`, service step
  (`@requireService`, `@allowService`), permission check and `@timeout`,
  applied with `route_layer` in that order. A generated router gives a
  route its operation's limiter from a `RateLimits` registry
  (`rate_limiter(limits.of(&OPERATION))`), one per operation, so the
  routers and the Topcoat procedures and pages that share the registry
  count a client against one budget (D44, amended); `rate_limit(n)` gives
  a manual route the service mounts itself a limiter of its own. A
  registry is meant for one app's operations: it keys a limiter by the
  operation's method, path, namespace, name and rate, so two APIs'
  operations of one name on different routes keep their own
- `OperationInfo`: an operation's route as the generated `operations`
  module states it, its rate limit and service clause (`ServiceClause`)
  included, for a caller that runs it in-process (D43). `admit` is the
  route's admission of a call that names no service caller, so it refuses
  a `@requireService` operation 401 `service_unauthorized`;
  `admit_service(Some(&caller))` is the route's service step for a caller
  the process names with `ServiceCaller::in_process(deployable, serves)`,
  by the rule `RouteControls` applies, and `admit_end_user` the end-user
  step; `context` and `service_context` build the `RequestContext` the
  route would hand the implementation (D37, amended)
- Service credential sources for a calling service, each a `TokenSource`:
  `GoogleIdTokenSource` (Cloud Run), `TokenFileSource` (a Kubernetes
  projected token) and `SignedKeySource` (an edge's Ed25519 key)
- What a server in a stack reads, opens and logs through, below

Signatures are checked with `ring`. The optional `http-client` feature adds
`HttpFetcher` (reqwest, native-tls), the default JWKS fetcher of
`JwtServiceAuthenticator` and HTTP client of `GoogleIdTokenSource`. Without
it, a service passes its own `KeyFetcher` or `HttpGetter`.

## Running in a stack (D57, D65)

A generated Rust server, job or worker in a stack reads its configuration
from the environment, opens its databases and its buckets, calls other APIs
with a service credential, enqueues and claims queue messages, stops on a
signal and logs JSON lines, through these pieces, the twins of the Go and
TypeScript runtimes' (D51):

- `stackconfig`, with no feature: the readers of the fields an API's edges
  derive (section 3.4 of `docs/stack-model.md`), each from one variable per
  member, `<field>_<MEMBER>`. `load_database` reads `<field>_URL`, or
  `<field>_CLOUD_SQL_INSTANCE`, `_DATABASE` and `_USER`, as a `Database`
  (`Url` or `CloudSql`); `load_service` the callee's `<field>_URL` and its
  `<field>_CREDENTIAL_*`, as a `Service`; `load_bucket` `<field>_NAME` and
  `<field>_ENDPOINT`; `load_callers` the indexed `<field>_ISSUERS_*`, as the
  `ServiceAuthConfig` `JwtServiceAuthenticator` takes; and `load_cors`
  `<field>_ORIGINS`. Each refuses what Go's refuses, with its messages, all
  of a field's in one `StackConfigError`, and has a `_from` twin over a map.
  The members only a Worker reads, a D1 binding, a service binding and an
  R2 binding with its credential (D64), are refused with a message that
  says so, as Go's are.
  `runtime/http/testdata/stackconfig_parity.json` holds the three runtimes
  to one encoding; `tests/stackconfig_parity.rs` runs every vector. An
  API's identity config, `<API>_IDENTITY`, is the JSON `identity::Config`
  reads.
- Credential sources: `stackconfig::credential_source` turns a `Service`'s
  credential into the `TokenSource` it names: `GoogleIdTokenSource` for
  `google-id-token` (with the `http-client` feature), `TokenFileSource`
  for `token-file`, and `SignedKeySource` for `signed-token`, signing as
  the issuer for the audience with a private JWK or, from the generic
  connector, an Ed25519 private key's PKCS#8 PEM (`SignedKeySource::from_pem`,
  its `kid` the key's thumbprint, D63). A callers field's key may be the
  public key's SubjectPublicKeyInfo PEM, which `ed25519_public_jwk_from_pem`
  reads as a JWK. A generated SDK's `ServiceTokenSource` is
  the same type, so its `ServiceCredential` is
  `{ token: credential_source(c)?, headers: c.header_names() }`.
- `cors`, with no feature: a site's CORS (D55), the twin of Go's
  `cors.Handler` and TypeScript's `corsHandler`. `cors::Api::new(&cors,
  operations::ALL)` is an API's policy, its `<API>_CORS` origins and the
  methods of its operations (`cors::methods`), and the requests its
  operations' routes take (`cors::match_operations`, a `{param}` taking one
  segment). `SiteCorsLayer::new(apis)`, around the server's router, finds
  the API a request with an `Origin` is, a preflight by the method it asks
  for: a preflight from an origin the policy lists is answered 204 with
  `Access-Control-Allow-Origin`, `-Credentials`, `-Methods`, `-Headers`
  (`Accept, Authorization, Content-Type`) and `-Max-Age: 600`, and any
  other request reaches the router, whose answer gets the policy's headers
  where it set none (`Allow-Origin` and `Allow-Credentials` for a listed
  origin, `Vary` always). A preflight from an origin the site's policy does
  not list reaches the router too, so `identity::CorsLayer` on the API's
  router answers the origins its identity config trusts (D55, amended).
  `Policy::decide` is the decision `runtime/http/testdata/cors_parity.json`
  holds the three runtimes to; `tests/cors_parity.rs` runs every vector.
- `search`, with no feature: what an implementation needs to answer a
  `SearchQuery` argument (D62), the twin of Go's `search` package and
  TypeScript's `searchTerms`. `search::terms(q)` is the text's words (runs
  of non-`White_Space`, the first 8), `search::like_pattern(word)` the
  value of one `search_text LIKE ? ESCAPE '\'` condition (`ILIKE` on
  Postgres), and `search::matches(text, &terms)` an in-memory match, by
  `search::fold`, each character's simple lowercase.
  `tests/search_parity.rs` runs `runtime/http/testdata/search_parity.json`,
  and `examples/fold_mappings.rs` prints every fold, from which the Go
  runtime writes the mappings its older Unicode tables lack.
- The `postgres` feature's `postgres` module: `connect(&Database)` opens a
  `deadpool-postgres` pool, which connects when first used, and
  `ping(&Pool)` is the `SELECT 1` a server's `/readyz` makes. A URL
  connects as it says, its `sslmode` read as libpq reads it: `disable` is
  no TLS, `prefer` encrypts when the server offers TLS and `require`
  always, neither verifying the certificate, and `verify-ca` and
  `verify-full` verify it against the system's roots. A
  Cloud SQL instance connects over the Unix socket Cloud Run mounts,
  `/cloudsql/<connection name>`, without TLS, as its IAM database user,
  with an OAuth access token from the metadata server
  (`GCE_METADATA_HOST` honoured) as the password, fetched for each new
  connection. The module re-exports `deadpool_postgres` and
  `tokio_postgres`. With `identity-postgres` too, `identity::PostgresPool`
  runs the identity store over the same pool.
- The `logging` feature's `logging` module: `init_json(stack, server)`
  installs a `tracing-subscriber` layer writing one JSON object per line on
  stdout at `info`, with the TypeScript `createLogger`'s members: `level`,
  `time` (RFC 3339 in UTC, to the millisecond) and `msg` first, then
  `stack` and `server`, the fields of the spans the event is in (`api`, in
  an `api_span(api)`), and the event's own. A job's and a worker's
  entrypoint install it with `init_json_as(stack, logging::JOB, name)` or
  `logging::WORKER`, whose lines name the deployable `job` or `worker` in
  place of `server`, as Go's and TypeScript's do. It re-exports `tracing`.
- `Shutdown`, with no feature: the cancellation a job's method watches and
  a worker's loop stops on, tokio-util's `CancellationToken` (re-exported)
  under the name the generated code takes. `Shutdown::on_signals()`, inside
  a tokio runtime, is cancelled by the first SIGTERM or SIGINT, which it
  logs (`"shutting down"`); a second ends the process at once with 143 or
  130, as a generated server's does. `BoxError` is the error a job's or a
  worker's method returns.
- The `postgres` feature's `queue` module, the twin of the Go ORM's
  `queues.go` and TypeScript's `queue.ts` (D53): a DB's Rust types carry
  each queue's descriptor as JSON, which `QueueDefinition::parse` reads in
  TypeScript's `QueueDefinition` member names (`name`, `table`, `retries`,
  `backoffSeconds`, `maxBackoffSeconds`, `leaseSeconds`, `retainSeconds`,
  `fields` with each `name`, `column`, `json`, `list` and `default`, and
  the `statements` `sqlutil.PostgresQueueStatements` writes). `enqueue(&tx, &queue, &message)`
  writes a message in the caller's transaction, a deadpool `Transaction`,
  each member of the message's serde form to its field's column, an unset
  enum to its schema default. `PostgresQueue::<M>::new(pool, queue)` claims
  (`claim(n, lease)`, expiring dead claims first, as Go does), `extend`s,
  `complete`s, `fail`s (returning whether the message is dead, due again
  after the backoff doubled for each attempt before and capped at the
  maximum backoff, D68) and `release`s, each change refusing a token that
  no longer claims its message with `QueueError::ClaimLost`, and
  `prune(limit)` deletes up to `limit` messages done for the retention,
  never a dead one, returning how many. Parameters go as text, which
  Postgres reads by each column's type, as node-postgres sends them, a
  base62 `Identity.UUID` hyphenated; a claimed row's columns come back as
  the JSON values a message's type reads: a `TIMESTAMPTZ` in RFC 3339 in
  UTC as superscalar's `DateTime` writes it, a `UUID` hyphenated, a list
  from its array, JSON as itself. A column of a type it does not read
  (`POINT`, `INTERVAL`, which the descriptors leave out) is refused.
- The `postgres` feature's `worker` module, Go's `worker.Run` ported:
  `run_worker(queue, handler, Options { concurrency, grace, idle,
  prune_every }, shutdown)` claims for each free slot up to the concurrency
  (`concurrency_from_env(default)` reads `WORKER_CONCURRENCY`), waits the
  idle second after a claim that found too few, and after a failed claim a
  wait that doubles to 30 s. It runs each handler, any `Fn(M) -> impl
  Future<Output = Result<(), BoxError>>`, in a task of its own, extends its
  claim every third of the lease, completes the message on `Ok` and fails
  it on an error or a panic, with the error's chain of causes, up to 4000
  characters, as the cause. Each queue operation has 5 s to answer. Once
  `shutdown` is cancelled it claims no more, lets the running handlers
  finish within the grace (8 s by default), then drops the rest and
  releases their messages. As it starts and every `prune_every` (five
  minutes by default) it prunes the queue, `PRUNE_BATCH` (1000) at a time
  until a batch is short. It logs Go's and TypeScript's messages and
  fields (`queue`, `message`, `attempt`, `took`, `error`, `retryIn`,
  `pruned`) through `tracing`. It claims through the `WorkerQueue` trait,
  which `PostgresQueue` implements; a queue that does not implement its
  `prune` prunes nothing. With the `otel` feature and export on, each
  message's handling is a consumer span, `process <queue>`.
- The `otel` feature's `telemetry` module (D67), OpenTelemetry trace
  export over OTLP/HTTP in protobuf. `telemetry::start(Defaults { stack,
  kind, name })` is what a generated server's, job's or worker's `main`
  calls in place of `logging::init_json_as`: it installs the same log and,
  when the environment sets `OTEL_EXPORTER_OTLP_ENDPOINT` or
  `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` and `OTEL_SDK_DISABLED` is not
  `true`, `tracing-opentelemetry`'s layer beside it, which takes spans but
  not events, and not the spans that live as long as the process (an
  `api_span`, the worker loop's). It reads OpenTelemetry's variables as
  Go's and TypeScript's runtimes do: `OTEL_SERVICE_NAME` and
  `OTEL_RESOURCE_ATTRIBUTES` over the defaults (`service.name` the
  deployable, `service.namespace` the stack,
  `superschematic.deployable.kind`), the six standard samplers,
  `tracecontext`, `baggage` or `none` for `OTEL_PROPAGATORS`, and
  `http/protobuf` alone for the protocol; a value it does not support is a
  `TelemetryError` naming the variable. The `Telemetry` it returns flushes
  the spans still buffered, within five seconds, when it drops. The
  exporter sends through the `http-client` feature's `reqwest`, on a
  current-thread runtime of its own from the batch processor's thread, so
  export runs whatever runtime the process runs on. `ServerLayer::new(&[
  operations::ALL, ...])` is the layer of a server's app: a server span per
  request but `/healthz` and `/readyz`, the child of an incoming
  `traceparent`, named `<METHOD> <path template>` by the most literal
  operation whose route takes it. `transport()` is the `transport` of a
  `calls` edge's SDK client, `None` with export off: a client span per
  call, whose context the call carries in `traceparent` and `tracestate`.
  `job(name, run)` runs a job's method in a span named after its `@job`
  class. The runtime's spans carry their OpenTelemetry attributes beside
  `tracing`'s fields, and the log leaves out a span's `otel.` fields, so
  its lines are the same with export on or off. `telemetry::dispatch`
  builds the subscriber without installing it, for a test.
  `tests/telemetry.rs` runs each against an OTLP/HTTP receiver in the
  test's process.

- `bucket`, with no feature: the provider-neutral interface of a bucket an
  API lists in its `buckets` (D54), which its `Deps` holds as an
  `Arc<dyn Bucket>`, the twin of Go's `bucket.Bucket` and TypeScript's
  `Bucket`: `put(name, body, PutOptions)` (a `Body` of bytes, text or a
  `Stream` of chunks, such as an axum request's data stream, with its
  content type), `get(name)` (a `Reader`, the object's `Object` and its
  bytes as a `Stream`, which an axum handler answers with as
  `Body::from_stream(reader)`), `delete(name)`, `list(ListOptions)` (a
  `Page` of the objects under a prefix, in name order, up to 1000 unless it
  asks fewer, with the next page's token) and `signed_url(name,
  SignedUrlOptions)` (a V4 URL to `GET` or `PUT` one object, a whole number
  of seconds up to seven days, a `PUT`'s content type signed). A missing
  object is `BucketError::NotFound`; a name that is empty, over 1024 bytes
  or holds a CR, LF or NUL, and options no provider signs, are
  `BucketError::Invalid` before any request, with Go's and TypeScript's
  messages; anything else is `BucketError::Failed`, naming the bucket, the
  operation and its causes.
- The `gcs` feature's `gcs` module: `open_bucket(&stackconfig::Bucket)`, a
  `GcsBucket` over Cloud Storage's JSON API, with no Google library, as
  Cloud SQL's connection has none. On GCS it sends an access token for the
  workload's account from the metadata server (`GCE_METADATA_HOST`
  honoured), kept until 3 min 45 s before it expires, and signs a URL by
  IAM's `signBlob` as the account the metadata server names, which needs
  `roles/iam.serviceAccountTokenCreator` on itself, as the gcp target
  grants. It reads no credentials file, so off Google Cloud it reaches a
  bucket through an emulator. A connection with an endpoint, or `STORAGE_EMULATOR_HOST`,
  reaches an emulator with no credential, and signs its URLs for the
  emulator's host with a key the process makes, which fake-gcs-server takes
  without checking. `put` is one multipart upload, streamed for a stream;
  `get` reads the metadata, then that generation's bytes; reads that fail
  with 408, 429, a 5xx or no answer are tried twice more. The V4 signature
  is the one `@google-cloud/storage` writes, which a vector of its output
  holds it to. `GcsClient::with_options` points it elsewhere, as the tests
  do. `tests/gcs.rs` runs it against a fake Cloud Storage, metadata server
  and IAM, and against the fake-gcs-server
  `SUPERSCHEMATIC_TEST_GCS_EMULATOR` names, when it is set:

  ```
  docker run --rm -p 127.0.0.1:4443:4443 fsouza/fake-gcs-server:1.56.1 -scheme http -port 4443 -public-host 127.0.0.1:4443
  SUPERSCHEMATIC_TEST_GCS_EMULATOR=http://127.0.0.1:4443 cargo test --features gcs --test gcs
  ```

The Postgres tests run on the database
`SUPERSCHEMATIC_POSTGRES_TEST_DATABASE_URL` names, and skip without one;
`SUPERSCHEMATIC_POSTGRES_TEST_TLS=1` says it offers TLS with a certificate
the system's roots do not sign. `tests/queue.rs` runs the queue client and
the worker loop over a schema of its own holding the tables of sqlgen's
golden DDL of fixture-queue-db (`tests/testdata/queue/create.sql`), with
the descriptors tsgen's golden `queues.ts` holds for them, as JSON. The
loop's timing runs on tokio's paused clock with no database:

```
cargo test --features postgres,identity-postgres,identity-sqlite,logging,otel
```

## Identity (D50)

The optional `identity` feature adds the `identity` module, the Rust runtime
of the core user model. It does what the Go runtime's
`runtime/http/go/identity` does, held to the shared vectors
(`runtime/http/testdata/identity_parity.json`, whose harness
`runtime/http/testdata/README.md` states):

- `identity::Config`: the identity config's JSON, read strictly, with its
  defaults and rules
- argon2id passwords as PHC strings (`hash_password`, `verify_password` and
  its rehash decision, `check_password` for `Auth.Password`), session tokens
  (`new_token`, `hash_token`), the credential on a request
  (`extract_credential`), the session cookie (`Config::session_cookie`,
  `Config::clear_cookie`), the cross-origin check (`check_cross_origin`,
  Go's `net/http.CrossOriginProtection`) and the credentialed `CorsLayer`
- permission names, a principal's permissions, the grant rule and
  capabilities over the router's operation table (`Route::of` an
  `OperationInfo`)
- `Store` and `SqlStore`, built from the schema's identity descriptor (the
  generated types' `IDENTITY_DESCRIPTOR`), which runs its SQL through a
  `Client`: `TokioPostgres` with `identity-postgres`, `Rusqlite` with
  `identity-sqlite`, or a binding of the service's own (a pool, another
  driver). The store parses logins, display names and keys with the scalar
  catalog the service passes as `Scalars`, superscalar's registry in a
  generated crate, since this crate does not link the scalar crate
- `Service`, every session and administration operation with the Go
  runtime's statuses and problem codes; `Service::handler` and
  `Service::routes`, the axum handlers of `ir/identity_routes.go`; and
  `IdentityAuthenticator`, the router's `Authenticator`, so `admit`,
  `RouteControls` and `OperationInfo::admit` work unchanged

A password hash runs on tokio's blocking pool, so the service needs a tokio
runtime. The store and route tests run on SQLite, and on Postgres too with
`identity-postgres` and the database `SUPERSCHEMATIC_IDENTITY_TEST_DATABASE_URL`
names:

```
cargo test --features identity-postgres,identity-sqlite
```
