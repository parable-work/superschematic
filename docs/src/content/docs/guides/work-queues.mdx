A row can be work: a worker takes it, holds it while it works, and gives
it back. A worker that stops renewing loses what it held, and the work
goes back for another. Five behaviors of the core do this, and you
compose the ones you need:

| Behavior | What it adds | Requires |
| --- | --- | --- |
| [`Lease`](#lease) | an exclusive, time-bounded lease with a fencing token, heartbeats, expiry and messages to the holder | |
| [`Presence`](#presence) | a heartbeat on a row that stands for a worker; a missed one releases its leases | |
| [`Blueprint`](#blueprint) | children created with their parent, with dependencies between them | |
| [`Budget`](#budget) | reserve-then-settle budgets against limits, across enclosing scopes | |
| [`Retries`](#retries) | attempts counted per failure class, with caps and stuck detection | `Workflow` |

They run on the behaviors' core, so a DB table implements them
(`implements Lease<Job, { ... }>`,
[Rows a worker leases, retries, beats and meters](/superschematic/guides/database-tables/#rows-a-worker-leases-retries-beats-and-meters)),
and [development mode](/superschematic/guides/development-mode/) serves
them for a General schema's `@behavior`. Two behaviors the work queue
once had are not behaviors any more:

- **Queue** folds into a schema feature (D103). A queue's messages are a
  `@queue`'s, which its workers claim
  ([Queues](/superschematic/guides/queues/)). Rows that are work are
  claimed by a read and a lease ([A claim](#a-claim)). The build refuses
  `Queue`, naming `@queue`.
- **Assignment** is a bundle on a table, `Seats` with one seat
  ([Beyond plain tables](/superschematic/guides/database-tables/#beyond-plain-tables)).

`examples/engine-jobs` is a job runner on development mode, which CI
builds and tests: workers claim jobs in priority order, hold them under
leases, retry them by failure class and reserve CPU seconds for them; a
worker that stops beating loses its jobs to another; and a batch stamps a
job per step and settles when they finish.

## A job queue

A job is queued, running, done or failed. A lease that lapses puts it
back in the queue, until its third expiry fails it; a claim reserves CPU
seconds from its budget; failures are retried per class; and a job a
batch stamped waits for the steps before it:

<Snippet example="engine-jobs" file="schemas/dev/jobs.schema.json" />

- **`batch` is a relation**, held as `batchId`: the Batch that stamped
  the job, which Blueprint and the batch's Reactions read.
- **`Dependencies` gates `running`**, so a step does not start before the
  steps it comes after, by a claim or by a plain transition.
- **`Constants` keeps `step` and `topic`**, so no one, the worker holding
  the job's lease included, turns a step into another one.

### A claim

A claim is a read and a lease. Read the rows that may be claimed, in the
order you want, and take Lease's `acquire` on the first you can. A
claimer that loses the race meets `held_by_another` and goes on to the
next row. The holder then moves the row with the lease's token, and
reserves its budget:

<Snippet example="engine-jobs" file="src/dev.ts" symbol="claim" />

- **Blocked work waits at its gate.** A read shows `Dependencies`'
  `dependenciesBlocked`, so the claim passes over a blocked row. Give
  `Dependencies` the state a claim moves to in `gatedStates`
  (`["running"]`), so a move that skips the read waits for the blockers
  too.
- **Every write presents the token**, in the `Preconditions` header over
  HTTP: `Preconditions: {"Lease": {"token": 1}}`.
- **Search is a filter.** A list's `filter[title][contains]=index`
  matches a field's text anywhere, case aside. A compiled table searches
  with `@searchField` and `@searchable`.

### Finish or fail

A successful attempt charges what the work used, records the attempt,
moves the job to done and releases the lease:

<Snippet example="engine-jobs" file="src/dev.ts" symbol={['finish', 'fail']} />

- **Retries keeps no result.** A table's Retries takes no `resultField`.
  The example keeps a result in the successful attempt's `detail`, since
  its workers write a job only through the work's operations; an app
  whose holders may update the row writes it there, with the token.
- **A failure of a terminal class** fails the job for good: the
  example's operator cancels a running job with a `cancel` directive,
  which the holder reads at its next heartbeat and records as a
  `cancelled` failure.

A refusal carries a code to branch on. A worker whose lease is gone gets
409 `vetoed`, its `details.vetoCode` `token_stale` (another lease replaced
it) or `lapsed` (it ran out), and stops writing.

## Lease

An exclusive, time-bounded lease on the row, held by one principal.

| | |
| --- | --- |
| Config | all optional: `ttlMs` (60000), `heartbeatMs` (a third of `ttlMs`, at most half), `maxHoldMs` or `maxHoldField`, `onExpiry` and `escalate` (`{ transition, from }`), `maxExpiries`, `exempt`, `requireToken`, `acquirePermission`, `overridePermission`, `directPermission`, and on a table with several Workflows `status` |
| Precondition | `{ token }`: `preconditions: { Lease: { token } }`, or the `Preconditions` header over HTTP |
| Fields | `holder`, `token`, `acquiredAt`, `renewedAt`, `expiresAt`, `active`, `expiries`, `ended`; a list filters on the holder |
| Operations | `acquire({ ttlMs? })`, `heartbeat({ acknowledge? })`, `release({ abandon? })`, `expire({ holder?, notRenewedAfter? })`, `direct({ name, data?, dedupeKey? })`, `acknowledge({ ids })`, `resetExpiries()`, and `expireHolder({ holder, notRenewedAfter? })`, an operation of the table as a whole |
| Deadline | `expire`, when the lease falls due, which a table's behavior worker or development mode's runner runs |
| Guard | a write that presents a stale token is refused, whoever calls; while a lease is active, only the holder may update, delete or call a writing operation, except `exempt` operations, read-only ones, operations beside the row (Comments' `post`), and principals with `overridePermission` |

- **The token is a fencing counter, not a secret.** It advances at every
  acquire, release and expiry. A write presents it as Lease's
  precondition, and one that presents an old token is refused
  (`token_stale`), so a worker process that lost its lease cannot write,
  renew or release after another process of the same principal took the
  job again. `heartbeat` and `acknowledge` need it.
- **`requireToken: true`** makes every write under an active lease
  present the token, the holder's own included, so a fleet under one
  principal cannot write unfenced by mistake.
- **Lapsed is not held.** A lease past `expiresAt`, or past its longest
  hold (`maxHoldField` on the row, else `maxHoldMs`), gives its holder
  nothing. A heartbeat never extends past the longest hold.
- **Expiry moves the status.** `onExpiry` moves it back (running to
  queued); at `maxExpiries`, `escalate` moves it instead (running to
  failed), and `acquire` is refused until `resetExpiries`. An expiry of a
  row already in a terminal state is not counted: a holder that finished
  and died before releasing has not failed.
- **Give up with `abandon`.** `release({ abandon: true })` counts as an
  expiry, so a job that every worker takes and drops reaches
  `maxExpiries` and escalates. A plain `release` hands it back without
  counting.
- **Expiries say why.** `expire` returns `reason`: `ttl` (the holder
  stopped renewing), `maxHold` (it renewed past its longest hold, so it
  is stuck) or `holder` (an active lease expired by its holder's name).
  `ended` keeps how the last lease ended.
- **Directives** are messages to the holder: `direct` sends one, every
  heartbeat returns those not yet acknowledged, and `acknowledge`, or a
  heartbeat's own `acknowledge`, stops them in the same write. A
  `dedupeKey` sends a directive once per lease. They end with the lease.
- **A gone holder.** `expireHolder` expires every lease one principal
  holds and returns the ids; `notRenewedAfter` spares a lease renewed
  after a time, whose own heartbeats show it alive.
- **Beside `Approvals`.** A sign-off is a writing operation of another
  principal than the holder, so the guard refuses
  [`Approvals`](/superschematic/guides/engine-behaviors/#approvals)'
  `signOff` and `withdrawSignOff` while a lease is active. List
  `"Approvals.signOff"` and `"Approvals.withdrawSignOff"` in `exempt` to
  let approvers sign leased work off.
- **Beside `Numbering` and `Timers`.** A create holds no lease, so
  [`Numbering`](/superschematic/guides/engine-behaviors/#numbering)
  numbers each new row whoever holds what; list
  `"Numbering.assignNumber"` in `exempt` to backfill leased rows. List
  `"Timers.fireTimer"` to let a
  [`Timers`](/superschematic/guides/engine-behaviors/#timers) deadline
  move leased work on.
- **Not yet.** `directOn`, which sends a directive when a linked row
  gains a revision or a release, waits for the core to hear one on a
  table, and the build refuses it. The engine's `sweepMs` has no use: a
  lease expires at its own deadline.

## Presence

A heartbeat on a row that stands for a worker. The row's
`principalField` names the principal, and only that principal may beat
it.

| | |
| --- | --- |
| Config | `ttlMs` and `principalField`, required; `onMissed` and `onBeat` (`{ transition, from }`), `releaseLeases` (the tables whose leases a miss releases), `ttlByState`, and `status` |
| Fields | `deadline`, `lastBeatAt`, `missed`, `released` |
| Operations | `beat()`, `miss()` |
| Deadline | `miss`, at the row's deadline |

The example's Worker beats while it runs:

<Snippet example="engine-jobs" file="schemas/dev/workers.schema.json" />

A worker that misses its deadline is marked `missed`, moved to
`missing`, and the leases its principal holds on the `releaseLeases`
tables are expired through Lease's `expireHolder`, so its jobs go back in
the queue even if their own leases had time left. A lease acquired or
renewed strictly after the worker's last beat is spared: its heartbeats
show the process holding it is alive, and it expires on its own if they
stop. Keep lease heartbeats at most the presence `ttlMs` apart. The miss
records the ids it expired in `released`. A later `beat` clears the miss,
and `ttlByState` keeps a state's rows present longer.

The example's test shows it on a clock it moves, with a worker `ttlMs`
of 15 seconds and a lease of 30:

## Blueprint

Children created with their parent: a map of steps says which rows of a
child table a row has, and which block which.

| | |
| --- | --- |
| Config | `schema` (the child table), `parentLink` (the child's relation to this table) and `keyField` (a string field of the child), required; `steps`; `copyFields`, `copyLinks` (this table's relations, each copied to the child's relation of the same name) |
| Steps | by key: `{ after?, when?, data? }`; `after` lists the steps that block this one, `when` is `{ field, equals }` or `{ field, includes }` |
| Field | `children`, which a read computes: the child rows that point at the row, in the template's order |

The example's Batch stamps three steps and settles from them:

<Snippet example="engine-jobs" file="schemas/dev/batches.schema.json" />

A create stamps a child per step in its own write, each through the child
table's own create with its relation to the parent and its
`Dependencies` blockers, so a failing child refuses the parent's create
and a step is blocked from its first write. A child's key is a UUID the
core draws. A step whose `when` does not hold is left out and the chain
closes over it. A step that ends in a failure state (`outcomes: { failed:
"failure" }` on the child's `Workflow`) stays a blocker, so the steps
after it wait until someone removes the edge. The child table needs the
`parentLink` relation, `Dependencies` when steps use `after`, and
[`Constants`](/superschematic/guides/engine-behaviors/#constants-and-variants)
over `keyField` and every copied field. To settle the parent from its
steps, give it `Reactions` with `allTerminal` and `anyTerminal` rules
([Reactions](/superschematic/guides/engine-behaviors/#reactions)). It
takes inline steps alone: the engine's `from`, a map read from a pinned
revision, needs a pin a relation does not keep.

## Budget

Reserve-then-settle budgets in units you name: each meter counts what the
row has used and reserved against a limit, and passes both up to the
enclosing scopes its `scope` relation points at.

| | |
| --- | --- |
| Config | `meters` (required, by name): each `limit` and `limitField`, `reserve` and `reserveField`, `scope` (a to-one relation), `reset`; `limitPermission`; `onExceeded: { direct }`; `escalate: { transition, from }`; on a table `observe`, `observePermission` and `status` |
| Field | `meters`: by meter, `{ used, reserved, limit, remaining }` |
| Operations | `reserve`, the read-only `checkReserve`, `recordUsage`, `settle`, `setLimit`, and the scope side, `reserveFor`, `settleFor` and `recordUsageFor` |

- A claim reserves each meter's amount, the row's `reserveField` or else
  `reserve`, and is refused when it does not fit (`over_limit`) in the
  meter's limit, the row's `limitField` or else `limit`. `checkReserve`
  says whether it would fit, without reserving.
- `recordUsage` is never refused, since the usage has happened. It
  releases the part the reservation covered and reports any overrun;
  with `onExceeded`, the lease holder also gets a directive, and with
  `escalate`, each row it leaves over its limit, a scope included, moves
  its status by its own config.
- On a table with `Lease`, a reservation lasts as long as the lease: a
  release or an expiry settles it.
- A `scope` relation to a pool or a project applies that scope's own
  limit too, in the same write.
- A table's meters reset `hourly`, `daily`, `weekly`, `monthly` or
  `{ everyMs }`, in a fixed or a `rolling` window
  ([Rows a worker leases, retries, beats and meters](/superschematic/guides/database-tables/#rows-a-worker-leases-retries-beats-and-meters)).

## Retries

Attempts counted per failure class, against per-class caps and a total.

| | |
| --- | --- |
| Config | `classes` (required: `{ attempts, hint?, backoff? }` or `"terminal"`), `totalAttempts` and `exhaustedState`, required; `limitsField`, `limitsPermission`, `keepBest`, `stuckAfter`, `from`, `permission`; on a table `retryInto`, `then`, `giveUpAfterMs`, `window`, `keyField` and `status` |
| Fields | `total`, `classAttempts`, `bestScore`, `exhausted`, `stuck`, `retryAt`, `failingSince`, `keyedBy`; a list filters on `exhausted` |
| Operation | `recordAttempt({ failure?, score?, result?, signature?, predicates?, detail? })`, which returns the class's `hint` |
| Guard | once exhausted, transitions to any state but `exhaustedState`, and acquiring, are `vetoed` (`exhausted`); `limitsField` changes only with `limitsPermission`, and never by the lease holder (`limits_fixed`) |

- An attempt without `failure` is a success.
- A terminal class, a class out of room, or the total reaching its cap
  exhausts the row and moves it to `exhaustedState`.
- A class's `backoff` waits before a retry, `retryInto` names the states a
  retry may enter, and `then` moves the row once its wait is over
  ([Rows a worker leases, retries, beats and meters](/superschematic/guides/database-tables/#rows-a-worker-leases-retries-beats-and-meters)).
- `stuckAfter` exhausts a row that fails with the same `signature` that
  many times in a row.
- A class's `hint` comes back from `recordAttempt` to steer the next
  attempt; an attempt's `detail` is kept with it.
- A worker cannot raise its own caps: `limitsField` needs
  `limitsPermission`, and the lease holder may not change it.
- Nothing resets exhaustion.

## The engine's work-queue package

`@superschematic/engine-workqueue` ran these behaviors, Queue and
Assignment among them, on the engine (`@superschematic/engine`), with a
worker loop over the engine's client. Nothing in the repository's
examples runs on the engine any more, and the engine and its packages are
removed in a later step. The package's
[README](https://github.com/parable-work/superschematic/blob/main/runtime/engine-workqueue/README.md)
documents it until then.
