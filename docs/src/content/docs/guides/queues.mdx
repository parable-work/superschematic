A queue holds messages for later work: an order placed now is fulfilled
by a worker a moment later, outside the request that placed it. A queue
is a table of a DB service's database, so a message commits with the
writes that caused it, or not at all, and the database a stack places the
service on is the queue's backing. A worker is a deployable that claims
the queue's messages and handles each with an API's `Deps`, as a
[job](/superschematic/guides/stacks/#jobs) runs with them.

This page is about queues your stack runs. The engine's
[work queues](/superschematic/guides/work-queues/), which turn an engine
schema's instances into claimable work, are another thing.

| a backoff that doubles with each failure up to a maximum, and done messages removed after a retention | |
| the Go ORM's `Enqueue<Queue>` in your transaction, and its claims on Postgres | claims on SQLite and D1 |
| the TypeScript types' `./queues` entry and the HTTP runtime's `enqueue` and `postgresQueue`, which run the Go ORM's statements; the Rust types' `queues` module and the Rust HTTP runtime's `queue::enqueue` and `PostgresQueue`, which run them too; a location (`POINT`) and a duration (`INTERVAL`) in a message, in every language | a list of locations or durations (`POINT[]`, `INTERVAL[]`) in a queue's message |
| `@worker` on an API, Go's `Workers` and `NewWorkers`, TypeScript's `Workers` and `createWorkers`, Rust's `Workers` and `create_workers`, the `worker` deployable, its entrypoint and image | |

D53 and D68 in `docs/DECISIONS.md` record the decisions, and section 8.8 of
[docs/stack-model.md](https://github.com/parable-work/superschematic/blob/main/docs/stack-model.md)
the design.

## Declare a queue

Put `@queue` from `@superschematic/db` on a class of a DB service's
schema. The class is the message: its fields are the message's, and it
stays a type, which every language's types declare. In the acme shop,
`shop-db` declares `OrderPlaced`:

<Snippet file="schemas/services/shop-db/src/orders.schema.ts" symbol="OrderPlaced" />

Every argument is optional:

| Argument | What it sets |
| --- | --- |
| `retries` | how many times a message whose handler fails is handled again before it is dead; five unless set |
| `backoff` | how long a message that failed once waits before it is due again, as `30s` or `5m`; thirty seconds unless set. Each failure after the first doubles the wait |
| `maxBackoff` | the longest a failed message waits, however many times it failed; the backoff or more, and an hour unless set, or the backoff when that is longer. Set it to the backoff for a wait that never grows |
| `lease` | how long a claim holds a message unless its worker extends it, which it does while the handler runs; a minute unless set |
| `retain` | how long a done message stays in the table before a worker removes it, as `168h`; a week unless set. `0s` keeps none: completing a message deletes it |

Every duration is whole seconds as Go writes one: `90s`, `10m`, `1h30m`
or `168h`, with no days. After its attempt `n` fails, a message waits
`backoff × 2^(n−1)`, up to the maximum: with the defaults 30 seconds,
then 1, 2, 4 and 8 minutes, and an hour at most.

```ts
@queue({ retries: 8, backoff: "10s", maxBackoff: "15m", retain: "72h" })
export abstract class InvoiceIssued {
  invoiceId: Identity.UUID;
}
```

A message's fields are values a column holds: a scalar, an enum, a list
or map of them, or a JSON value such as a `@jsonField` type. A message
names an order by its key, not by a relation to its table. The build
refuses a `@key`, a generated field, a relation, an index, and a field
named like a column the queue keeps.

The DB service's build writes the queue's table, after its tables, named
after the class with `_queue`. It holds a column per field, and the
columns the queue keeps: the message's `id`, its `state` (`ready`,
`claimed`, `done` or `dead`), its `attempts`, when it is next due, when
its claim expires and the claim's token, its last error, and when it was
enqueued and last changed:

<Snippet file="testdata/generated/sql/shop-db/create.sql" from="CREATE TABLE order_placed_queue" to=");" />

A partial index on `due_at` of the ready messages and one on
`claim_expires_at` of the claimed ones serve the claims, and one on
`updated_at` of the done ones serves the prune: nothing changes a done
message, so its `updated_at` is when it was done.
[Schema migrations](/superschematic/reference/migrations/) plan the table
as any table, in each dialect the service lists.

## Enqueue a message

The DB service's Go ORM writes a typed `Enqueue` per queue, which takes
the transaction you write in. `shop-orders`' `PlaceOrder` writes the order
and its lines, then enqueues the order's message in the same transaction:

<Snippet file="go/shop-orders/orders.go" from="placed = order" to="return orm.EnqueueOrderPlaced" />

A field reaches its column as a table's field does through the ORM, and
an optional field you leave unset takes its column's default.

### From TypeScript

There is no TypeScript ORM, so the DB service's TypeScript types package
carries each queue as data in its `./queues` entry: `orderPlacedQueue`,
the queue's table, its arguments, the column each field writes, and the
statements the Go ORM runs, written from one place, so a message one
language enqueues the other claims alike. Enable the database's
TypeScript types (`outputs.types` for TypeScript), and enqueue with the
HTTP runtime's `enqueue`, which takes the client of the transaction you
write in:

```ts
import { enqueue } from '@superschematic/http-runtime/postgres';
import { orderPlacedQueue } from '@acme/shop-db-types/queues';

const client = await deps.db.connect();
try {
  await client.query('BEGIN');
  const orderId = await placeOrder(client, input); // your writes, on the same client
  await enqueue(client, orderPlacedQueue, { orderId });
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
```

`enqueue` is typed by the definition: the message is `OrderPlaced` from
the database's types. A field writes its column as the Go ORM writes
it: a JSON field its JSON text, an unset optional field or list nothing,
and an unset enum its schema default. A `Geo.Location` goes to its
`POINT` column as `(lon,lat)` and comes back as `{lat, lon}`. A
`Temporal.Duration` goes to its `INTERVAL` column as its whole
microseconds, so `-1h2m` stays negative as a whole and `1500ns` is stored
as `1us`, and comes back in the scalar's canonical text (`1h30m0s`,
`250us`), a day of an interval written by hand as 24 hours and a month as
30 days, as Go's `time.Duration` reads it. A message whose fields hold a
list of either, a `POINT[]` or an `INTERVAL[]` column, stays out of
`./queues` for now, which says so, and the Go ORM refuses it; hold such a
list in a `@jsonField` type. The implementation's
`package.json` depends on the database's types package by its name, with
`workspace:*`; the scaffold adds it for an API with workers.

### From Rust

The DB service's Rust types carry each queue's descriptor in their
`queues` module, the same data as JSON: `STOCK_LOW_QUEUE`, which the Rust
HTTP runtime's `queue::QueueDefinition::parse` reads. Enable the
database's Rust types (`outputs.types` for Rust). The API crate of an API
with workers re-exports them as `database_types`, and the runtime's
`queue::enqueue` writes a message in the transaction you write in, a
deadpool `Transaction` of the pool `Deps.db` holds:

```rust
use schemas_shop_stock_api::database_types::{self, StockLow};
use superschematic_http_runtime::queue::{enqueue, QueueDefinition};

let queue = QueueDefinition::parse(database_types::STOCK_LOW_QUEUE)?;
let mut client = deps.db.get().await?;
let tx = client.transaction().await?;
// your writes, on the same transaction
enqueue(&tx, &queue, &StockLow { product_id, quantity, threshold }).await?;
tx.commit().await?;
```

A location and a duration cross as they do from TypeScript and Go. A
queue whose message holds a list of either, a `POINT[]` or an
`INTERVAL[]` column, stays out of `queues`, which says so, and the build
refuses a Rust worker of it.

In the acme shop, `shop-db` declares `StockLow` too, which `shop-stock`'s
reservation, in Rust, enqueues in its transaction for each line that takes
a product's level below its threshold:

<Snippet file="schemas/services/shop-db/src/stock.schema.ts" symbol="StockLow" />

<Snippet file="rust-impl/shop-stock/src/lib.rs" from="if let Some(threshold) = fell_below" to="                levels.push(level);" />

The descriptor carries the statements the Go ORM runs, so a message
enqueued from Rust is claimed alike by a worker in any language, and the
other way round.

## Write a worker

Put `@worker` from `@superschematic/api` on a class of an API's schema,
which holds nothing, naming the queue's class, which the API imports from
its database:

<Snippet file="schemas/services/shop-orders/src/workers.schema.ts" symbol="FulfilOrders" />

| Argument | What it sets |
| --- | --- |
| `queue` | the `@queue` class whose messages the worker handles; required. It is a queue of the database the API connects to, its `authDb` or its one DB dependency |
| `concurrency` | how many messages an instance handles at a time; one unless set |
| `grace` | how long a stopping worker lets its running handlers finish before it gives their messages back; eight seconds unless set |

The API's Go package gets `Workers`, a method per worker that handles one
message, typed from the database's Go types, and the signature of the
constructor your implementation writes beside `New`:

```go
type Workers interface {
	FulfilOrders(ctx context.Context, msg shopdb.OrderPlaced) error
}

type WorkersConstructor func(deps Deps) (Workers, error)
```

A TypeScript API's `deps.ts` declares the same, a method per worker in
camel case, its message typed from the database's TypeScript types, which
the API's build then needs, and a signal for Go's context:

```ts
export interface Workers {
  fulfilOrders(message: OrderPlaced, signal: AbortSignal): Promise<void>;
}

export type WorkersConstructor = (deps: Deps) => Workers | Promise<Workers>;
```

A Rust API's crate declares `Workers`, a trait with a method per worker
in snake case, its message typed from the database's Rust types, which
the crate re-exports as `database_types` (D65):

```rust
#[async_trait]
pub trait Workers: Send + Sync {
    async fn reorder_stock(&self, message: schemas_shop_db_types::StockLow) -> Result<(), BoxError>;
}
```

The scaffold writes `NewWorkers`, or exports `createWorkers` in
TypeScript, or declares `create_workers` in Rust, and each method returns the not-implemented error, or throws
it, which fails every message, until you write it. A build never writes
into an implementation that exists, so one that predates its workers
fails the stack's build, which says what to add. The acme shop's worker
marks the order fulfilled:

<Snippet file="go/shop-orders/workers.go" symbol="Workers.FulfilOrders" />

`shop-stock`'s worker `ReorderStock`, in Rust, handles `StockLow`. Its
method in `rust-impl/shop-stock` files one open restock request per
product, which a unique index of `shop-db`'s `RestockRequest` table holds
it to, so a message that comes again files none:

<Snippet file="schemas/services/shop-stock/src/workers.schema.ts" symbol="ReorderStock" />

<Snippet file="rust-impl/shop-stock/src/lib.rs" from="    /// Files an open restock request" to="        Ok(())" />

A method that returns nil, or resolves, or returns `Ok`, completes its
message. One that returns an error, or panics, or rejects, fails it: the
message is due again after the queue's backoff, doubled for each attempt
before and capped at its `maxBackoff`, until its retries are spent, and
then it is dead, where its last error stays. Delivery is at least once: a
worker that dies holding a message gives it back when its claim expires,
and another worker handles it again, so write each method to be safe to
run twice for one message.

## Run it

In a stack each worker is a deployable of its own, named after its API
and its class as a job is: `shop-orders-fulfil-orders`. Its edges, config,
secrets and identity are its API's, so it connects to the database that
holds its queue, and an operation whose `from` lists `ShopOrders` admits
it. It rolls out after the migrations and after its callees.

The build writes each worker an entrypoint module beside the servers',
`server/shop-stack/shop-orders-fulfil-orders/`, whose `main` builds the
API's `Deps`, calls your `NewWorkers`, and claims and handles messages
until it is stopped. A TypeScript worker's is a package with a `main.ts`,
which calls your `createWorkers` and runs the HTTP runtime's `runWorker`
(`@superschematic/http-runtime/worker`) over the claims, and a Rust
worker's a crate whose `main.rs` calls your `create_workers` and runs the
Rust HTTP runtime's `worker::run_worker` over a `queue::PostgresQueue` of
the queue's descriptor, the same loop:

- it claims for its free slots, as many as its concurrency, with
  `FOR UPDATE SKIP LOCKED`, so workers that claim at once take different
  messages;
- it extends each message's claim while the method runs;
- it logs each message's outcome;
- as it starts and every five minutes after, it deletes the done
  messages older than the queue's `retain`, a thousand at a time until a
  batch is short, and logs how many as `done messages pruned` with
  `pruned`, or `pruning the done messages failed` with the error, which
  the next prune tries again. Every instance of every worker of the queue
  prunes, which is safe: each batch skips rows another holds, and a row
  deleted once is gone. Dead messages are never pruned;
- on SIGTERM it claims no more, lets the running methods finish within
  the grace, then cancels them and gives their messages back, due at once
  for another worker, and exits. A TypeScript method's signal aborts when
  the grace is over; one that ignores it cannot be stopped, but its
  message is given back all the same, and the process exits. A Rust
  method still running is dropped where it waits.

Its Dockerfile builds an image as a server's does, and `stack build` and
`stack deploy` build and pin it beside the servers'.

`stack dev` runs each worker as a process with no port, a TypeScript one
as `bun main.ts` and a Rust one from the binary its crate builds with
cargo, started with the servers of its wave, each line of its output
with its name in front. Its exit stops the environment, as a server's
does:

```text
  worker   shop-orders-fulfil-orders handles OrderPlaced of shop-db, 4 at a time
...
[shop-orders-fulfil-orders] {"level":"info",...,"msg":"fulfilled the order",...}
[shop-orders-fulfil-orders] {"level":"info",...,"msg":"message handled","queue":"OrderPlaced","attempt":1,...}
```

## Dead messages

A message is dead once its handler has failed on every try its queue's
`retries` allow, or once its last attempt's claim expired, as when the
message kills its worker every time. It stays in the queue's table with
its last error, and no worker claims it again. `stack queue` reads and
repairs a queue's dead messages; it names a queue by its DB service and
its class, `shop-db.OrderPlaced`.

`stack queue dead` lists them, the oldest death first, up to `--limit`
(a hundred unless set), and says how many there are in all. The message
shows as its columns:

```text
$ superschematic stack queue dead Dev shop-db.OrderPlaced
Queue shop-db.OrderPlaced of Dev: 2 dead messages, the oldest death first.

3f2c8a10-5b1e-4c7a-9d2e-8f6b4a1c0e93
  attempts:   6
  died at:    2026-10-19T12:04:31Z
  last error: the payment provider refused the card
  message:    {"order_id":"9d0f6c2e-3a41-4b7e-8c55-1e2f3a4b5c6d"}

8a41c6e2-7d3b-4f19-a0c5-2b9e6d4f1a37
  attempts:   1
  died at:    2026-10-19T12:20:07Z
  last error: the claim of its last attempt expired before its handler finished
  message:    {"order_id":"c7e3b1a9-0f2d-4e86-9b14-6a5d8c2f3e01"}
```

Once the cause is fixed, `stack queue retry` makes the messages it names
ready again, or every dead one with `--all`: each is due at once with no
attempts, so its retries start over, and a worker claims it as it claims
a new message. Its last error stays until its next failure replaces it.
`stack queue drop` deletes the messages it names, or every dead one with
`--all --yes`:

```sh
superschematic stack queue retry Dev shop-db.OrderPlaced 3f2c8a10-5b1e-4c7a-9d2e-8f6b4a1c0e93
superschematic stack queue retry Dev shop-db.OrderPlaced --all
superschematic stack queue drop Dev shop-db.OrderPlaced 8a41c6e2-7d3b-4f19-a0c5-2b9e6d4f1a37
```

A retry or a drop that names a message that is not dead, one a worker
already took again or one that is not in the queue, changes none of the
messages it names and says what each such one is. `--format json` prints
the result as JSON.

Each command resolves the environment from your schemas and runs the
operation with the migration runner, `superschematic-migrate`, which holds
the database drivers, as `stack dev`'s migrations do. On the `local`
target it reaches the Postgres container `stack dev` runs, so run it from
another terminal while the environment runs. It runs on Postgres alone,
as the claims do.

On gcp it reaches the deployed run's Cloud SQL database the way a
deploy's migrations do, as one execution of the stack's migration job,
and takes a member of a parameterized environment by `--param`:

```sh
superschematic stack queue dead Staging shop-db.OrderPlaced
superschematic stack queue retry Preview shop-db.OrderPlaced --all --param pr=123
```

A dead message's columns may hold personal data, so the runner never
prints them where Cloud Logging would keep them: it writes its result to
an object of the state bucket, under a random name, which the command
reads once and deletes. If the command dies before it does, the bucket's
lifecycle deletes the object a day after it was written. A deleted
result stays restorable, by an account that may restore objects, for the
bucket's soft-delete window, seven days unless your project set another.
The `migrator` account may create objects there and read none.

The command runs the job as your last deploy left it and never changes
it, since your deploys share it: deploy with the release you run `stack
queue` from first, or it says the job's runner is too old. A project
bootstrapped before this needs `superschematic stack bootstrap` once
more, which lets the migrator write the result; without it the runner
stops before it changes the queue, and says so. `--timeout`, 30 minutes
unless set, bounds the wait.

## Change it per environment

An environment sets how many instances of a worker run, and how many
messages each handles at a time, beside the worker's platform settings:

```ts
@environment({
  target: "local",
  settings: [{ of: ShopOrders, worker: "FulfilOrders", concurrency: 8 }],
})
export abstract class Dev {}
```

| Setting | What it sets |
| --- | --- |
| `instances` | how many instances run; one unless set. `stack dev` runs one process whatever it says |
| `concurrency` | replaces the `@worker` decorator's |
| `enabled` | `false` runs none, and the queue's messages wait |

`worker` takes only a worker the API declares, which its handle names.
The worker's entrypoint reads its concurrency from `WORKER_CONCURRENCY`,
which the platform sets.

The claims run on Postgres, the dialect of the Go ORM and of the
TypeScript client, so an environment that places the queue's database on
a platform of another dialect does not resolve.

## On gcp

The gcp target runs a worker, in Go or TypeScript, as a Cloud Run worker
pool, `gcp.cloudrunworker`, named after the worker as its service account is:
no port, no URL and nothing that calls it, scaled by hand to the worker's
`instances`, with `WORKER_CONCURRENCY` set to its concurrency. Its config,
secrets, Cloud SQL volume and egress are a server's of its API, and its
account gets the queue's database as a server's does: the Cloud SQL roles,
an IAM database user, and read and write privileges the migration job
grants. A worker the environment turns off keeps its pool at zero
instances. Cloud Run stops an instance ten seconds after SIGTERM, so a
worker whose `grace` is ten seconds or more does not resolve on gcp. A
worker pool takes `cpu` and `memory`, one CPU and `512Mi` unless set:

```ts
settings: [{ of: ShopOrders, worker: "FulfilOrders", instances: 3, memory: "1Gi" }],
```
