Every kind of schema declares its types the same way. This guide uses the
acme shop's `shop-common` service, which generates types in all four
languages, and the address type in `shop-db`. For each construct it shows
what the generated code does, and every example here runs in
`examples/acme-shop` in each language.

## Object types

An abstract class declares an object type, and each property a field. The
shop reads its suppliers' product feeds as `FeedItem` rows:

<Snippet file="schemas/services/shop-common/src/feed.schema.ts" symbol="FeedItem" />

- A field's type is a scalar, another object type, an enum, a list or a
  map. `Price` comes from the same service, so it needs no import beyond
  the file.
- The comment above a type or a field becomes its documentation in every
  language, in OpenAPI and, for a table, in the SQL. Write it for the
  reader of the API.
- `extends` copies the base class's fields, first, into the subclass. The
  base class is still generated as a type of its own. In a DB schema it is
  not a table: `shop-db`'s `Auditable` gives every table its timestamps.

## Scalars

A scalar is a value type from
[superscalar](https://github.com/parable-work/superscalar), grouped in
namespaces: `Identity`, `Contact`, `Temporal`, `Generic`, `Network`,
`Localization`, `Geo`, `Text`, `Ordering`, `Finance`, `File`, `Crypto` and
more. Each parses and validates the same way in every language. The
scalars the shop uses become:

| Schema | Go | TypeScript | Python | Rust |
| --- | --- | --- | --- | --- |
| `Identity.UUID` | `IdentityUUID` (a `uuid.UUID`) | `IdentityUUID` (a branded `string`) | `str` | `superscalar::Uuid` |
| `Identity.Name`, `Identity.Slug`, `Contact.Email`, `Contact.PhoneNumber` | a named `string` type | a branded `string` (`IdentityName`, ...) | `str` | `String` |
| `Generic.Int64` | `GenericInt64` (an `int64`) | `GenericInt64` (a `number`) | `int` | `i64` |
| `Temporal.DateTime` | `TemporalDateTime` (a `time.Time`) | `TemporalDateTime` (a `Date`) | `datetime` | `superscalar::DateTime` |
| `string`, `number`, `boolean` | `string`, `float64`, `bool` | the same | `str`, `float`, `bool` | `String`, `f64`, `bool` |

- `Generic.Int64` is limited to JavaScript's safe-integer range, so a value
  means the same in TypeScript as elsewhere.
- `Identity.UUID` accepts a UUID in its usual hyphenated form or in its
  short base62 form. Python's parser writes the base62 form, which the Go
  server takes like any other.
- The scalar decides the SQL column type too: `Contact.Email` is `CITEXT`,
  which compares case-insensitively. [Database tables](/superschematic/guides/database-tables/)
  has the list.
- For a JSON value with no fixed shape, use `Generic.JSON`; for one with
  known fields, an object type. A scalar a schema file declares with the
  `object` language primitive must say which JSON it holds in
  `typeMappings.json_schema` (`object`, `array` or `any`), or the build
  refuses it. [JSON-valued scalars](/superschematic/reference/json-scalars/#a-scalar-of-your-own-that-holds-json)
  has the rule.

### Branded values in TypeScript

A field of a scalar is typed by the scalar's symbol, which the types
package's `types/scalars.ts` re-exports from superscalar. Most symbols are
brands, a base type joined to a marker
(`string & { readonly __brand: "Contact.Email" }`), so a plain `string` does
not assign to a `ContactEmail` field. Others are plain aliases, such as
`GenericInt64` (`number`), `TemporalDateTime` (`Date`) and `EmbeddingVector`
(`number[]`). A scalar default is cast to its symbol
(`"UTC" as TemporalTimeZone`), as an enum default is cast to its enum.

To make a branded value:

- Parse a value where it enters the program, with superscalar's
  `parse<Scalar>Strict`, which throws, or `parse<Scalar>`, which returns
  null: `parseContactEmailStrict(form.email)`. Request and search params,
  form fields, storage reads and third-party responses are such places.
- Carry the type from there: type a parameter or a variable as the
  generated field (`Order['productId']`) or as its symbol.
- Do not cast to a brand (`as ContactEmail`). The cast skips the check the
  brand stands for.

The generated scalar validators still take the base type, so they check a
value that has not been parsed yet. `parse<Type>Json` and `parse<Type>Yaml`
check every field before they return a typed value, and a generated router
checks a request before the implementation sees it. The shop's TypeScript
client parses its ids and the recipient's name before it sends them:

## Required, nullable and optional

A field is required unless it is `Nullable<T>` or declared optional with
`name?: T`. The two mean the same thing: the field may be absent or null.
For most types the two are the same missing value. For `Generic.JSON`,
null is a value of an optional field, apart from absent
([null in an optional Generic.JSON](/superschematic/reference/json-scalars/#null-in-an-optional-genericjson)).

| Language | A nullable field |
| --- | --- |
| Go | a pointer for a scalar or object type (`UpdatedAt *TemporalDateTime`) and for a `boolean` without a default (`*bool`); the plain value, left out when empty, for `string` and `number` |
| TypeScript | `updatedAt?: TemporalDateTime \| null` |
| Python | `Optional[T]` with a default of `None` |
| Rust | `Option<T>` |

A nullable `boolean` is `*bool` in Go because `encoding/json` leaves a
`false` out of a plain `bool` with `omitempty`, and a reader then cannot tell
`false` from absent. With `Default<boolean, true>` the field stays `bool`
and is always written, since an absent value would read back as `true`.
With `Default<boolean, false>` it stays `bool` and is left out when `false`.

## Defaults

`Default<T, V>` fills in a value when a payload leaves the field out. It is
a default for decoders, not for the database: the Go, TypeScript, Python
and Rust decoders all apply it, and the SQL column has no default. The
build checks `V` as a validator checks a value: its type, its scalar's
lengths, pattern and range, and the field's own `Validate<T, C>` rules. A
default that breaks them fails the build. A new order starts `Placed`:

## Constraints

`Validate<T, C>` adds constraints to a field. `shop-db`'s address bounds
its lines and checks the country code:

<Snippet file="schemas/services/shop-db/src/orders.schema.ts" symbol="ShippingAddress" />

| Constraint | Applies to |
| --- | --- |
| `min`, `max` | numbers |
| `minLength`, `maxLength`, `pattern` | strings; lengths count and patterns match Unicode code points, and a pattern's `\d`, `\w` and `\b` are ASCII classes |
| `listMin`, `listMax` | lists (`Validate<T[], { ... }>`); `[]` satisfies a required list |
| `uploadMaxBytes` | file-upload scalars |

The generated validators check them: `Validate()` in Go, `validate<Type>`
and the parsers in TypeScript, `validate_all()` in Python, and
`validators::validate_<type>` and `validators::parse_<type>` in Rust. A
failure names the rule it broke:

<Snippet file="go/types_test.go" symbol="ExampleShippingAddress_Validate" />

The generated servers check every request against them and answer 400,
and every generated SDK checks an input before it sends it. The database
does not: constraints are not part of the DDL.

## Enums

An enum is a TypeScript `enum` of string values. Numeric enums are refused.

<Snippet file="schemas/services/shop-common/src/price.schema.ts" symbol="Currency" />

Go gets `type Currency string` with a constant per member, `IsValid()` and
`Values()`. TypeScript gets the same `enum`, Python a `str` `Enum` and Rust
an `enum` with one serde rename per member. A value outside the enum fails
validation with the `enum` rule.

## Lists and maps

- `T[]` is a list: a slice in Go, an array in TypeScript, `List[T]` in
  Python and `Vec<T>` in Rust. `T[][]` is a list of lists; see
  [arrays of arrays](/superschematic/reference/arrays-of-arrays/).
- `Record<string, T>` is a map with string keys: `map[string]T`,
  `Record<string, T>`, `Dict[str, T]` and `HashMap<String, T>`. Its values
  may be scalars, enums, object types or lists. A map is stored as `JSONB`
  in a table, and an API takes one only in a request body.

## Strict decoding

By default the decoders are lenient about keys a type does not declare, in
the way each language usually is:

- Go: `FeedItemFromJSON` refuses an unknown key and `FeedItemFromJSONNonStrict`
  skips it.
- TypeScript: `parseFeedItemJson` refuses one and `parseFeedItemJsonNonStrict`
  skips it.
- Python: the pydantic models skip unknown keys.
- Rust: serde skips unknown keys.

`@strictJSON` on a type makes every decoder of it refuse a key it does not
declare, non-strict ones included. It suits a closed contract like a
supplier feed, where a misspelled key that quietly disappears is the bug.
It applies to that type only; a nested type opts in on its own. The same
payload with an extra `colour` key, in each language:

## Environment variables

A General schema can declare a service's configuration. Put `@envVars`,
from `@superschematic/schema-config`, on one class; each field is one
environment variable, named as the field is:

```ts
import { Network } from "superscalar";
import { Default, Secret } from "@superschematic/schema";
import { envVars } from "@superschematic/schema-config";

export enum Environment {
  Development = "development",
  Production = "production"
}

@envVars
export abstract class ServiceConfig {
  DATABASE_URL: Network.Url;
  JWT_SECRET: Secret<string>;
  PORT: Default<number, 8080>;
  ENVIRONMENT: Default<Environment, Environment.Development>;
}
```

A field is a `string`, a `number` (read as an integer), a `boolean`
(`true` or `false`), an enum, or a scalar, which runs its validators.
`Default<T, V>` makes a variable optional; any other field is required.

The build writes a loader that reads and checks every variable and
reports every one that is missing or invalid at once, never a value:

| Language | Loader | Where |
| --- | --- | --- |
| Go | `LoadConfig() (*ServiceConfig, error)`; it also reads a `.env` file when one is present | `api/<service>`, when `outputs.types` lists Go |
| Rust | `load_config()` | `api/<service>`, when `outputs.types` lists Rust but not Go |
| TypeScript | `loadServiceConfig()`, from the types package's `./config` export; it reads no `.env` file | the TypeScript types package ([TypeScript](/superschematic/install/typescript/#load-environment-variables)) |

Beside the loader, `api/<service>/values-schema.json` is a JSON Schema of
the variables (types, defaults and which are required), with an
`x-superschematic.envVars` list that also says which are enums, scalars
and secrets. Deployment tooling can check a values file against it; the
[deploy extension](/superschematic/extending/deploy/) is one that maps
the same fields to Helm values.

## Secrets

`Secret<T>` marks a field whose value must not leak into logs. It is a
`T` everywhere it is decoded and validated, and:

- every generated type gets a mask helper that returns a copy with its
  secret fields cleared: `MaskSecrets()` in Go, `mask_secrets()` in
  Python, and `maskSecrets<Type>()` in TypeScript;
- an `@envVars` field marked secret is `"secret": true` in
  `values-schema.json`, and the TypeScript loader holds it as a
  `SecretValue` that prints as `[secret]` until you call `reveal()`.

Rust types have no mask helper.
