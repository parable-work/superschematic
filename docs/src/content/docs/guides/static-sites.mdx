A static site is a directory a front-end build writes, served as files: a
single-page application, a marketing page, an admin console. A front end
rendered on a server is a TypeScript or Rust server instead.

A site is a service of the core kind `Site`. Its config names the APIs its
browser code calls and how it builds; its code is a package of your own.
In a stack, a site is always exposed, each API it calls must be exposed
too, and each of those APIs answers CORS for the site's origin, beside
the origins its identity config trusts. Or the stack puts the site and
its APIs on [one origin](#one-origin), each API under `/api/<service>` on
the site's own address, as `stack dev` serves them, so a cookie session
needs no CORS and no trusted origin. One build of the site serves every
environment: the site reads each API's address from a config the
environment serves beside its files.

The design is section 8.10 of
[docs/stack-model.md](https://github.com/parable-work/superschematic/blob/main/docs/stack-model.md),
and D55, D82 and D91 in `docs/DECISIONS.md` record the decisions.

## Declare a site

```ts
// schemas/services/shop-web/schema.config.ts
import { ShopApi } from "@acme/shop-api";
import { defineConfig, SchemaKind } from "@superschematic/schema-config";

export default defineConfig({
  name: "shop-web",
  kind: SchemaKind.Site,
  calls: [ShopApi],
  site: { build: "build", output: "dist", fallback: "index.html", dev: { command: "dev" } },
});
```

- **`calls`** names the APIs the site's browser code calls, by handle.
- **`site.build`** is the script of the site's `package.json` that builds
  it, `build` unless set.
- **`site.output`** is the directory the build writes, relative to the
  site's package, `dist` unless set.
- **`site.fallback`** is the file, relative to the output, served for a
  path that names no file, so a single-page application's router reads
  the path. Without it such a path answers 404.
- **`site.dev`** is the site's dev server, which `stack dev` runs in
  place of the build ([Run it locally](#run-it-locally)): `command`, the
  script of the site's `package.json`, or a binary of its dependencies,
  `dev` unless set, and `port`, for a dev server that picks its own port.
  A deploy builds the site whether `dev` is set or not.

A Site schema declares nothing, and its config may leave `outputs` out.
Its sentinel, `ShopWeb`, is what a stack deploys.

## The site's code

The site's package sits at the naming file's `[implementation_paths]
site`, `web/{service}` unless set, under the repository root, and is a
member of the output root's Bun workspace, so it imports the SDKs of the
APIs it calls with `workspace:*`. When the directory is missing, the
build scaffolds a minimal site there once: `index.html`, `src/main.ts`, a
`package.json` whose `build` script bundles them with `bun build`, and a
`.gitignore` for the output. It is yours to change, or to replace with
your framework's project.

Every build writes the site's typed browser config into the package,
`config.generated.ts`. Its `loadApis()` fetches the config the
environment serves at `/__superschematic/config.json`, uncached, and
returns each API the site calls, by the camel case of its name, with its
public `baseUrl` and `client(options)`, which builds the API's generated
TypeScript SDK at that address:

```ts
import { loadApis } from "../config.generated";

const { shopApi } = await loadApis();
const products = await shopApi.client({ auth: { token } }).product.listProducts({ inStock: true });
```

`client` takes the SDK's options but `baseUrl`: `auth`, `credentials` for
a cookie session, `fetch`, a timeout. The scaffold's `package.json`
depends on each SDK with `workspace:*`. An API whose config generates no
TypeScript SDK has its `baseUrl` alone; enable `outputs.sdk.typescript`
in its config for a client, or call it with `fetch`.

The SDK checks each value through superscalar, whose browser build a
bundler takes through the `browser` export condition: `bun build
--target=browser`, or an HTML entry point, bundles it with no plugin. That
build carries superscalar's WebAssembly module inlined, about 2.9 MB of a
page's script, or 1 MB gzipped, and compiles it when the page loads. A
page served with a Content-Security-Policy must allow it in `script-src`:

```
Content-Security-Policy: script-src 'self' 'wasm-unsafe-eval'
```

Without `'wasm-unsafe-eval'` the import of the SDK throws, naming the
policy. superschematic serves no Content-Security-Policy of its own, in
`stack dev` or on a target; set one where you set your other headers.

### Load superscalar on the first call

An API whose config sets `lazyValidation` on its TypeScript SDK keeps
superscalar out of a page's first load:

```ts
sdk: { [TargetLanguage.TypeScript]: { enabled: true, lazyValidation: true } }
```

Each namespace of the SDK then imports its types package's types alone,
and loads the package's validators and parsers, and superscalar's browser
build with them, with a dynamic `import()` that its first call awaits. The
checks and the parsing are the same; they run once the import resolves. A
bundler that splits code, as Vite does and `bun build --splitting` does,
puts them and the WebAssembly module in a chunk of its own, which the
browser fetches on the first call:

| A React page on Vite, calling one API | Its entry chunk | The chunk the first call loads |
| --- | --- | --- |
| without `lazyValidation` | 3,227 kB, 1,108 kB gzipped | |
| with `lazyValidation` | 241 kB, 75 kB gzipped | 3,024 kB, 1,041 kB gzipped |

The page renders before the module is fetched or compiled, and a page
that makes no call never loads it. The policy still needs
`'wasm-unsafe-eval'` for the first call, which rejects without it. A page
keeps the module out of its entry chunk only if its own code imports the
types package's values from its `/types` entry, enums and all, as
`import { SessionTransport } from "@acme/shop-api-types/types"` does, since
the package's root imports superscalar.

## Deploy it in a stack

Name the site in `deploy`. It is exposed whether `expose` names it or
not, and every API it calls must be exposed, unless the site serves it on
its [origin](#one-origin), or the stack does not resolve
(`site-calls-unexposed`):

```ts
@stack({ deploy: [ShopApi, ShopOrders, ShopWeb], expose: [ShopApi, ShopOrders] })
export abstract class Shop {}
```

Resolution gives the site a `site` edge to the server of each API it
calls, which derives the API's public address and nothing else, since the
browser carries its end user's token. The site rolls out a wave after
those servers. Each API a site calls gets a CORS field, `<API>_CORS`
(`SHOP_API_CORS`), whose one variable, `SHOP_API_CORS_ORIGINS`, lists the
origin of each site that calls it.

## CORS

The generated entrypoint of a server whose API a site calls reads the
API's CORS field and answers CORS for those origins only, in Go and in
TypeScript alike:

- a preflight from a listed origin is answered 204 with the origin,
  credentials, the `Accept`, `Authorization` and `Content-Type` headers,
  the methods of the API's operations and a max age of ten minutes;
- any other request from a listed origin carries the origin and
  credentials;
- any other origin gets `Vary: Origin` alone, and its preflight goes on to
  the API, which answers it as it would with no site.

So an API over the core user model still answers the origins its identity
config trusts, `trustedOrigins`, with the method and headers their
preflights ask for ([users and sessions](/superschematic/guides/users-and-sessions/)),
and an origin that is both a site and trusted gets the site's answer. An
origin neither lists gets no `Access-Control-Allow-Origin` from either,
so the browser refuses the answer.

On a server that serves several APIs, a request is the API's whose routes
take it, so each API answers only the sites that call it.

## One origin

A stack's `origins` put a site and the APIs it calls on one origin in
every environment, the way `stack dev`'s proxy puts a dev server and its
APIs on one ([With a dev server](#with-a-dev-server)): each API under
`/api/<service>` on the site's own address.

```ts
@stack({
  deploy: [ShopApi, ShopWeb],
  origins: [{ site: ShopWeb, apis: [ShopApi] }],
})
export abstract class Shop {}
```

- **`site`** is the Site service whose origin it is. A site has one.
- **`apis`** are the APIs the origin serves, each one the site calls.
  Left out, it serves every API the site calls.

| Path on the site's address | What answers it |
| --- | --- |
| `/__superschematic/config.json` | the site's config, each API of the origin at `<site's address>/api/<service>` |
| `/api/<service>`, and every path under it, for each API of the origin | the API's server, with `/api/<service>` taken off and the query kept: `/api/shop-api/api/products` is shop-api's `/api/products`. The server sees the browser's `Host`, with `X-Forwarded-Prefix: /api/<service>` and `X-Forwarded-Proto` |
| every other path | the site's files and its fallback |

`loadApis()` hands each SDK its API's path on the page's own origin, in
`stack dev` and on a deploy alike, so the SDK's code does not change
between them. A cookie session
([users and sessions](/superschematic/guides/users-and-sessions/#a-site-on-the-apis-origin))
needs nothing set: the identity runtime's cross-origin check sees a
same-origin request, its default `__Host-session` cookie is the site's
host's alone, and no CORS answers, so `trustedOrigins` and
`cookie.domain` stay unset.

- **Exposure.** An API of an origin needs no `expose` when its server
  runs on the site's provider: the browser reaches it through the site.
  Name it in `expose` too when other clients need an address of its own.
  A server on another provider is reached at its public address, so it
  must be exposed (`cross-provider-unexposed`).
- **CORS.** The API's CORS field leaves the site out. Another site that
  calls the API from its own origin stays in it.
- **The server.** The origin forwards to the API's server, which answers
  every API it serves, as an exposed server does.
- **Refusals.** A site the stack does not deploy, a site in two origins,
  an API the site does not call or listed twice (`origin`), and a site on
  a platform that serves no origin (`unrealizable`). The local, gcp and
  cloudflare targets serve one.

## Run it locally

`superschematic stack dev` builds each site once, `bun run build` in its
package after the workspace's install, and serves its output from a file
server of its own on `http://127.0.0.1:<port>`: its files, its config with
each API's loopback URL, and its fallback. The config is served
uncached, and every file with the Cache-Control it has on Google Cloud
(below). The summary prints the site's URL:

```
  server   shop-api                 http://127.0.0.1:22424
  site     shop-web                 http://127.0.0.1:22638
```

A site's `port` setting pins its port.

### With a dev server

A site whose config names a dev server is not built. `stack dev` runs
its dev server, which reloads the page as you edit it, and serves the
site's port from a proxy in front of it:

```ts
site: { build: "build", output: "dist", fallback: "index.html", dev: { command: "dev" } }
```

```json
"scripts": {
  "build": "vite build",
  "dev": "vite --port $PORT --strictPort"
}
```

- **The dev server** is `bun run <command>` in the site's package, after
  the workspace's install. Its environment is yours, with `PORT` the port
  to listen on, `SUPERSCHEMATIC_SITE_URL` the site's origin, and
  `<API>_URL` (`SHOP_API_URL`) each API's own loopback URL. `PORT` is
  `site.dev.port` when set, for a dev server that picks its own port;
  otherwise `stack dev` derives one per checkout, as it does a server's,
  so pass it on, as `--port $PORT --strictPort` does for Vite. Bun's own
  dev server takes it as `bun --port=$PORT ./index.html`, which the site
  scaffold's `dev` script runs. `stack dev` waits until it answers on
  `localhost`, prints its output with the site's name in front, and
  stops when it exits, as when a server does.
- **The proxy** serves the site's port, `http://127.0.0.1:<port>`, the
  origin the summary prints:

  | Path | What answers it |
  | --- | --- |
  | `/__superschematic/config.json` | the site's config, each API at `http://<host>/api/<service>` on the origin the page was opened on |
  | `/api/<service>/<route>`, for each API the site calls | the API's server, at `<route>`: `/api/shop-api/api/products` is shop-api's `/api/products`. The query is kept, the browser's `Host` is passed on with `X-Forwarded-Prefix: /api/<service>`, and a redirect within the API's own routes gets the prefix back |
  | every other path | the dev server, as it is, WebSocket upgrades among them, so its hot reload reaches the page |

- **One origin.** The page, its hot reload and its APIs share the site's
  origin, and `loadApis()` hands each SDK its API's path there. A cookie
  session ([users and sessions](/superschematic/guides/users-and-sessions/#sign-in-from-an-sdk))
  works as it does for an API on the page's own origin: the session
  cookie, `SameSite=Lax`, travels with each call, and the identity
  runtime's cross-origin check sees a same-origin request, so neither
  `trustedOrigins` nor CORS needs setting. The proxy serves the APIs the
  site calls alone: an API's [app](/superschematic/guides/stacks/#apps)
  keeps its own address, where it signs its users in on its own pages.

```
  site     shop-web                 http://127.0.0.1:22638, its dev server (bun run dev) and its APIs under /api/<service>
```

`stack dev --build-sites` builds such a site once and serves its files
instead, as a deploy does, with each API at its own address and CORS
between them.

A site with an [origin](#one-origin) is served from the same proxy
whether it runs a dev server or, with `--build-sites` or no `site.dev`,
its build: the APIs of its origin under their paths, and every other API
it calls at its own address, which answers CORS for the site, as a
deploy serves them.

```
  site     shop-web                 http://127.0.0.1:22638, its build and shop-api under /api/<service>
```

## Deploy it

`stack deploy` builds each site after a frozen install of the workspace,
digests the files its build wrote, and, before the wave that rolls the
site out, publishes them through the target, under their digest when they
are new, with the site's config for the run: each API's public address,
read from the run's outputs. The wave's apply then serves the new files at
once. The deploy manifest records the digest. `stack build` builds and
uploads the files without deploying them, and prints them as a `--site`
flag, which `stack deploy` takes to serve those files again with no build:

```
superschematic stack build Staging
superschematic stack deploy Staging --site shop-web=sha256:...
```

The [generated CI](/superschematic/guides/stacks/#generated-ci) builds each
site too: its `check` job installs the workspace from
`schemas/dist/bun.lock` and runs the site's build script, so a site that
does not build fails the pull request, and its `prepare` job sets up Bun,
installs the workspace and builds the site with no credentials, even in a
project whose schemas root installs with npm. The jobs that deploy the
site take those files with `stack deploy --prepared` and build nothing.

### On Google Cloud

The gcp target serves each site from a Cloud Storage bucket of its own,
`<project>-<site>` (`acme-staging-shop-web`), through a global external
Application Load Balancer with Cloud CDN. A deploy puts the files of a new
build in the bucket under the hex of their digest, writes the site's
config beside them, and then switches the load balancer's URL map to that
prefix in the site's rollout step, so the site moves to the new build in
one change; `--site` with an earlier digest moves it back.

| Environment | The site's address |
| --- | --- |
| with a `domain` | `https://<site>.<domain>` (`https://shop-web.staging.acme.dev`), with a Google-managed certificate and the records the environment's DNS platform writes, as an exposed server has |
| without one | `http://<address>`, the load balancer's address, over HTTP: a certificate needs a host. `stack outputs` holds the address as the `address` of `<site>.address` |

A site with a `fallback` serves it, with 200, for a path that names no
file. The config is served `no-store`, and each file by its name:

| File | Cache-Control |
| --- | --- |
| a name whose last part before its extension is a hex hash of 8 or more digits, with a digit and a letter: `app.3f9a2c1d.js`, `vendor-3f9a2c1d.css`, `3f9a2c1d5e7b.png` | `public, max-age=31536000, immutable`: the name has that content in every build |
| `index.html`, any other HTML file, the fallback, and every other file | `no-cache`: Cloud CDN checks with the bucket before it serves the file again, so a deploy shows at once |

The pattern is conservative. A hash in another alphabet does not count,
since a name written by hand, such as `og-1200x630.png`, looks as much
like one: Bun's and esbuild's (`index-5psy29er.js`), which the scaffold's
`bun build` writes, and Rollup's and Vite's unless you set its
`output.hashCharacters` to `"hex"`. Such files are served `no-cache`.

The bucket is readable by `allUsers`, since the load balancer reads only
public objects for a browser's request; `nothing-public-unless-exposed`
allows that for a site, which is always exposed. A project whose
organization policy forbids public buckets cannot serve a site.
`stack bootstrap` gives the `deployer` account Storage's admin role,
which creates the bucket and publishes its files. The bucket comes with
the first deploy's infrastructure step, so run `stack deploy` once before
`stack build` uploads a site's files.

A site with an [origin](#one-origin) serves the APIs of it from the same
load balancer, host and certificate. For each API, a serverless network
endpoint group of its Cloud Run service sits behind a backend service
without Cloud CDN, so no API answer is cached, and the URL map sends
`/api/<service>` and every path under it there, ahead of the files' rule,
with the prefix rewritten to `/` and `X-Forwarded-Prefix` added; Google's
load balancer passes the browser's `Host` on and sets
`X-Forwarded-Proto`. The fallback then answers only the files' 404s, so
an API's 404 reaches the page as the API wrote it. An API that only the
origin serves has no load balancer of its own: its Cloud Run service
takes load balancers' traffic alone, with its invoker check off. A site
with no domain serves its origin over HTTP, where a browser keeps no
`Secure` cookie: give the environment a domain for a cookie session. The
load balancer rewrites no answer's header, so a redirect an API answers
with a path of its own routes does not get the prefix back, as `stack
dev`'s proxy and the Worker do; no route the runtimes generate
redirects.

### On Cloudflare

The cloudflare target serves each site from a Worker of its own, named
after the site, with the build's files as the Worker's static assets
([Sites on Workers](/superschematic/guides/stacks/#sites-on-workers)). A
deploy keeps the files of a new build in the account's state bucket,
under `superschematic/sites/<stack>/<site>/<hex>/`, and the site's
rollout step uploads them with a new version of the Worker, which takes
all traffic at once; `--site` with an earlier digest fetches that
build's files back from the bucket and serves them again. `stack build`
needs no deploy first: the state bucket is bootstrap's.

| Environment | The site's address |
| --- | --- |
| with a `domain` | `https://<site>.<domain>` (`https://shop-web.staging.acme.dev`), a custom domain whose record and certificate Cloudflare writes in the account's zone |
| without one | `https://<stack>-<env>-<site>.<workersSubdomain>.workers.dev`, the site's Worker's name (`https://acme-shop-staging-shop-web.acme.workers.dev`), under the account's workers.dev subdomain, which `stack bootstrap` records |

The config is not a file of the publish: the Worker's version holds it,
each API's public address composed from names, so it changes with the
environment's graph and needs no step of its own. A script the
extension embeds, the same in every release, runs for a path that names
no file. It answers `/__superschematic/config.json` with the config,
`no-store`, whatever the build holds at that path; a directory, `/`
among them, with its `index.html`, since the assets match a path to a
file exactly; and any other path with the fallback at 200, or 404 when
the site has none. Every file is served with Cloudflare's asset caching,
which revalidates it by its ETag; the year's caching gcp gives a hashed
name is not given here.

Each API a site calls must be a TypeScript server on Workers in the same
environment, exposed, and answers CORS for the site's origin, its
address above.

A site with an [origin](#one-origin) runs the script first for each API
of it, which forwards the API's paths to the API's Worker through a
service binding of the site's version, `SITE_API_<API>`
(`SITE_API_SHOP_API`), on a URL with the browser's host, the prefix
taken off and the query kept, with `X-Forwarded-Host`, `-Proto`,
`-Prefix` and `-For` set, and puts the prefix back on a redirect within
the API's routes. Every method reaches the API; the site's own paths
still take `GET` and `HEAD` alone. The API's Worker then needs no
workers.dev address or custom domain: the binding admits the site's
Worker, as a caller's admits it. It works at workers.dev and under a
domain alike, since it needs no route on a zone.
