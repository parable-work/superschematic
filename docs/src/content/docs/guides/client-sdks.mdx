An API schema can generate a client SDK in each of Go, TypeScript, Python
and Rust, whatever language serves the API. Each SDK has a method per
route, with the route's arguments typed from the schema, and returns the
schema's types. `shop-orders` generates all four, and a test calls its Go
server and its generated Rust server from each and checks they see the
same answers.

An operation marked `@webhook` has no method in any SDK, since a third
party calls it
([Webhooks](/superschematic/guides/api-routes/#webhooks)).

## Generate them

The types of a service that another service imports must exist in those
languages too. `shop-orders` uses `shop-db`'s `ShippingAddress` and
`OrderStatus`, so `shop-db` generates types in all four languages as well.

The naming file names the packages:

| Language | Package | Client |
| --- | --- | --- |
| Go | module `example.com/acme/sdk/go/shop-orders` (`go_module_root`) | `sdk.New(sdk.SDKConfig{...})` returns a `*ShopOrdersSDK` |
| TypeScript | `@acme/shop-orders-sdk` (`npm_scope`) | `new ShopOrdersSDK({...})` |
| Python | `acme_shop_orders_sdk` (`python_sdk_module_prefix`, `_suffix`) | `ShopOrdersSDK(ClientConfig(...))` |
| Rust | crate `acme-shop-orders-sdk` (`rust_crate_prefix`) | `ShopOrdersSdk::new(ClientConfig {...})` |

## Call an API

Each client has one member per namespace of the API: `OrderNamespace` in
Go, `order` in TypeScript, Python and Rust, and so on. Each method takes
the route's path, query and body arguments, in the language's own style:
Go and Rust take a context or options, TypeScript returns a promise,
Python is synchronous, and Rust is async on the runtime you choose.

## Pages

A `@paginated` list operation
([Pages](/superschematic/guides/api-routes/#pages)) answers one page: its
items and `next`, the cursor of the page after it, null after the last.
Each SDK's method takes `cursor` and `limit` and returns the page, and
`<operation>All` yields every item, asking for each page with the `next` of
the one before only once the loop has taken its items:

| Language | One page | Every item | The sort |
| --- | --- | --- | --- |
| Go | `ListOrders(ctx, query, runtime.PageRequest{Cursor, Limit})` returns a `runtime.Page[T]`, `Items` and `Next` | `ListOrdersAll(ctx, query, page)`, an `iter.Seq2[T, error]` | `Sort *string` on the query struct |
| TypeScript | `listOrders({ ...query, cursor, limit })` returns a `Page<T>`, `items` and `next` | `listOrdersAll(params)`, an `AsyncIterable<T>` | `params.sort` |
| Python | `list_orders(..., cursor=..., limit=...)` returns a `Page[T]`, `.items` and `.next` | `list_orders_all(...)`, an `Iterator[T]` | `sort=`, before `cursor` and `limit`; the three are keywords alone |
| Rust | `list_orders(Some(&ListOrdersQueryParams { cursor, limit, .. }), options)` returns a `Page<T>`, `items` and `next` | `list_orders_all(query, options)`, a `Pager<T>` whose `next().await` yields each item | `sort: Option<String>` on the query struct |

A list whose operation takes a `SortBy` argument
([Pages](/superschematic/guides/api-routes/#pages)) takes its sort as the
optional query argument it is, named after the schema's argument: a field,
`placedAt`, or `-` and a field for descending, `-placedAt`. Left out, the
page is in the operation's `defaultSort`. A cursor holds the sort it was
returned under, so the page after it is asked with the same sort, and
`<operation>All` sends the sort it was given with every page. Python's
`sort`, `cursor` and `limit` come after the operation's own optional
arguments, by keyword alone, so a list that gains a sort keeps its
callers' positional arguments. The SDKs
send a sort as it is, with no list of their own of the values; the
server refuses one it does not offer, and a cursor of another sort, with
400. The OpenAPI document and the tool documents list the values
([MCP tools](/superschematic/reference/mcp-tools/#toolsschemajson)).

```ts
// Every order, the newest first.
for await (const order of shopper.order.listOrdersAll({ sort: "-placedAt" })) {
  console.log(order.id, order.placedAt);
}
```

An SDK refuses a `limit` past the operation's most before it sends, and an
iterator ends with an error, not a loop, on a page whose `next` is the
cursor it was asked with. The server refuses a cursor it never returned
with 400, and the caller starts again from the first page.

## Files

An operation whose input has file fields
([Uploads](/superschematic/guides/api-routes/#uploads)) takes the files
beside the input, which leaves the file fields out, and each SDK sends them
as `multipart/form-data`: the input as JSON in the `data` part, and each
file in a part named as its field, with its filename and media type.

| Language | The files | A FileDownload result |
| --- | --- | --- |
| TypeScript | `importCartLines(cartId, input, { lines: file })`, each a `File`; `importCartLinesRaw(cartId, formData)` sends a `FormData` of your own | `{ blob, filename, contentType }` (`DownloadedFile`) |
| Go | a `<Namespace><Operation>Files` struct of `runtime.UploadFile{Filename, ContentType, Reader}` | `*runtime.DownloadedFile{Body, Filename, ContentType}` |
| Python | a `FilePart(filename, content, content_type)` for each file field | `DownloadedFile(content, filename, content_type)` |
| Rust | a `<Namespace><Operation>Files` struct of `UploadFile` | refused at build, for now |

A refused file is a refused input, its error at its field, so the 400's
error carries it among its field errors, as a refused rule's
([Errors](#errors)): TypeScript's `ApiError.validationErrors.lines`, say.

An operation whose result is a `FileDownload`
([Downloads](/superschematic/guides/api-routes/#downloads)) resolves to
the file: its bytes, the media type the server sent, and the filename its
`Content-Disposition` offered, `filename*` before `filename`, or null (Go:
`""`, Python: `None`) when it offered none. A refusal is the error any call's is. The
storefront's test imports a cart from a CSV and reads it back:

<Snippet file="typescript/shop-storefront/index.test.ts" from="test('a shopper imports lines" to="  });" />

The Rust SDK refuses to generate an API with a `FileDownload` result,
naming the operation; generate another language's SDK for it, or leave
Rust out of `outputs.sdk`. Support follows.

## Errors

A response outside 2xx is an error that carries the status, the problem's
`detail` as its message, its `code` and the request id.

| Language | Any status | 401 | 403 | 429 |
| --- | --- | --- | --- | --- |
| Go | `*APIError` | `*AuthenticationError` | `*AuthorizationError` | `*RateLimitError` (`RetryAfter`) |
| TypeScript | `ApiError` (`statusCode`) | `AuthenticationError` | `AuthorizationError` | `RateLimitError` (`retryAfter`) |
| Python | `APIError` (`status_code`, `code`, `request_id`) | `AuthenticationError` | `AuthorizationError` | `RateLimitError` (`retry_after`) |
| Rust | `SDKError::Api { status_code, .. }` | `is_auth_denied()` | `is_auth_denied()` | `is_transient()`, `retry_after()` |

A Rust `SDKError::Api` reads the request id from `X-Request-ID` (else the
problem's `requestId`) into `request_id()`, the seconds of `Retry-After`
into `retry_after()`, and a refused input's field errors, the problem's
`errors`, into `validation_errors()`; `problem()` holds them with the
problem's `details`.

In TypeScript and Python the 401, 403 and 429 classes extend the general
one. In Go they are types of their own that embed `*APIError` and unwrap
to it, so `errors.As(err, &apiErr)` finds the `*APIError` behind each of
them; to tell them apart, check for them first, as `status` in the Go
program above does. A request that never reached the server is a
`NetworkError`, or `SDKError::Network` in Rust. In Go a `NetworkError`
does not unwrap, so `errors.As(err, &apiErr)` does not read a transport
failure as an answer with status 0.

## Checks before sending

The Go, TypeScript and Python SDKs check an input against its type and
constraints before sending it, and fail with a `ValidationError` without a
request. The error names each broken rule at its path, the same in all
three (`lines` for `listMin`, `lines[1].quantity` for `min`), except that
for a map field inside an input type Go keys a value `field[key]` where
TypeScript and Python key it `field.key`. A map argument is keyed
`name[key]` in all three. The Python SDK checks with the generated types package,
pydantic for the types and `validate_all` for the constraints, so it
needs that package installed. A TypeScript SDK whose API sets
`lazyValidation` loads its checks, and superscalar with them, on its first
call, which keeps them out of a browser page's first load
([static sites](/superschematic/guides/static-sites/#load-superscalar-on-the-first-call)). The Rust SDK checks an input against the
schema before sending too, and fails with one `SDKError::Config` message
that names each path.

## Path parameters

Every SDK percent-encodes a path parameter's value once, as one path
segment, so a value holding `/`, `%`, `?`, `#`, a space or non-ASCII text
reaches the route intact: `a/b` as the label in `grids/{id}/cells/{label}`
is one segment, not two. Every generated server decodes it exactly once
before your implementation sees it, and answers 400 to an escape that does
not decode. The one value that cannot be sent is `.` or `..` through the
TypeScript or Rust SDK, whose URL parsers remove a dot segment; the Go and
Python SDKs send it as it is.

## Timeouts, retries and hooks

| | Go | TypeScript | Python | Rust |
| --- | --- | --- | --- | --- |
| Timeout (default 30 s) | `Timeout` (ms) | `timeout` (ms) | `timeout_seconds` | `timeout_ms` |
| Token per request | `AuthConfig.GetToken` | `auth.getToken` | `auth_token_provider` | `auth_token_provider` |
| Refresh after a 401 | `AuthConfig.RefreshToken` | `auth.refreshToken` | `auth_token_refresher` | `refresh_auth_token` |
| Service credential | `ServiceCredential` | `serviceCredential` | `service_credential` | `service_credential` |
| Forward the end user | `AuthConfig.GetToken`, from the call's context | `{ forward: ctx }`, a method's last argument | no | `RequestOptions::forward` |
| Retries a 429 | up to 3 times, after `Retry-After` (`MaxRateLimitRetries`) | no | up to 3 times, after `Retry-After` (`max_rate_limit_retries`) | no |
| Edit each request | `RequestInterceptor`, `Transport` | `requestInterceptor`, `fetch` | `request_interceptor`, `default_headers` | `request_interceptor` |

The Python SDK also retries a `GET`, `HEAD` or `OPTIONS` that failed on the
network, and logs each failed request through its logger.

## Service credentials

A server that calls another API sends its own credential beside the end
user's, which the callee admits by its operations' `@requireService` and
`@allowService` clauses
([Service callers](/superschematic/guides/auth-and-permissions/#service-callers)).
Each SDK's config takes a source, a function from a `fresh` flag to a
token, and the headers to send it in: `Service-Authorization` unless you
list others, such as `X-Serverless-Authorization` too for a Cloud Run
callee whose invoker check is on. The SDK sends `Bearer <token>` in each on
every request, whatever the API's operations need. A 401 whose problem
`code` is `service_unauthorized` (or whose `error.code` is, in the older
`{"error": {...}}` envelope) asks the source for a fresh token once and
retries, without the end-user refresh; any other 401 runs the end-user
refresh and never asks the source. One call spends at most one of each.

To act for its own caller, a server forwards that end user's
`Authorization` per call. In Go, the client's `AuthConfig.GetToken` reads
the token of the request on the call's context
(`serviceauth.ForwardedToken`), so a handler that passes its context
forwards; `GetToken` is asked on every call when no static `Token` is set. In
TypeScript a method's last argument, an `AbortSignal` until now, also takes
`{ signal, forward: ctx }`, and in Rust a method takes
`RequestOptions::forward(ctx.bearer_token())`. A forwarded call sends that
token, or no `Authorization` when the request has none, in place of the
client's own, and never refreshes it. The Python SDK has the credential and
no forward option, since no server is written in Python.

## Install them

Until the packages are published, a service uses the generated packages
from `schemas/dist`:

- **Go**: require the module and add a `replace` line pointing at its
  directory, for the SDK and the types modules it imports.
- **TypeScript**: `schemas/dist/types/typescript` is a Bun workspace of the
  types packages; link the SDK and its types package into your
  `node_modules`, as `scripts/check.sh` does.
- **Python**: put the SDK's and the types packages' directories on
  `PYTHONPATH`, or install them with pip from their directories.
- **Rust**: depend on the crate by path. It brings no async runtime; add
  `tokio` or another.

The [language pages](/superschematic/install/go/) cover each in more
detail.
