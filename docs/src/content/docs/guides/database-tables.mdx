A DB schema declares tables. Its build writes Postgres DDL
(`sql/<service>/create.sql` and `drop.sql`), a Go ORM over pgx, and the row
types in the languages `outputs.types` lists. A service whose
`outputs.sql.dialects` lists `sqlite` also gets SQLite DDL
(`sql/<service>/sqlite/create.sql`; see [SQLite](/superschematic/reference/migrations/#sqlite)). This guide walks the acme
shop's order and review tables in `shop-db`. [Your first project](/superschematic/first-project/database/)
covers the basics of the users and products tables.

## Tables and keys

Every class in a DB schema is a table, named after the class in snake case
(`OrderLine` is `order_line`). Postgres keywords are quoted: the `Order`
class is the `"order"` table.

<Snippet file="schemas/services/shop-db/src/orders.schema.ts" symbol="Order" />

- `@key` marks the primary key. `AutoGenerate<Identity.UUID>` makes it a
  `UUID DEFAULT gen_random_uuid()`, so the ORM leaves a zero id out of an
  insert and the row type holds the id as a pointer until then.
- A class that other tables extend, like `Auditable`, is not a table: its
  fields become columns of each table that extends it. A required
  `Temporal.DateTime` column defaults to `CURRENT_TIMESTAMP`, and the ORM's
  `UpdateOne` sets `updatedAt`.
- `@unique` on a field adds a unique constraint on its column.
- The class comment becomes `COMMENT ON TABLE`.

<Snippet file="testdata/generated/sql/shop-db/create.sql" from={'CREATE TABLE "order" ('} to=");" />

## Columns

The field's type decides its column:

| Field type | Column |
| --- | --- |
| `Identity.UUID` | `UUID` |
| `Identity.Slug`, `Contact.Email` | `CITEXT` (compares case-insensitively) |
| `Identity.Name` | `VARCHAR(80)` |
| `Generic.Int64` | `BIGINT` |
| `Temporal.DateTime` | `TIMESTAMPTZ` |
| `Temporal.Duration` | `INTERVAL` |
| `Geo.Location` | `POINT`, x the longitude and y the latitude |
| `string`, an enum | `TEXT` |
| `number` | `DOUBLE PRECISION` |
| `boolean` | `BOOLEAN` |
| a list of any type above, like `Temporal.DateTime[]` | an array of its column, like `TIMESTAMPTZ[]` |
| a `@jsonField` type, a map, a list of lists | `JSONB` |

A field is `NOT NULL` unless it is `Nullable<T>`. A required array column
defaults to the empty array `'{}'`, whatever its element type, and a
required `JSONB` column has no default.

The DDL says what the schema says about a column's values too, so a row
written outside the generated code, by a script, a trigger or by hand, is
held to them:

- A required field's `Default<T, V>` is the column's `DEFAULT` when `V` is
  text, a number, a boolean or an enum member: `status TEXT DEFAULT
  'placed' NOT NULL`. An optional field's column defaults to `NULL`, which
  the ORMs write for an unset value; a UUID, a time or a JSON value keeps
  its default in the decoders alone, since `V` is written in the wire
  form.
- An enum column has a `CHECK` that its members' values hold it to:
  `CONSTRAINT ck_order_status CHECK (status IN ('placed', 'fulfilled',
  'shipped', 'cancelled'))`.
- `Validate`'s `min` and `max` on a number column, and `minLength` and
  `maxLength` on a text column, are the column's `CHECK`:
  `CHECK (length(cancel_reason) <= 500)`. `length` counts characters, as
  every validator does. A pattern and the list rules stay the generated
  code's.

A check is named `ck_<table>_<column>`, and `NULL` passes it. A list, a
map and a JSON value get neither a default nor a check.

The SQLite DDL stores each column as the type its values need, such as a
list as JSON text, with the same defaults and checks;
[SQLite](/superschematic/reference/migrations/#types-and-defaults)
has the table.

The Go ORM writes a `Temporal.Duration` as its whole microseconds, the
precision of an `INTERVAL`, and drops a remainder of nanoseconds toward
zero. It reads an `INTERVAL` with a day as 24 hours and a month as 30
days, so one written by hand as `'1 mon 2 days 03:04:05'` reads as
`771h4m5s`. A duration's filter, `DurationFilter`, takes `time.Duration`
values: `Eq`, `Gt`, `Gte`, `Lt`, `Lte`, `Between` and `IsNull`. A
`Geo.Location`'s filter, `GeoPointFilter`, has `IsNull` only; [JSON-valued
scalars](/superschematic/reference/json-scalars/) says why.

## Relations

`Relation<T>` stores a foreign key to another table of the same schema, in
a column named after the field with `_id`. `onDelete` says what deleting
the referenced row does: `CASCADE`, the default, deletes this row too;
`RESTRICT` and `NO ACTION` refuse the delete; `SET NULL` keeps the row and
clears its reference. `SET NULL` needs a column that can hold null, so it
goes on a nullable relation only, `Nullable<Relation<Category, { onDelete:
"SET NULL" }>>`, and a required one fails the load with that fix. The DDL
adds the foreign keys once every table exists:

<Snippet file="testdata/generated/sql/shop-db/create.sql" from={'ALTER TABLE "order"'} to="ON DELETE RESTRICT;" />

In the row types a relation holds the related row (`Order.Customer` is a
`User` in Go). To write one, give it the related row's id:
`Customer: db.User{Id: &customer}`. The filter for it is `CustomerID`.

## Indexes

`@index<T>(keys, options?)` on the class adds an index over the listed
fields, in order. A relation field indexes its foreign key column.
`{ unique: true }` makes it unique, and `name` names it. A key that names
no field fails the build. The other options shape the index:

| Option | What it does |
| --- | --- |
| `method` | the access method: `btree`, `gin`, `gist`, `brin`, `hnsw` or `ivfflat`. Unset picks one from the columns' types: GIST for `ltree` and geometric types, GIN for `JSONB`, arrays and `tsvector`, else BTREE. `hnsw` and `ivfflat` index vector columns, which follow, so either fails the load today |
| `ops` | the operator class each key is indexed with, such as `gin_trgm_ops`, whose extension the DDL enables |
| `where` | makes the index partial: a SQL predicate over the table's columns, without `WHERE`. On a unique index of a soft-deletable table it is ANDed with `deleted_at IS NULL` |
| `expression` | indexes a SQL expression over the table's columns, such as `lower(email)`, in place of the keys' columns; the keys name the fields it reads and give the index its default name |
| `concurrently` | how a migration plan builds the index on a table that holds rows: `true`, the default, builds it concurrently, outside a transaction; `false` builds it inside the step's transaction, which blocks writes while it builds |

`where` and `expression` are SQL, written once for every dialect the
service lists, and hold one expression each. SQLite takes an expression
and a predicate, and refuses a method other than BTREE and an operator
class. An engine type's index is the engine's, over its fields alone, so
it takes none of these options.

<Snippet file="schemas/services/shop-db/src/orders.schema.ts" symbol="Review" />

<Snippet file="testdata/generated/sql/shop-db/create.sql" from="CREATE INDEX idx_order_customer_placed_at" to="idx_review_search_trgm" />

`one_per_author` is unique only among rows that are not deleted: on a
table with `deletedAt`, a unique index leaves deleted rows out.

A [page](#pages) reads fastest with an index over the columns its filter
compares for equality, then its sort's column, then the key: the index
holds the page's rows in its order, from the cursor's on.
`idx_order_customer_placed_at` serves a shopper's orders by `placedAt`.

## Text search

`@searchField` on one or more fields adds a generated `search_text` column
that joins them, and a trigram index on it. The DDL enables the `pg_trgm`
extension.

<Snippet file="testdata/generated/sql/shop-db/create.sql" from="ALTER TABLE review ADD COLUMN search_text" to="STORED;" />

The SQLite DDL has the same column, `VIRTUAL`, and no index over it:
SQLite has no trigram index ([SQLite](/superschematic/reference/migrations/#types-and-defaults)).

An API's search argument, a `SearchQuery`, is what reads it
([References and search](/superschematic/reference/references-and-search/)):
`shop-orders`' `listReviews` keeps the reviews whose `search_text` holds
each word of its `q`, with `ILIKE` on Postgres and `LIKE` on SQLite, and
`listProducts` the products whose name does: `Product.name` is a search
field too.

The Go ORM's filter of a table with search fields has `SearchText`
(`ReviewFilter.SearchText`). Left out, it filters nothing. Given, it keeps
the rows whose `search_text` holds each of its words, in any case: the
first 8 runs of characters that are not white space, each one condition,
`review.search_text ILIKE $1 ESCAPE '\'`, its `\`, `%` and `_` escaped so
they match themselves. A blank text has no words and keeps every row.
`ReviewFilterConditions(filter, &args)` gives a filter's conditions for a
query of your own, each column qualified by its table and each value's
placeholder numbered after the values `args` already holds; `FindMany`
joins the same conditions with `AND`. The soft-delete condition is not
among them: `FindMany` adds `deleted_at IS NULL` itself unless its options
include deleted rows ([Soft delete](#soft-delete)), so a query of your own
that leaves deleted rows out adds it too. A field whose column would be
`search_text` beside search fields fails the build, since the generated
column takes that name.

## Pages

`FindPage` reads one page of the rows a filter finds, in the order of one
column, as a paged list asks for it
([Pages](/superschematic/guides/api-routes/#pages)). acme's list of
orders reads its pages through it:

<Snippet file="go/shop-orders/orders.go" symbol="Orders.ListOrders" />

A table sorts by its key, and by each column of the table's own that
holds one value of text, a number, a time, a date or a UUID and is never
null: `createdAt` among them, and `updatedAt` when it is required.
`OrderSortByPlacedAt` names one, and
`orm.OrderSort{Field: orm.OrderSortByPlacedAt, Desc: true}` reads the
newest orders first. A column that may be null, or holds an enum, a
boolean, JSON, a list, a map, a union or a point, is not a sort field.
Neither is a relation's key, an audit actor (`createdBy`, `updatedBy`,
`deletedBy`), internal metadata such as `_version`, or a `@secret`
column, whose values an order by it would reveal. `ParseOrderSort` reads a sort as a
page request writes it, `placedAt` or `-placedAt`, and refuses a field
the table cannot sort by. A sort never reaches the SQL as text:
`FindPage` takes the column from the table's generated list of sort
fields.

The page is one query, with no count. Its conditions are the filter's,
then `deleted_at IS NULL` unless the options set `IncludeDeleted`
([Soft delete](#soft-delete)), then, after `After`, one row comparison
with the row `After` names, which a subquery reads by its key:
`("order".placed_at, "order".id) < ((SELECT placed_at FROM "order" AS
page_key WHERE page_key.id = $1), $1)` for a descending sort. It orders by
the column, then the key, both in the sort's direction, so rows of one
value read in the order of their keys, and it reads one row more than
`Limit`, 100 when it is 0. `Rows` holds up to `Limit` rows. When more
follow, `Next`, an `OrderPageKey`, is the position of the last of them:
its key alone, under its schema name, `{"id": "…"}`. A key is as long as
an id whatever the row holds, so a long name never pushes a cursor past
its 1024 characters, and it is the same in every order. An implementation
encodes it as the page's cursor and decodes the next request's cursor
into `After`.

The subquery reads the row with no `deleted_at` condition and none of the
filter's, so a row deleted, or changed so the filter no longer finds it,
since the page before still places the next page. An `After` without a
key, or, in an order by another column than the key, whose row no longer
exists, is `ErrPageKey`, which the implementation answers as a cursor it cannot read. A key does not say
which order it came from, so `FindPage` cannot refuse the key of another
sort; a router binds each cursor to its sort and refuses one sent back
with another before the implementation reads it
([Pages](/superschematic/guides/api-routes/#pages)). `Fields` selects the
columns as `FindMany`'s do, a nested selection hydrating its relations
the same way, and the page reads its key besides, which `Next` holds.

Give each sort a list offers an `@index` of its own, over the columns
the filter compares for equality, then the sort's column, then the key
([Indexes](#indexes)): without one, each page sorts every row the filter
finds.

## JSON columns

A class marked `@jsonField` (from `@superschematic/schema`) is not a table.
A field of its type, or of a list of it, is a `JSONB` column, read and
written with its row, and the ORM marshals it for you. `shop-db`'s
`ShippingAddress` is one; see
[Modeling types](/superschematic/guides/modeling-types/#constraints). Maps
and lists of lists are `JSONB` too. A compiler before D78 made such a
field `TEXT`; a migration plan from a database it built casts the column
with `USING shipping_address::JSONB`, which fails on text that is not JSON
(`data-dependent`).

## Inserts

`CreateOne` inserts only the optional fields a row sets, so an unset
optional column takes its database default. `CreateMany` writes the batch
as one multi-row `INSERT` by the same rule: its rows may set different
optional fields, and some may supply an id while others take the generated
one. A row that leaves unset a column another row sets writes `DEFAULT`
for it, not `NULL`.

## Soft delete

A table with nullable `deletedAt` and `deletedBy` fields, like `Review`, is
soft-deletable:

- `DeleteOne` sets `deleted_at` and `deleted_by` instead of removing the
  row, and `HardDeleteOne` removes it.
- `FindMany` and `FindOne` leave deleted rows out unless the options set
  `IncludeDeleted`.
- Unique indexes cover live rows only, as above.

## Transactions

`Transaction` runs a function with repositories bound to one transaction,
and rolls it back when the function returns an error. Placing an order
writes the order and its lines together:

<Snippet file="go/shop-orders/orders.go" symbol="Orders.PlaceOrder" />

The transaction also takes raw SQL for what the repositories do not
express: `Exec` for a write, and `Query` for a read such as a keyset-paged
join across tables. `Query` returns pgx rows, which the caller closes; the
no-op transaction returns none.

`ErrNotFound` from a lookup, and the unique index's `23505` error from
Postgres, are the errors an implementation usually turns into a 404 or a
409; [API routes](/superschematic/guides/api-routes/) shows how.

## Raw SQL

What the schema cannot say, such as a function, an extension or a
materialized view for a dashboard, is raw SQL the DB service declares with
`@rawSql` on any of its tables. The class is only where it is written: the
piece belongs to the service. `examples/migrations`' `tasks-db` keeps a
materialized view of each project's open tasks for a dashboard:

<Snippet example="migrations" file="v2/schemas/services/tasks-db/src/tasks.schema.ts" symbol="Project" />

- `id` names the piece: a lowercase identifier, unique in the service.
- `up` is one or more statements, separated by semicolons. A migration
  plan runs the piece again when it changes, so each statement must run
  again over what it made: `CREATE OR REPLACE`, `CREATE ... IF NOT
  EXISTS`, `DROP ... IF EXISTS`, `REFRESH`, `COMMENT ON`, `GRANT`,
  `REVOKE`, `INSERT ... ON CONFLICT` (or SQLite's `INSERT OR IGNORE`), or a
  `DO` block, which you vouch for. Any other statement fails the load and
  names the fix. So does `CONCURRENTLY`, which a plan's transaction
  refuses; an `@index` is built concurrently.
- `down`, under the same rules, is what a plan runs when the piece is no
  longer declared.
- `after` places it: `"tables"` runs it after the tables, before the
  indexes; `"indexes"`, the default, after every object the schema
  declares; another piece's id, right after that piece. Pieces in one
  place run in the order of their ids. An `after` that names no piece, and
  pieces that run after each other, fail the load.
- `dialects` lists the dialects it runs on, `postgres` and `sqlite`; unset
  is every dialect the service lists.

A template literal with no `${}` is a string, so the SQL can span lines.
`create.sql` runs every piece, in order, at its place, and `drop.sql` runs
each `down` first. A migration plan records each piece by id and the
checksum of its statements, runs a new or changed one in `expand` and a
removed one's `down` in `contract`, and marks each such step `raw-sql`,
since it cannot judge what the SQL does
([Raw SQL](/superschematic/reference/migrations/#raw-sql)).

## Change tables that hold data

`create.sql` builds the database from nothing. `drop.sql` drops the
tables, views, triggers and functions it creates, and leaves the Postgres
extensions, which it names in a comment. A database that already holds
rows changes through a migration plan instead: `superschematic migrate
plan` compares the DB service with a previous version of it, with no
database at hand, and prints ordered steps, each with its SQL and its
hazards.

```sh
superschematic migrate plan schemas/services/shop-db --from-ref origin/main --format markdown --fail-on destructive
```

The `expand` steps run before the new servers roll out and keep the
previous version's servers working; the `contract` steps, such as drops,
run after. A rename reads as a drop and an add until `--rename` names it.
`superschematic-migrate`, a binary of its own, applies the plan to
Postgres, to a SQLite file or to Cloudflare D1, and records the model the
database is at. [Schema migrations](/superschematic/reference/migrations/)
covers the plan, its hazards and the runner.

## Beyond plain tables

Three reference pages cover what a DB schema can add on top of this guide:

- [Versioned tables](/superschematic/reference/versioned-tables/): `@versioned`
  keeps every version of a row in a history table, with readers for a
  past version or a past time, and writes fenced on the version a caller
  read. `@optimistic` keeps only the fence.
- [Version graphs](/superschematic/reference/version-graphs/): branch,
  commit, merge, release and rebase a tree of versioned tables as a
  whole, with engines in Go, TypeScript, Rust and Python.
- [Projection views](/superschematic/reference/projections/): read-only SQL
  views over joined tables, with `@projection`, `@join` and `@column`.

A type of a DB schema that composes a behavior, `@behavior("Workflow",
...)` say, is no table: it is an engine type, whose instances the engine
keeps, so the build writes it no table, no repository and no migration,
and writes the schema's engine document instead
([Engine types](/superschematic/guides/engine-behaviors/#engine-types)).
