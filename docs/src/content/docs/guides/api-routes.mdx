An API schema declares routes as methods of classes. Its build writes a
server (Go by default, a TypeScript Hono router or a Rust axum crate), an OpenAPI document, the
request and response types, and an SDK per language the config lists. This
guide walks the acme shop's `shop-orders` service, served in Go.
[Auth and permissions](/superschematic/guides/auth-and-permissions/) covers
who may call each route.

## Operation sets

A class of methods is an operation set, and each method one route. The
method bodies never run: the compiler reads their signatures.

<Snippet file="schemas/services/shop-orders/src/orders.schema.ts" symbol={['OrderQueries', 'OrderMutations']} />

- `@rest(method, path)` sets the route's HTTP method and path. The server
  mounts every path under `/api`, so `orders/{id}` is `GET /api/orders/{id}`.
- Sets group into namespaces. `OrderQueries` and `OrderMutations` share the
  `order` namespace: a set named `<Name>Queries`, `<Name>Mutations`,
  `<Name>Operations` or `<Name>Actions` belongs to `<name>` (kebab-case),
  sets named exactly `Query` or `Mutation` belong to `root`, and any other
  set, like `ProductReviews`, is its own. A namespace is one interface to
  implement in the server and one field or property of each SDK
  (`sdk.order`).

`@rest` may leave out the path, and a method may leave out `@rest`. The
route then gets defaults:

- **Method**: `POST` in a set whose name ends in `Mutations` or `Actions`,
  `GET` in any other.
- **Path**: `/api/<namespace>/<method-name>` in kebab-case (no namespace
  segment for `root`), then a `{param}` segment for each argument whose
  type can be one: a scalar that is an id, a UUID, an integer or
  path-like, never a list. `getOrder(id: Identity.UUID)` in `OrderQueries`
  is `GET /api/order/get-order/{id}`.

Give public routes an explicit path, so renaming a method or a set does
not move them.

The server asks for one implementation per namespace, with a method per
route and typed arguments:

## Start an implementation

Set `outputs.api.scaffoldsOutputDir` to a directory, relative to the
service directory, and the Go and Rust servers write a stub implementation
of each route there. A later build never overwrites one that exists, so
you edit the stubs in place; the build log says how many it created and
skipped. The TypeScript server writes none.

A Go server also says what its implementation is built from. Its
`deps.go` declares `Deps`, which holds:

- `Config`, the API's `EnvConfig`: its `@envVars` settings and the fields
  its edges derive
  ([Derived fields](/superschematic/guides/modeling-types/#derived-fields)),
  when it has either;
- `DB`, the ORM of the API's database (its `authDb`, or its one DB
  dependency), when it has one;
- a Go SDK client of each API its config `calls`, in a field named after
  that API (`ShopCatalog` for `shop-catalog`), so each callee generates a
  Go SDK;
- `Logger`, a zap logger.

`Constructor`, `func(deps Deps) (Implementations, error)`, is the
signature of the implementation's `New`. The implementation lives at the
naming file's
[`[implementation_paths]`](/superschematic/reference/naming/#implementation_paths),
`go/<service>` from the parent of the schemas root by default, and a
missing one is scaffolded there: by a
[stack's](/superschematic/guides/stacks/) build for each API its servers
serve, and by `build --scaffold` or `build-all --scaffold` for each Go API
built ([CLI](/superschematic/reference/cli/#build-service-dir)). The
scaffold is one `implementation.go` whose `New` asserts `Constructor` and
whose methods answer 501 until you write them. A `public` API's scaffold
also has `AuthMiddleware(deps)`, which refuses every request with 401, and
an API with encrypted operations `PayloadDecryptor(deps)`, which decrypts
nothing; replace both. An API whose `authDb` declares the user model
authenticates with the identity runtime and gets no `AuthMiddleware`
([Auth and permissions](/superschematic/guides/auth-and-permissions/#turn-it-on-the-user-model)). A scaffold never overwrites a file, and a build
without a stack or the flag writes no `implementation.go`.

A stack's build also writes each Go server's entrypoint, which fills
`Deps`, calls each implementation's `New`, and its `AuthMiddleware` and
`PayloadDecryptor` where the API's `Config` takes them, builds the
identity service of an API over the user model, and serves the result, as
[the Go tutorial](/superschematic/first-project/go-api/#run-it) shows for
acme-shop. Without a stack, your own `main` does that, as the tutorial's
tests do in-process
([Call it from Go](/superschematic/first-project/go-api/#call-it-from-go)).
A TypeScript API package has its `Deps` too, with a `pg` Pool as its
database, and its implementation is scaffolded at `typescript/<service>`
([TypeScript](/superschematic/install/typescript/#serve-a-generated-api)).
The TypeScript entrypoint is not built yet, and neither `Deps` nor the
entrypoint is built for Rust servers.

## Arguments

A method's arguments say where each value comes from:

- **Path**: an argument named in the path, such as `id` in `orders/{id}`.
- **Query**: `QueryParam<T>`. `Nullable<T>` makes it optional, and the Go
  implementation receives a pointer (`limit *float64`) or a nil slice. A
  list is read from repeated keys and comma-separated values
  (`?statuses=placed,shipped`), and each item is checked at
  `statuses[i]`.
- **Body, as an input type**: an argument of an object type, such as
  `input: PlaceOrderInput`, is the JSON body.
- **Body, as fields**: on a method without an input type, the other
  arguments are the fields of a JSON body object. `cancelOrder`'s `reason`
  is one: `POST /api/orders/{id}/cancel` with `{"reason": "..."}`. An
  optional one reaches Go as its zero value, here `""`, but an optional
  `Generic.JSON` keeps a null apart from an absent key
  ([null in an optional Generic.JSON](/superschematic/reference/json-scalars/#null-in-an-optional-genericjson)).
  On `GET`, such arguments come from the query string instead.

<Snippet file="schemas/services/shop-orders/src/orders.schema.ts" symbol={['PlaceOrderLine', 'PlaceOrderInput']} />

Before a method runs, the server decodes every argument, checks it
against its type and constraints, and answers 400 with every failure at
once, keyed by path, as an RFC 9457 problem body. A top-level key an
input type does not declare is refused too, by every server. A list of order lines
must hold one to 50 lines, and a country must match `^[A-Z]{2}$`:

## Responses and views

A method returns one view or a list of them. The server writes it in the
success envelope, `{"data": <view>, "meta": {"requestId": "..."}}`, and the
SDKs unwrap it.

A view can be declared over a table of the DB schema with `@source`. It
lists the columns a caller may see, and the loader checks each against the
table's field of the same name. A field with no column behind it is
`@virtual`, and the implementation fills it in:

<Snippet file="schemas/services/shop-orders/src/orders.schema.ts" symbol={['OrderLineView', 'OrderView']} />

`@display` says how a UI shows an order: what to call one and several, and
the fields a list of orders shows
([Display on a type](/superschematic/reference/documentation/#display-on-a-type)).
The Topcoat app's table of orders reads it

## Errors

An implementation returns an error to fail the call. The generated package
has a constructor per common status, each answering with a problem body
whose `detail` is the message:

- `NotFoundError(resource, err)` answers 404.
- `BadRequestError(message, err)` answers 400.
- `ConflictError(message, err)` answers 409.
- `UnauthorizedError(err)` and `ForbiddenError(err)` answer 401 and 403.
- Any other error is logged and answers 500 with a generic message, so no
  internal detail reaches the caller.

## Encrypted payloads

An operation is encrypted when its class extends `Encrypted`, when the
method is declared `@encrypted`, or when its result or one of its arguments
is an `EncryptedField<T>`:

```ts
import { EncryptedField, HttpMethod, rest } from "@superschematic/api";

export class CardMutations {
  @rest(HttpMethod.POST, "customers/{customerId}/cards")
  storeCard(customerId: string, number: EncryptedField<string>, label: string): CardReceipt {
    throw new Error("schema declaration only");
  }
}
```

The Go server takes an encrypted operation's whole request body as one
envelope, `{ "algorithm", "payload", "keyId" }` plus `encryptedKey` and
`iv` for the hybrid algorithm, where `payload` is the body's JSON,
encrypted: the same JSON an unencrypted request would send, with nothing
wrapped around it. It opens the envelope with its `Config.PayloadDecryptor`
before it decodes any argument, and answers 400 to a plain JSON body. The
generated SDKs in all four languages send the envelope, encrypted with the
public key from their encryption config or the call's options
(`publicEncryptionKey`). Every argument in the body travels encrypted, not
only the one declared `EncryptedField<T>`; `storeCard`'s path parameter
`customerId` does not.

The envelope is the body of a `POST`, `PUT` or `PATCH` request. The build
refuses an encrypted operation whose method is `GET` or `DELETE`, declared
or its set's default, since that request has no body to encrypt. It also
refuses an `EncryptedField<T>` argument that would travel outside the
envelope, a path or query parameter, and an encrypted operation that
uploads files: the envelope carries a JSON body, not a multipart one. On a field of an object type,
`EncryptedField<T>` is recorded in the IR and changes no generated code: an
input type with such a field does not make its operation encrypted. The
TypeScript and Rust servers have no decryption step, so they refuse an
encrypted operation that is not `@manualRouteRegistration`
([TypeScript](/superschematic/install/typescript/#serve-a-generated-api),
[Rust](/superschematic/install/rust/#serve-a-generated-api)).

## Traffic controls

Three decorators bound a route's use. On a class they apply to every route
of the set; on a method, to that route.

- `@rateLimit({ requestsPerMinute })` counts a client's requests to the
  route, by IP address, and answers 429 past the limit for the minute,
  with `Retry-After` and the code `too_many_requests`. The
  address is the connection's peer, not a forwarding header a client could
  write; behind a proxy you trust, each server takes the client IP from it
  as you tell it to (Go: chi's `ClientIPFromXFF` or `ClientIPFromHeader`
  middleware; TypeScript: `rateLimit: { keyOf: clientIpKey }`; Rust: a
  `ClientIp` request extension).
- `@bodyLimit({ megabytes })` answers 413 to a larger body before reading
  it.
- `@timeout({ seconds })` cancels the request's context when the time runs
  out, and answers 504 with the code `gateway_timeout`.

Each refusal is an RFC 9457 problem body, as an implementation's error is.
The generated route table lists them as middleware on each route, in the
order they run: the rate limit, the body limit, the permission check, then
the timeout around the handler. A server whose schema admits
[service callers](/superschematic/guides/auth-and-permissions/#service-callers)
runs its service step after the body limit and before the permission
check.

<Snippet file="testdata/generated/api/shop-orders/routes.go" from="createOrderPlaceOrderHandler(" to="Timeout(10*time.Second" />

The cheap refusals come first. A `@hmacVerified` webhook's signature check
runs before all of them. On an
[encrypted operation](#encrypted-payloads), the server's `PayloadDecryptor`
runs after the permission check and before the timeout. A request the rate
limit, the body limit or the permission check refuses never reaches the
decryptor, which in a deployment calls a key service. On such a route
`@bodyLimit` counts the envelope, not the decrypted payload.

<Snippet file="go/orders_test.go" symbol="TestTrafficControls" />

Each value is a whole number of at least 1; the build refuses 0, a
negative number or a fraction. The TypeScript and Rust servers apply the
same three, the service step and the permission check, in the same order
([TypeScript](/superschematic/install/typescript/#serve-a-generated-api),
[Rust](/superschematic/install/rust/#serve-a-generated-api)).

## Webhooks

`@webhook` marks an operation a third party calls, not your clients.
Every SDK leaves it out, methods and tools alike, since the provider
sends its own request from its own servers and no SDK holds the signing
secret `@hmacVerified` checks. A route your own clients or services call
is an ordinary route, not a webhook.

`@hmacVerified({ provider: "stripe" })` puts a signature check in front of
the route, in every server. `Implementations` gains a verifier for each
provider the schema names, which you write, and the server does not start
without one for every provider. The verifier runs before the rate limit,
the body limit and the permission check, so an unsigned request costs
nothing else. It also runs before the body limit caps the body, so cap
the read in the verifier if a large body matters.

| Server | The verifier | Without one |
|---|---|---|
| Go | `WebhookVerifiers["stripe"]`, a `WebhookVerifier` (`func(http.Handler) http.Handler`) | `ValidateImplementations` fails |
| TypeScript | `webhookVerifiers.stripe`, a `WebhookVerifier` from `@superschematic/http-runtime/hono` (Hono middleware) | tsc fails, and `buildRouter` throws |
| Rust | `webhook_verifiers["stripe"]`, an `Arc<dyn WebhookVerifier>` whose `verify(request, next)` is axum middleware | `build_router` panics |

A verifier answers a request it refuses and passes one it accepts on. One
that reads the body to check the signature passes the body on with it: the
Go verifier replaces `r.Body`, and the Rust verifier rebuilds the request
it hands to `next`. The TypeScript router gives the route a copy of the
request taken before the verifier ran, so its verifier can call
`c.req.text()`.

A `@manualRouteRegistration` webhook needs its provider's verifier too.
The TypeScript router runs it before the service's handler. The Go and Rust
routers do not mount the route, so the service wraps the route it adds: in
Go with the verifier from `WebhookVerifiers`, in Rust with
`webhook_verified(route, verifier)`.

## OpenAPI

The build writes `api/<service>/openapi.json`, and the Go and Rust servers
serve it at `GET /api/openapi.json` with a browsable page at
`GET /api/docs`. The TypeScript router serves neither; its package exports
the document as `<package>/openapi.json` for you to serve. Each
schema comment becomes a description, and each constraint the matching
JSON Schema keyword: `minLength`, `pattern`, `minimum`, and `minItems` and
`maxItems` for `listMin` and `listMax`.

## The TypeScript server

The same schema served in TypeScript generates a
[Hono](https://hono.dev) router with the same routes, argument rules,
envelopes, auth rules and traffic controls, and an `Implementations`

## The Rust server

`outputs.api.language: "RUST"` generates an [axum](https://docs.rs/axum)
crate with the same routes, argument rules, envelopes, auth rules and
traffic controls, and it serves the OpenAPI document. Each namespace is a
trait whose methods take one struct of the route's typed arguments,
`<Namespace><Operation>Args`, and return its result type. The router decodes and checks every argument first, as the
TypeScript router does, and refuses a key an input type does not declare.
The [Rust page](/superschematic/install/rust/#serve-a-generated-api)
lists what it refuses.

The example serves shop-orders on it too, keeping its orders in memory and
its users in SQLite, and runs all four SDKs' clients against it as against
the Go server. It builds the service with its API in Rust, into an output
root of its own:

```bash
superschematic build --with-deps --api-language RUST --out schemas/dist-rust schemas/services/shop-orders
```

The router takes one `Implementations` value: an implementation of each
namespace's trait, and the authenticator that says who the caller is.
`shop-orders`' users are the core user model's, so that is the identity
runtime's `IdentityAuthenticator`, over the API's identity service
([Auth and permissions](/superschematic/guides/auth-and-permissions/#say-who-the-caller-is-rust)).
One shop serves both namespaces here, and the users are in a SQLite
database of `shop-db`'s identity tables:
