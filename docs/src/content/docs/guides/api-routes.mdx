An API schema declares routes as methods of classes. Its build writes a
server (Go by default, a TypeScript Hono router or a Rust axum crate), an OpenAPI document, the
request and response types, and an SDK per language the config lists. This
guide walks the acme shop's `shop-orders` service, served in Go.
[Auth and permissions](/superschematic/guides/auth-and-permissions/) covers
who may call each route.

## Operation sets

A class of methods is an operation set, and each method one route. The
method bodies never run: the compiler reads their signatures.

<Snippet file="schemas/services/shop-orders/src/orders.schema.ts" symbol={['OrderQueries', 'OrderMutations']} />

- `@rest(method, path)` sets the route's HTTP method and path. The server
  mounts every path under `/api`, so `orders/{id}` is `GET /api/orders/{id}`.
- Sets group into namespaces. `OrderQueries` and `OrderMutations` share the
  `order` namespace: a set named `<Name>Queries`, `<Name>Mutations`,
  `<Name>Operations` or `<Name>Actions` belongs to `<name>` (kebab-case),
  sets named exactly `Query` or `Mutation` belong to `root`, and any other
  set, like `ProductReviews`, is its own. A namespace is one interface to
  implement in the server and one field or property of each SDK
  (`sdk.order`).

`@rest` may leave out the path, and a method may leave out `@rest`. The
route then gets defaults:

- **Method**: `POST` in a set whose name ends in `Mutations` or `Actions`,
  `GET` in any other.
- **Path**: `/api/<namespace>/<method-name>` in kebab-case (no namespace
  segment for `root`), then a `{param}` segment for each argument whose
  type can be one: a scalar that is an id, a UUID, an integer or
  path-like, never a list. `getOrder(id: Identity.UUID)` in `OrderQueries`
  is `GET /api/order/get-order/{id}`.

Give public routes an explicit path, so renaming a method or a set does
not move them.

The server asks for one implementation per namespace, with a method per
route and typed arguments:

## Start an implementation

Set `outputs.api.scaffoldsOutputDir` to a directory, relative to the
service directory, and the Go and Rust servers write a stub implementation
of each route there. A later build never overwrites one that exists, so
you edit the stubs in place; the build log says how many it created and
skipped. The TypeScript server writes none.

A Go server also says what its implementation is built from. Its
`deps.go` declares `Deps`, which holds:

- `Config`, the API's `EnvConfig`: its `@envVars` settings and the fields
  its edges derive
  ([Derived fields](/superschematic/guides/modeling-types/#derived-fields)),
  when it has either;
- `DB`, the ORM of the API's database (its `authDb`, or its one DB
  dependency), when it has one;
- a Go SDK client of each API its config `calls`, in a field named after
  that API (`ShopCatalog` for `shop-catalog`), so each callee generates a
  Go SDK;
- `Logger`, a zap logger.

`Constructor`, `func(deps Deps) (Implementations, error)`, is the
signature of the implementation's `New`. The implementation lives at the
naming file's
[`[implementation_paths]`](/superschematic/reference/naming/#implementation_paths),
`go/<service>` from the parent of the schemas root by default, and a
missing one is scaffolded there: by a
[stack's](/superschematic/guides/stacks/) build for each API its servers
serve, and by `build --scaffold` or `build-all --scaffold` for each Go API
built ([CLI](/superschematic/reference/cli/#build-service-dir)). The
scaffold is one `implementation.go` whose `New` asserts `Constructor` and
whose methods answer 501 until you write them. A `public` API's scaffold
also has `AuthMiddleware(deps)`, which refuses every request with 401, and
an API with encrypted operations `PayloadDecryptor(deps)`, which decrypts
nothing; replace both. An API whose `authDb` declares the user model
authenticates with the identity runtime and gets no `AuthMiddleware`
([Auth and permissions](/superschematic/guides/auth-and-permissions/#turn-it-on-the-user-model)). A scaffold never overwrites a file, and a build
without a stack or the flag writes no `implementation.go`.

A stack's build also writes each Go server's entrypoint, which fills
`Deps`, calls each implementation's `New`, and its `AuthMiddleware` and
`PayloadDecryptor` where the API's `Config` takes them, builds the
identity service of an API over the user model, and serves the result, as
[the Go tutorial](/superschematic/first-project/go-api/#run-it) shows for
acme-shop. Without a stack, your own `main` does that, as the tutorial's
tests do in-process
([Call it from Go](/superschematic/first-project/go-api/#call-it-from-go)).
A TypeScript API package has its `Deps` too, with a `pg` Pool as its
database, and its implementation is scaffolded at `typescript/<service>`.
A stack's build writes each TypeScript server's `main.ts`, which builds
each implementation from its `Deps` and serves the routers on Bun
([TypeScript](/superschematic/install/typescript/#serve-a-generated-api)).
A Rust API crate has its `Deps` as well, with a Postgres pool as its
database, and its implementation crate is scaffolded at `rust/<service>`.
A stack's build writes each Rust server's crate, whose `src/main.rs`
builds each `Deps`, calls the implementation's `create` and serves the
routers ([Rust](/superschematic/install/rust/#rust-servers)).

## Arguments

A method's arguments say where each value comes from:

- **Path**: an argument named in the path, such as `id` in `orders/{id}`.
  A parameter is in braces, as OpenAPI writes it. The load refuses a
  segment written as a router's `:id`, which every generator would publish
  and route as the text `:id`, and gives the path in braces:

  ```
  src/businesses.schema.ts:12:25: @rest path "businesses/:businessId/export" writes a path parameter as ":businessId", which OpenAPI and the generated routers read as text; write it in braces: "businesses/{businessId}/export"
  ```
- **Query**: `QueryParam<T>`. `Nullable<T>` makes it optional, and the Go
  implementation receives a pointer (`minRating *float64`) or a nil slice. A
  list, such as the catalog's `ids`, is read from repeated keys and
  comma-separated values (`?ids=<id>,<id>`), and each item is checked at
  `ids[i]`. What a list filters by is not a query argument: it is one
  [`FilterBy`](#filters) argument.
- **Body, as an input type**: an argument of an object type, such as
  `input: PlaceOrderInput`, is the JSON body.
- **Body, as fields**: on a method without an input type, the other
  arguments are the fields of a JSON body object. `cancelOrder`'s `reason`
  is one: `POST /api/orders/{id}/cancel` with `{"reason": "..."}`. An
  optional one reaches Go as its zero value, here `""`, but an optional
  `Generic.JSON` keeps a null apart from an absent key
  ([null in an optional Generic.JSON](/superschematic/reference/json-scalars/#null-in-an-optional-genericjson)).
  On `GET`, such arguments come from the query string instead.

<Snippet file="schemas/services/shop-orders/src/orders.schema.ts" symbol={['PlaceOrderLine', 'PlaceOrderInput']} />

`@display` and `@docs` on `PlaceOrderLine` change no route, type or
check: they name the rows and the product control of the form a Topcoat
page places an order with
([Rows without JavaScript](/superschematic/guides/topcoat/#rows-without-javascript)).

Before a method runs, the server decodes every argument, checks it
against its type and constraints, and answers 400 with every failure at
once, keyed by path, as an RFC 9457 problem body. A top-level key an
input type does not declare is refused too, by every server, unless the
type is `@allowUnknownFields` or the operation a `@webhook`, whose input
drops it ([Webhooks](#webhooks)). A list of order lines
must hold one to 50 lines, and a country must match `^[A-Z]{2}$`:

## Responses and views

A method returns one view or a list of them. The server writes it in the
success envelope, `{"data": <view>, "meta": {"requestId": "..."}}`, and the
SDKs unwrap it.

A view can be declared over a table of the DB schema with `@source`. It
lists the columns a caller may see, and the loader checks each against the
table's field of the same name. A relation's key reads the relation's
foreign key: `OrderLineView.productId` is the `product_id` of
`OrderLine.product`, and it refers to `ProductView`, the API's view of the
products' table, or of several views of it the one an operation lists,
with no `RefersTo` written
([What a value refers to](/superschematic/reference/references-and-search/#what-a-value-refers-to)).
A field with no column behind it is `@virtual`, and the implementation
fills it in:

`@display` says how a UI shows an order: what to call one and several, and
the fields a list of orders shows
([Display on a type](/superschematic/reference/documentation/#display-on-a-type)).

### Pages

A list operation pages when it declares `@paginated` from
`@superschematic/api` (D60):

```ts
@rest(HttpMethod.GET, "items")
@paginated({ defaultLimit: 20, maxLimit: 100 })
listItems(inStock: QueryParam<Nullable<boolean>>): ItemView[] {
  throw new Error("schema declaration only");
}
```

The route takes two query parameters the method does not declare: `limit`,
a whole number from 1 to `maxLimit` (100 when left out), `defaultLimit` when
the request sends none (20, or `maxLimit` when that is less); and `cursor`,
the `next` of the page before. `data` is the page,
`{"items": [...], "next": "<cursor>"}`, which may hold fewer items than its
limit, and `next` is null after the last page. A cursor is opaque: the
implementation names the position of a page's last item in the operation's
order, a key such as an order's `placedAt` and `id`, and the runtime writes
it as the unpadded base64url of its JSON. A cursor it cannot read back is a
400 at `cursor`, and the caller starts again. The operation must be a GET
returning `T[]`, with no argument named `cursor`, `limit` or `page`, and no
operation named `<operation>All` beside it, the name the SDKs give its
iterator. The OpenAPI document and the MCP tool describe both parameters
and the page.

Each runtime reads and builds a page: Go's `paging` package (`Read`,
`FromRows`, `EncodeCursor`, `DecodeCursor`), TypeScript's `readPage`,
`pageFromRows`, `encodeCursor` and `decodeCursor`, and Rust's `page` module
(`PageSpec`, `Page::from_rows`, `Cursor`). An implementation reads up to
`limit + 1` rows after the cursor's position and builds the page from them.
Every server and SDK renders it: the implementation takes `page`, the
page request, and returns the page, and each SDK's method takes `cursor`
and `limit` and returns the page, beside `<operation>All`, which yields
every item, asking for each page with the last one's `next`. A Topcoat
crate's call, procedure and argument form take the page too, and its
console links a list's next and first pages
([A paged list and a search box](/superschematic/guides/topcoat/#a-paged-list-and-a-search-box)).

A paged list sorts by an argument declared `SortBy<Item, Fields>` (D60,
amended), with `@paginated`'s `defaultSort` the order of a request that
sends none:

```ts
@rest(HttpMethod.GET, "items")
@paginated({ defaultLimit: 20, maxLimit: 100, defaultSort: "name" })
listItems(
  inStock: QueryParam<Nullable<boolean>>,
  sort: SortBy<ItemView, ["name", "sku"]>
): ItemView[] {
  throw new Error("schema declaration only");
}
```

The argument is an optional query parameter. Its value is a field that
`Fields` names, ascending, or the field after a `-`, descending: `name`,
`-name`, `sku` and `-sku` here. Ties break by `id` in the same direction.
An absent or empty sort is `defaultSort`, and the first value counts. Any
other value is the 400 an enum parameter gets, `Invalid query parameter
sort: expected one of name, -name, sku, -sku`. The router refuses a cursor's
text first, then the limit, then the sort, then a cursor of another sort.

A sort field may be `Nullable` (D112). An item that holds no value comes
after every item that holds one, in either direction: `sort=dueOn` reads
the earliest due date first and `sort=-dueOn` the latest, and each ends
with the items that have none, in `id` order in the sort's direction. A
caller who wants only the items with a value adds
`filter[dueOn][isNull]=false`. The repositories' `findPage` reads that
order, and an implementation that sorts its own rows reads the same, so
a list's pages mean one thing whoever serves them.

The implementation takes the sort only in its page request, its default
filled in: Go's `page.Sort` (`paging.Sort{Field, Desc}`), TypeScript's
`args.page.sort` (`{field, desc}`), and Rust's `args.page.sort`
(`Some(Sort)`). Its keys are its own, as an unsorted list's are. The
router binds the page's `next` to the sort, as the unpadded base64url of
exactly `{"sort":"-name","key":K}`, `K` the key's JSON, and unbinds a
cursor sent back before the implementation reads it. A cursor returned
under one sort and sent with another is the 400 `cursor is not one this
sort returned`, at `cursor`. Go's `paging.Read` unbinds, and `paging.Bind`
binds; TypeScript's `readPage` and `bindPage` do the same. Rust's router
reads the request with `PageSpec::query`, unbinds it with
`PageSpec::unbind` and binds the next with `Page::bind`, and an in-process
call does the same, so a cursor from the JSON API pages an in-process
call and back. The OpenAPI parameter is a string with the values as its
`enum`, `defaultSort` as its `default`, and `x-superschematic-sort: true`.
Each SDK sends the sort as the optional query argument it is.

The envelope is the only check of a cursor's sort, so a key need not
name its sort, and the ORM's key and acme's Rust keys are a row's id
alone: the implementation reads that row's value of the sort field. A key
that holds the value itself can carry a long text past the bound
cursor's 1024 characters, and a `next` past them is the implementation's
error, a 500, for every reader paging past that row. The loader warns of
a text sort field without a `maxLength` for that reason.

A Go implementation over a database service reads a page through the
ORM: `FindPage` runs one query of `limit + 1` rows after a key, in the
order of one column, then the key, with a filter's conditions beside the
keyset, and its `Next` is the key the page's cursor holds, the last row's
key alone ([Pages](/superschematic/guides/database-tables/#pages)).
`Parse<Type>Sort` reads the page request's sort into the ORM's order, and
`ErrPageKey` is a key without an id, or whose row no longer exists.

`shop-orders` pages its orders, a product's reviews and its catalog, each
in a sort: the orders by `placedAt` or `totalCents`, the products by
`name` or `priceCents`, and the reviews by `createdAt` or `rating`, each
list's `defaultSort` the order it had before it took a sort. An order
stores its total when it is placed, since its lines do not change after,
so its table can order by it. The Go implementation reads each page
through `FindPage`: the caller's orders (every customer's for staff),
of the statuses the request's [filter](#filters) keeps, in the sort
`ParseOrderSort` reads, after the key the cursor holds, with their lines:

### Filters

A list takes its filters as one argument declared `FilterBy<Item, Fields>`
from `@superschematic/api` (D106): `Item` is the type the operation lists,
and `Fields` the fields of it a caller may filter by.

`shop-orders` lists a caller's orders by their status:

<Snippet file="schemas/services/shop-orders/src/orders.schema.ts" from="// The caller's orders, or every customer's for staff, oldest first:" to="  }" />

The operation is a `GET` whose result is a list, paged or not, and it
takes one `FilterBy`. The argument is written as it stands: a filter is
optional already, so it takes no `?`, `Nullable`, `QueryParam`, `Validate`
or list around it. Its name is what the implementation and the SDKs call
the filter. On the wire the parameter is `filter` whatever the argument is
called, so no other argument of the operation is named `filter`, and a
paged operation's filter is not named `cursor`, `limit` or `page`. The
JSON and YAML forms write `filter: { argument, fields: [{ name }] }` on
the operation.

Each of `Fields` names a field of the item, once, that holds one value a
filter can compare. The loader refuses:

- a list or a map, a `Secret`, a `@decrypted` field, whose column holds
  ciphertext, JSON, an object type, a union and a duration;
- on an item that is a `@source` view, a `@virtual` field, which no column
  of the table holds, and `deletedAt` and `deletedBy`, which no row a
  list holds has a value in.

The other audit fields filter as any field of their type: `createdBy` and
`updatedBy` as an id (`filter[createdBy]=<id>` is "what I filed"), and
`createdAt` and `updatedAt` as a time.

So a list filters by nothing its view does not show, and narrowing a list
cannot probe a column no view returns. The refusal names the operation,
the argument and the field:

```
OrderQueries.listOrders: filter argument filter names OrderView.lines, which holds OrderLineView[]; a filter compares one value
```

A field's type gives its kind, the one both ORMs give a column of that
type, and its kind gives its operators:

| Kind | A field of | Operators |
| --- | --- | --- |
| `uuid` | a UUID, such as `Identity.UUID`, a relation's key among them | `eq`, `ne`, `in`, `notIn` |
| `enum` | an enum | `eq`, `ne`, `in`, `notIn` |
| `bool` | `boolean` | `eq`, `ne`, `in`, `notIn` |
| `string` | `string`, or a scalar of text | `eq`, `ne`, `in`, `notIn`, `contains` |
| `int` | a whole number, such as `Generic.Int64` | `eq`, `ne`, `in`, `notIn`, `gt`, `gte`, `lt`, `lte` |
| `float` | `number` | `eq`, `ne`, `in`, `notIn`, `gt`, `gte`, `lt`, `lte` |
| `decimal` | `Generic.Decimal` | `eq`, `ne`, `in`, `notIn`, `gt`, `gte`, `lt`, `lte` |
| `datetime` | `Temporal.DateTime` | `eq`, `ne`, `in`, `notIn`, `gt`, `gte`, `lt`, `lte` |
| `date` | `Temporal.Date` | `eq`, `ne`, `in`, `notIn`, `gt`, `gte`, `lt`, `lte` |

A field that may be null, a `Nullable` one, takes `isNull` as well, and no
other field does. Here `status` is an enum, so the orders take `eq`,
`ne`, `in` and `notIn` of it. `shop-cart`'s catalog filters its products by `inStock`, a
boolean, and `priceCents`, a whole number, which takes the comparisons
too.

On the wire a filter is the bracket form: `filter[field]=value` is
equality, as `filter[field][eq]=value` is, and `filter[field][op]=value`
names an operator.

```
GET /api/orders?filter[status][in]=placed,shipped
GET /api/orders?filter[status][notIn]=cancelled,refunded
GET /api/catalog/products?filter[inStock]=true&filter[priceCents][gte]=500&filter[priceCents][lt]=2000
```

- `eq`, `ne`, `gt`, `gte`, `lt` and `lte` take one value of the field's
  type.
- `in` and `notIn` take 1 to 100 values separated by commas. Each is
  trimmed, and an empty one is dropped.
- `ne` and `notIn` negate `eq` and `in` (D112): each keeps exactly the
  items the other leaves out. An item whose field is null is among them:
  `filter[assigneeId][ne]=<id>` keeps the issues assigned to anyone else
  and the ones assigned to no one, where SQL's `<>` would drop the
  second. Add `filter[assigneeId][isNull]=false` for the first alone.
- `contains` takes text, at least one character, and keeps the items whose
  field holds it, in any case.
- `isNull` takes `true`, which keeps the items whose field is null, or
  `false`, which keeps the others.

Every filter a request sends holds at once; there is no way to ask for one
or another across fields, and `in` is "one or another" of one field's
values. A request holds at most 50 filter parameters, and each
operator of a field once: `filter[status]` and `filter[status][eq]` are
the same one. Fields and operators are named exactly, so `filter[Status]`
and `filter[status][IN]` are refused. A list without a `FilterBy` leaves a
`filter` parameter alone, as it leaves any parameter it does not declare.

Each server reads the filters with its runtime's reader, after the
operation's query parameters and before its page: Go's `filterparse.Read`,
TypeScript's `readFilter` and Rust's `FilterSpec::query`, held to one set
of answers by `runtime/http/testdata/filter_parity.json`. A refusal is a
400 problem whose `detail` names the parameter and whose `details` hold
the `location` (`query`), the `parameter` and the `reason`:

```json
{
  "status": 400,
  "code": "bad_request",
  "detail": "Invalid query parameter filter[status]: takes no operator gt; expected one of eq, ne, in, notIn",
  "details": {
    "location": "query",
    "parameter": "filter[status]",
    "reason": "takes no operator gt; expected one of eq, ne, in, notIn"
  }
}
```

The reader refuses more than 50 filter parameters first, at `filter`
(`must hold at most 50 filters`). It then reads the keys in ascending
order of their bytes, so a request with two faults gets the same answer
from every server, and refuses the first key that is, in this order:

| The fault | Named at | The reason |
| --- | --- | --- |
| not `filter[field]` or `filter[field][operator]` | the key | `expected filter[field] or filter[field][operator]` |
| a field `Fields` does not name | `filter[field]` | `is not a field this operation filters by; expected one of status` |
| an operator the field does not take | `filter[field]` | `takes no operator gt; expected one of eq, ne, in, notIn` |
| an operator sent twice | `filter[field]` | `holds eq more than once` |
| a value the operator does not take | `filter[field]` | `isNull expects true or false`, `in names no value`, `in must hold at most 100 values`, the same two of `notIn`, or `contains needs text` |

The route then decodes each value as an item of a query list of its
field's type, and a value the type refuses is a 400 at `filter[field]`
too. The Go server answers every such field at once, in the problem's
`errors`; the TypeScript and Rust servers answer the first, `Invalid query
parameter filter[priceCents]: expected an integer`. A refused filter never
reaches the implementation, and it is refused before the page is read:
`limit=0&filter[colour]=red` is refused for its filter.

The implementation takes the filter typed, a member per field. A member
is set only for a field the request filters by, and holds each operator
the request sent, its values decoded:

| Server | The filter | A member |
| --- | --- | --- |
| Go | the method's `filter` argument, an `OrderListOrdersFilter` (`<Namespace><Operation>Filter`) | `*filterparse.Equals[T]`, `*filterparse.Ordered[T]` or `*filterparse.Text[T]`, nil for a field the request does not filter by: `Eq`, `Ne`, `Gt`, `Gte`, `Lt` and `Lte` a `*T`, `In` and `NotIn` a `[]T`, `Contains` a `*string`, `IsNull` a `*bool` |
| TypeScript | `args.filter`, a `ListOrdersFilter` (`<Operation>Filter`), `{}` when the request filters by nothing | `EqualsFilter<T>`, `OrderedFilter<T>` or `TextFilter<T>` of the HTTP runtime, absent for a field the request does not filter by: `eq`, `ne`, `in`, `notIn`, `gt`, `gte`, `lt`, `lte`, `contains`, `isNull` |
| Rust | `args.filter`, an `OrderListOrdersFilter` (`<Namespace><Operation>Filter`), whose `default()` filters by nothing | `Option<runtime::filter::Equals<T>>`, `Ordered<T>` or `Text<T>`: `eq`, `ne`, `in_` (`in` is a keyword), `not_in`, `gt`, `gte`, `lt`, `lte`, `contains`, `is_null` |

The member's type follows the field's operators: `Equals` for a UUID, an
enum and a boolean, `Ordered` for a number, a date and a time, and `Text`
for text. `T` is the field's type in the server's types: an enum is its
generated type, a `Temporal.DateTime` a `Date` in TypeScript. The
argument is named as the schema names it, so `where: FilterBy<...>` is
Go's `where` and `args.where`. A Rust implementation is also called in
process, by a caller that builds the filter itself; the filter's
`check()` holds such a one to the route's rules, each member by its
field's operators and then its values by the field's type, with the 400
the router answers.

An implementation reads every member its field's type holds. The router
admits each operator the field takes whether or not the implementation
reads it, so one that copies `Eq` and `In` alone answers a request for
`ne` as if it had sent no filter, and the build cannot see that. A list
the build serves (`@tableOperation`) reads them all.

The members are shaped as the Go ORM's filters are, so one copies across.
`shop-api` lists its products by `inStock`, a `bool` on both sides:

A number's member copies the same way, its `Gt`, `Gte`, `Lt` and `Lte`

([Pages](/superschematic/guides/database-tables/#pages)).

A cursor carries no filter. The caller asks for each next page with the
same filters, and a page that changes one starts again at the first
page. Each SDK takes the filter typed and writes the bracket form, and
its `<operation>All` sends the filter with every page
([Client SDKs](/superschematic/guides/client-sdks/#filters)).

The OpenAPI document gives the filter as one query parameter, `filter`,
with `style: deepObject` and `explode: true`: an object with a property
per field, each an object of the field's operators, `in` and `notIn` an
array of 1 to 100 items. Its description gives the query string's form and the limit
of 50 filters. An MCP tool takes the filter as an object
([MCP tools](/superschematic/reference/mcp-tools/#toolsschemajson)).

`FilterBy` is the only way to declare a list's filters. Earlier IR held a
`Filterable` flag on an operation, which the Go routes and the SDKs read,
but no decorator ever set it: there was no `@filterable`. The flag is
gone, and the SDKs' untyped filter parameters with it.

## Files

### Uploads

A field of an input type declared `FileUpload<C>` is a file. Its
operation's body is `multipart/form-data`: each file is a part named as its
field, and the input's other fields travel as JSON in a part named `data`.
A JSON body, which holds no file, is read too. The storefront imports a
cart's lines from a CSV:

```ts
import { FileUpload, HttpMethod, requirePermission, rest } from "@superschematic/api";

// A CSV of lines to add to a cart: a header row, then one sku,quantity
// row a line, at most 64 KiB.
export abstract class ImportCartLinesInput {
  lines: FileUpload<{ maxBytes: 65536; contentTypes: ["text/csv"]; extensions: [".csv"] }>;
}

export class CartMutations {
  @rest(HttpMethod.POST, "carts/{cartId}/lines/import")
  @requirePermission(["carts.write"])
  importCartLines(cartId: Identity.UUID, input: ImportCartLinesInput): CartView {
    throw new Error("schema declaration only");
  }
}
```

- `maxBytes` bounds the file, 100 MiB when unsaid. `contentTypes` lists
  the media types the part's `Content-Type` may name, compared without
  parameters, so `text/csv; charset=utf-8` is `text/csv`; a part without
  one is `application/octet-stream`. `extensions` lists the endings its
  filename may have, in any case. Each one unsaid admits any file, and
  `Nullable<FileUpload>` makes the file optional.
- Every server checks the files first, in the input's field order, then
  reads the other fields as it reads a JSON input, setting aside the
  errors at the file fields, which the JSON never holds. A file its field
  does not admit is a [refused input](/superschematic/install/go/#serve-a-generated-api):
  `errors` holds its error at its field, `required`, `uploadMaxBytes`,
  `uploadContentType` or `uploadExtension`, and the implementation never
  runs:

  ```json
  {"type": "about:blank", "title": "Bad Request", "status": 400, "code": "bad_request",
   "detail": "Request body does not match the declared input",
   "details": {"location": "body", "reason": "validation failed"},
   "errors": {"lines": [{"validator": "uploadExtension", "message": "file name does not end in .csv"}]}}
  ```

  A body that is neither multipart nor JSON is "Request body is not
  multipart/form-data". So is one of more than 1000 parts, or whose part
  headers run past 10000 lines of file parts or 10 MiB in all: both
  servers read multipart under the limits of Go's `ReadForm`.
- `@bodyLimit` caps the whole body, and a larger one answers 413. Without
  it, the TypeScript server caps it at its files' limits beside its JSON
  cap, and the Go server does not cap it.
- The Go method takes `files map[string]*FileUploadData` after the input,
  each with its `Filename`, `ContentType`, `Size` and `Data`. The
  TypeScript method takes `args.files`, each a `File`, and `args.input`
  without the file fields. The Rust server refuses the operation unless it
  is `@manualRouteRegistration` ([Rust](/superschematic/install/rust/#serve-a-generated-api)).
- A file is one string field of a type that is only an operation's input,
  the single input of a `POST`, `PUT` or `PATCH` that is not encrypted;
  the build refuses any other. A field of an extension's upload scalar is a
  file too, under the scalar's limits
  ([Write an extension](/superschematic/extending/write-an-extension/#a-scalar-catalog)).
- The SDKs send the file beside the input
  ([Client SDKs](/superschematic/guides/client-sdks/#files)), and the
  OpenAPI document describes the multipart body: the `data` part, each
  file as binary with its limits, and its media types as the part's
  `encoding`.

### Downloads

An operation whose result is `FileDownload<C>` answers a file, not the
JSON envelope. The storefront exports a cart as the CSV its import reads:

```ts
export class CartQueries {
  @rest(HttpMethod.GET, "carts/{cartId}/export")
  @requirePermission(["carts.read"])
  exportCart(cartId: Identity.UUID): FileDownload<{ contentType: "text/csv; charset=utf-8"; filename: "cart.csv" }> {
    throw new Error("schema declaration only");
  }
}
```

- The implementation returns the file. In TypeScript it is
  `{ body, filename?, headers? }`: the body is text, sent as UTF-8, bytes,
  a `Blob`, or a `ReadableStream`, sent as the implementation writes it.
  In Go it is `*FileDownload{Body, Filename, Header}`, whose `Body` the
  route copies as it reads it and closes when it can.
- The server sets `Content-Type` to C's `contentType`, and
  `Content-Disposition` to an attachment under the implementation's
  filename, or C's `filename` when it names none (RFC 6266):
  `attachment; filename="M_rz.csv"; filename*=UTF-8''M%C3%A4rz.csv` for
  a name with a letter outside ASCII. `filename` holds the name with each
  such letter, and each of `"`, `\` and `%`, as `_`, and `filename*` the
  name itself; a directory or a control character in the name is dropped.
  The Go and TypeScript servers write the same header for every name
  (`runtime/http/testdata/content_disposition_parity.json`). Its
  `Cache-Control` is `no-store` unless the implementation sets one, and a
  refusal is still a problem body.
- The OpenAPI document describes the 200 as C's media type, a binary
  string, with its `Content-Disposition` header.
- The TypeScript SDK returns `{ blob, filename, contentType }`, and the
  Go and Python SDKs a `DownloadedFile`
  ([Client SDKs](/superschematic/guides/client-sdks/#files)). The Rust SDK
  and the Rust server refuse the operation for now, naming it; support
  follows.
- A file is no tool result: the [tool documents](/superschematic/reference/mcp-tools/)
  list the operation hidden, and the build refuses a visible `@mcp` on it.
  A `FileDownload` result is never null, encrypted or `@paginated`.

## Encrypted payloads

An operation is encrypted when its class extends `Encrypted`, when the
method is declared `@encrypted`, or when its result or one of its arguments
is an `EncryptedField<T>`:

```ts
import { EncryptedField, HttpMethod, rest } from "@superschematic/api";

export class CardMutations {
  @rest(HttpMethod.POST, "customers/{customerId}/cards")
  storeCard(customerId: string, number: EncryptedField<string>, label: string): CardReceipt {
    throw new Error("schema declaration only");
  }
}
```

The Go server takes an encrypted operation's whole request body as one
envelope, `{ "algorithm", "payload", "keyId" }` plus `encryptedKey` and
`iv` for the hybrid algorithm, where `payload` is the body's JSON,
encrypted: the same JSON an unencrypted request would send, with nothing
wrapped around it. It opens the envelope with its `Config.PayloadDecryptor`
before it decodes any argument, and answers 400 to a plain JSON body. The
generated SDKs in all four languages send the envelope, encrypted with the
public key from their encryption config or the call's options
(`publicEncryptionKey`). Every argument in the body travels encrypted, not
only the one declared `EncryptedField<T>`; `storeCard`'s path parameter
`customerId` does not.

The envelope is the body of a `POST`, `PUT` or `PATCH` request. The build
refuses an encrypted operation whose method is `GET` or `DELETE`, declared
or its set's default, since that request has no body to encrypt. It also
refuses an `EncryptedField<T>` argument that would travel outside the
envelope, a path or query parameter, and an encrypted operation that
uploads files: the envelope carries a JSON body, not a multipart one. On a field of an object type,
`EncryptedField<T>` is recorded in the IR and changes no generated code: an
input type with such a field does not make its operation encrypted. The
TypeScript and Rust servers have no decryption step, so they refuse an
encrypted operation that is not `@manualRouteRegistration`
([TypeScript](/superschematic/install/typescript/#serve-a-generated-api),
[Rust](/superschematic/install/rust/#serve-a-generated-api)).

## Traffic controls

Three decorators bound a route's use. On a class they apply to every route
of the set; on a method, to that route.

- `@rateLimit({ requestsPerMinute })` counts a client's requests to the
  route, by IP address, and answers 429 past the limit for the minute,
  with `Retry-After` and the code `too_many_requests`. The
  address is the connection's peer, not a forwarding header a client could
  write; behind a proxy you trust, each server takes the client IP from it
  as you tell it to (Go: chi's `ClientIPFromXFF` or `ClientIPFromHeader`
  middleware; TypeScript: `rateLimit: { keyOf: clientIpKey }`; Rust: a
  `ClientIp` request extension).
- `@bodyLimit({ megabytes })` answers 413 to a larger body before reading
  it.
- `@timeout({ seconds })` cancels the request's context when the time runs
  out, and answers 504 with the code `gateway_timeout`.

Each refusal is an RFC 9457 problem body, as an implementation's error is.
The generated route table lists them as middleware on each route, in the
order they run: the rate limit, the body limit, the permission check, then
the timeout around the handler. A server whose schema admits
[service callers](/superschematic/guides/auth-and-permissions/#service-callers)
runs its service step after the body limit and before the permission
check.

<Snippet file="testdata/generated/api/shop-orders/routes.go" from="createOrderPlaceOrderHandler(" to="Timeout(10*time.Second" />

The cheap refusals come first. A `@hmacVerified` webhook's signature check
runs before all of them. On an
[encrypted operation](#encrypted-payloads), the server's `PayloadDecryptor`
runs after the permission check and before the timeout. A request the rate
limit, the body limit or the permission check refuses never reaches the
decryptor, which in a deployment calls a key service. On such a route
`@bodyLimit` counts the envelope, not the decrypted payload.

negative number or a fraction. The TypeScript and Rust servers apply the

[Rust](/superschematic/install/rust/#serve-a-generated-api)).

## Webhooks

`@webhook` marks an operation a third party calls, not your clients.
Every SDK leaves it out, methods and tools alike, since the provider
sends its own request from its own servers and no SDK holds the signing
secret `@hmacVerified` checks. A route your own clients or services call
is an ordinary route, not a webhook.

A provider adds keys to its payloads over time, so a webhook's input
reads only the keys its type declares and drops the others, in every
server, where any other input refuses them (D87). The declared keys are
checked as on any route, and the method gets its typed input with no
manual route:

```ts
export abstract class PlaidWebhookEvent {
  webhook_type: string;
  webhook_code: string;
  item_id: string;
}

export class PlaidWebhooks {
  @webhook
  @publicRoute
  @hmacVerified({ provider: "plaid" })
  @rest(HttpMethod.POST, "plaid/webhook")
  plaidWebhook(input: PlaidWebhookEvent): Accepted {
    throw new Error("schema declaration only");
  }
}
```

A body with an `environment` key reaches `plaidWebhook` as the three
declared keys; one without `item_id` is refused. A key is declared only as
the type spells it, so `Item_Id` is dropped too, in Go as elsewhere. A
nested object's keys follow its own type: mark it `@allowUnknownFields` to
drop them in every decoder of it
([Modeling types](/superschematic/guides/modeling-types/#lenient-decoding)).
A provider whose payload is a closed contract keeps the refusal with
`@strictJSON` on the input type.

`@hmacVerified({ provider: "stripe" })` puts a signature check in front of
the route, in every server. `Implementations` gains a verifier for each
provider the schema names, which you write, and the server does not start
without one for every provider. The verifier runs before the rate limit,
the body limit and the permission check, so an unsigned request costs
nothing else. It also runs before the body limit caps the body, so cap
the read in the verifier if a large body matters.

| Server | The verifier | Without one |
|---|---|---|
| Go | `WebhookVerifiers["stripe"]`, a `WebhookVerifier` (`func(http.Handler) http.Handler`) | `ValidateImplementations` fails |
| TypeScript | `webhookVerifiers.stripe`, a `WebhookVerifier` from `@superschematic/http-runtime/hono` (Hono middleware) | tsc fails, and `buildRouter` throws |
| Rust | `webhook_verifiers["stripe"]`, an `Arc<dyn WebhookVerifier>` whose `verify(request, next)` is axum middleware | `build_router` panics |

A verifier answers a request it refuses and passes one it accepts on. One
that reads the body to check the signature passes the body on with it: the
Go verifier replaces `r.Body`, and the Rust verifier rebuilds the request
it hands to `next`. The TypeScript router gives the route a copy of the
request taken before the verifier ran, so its verifier can call
`c.req.text()`.

A `@manualRouteRegistration` webhook needs its provider's verifier too.
Every router runs it before the service's handler: the TypeScript one,
the Go one, which mounts the handler `Config.ManualRoutes` holds, and the
Rust one's `build_router_with_manual_routes`. A service that mounts the
route itself wraps it: in Go with the verifier from `WebhookVerifiers`,
in Rust with `webhook_verified(route, verifier)`.

### A JWT that carries the body's hash

Some providers sign a webhook with a JWT instead of an HMAC. Plaid sends an
ES256 JWT in `Plaid-Verification`: its `kid` names the key to ask
`/webhook_verification_key/get` for, and its `request_body_sha256` claim
is the SHA-256 of the raw body. Each runtime has this verifier built in:

| Server | The verifier |
|---|---|
| Go | `webhook.JWTBodyHashVerifier(webhook.JWTBodyHashOptions{...})` from the runtime's `webhook` package, a `func(http.Handler) http.Handler` |
| TypeScript | `jwtBodyHashVerifier({...})` from `@superschematic/http-runtime/hono` |
| Rust | `JwtBodyHashVerifier::new(JwtBodyHashOptions {...})`, whose `verify(request, next)` your `WebhookVerifier` calls |

It checks, in order:

1. The header holds a compact JWS whose `alg` is the configured one
   (`ES256`; `none` and every other `alg` are refused) and whose `kid`
   names a key.
2. The signature verifies with that key.
3. `iat` is no older than the maximum age, and no further ahead than the
   clock skew (60 seconds unless set).
4. The claim equals the lowercase hex SHA-256 of the raw body, compared in
   constant time.

A refusal is 401 `invalid_signature`. When the key cannot be fetched and
none is held, the answer is 503 `service_unavailable`, so the provider
sends the webhook again. A body over the cap (1 MiB unless set) is 413.
The route then reads the body as usual.

The keys come from a lookup by `kid`, or from a JWKS URL fetched whole. A
key is held for an hour. An unknown `kid` is looked up at once, but the
provider is asked at most once a minute, so a flood of made-up kids costs
one lookup a minute, and a held key keeps verifying meanwhile. A lookup
has 10 seconds, and a JWKS URL's answer at most 1 MiB; past either, the
lookup has failed. A token whose `alg` is not `ES256`, `none` among them,
is refused before any key is looked up.

```ts
import { jwtBodyHashVerifier } from "@superschematic/http-runtime/hono";

const implementations: Implementations = {
  // ...one object per operation namespace
  webhookVerifiers: {
    plaid: jwtBodyHashVerifier({
      header: "plaid-verification",
      // The key with this kid, or null for one Plaid has expired.
      jwks: async kid => {
        const { key } = (await plaid.webhookVerificationKeyGet({ key_id: kid })).data;
        return key.expired_at === null ? key : null;
      },
      alg: "ES256",
      maxAge: "5m",
      bodyHashClaim: "request_body_sha256",
    }),
  },
};
```

In Go, `MaxAge` is a `time.Duration` and the lookup returns a
`*serviceauth.JWK`, nil when there is no such key:

```go
plaidVerifier, err := webhook.JWTBodyHashVerifier(webhook.JWTBodyHashOptions{
	Header:        "Plaid-Verification",
	Keys:          plaidKey, // func(ctx context.Context, kid string) (*serviceauth.JWK, error)
	Alg:           webhook.AlgES256,
	MaxAge:        5 * time.Minute,
	BodyHashClaim: "request_body_sha256",
})
```

The three runtimes run the same vectors
(`runtime/http/testdata/webhook_jwt_parity.json`).

## Operations the build serves

Most operations over a table do one thing: read a row and copy its columns
into a view, list rows, or copy an input into the repository's create or
update. `@tableOperation()` from `@superschematic/api` has the build write
that handler (D106). The method's views are `@source` views of one table,
and the generated server reads or writes that table through the
database's repositories, so the implementation has no method for it.

```ts
// An issue as a caller who may read issues sees it.
@source(Issue)
export abstract class IssueView {
  id: Identity.UUID;
  teamId: Identity.UUID;
  title: string;
  body: Nullable<string>;
  status: IssueStatus;
  priority: Generic.Int64;

// What a caller sets to create an issue under a team: the team is the
// path's, and status and priority take the table's defaults when unsaid.
@source(Issue)
export abstract class CreateIssueInput {

  body: Nullable<string>;
  priority: Nullable<Generic.Int64>;

}

// What a caller may change of an issue.
@source(Issue)
export abstract class UpdateIssueInput {
  title: Nullable<Validate<string, { minLength: 1; maxLength: 200 }>>;
  body: Nullable<string>;
  status: Nullable<IssueStatus>;
  priority: Nullable<Generic.Int64>;
  assigneeId: Nullable<Identity.UUID>;
}

export class Issues extends Authenticated {
  @rest(HttpMethod.GET, "teams/{teamId}/issues")
  @requirePermission(["issues.read"])
  @paginated({ defaultLimit: 20, maxLimit: 100, defaultSort: "-createdAt" })
  @tableOperation()
  listIssues(
    teamId: Identity.UUID,
    q: SearchQuery<Validate<string, { maxLength: 100 }>>,

    filter: FilterBy<IssueView, ["status", "priority", "title", "assigneeId", "createdAt"]>
  ): IssueView[] {
    throw new Error("schema declaration only");
  }

  @rest(HttpMethod.GET, "issues/{id}")
  @requirePermission(["issues.read"])
  @tableOperation()
  getIssue(id: Identity.UUID): IssueView {
    throw new Error("schema declaration only");
  }

  @rest(HttpMethod.POST, "teams/{teamId}/issues")
  @requirePermission(["issues.write"])
  @tableOperation()
  createIssue(teamId: Identity.UUID, input: CreateIssueInput): IssueView {

  }
```

The method stays an ordinary declaration. Its `@rest` route, its guards,
its `@rateLimit`, its arguments and its result are what it writes, its
`@docs` and `@mcp` what it writes or what [its declaration gives
it](#docs-and-tools), and the OpenAPI document, the SDKs, the permission
catalog and the tool documents read it as any operation. The decorator changes one
thing: the server mounts the route on a handler the build writes, and the
implementation's interface and its scaffold leave the method out. Take the
decorator off and the operation is one you implement, with the same route,
types, SDK method and tool. A set may hold both kinds, so one operation
that needs code of yours does not cost the others theirs. The decorator
takes no argument, or one, its [row rule](#row-rules); the JSON and YAML
forms write `tableOperation: {}` on the operation, with the rule's `by`
and `overridePermission` inside it.

### The table and the kind

The table is the `@source` of the method's result view, a table of the
API's database: its `authDb`, or its one DB dependency. Every view the
method names, its result and its body, is the API's own `@source` view of
that table, and a method that names a plain type, or views of two tables,
fails the load. A read and a list may read a projection with a key in the
table's place ([Projections](/superschematic/reference/projections/)); a
write may not, a projection being read-only.

The HTTP method and the shape say what the handler does:

| Method and shape | Kind | The handler | It answers |
| --- | --- | --- | --- |
| `GET`, the table's key in the path, one view | read | reads the live row the key names | the row's view |
| `GET`, a list of views, no key in the path | list | reads one page of the live rows | the page, `{ items, next }` |
| `POST`, one body argument, no key | create | creates a row from the body's members | the view of the row as the write left it |
| `PATCH`, the key, one body argument | update | sets the members the body sets | the view of the row as the write left it |
| `DELETE`, the key | delete | deletes the row | the view of the row as it was before |

A success is the envelope a hand-written route answers, with the status it
answers, 200. A shape that fits no kind fails the load, and the message
says what it found:

```
Issues.getIssue: a GET whose result is one view reads a row of Issue, and its path holds no {id}, the table's key; a GET that lists rows answers IssueView[]
```

A `PUT` is refused: it would replace the row, or upsert it by a key the
caller names, and neither is built. So is a `Nullable` result, since a key
that holds no live row is a 404, a `@webhook`, and an argument a kind
reads nothing from, such as a `QueryParam` on a read.

### The path

The key travels in the path under the key field's name: `{id}` for a
table whose `@key` is `id`, with the key's type. A path parameter beside
it is named for the key of one of the table's to-one relations, `{teamId}`
for `Issue.team`, and holds the row to that parent:

- a create sets the relation from the path, and its body may not carry
  the same field;
- a read, a list, an update and a delete keep only the rows whose relation
  is the path's, so a row under another parent is a 404, as
  `DELETE /api/issues/{issueId}/comments/{id}` is for a comment of
  another issue;
- a create under a parent that does not exist is a 404 that names the
  parent, `Team not found`.

A path parameter that names neither the key nor a relation's key fails
the load, since nothing says what it compares.

### What a view holds

Nothing is served that a view does not list. A result view's field reads
the row's column of the same name, a relation's key (`assigneeId`) the
relation's foreign key, and a field marked `@decrypted` the opened value
of its `Encrypted<T>` column. A result view with a `@virtual` field fails
the load, since no implementation fills it: leave the field out, or write
that operation by hand.

A create's body is a `@source` view of the columns a caller may set. The
loader refuses, in it and in an update's body:

| A field that is | Because |
| --- | --- |
| the key of a table that generates its own; in an update, any key | the table generates it; it names the row and never changes |
| an audit field: `createdAt`, `createdBy`, `updatedAt`, `updatedBy`, `deletedAt`, `deletedBy` | the repository stamps it |
| internal metadata, `_version` | no write sets it |
| a field a behavior owns | only the behavior's operations change it. A create's body may hold a `Workflow` field: [the state a row starts in](#the-state-a-row-starts-in) |
| the relation a path parameter sets, `teamId` under `teams/{teamId}/issues` | the path sets it |
| `@virtual` | no column holds it |

A create's body must also hold every column the table requires and gives
no default, or no request could create a row:

```
Issues.createIssue: its body CreateIssueInput leaves out title, which Issue requires and gives no default: no request could create a row; add it to the view, or name it in the path
```

A member of a create's body that the request leaves out, or sends as
null, is left unset, so its column takes the table's default, or null.

### The state a row starts in

A table's `Workflow` field starts every row in its initial state, and
only the Workflow's `transition` moves it. A create's body may hold the
field all the same, as the state the row starts in:

```ts
// What a caller sets to place an order: its title and, when it is not a
// draft, the state it starts in.
@source(Order)
export abstract class PlaceOrderInput {
  title: string;
  status: Nullable<string>;
}

@rest(HttpMethod.POST, "orders")
@tableOperation()
placeOrder(input: PlaceOrderInput): OrderView {
  throw new Error("schema declaration only");
}
```

The handler creates the row in the initial state and then makes the
Workflow's own transition to the state the body names, in the create's
transaction and as its caller. So the move is held to everything a
caller's transition is: it needs a transition from the initial state to
that state, the transition's permission and its `by`, and every behavior
that hears a move hears this one. A move the Workflow refuses is its
refusal, the 409 `vetoed` a `transition` answers, and no row is kept. A
body that leaves the member out, sends null, or names the initial state
makes no move.

It is one move. A state the initial one does not lead to in one
transition is refused: list a transition to it, or create the row and
move it. An update's body may not hold the field: a row that exists
changes state through the Workflow's operations
([A table's behavior operations](#a-tables-behavior-operations)), and the
loader says so. The OpenAPI document leaves the member writable in the
create's body, where every other view of the field is `readOnly`.

The TypeScript server serves it. A Go server leaves such a create to the
implementation, with the build's warning.

### An update's members

An update's members are all optional, `Nullable` each, and the loader
refuses a required one. The request's own JSON says what to write:

| The request | The column |
| --- | --- |
| leaves the member out | stays as it is |
| sends the member as null, and the column may be null | is set to null |
| sends the member as null, and the column may not be null | is not written: a 400 at that member |
| sets no member at all, `{}` | nothing is written, and neither `updatedAt` nor `updatedBy` moves; the answer is the row |

A delete is the repository's: a soft delete of a table with `deletedAt`
and `deletedBy`, stamped with the caller, and a hard delete of any other.
It answers the view of the row as it was before. A read, a list, an
update and a delete leave soft-deleted rows out, so each answers 404 for
one.

### The list

A generated list is `@paginated`, or the load fails: it reads a page
through the repository's `findPage`, never the whole table
([Pages](#pages)). It takes three kinds of argument beside its path's
parents:

- a `SortBy`, whose fields are columns the repository pages by, one that
  may be null among them, its nulls last in either direction. Without
  one, the list reads in the repository's own order, by key;
- a `SearchQuery`, which needs a `@searchField` on the table, and keeps
  the rows whose search fields hold each word of the text
  ([References and search](/superschematic/reference/references-and-search/#searchquery-a-lists-search-text));
- a `FilterBy`, which the handler turns into the repository's filter
  member for member, `ne` and `notIn` among them, `contains` as its
  case-insensitive `LIKE` of the text with `\`, `%` and `_` escaped
  ([Filters](#filters)).

A `QueryParam` on a generated list fails the load, since nothing says
what it compares: filter by the field with `FilterBy`, or write the list
by hand. The page's cursor is the repository's page key, and a cursor
that names no row of its order is the 400 of a cursor the operation never
returned.

### The transaction and the caller

Every handler runs in one transaction of the database's repositories, as
the request's caller. So `createdBy`, `updatedBy` and `deletedBy` are
stamped, an `Encrypted<T>` column is sealed and opened, and a table that
composes behaviors is written through the behaviors' core, where a rule's
refusal is the 409 `vetoed` a behavior operation answers
([A table's behavior operations](#a-tables-behavior-operations)). The
outbox, `@enqueueOnChange` and Reactions see the write as they see any
other. The handler has no hook before or after it: work that follows a
write belongs to Reactions and the change queue, and anything else is a
reason to take the decorator off.

### Refusals

The body is decoded and checked against its input type before the handler
runs, as any body is. The handler's own refusals are the ones a
hand-written operation answers, mapped once the transaction has rolled
back, and none carries a statement's or the driver's words:

| The request | Status and code |
| --- | --- |
| a key that holds no live row under the path's parents, or a parent the path names that does not exist | 404 `not_found` |
| a write that breaks a unique key | 409 `conflict` |
| a delete of a row another table's row still references | 409 `conflict` |
| a create or an update whose relation's key names no row | 400 `bad_request`, at the body's member |
| an update that sends null for a column that may not be null | 400 `bad_request`, at the body's member |
| a write that stamps its caller, on a route that admitted none | 401 `unauthorized` |

### Guards

A route's guards are the method's, as on any operation: `@auth`,
`@requirePermission`, `@publicRoute`, `@requireService`, `@allowService`,
`@rateLimit`, `@bodyLimit` and `@timeout`
([Auth and permissions](/superschematic/guides/auth-and-permissions/)).
A caller the route admits reaches every live row the path holds, unless
the operation names a [row rule](#row-rules). `@requireOwnership` fails
the load on a `@tableOperation`, since no implementation of yours runs to
check what the caller owns: a row rule says it instead. So does
`@manualRouteRegistration`, which hands the route to a handler of yours.

Different callers get different views through different operations. A
table may have any number of `@tableOperation` methods, in any sets, each
with its own views and guards:

```ts
// An issue as anyone sees it: fewer of the same columns.
@source(Issue)
export abstract class IssueGuestView {
  id: Identity.UUID;
  title: string;
  status: IssueStatus;
}

@rest(HttpMethod.GET, "public/issues/{id}")
@publicRoute
@tableOperation()
getIssueForGuest(id: Identity.UUID): IssueGuestView {
  throw new Error("schema declaration only");
}
```

Several views of one table do not confuse a relation's key: it refers to
the one of them an operation lists
([What a value refers to](/superschematic/reference/references-and-search/#what-a-value-refers-to)).

### Row rules

A permission says who may call a route. A row rule says which rows that
caller reaches. `@tableOperation({ by: [...] })` lists the row's members
that name who the row is for, and the operation then reaches only the
rows one of them holds the caller in:

```ts
export class Notes extends Authenticated {
  // The caller's notes, their own and the ones shared with them.
  @rest(HttpMethod.GET, "notes")
  @paginated({ defaultSort: "createdAt" })
  @tableOperation({ by: ["owner", "sharedWith"], overridePermission: "notes.admin" })
  listNotes(sort: SortBy<NoteView, ["createdAt"]>, filter: FilterBy<NoteView, ["issueId", "owner"]>): NoteView[] {
    throw new Error("schema declaration only");
  }

  // A new note on the issue the path names, the caller's own.
  @rest(HttpMethod.POST, "issues/{issueId}/notes")
  @tableOperation({ by: ["owner"] })
  createNote(issueId: Identity.UUID, input: CreateNoteInput): NoteView {
    throw new Error("schema declaration only");
  }

  // Changes a note of the caller's own.
  @rest(HttpMethod.PATCH, "notes/{id}")
  @tableOperation({ by: ["owner"] })
  updateNote(id: Identity.UUID, input: UpdateNoteInput): NoteView {
    throw new Error("schema declaration only");
  }

  // Deletes a note the caller wrote, or any note for an admin.
  @rest(HttpMethod.DELETE, "notes/{id}")
  @tableOperation({ by: ["createdBy"], overridePermission: "notes.admin" })
  deleteNote(id: Identity.UUID): NoteView {
    throw new Error("schema declaration only");
  }
}
```

| Kind | With a rule |
| --- | --- |
| read, update, delete | the live row under the path's key and parents that also names the caller; a row that names someone else is the 404 of a row that is not there, and nothing is written |
| list | the rows that name the caller, beside the path's parents and whatever the request's filter says: `filter[owner]=<someone else>` finds only what the rule already reaches |
| create | each member the rule names is set to the caller, and the body's view may not hold one; `createdBy` is the repository's stamp as on any create |

A member of `by` is named as a view names it: a field of the table that
holds an id (`Identity.UUID`, `Identity.UserID`), a to-one relation's
key (`assigneeId`), text, or `createdBy`. The caller is the request's
principal, by its subject: a user's id. A row is reached when any one
member holds it, so `["owner", "sharedWith"]` is "mine or shared with
me". An operation carries its own rule, so a table's read may reach the
rows shared with the caller while its update reaches only the owner's.

`overridePermission` names one permission whose holder the rule does not
hold back: they reach every row, as an operation without a rule does. A
grant covers it as it covers a route's permission (`notes` covers
`notes.admin`), and the permission catalog lists it under the operation.
Without it the rule holds for every caller.

The loader holds the rule to the table. It fails the load for a rule on a
route that admits a request with no caller (`@publicRoute`, or no guard
at all), for a member the table does not have, for one that holds no
subject (a number, a time, `updatedBy`, a secret, a field a behavior
owns), for a rule over a projection, for an `overridePermission` with no
`by`, and for a create whose rule names the table's key or a relation its
path sets.

What a rule does not say yet:

- A caller named through another table: "the rows of a team I am a
  member of". Give the row the member itself, or write the operation by
  hand.
- A behavior's seat (`Seats`): the same.
- A caller that is a service, or any principal whose subject is no id.
  It is named by no member that holds an id, so it lists nothing, reads
  a 404 and cannot create; give it the override permission.
- On a Go server, a member that holds text. The Go handlers compare the
  caller with an id; the operation stays one you implement, with a
  warning. The TypeScript server serves it.

A row rule is the generated handler's. An operation you write by hand,
an ORM call in a worker and SQL of your own reach every row, as before.

### Docs and tools

A table operation says what it does in its declaration, so it documents
itself. One that declares no `@docs` is given them, and one that declares
no `@mcp` is a tool, as an operation of a `@behaviorOperations` set is:

| | From | `listIssues` in `Issues` |
| --- | --- | --- |
| title | the method's name, as words | `List issues` |
| description | the method's comment; without one, a sentence of its kind and its table | `A team's issues, newest first unless the caller sorts them, searched by their text and filtered by their fields.` |
| capability | the set and the method | `issues.list-issues` |
| lifecycle, visibility | | `active`, `public` |
| replay mode | a read and a list | `read_only` |
| tool handle | the method's name in snake_case | `list_issues` |
| invocation policy | the policy's default | `auto` |

So a table's five operations are five `@rest` lines, their guards and
their views. Write the comment for the person and the agent who will read
it: it is the OpenAPI description and the tool's.

What the operation declares is kept. `@docs` replaces the docs, `@mcp`
the tool, and each is given when only the other is written:

```ts
// Deletes the issue, which is kept, and answers it as it was.
@rest(HttpMethod.DELETE, "issues/{id}")
@requirePermission(["issues.write"])
@mcp({ handle: "delete_issue", invocationPolicy: "ask" })
@tableOperation()
deleteIssue(id: Identity.UUID): IssueView {
  throw new Error("schema declaration only");
}
```

`@mcp({ hidden: true, reason: "..." })` keeps an operation out of the
tools. An operation only a calling service reaches (`@requireService`) is
hidden without being asked, and so is one whose payload is encrypted.

An API's tools are told apart by their handles and their names. When two
sets each declare a method of one name, `list` say, or a default would
repeat a handle or a title another operation declares, the defaults take
the set's before them: `teams_list` and `members_list`, "Teams: list" and
"Members: list".

An operation you implement by hand is given neither: take `@tableOperation`
off and its `@docs` and `@mcp` are yours to write.

### The servers

The TypeScript and Go servers write the handlers. A TypeScript router
runs them through the database's repositories, which it takes as
`RouterOptions.orm`, `createOrm(pool)` from the database's types package
(`Deps.orm`); `buildRouter` throws without them
([TypeScript](/superschematic/install/typescript/#serve-a-generated-api)).

A Go server runs them through the Go ORM, in `tables.go` of the API's
package: one typed function per view and one per operation, mounted with
the database the routes take as `Config.DB`. It serves a view whose
fields each hold one value, a scalar, text, a number, a boolean or an
enum, of a table. A read or a list of a projection, and a view that
holds a list, a map, a JSON value or an embedded object, it leaves to
the implementation: the method stays in the namespace's interface and
its scaffold, and the build warns of each, with why:

```
warning: tracker-api: the Go server writes no handler for Issues.getIssue, a @tableOperation (D106): its view IssueView holds labels, string[], and the Go server writes handlers for a view of single values so far, each a scalar, text, a number, a boolean or an enum; it stays a method of the implementation's interface, to be written by hand, with the same route and types
```

The API's other table operations are still served. A Go type holds an
optional number or text without a pointer, so a Go response leaves such
a member out when its column is null, zero or empty, as every Go route's
does, and a create reads a zero or an empty optional member as unset. An
update reads the request's own JSON, so `"estimate": 0` writes 0 and
`"estimate": null` clears it.

A Rust server writes no handler yet. It keeps each method in the
namespace's trait and its scaffold, to be written by hand, and the build
warns once per API, naming every such operation, so a project that
builds the API in two languages still builds:

```
warning: tracker-api: the Rust server writes no handler for a @tableOperation yet (D106): Issues.listIssues, Issues.getIssue, Issues.createIssue, Issues.updateIssue, Issues.deleteIssue stay methods of the implementation's interface, to be written by hand, with the same route and types
```

A TypeScript server answers a `Temporal.DateTime` to the millisecond,
`2026-03-01T09:30:00.123Z`, while its column holds microseconds. So an
equality filter on a time a response gave, `filter[createdAt]=…`, may
miss the row it came from. A range finds it:
`filter[createdAt][gte]=…` with `filter[createdAt][lt]=…` a millisecond
later.

`shop-cart`, a TypeScript API over `shop-db`, serves its catalog this
way: a list anyone may read, paged, sorted, searched and filtered, one
product, and an update for staff. Its implementation has no method for
any of the three:

### What is not built yet

Each of these has something that stands in until it is:

| Not built | Until then |
| --- | --- |
| a row rule that names the caller through another table (a team's members) or a behavior's seat | a [row rule](#row-rules) names members of the row itself; an operation that needs more is written by hand |

| the Go server's handlers over a projection, over a view that holds a list, a map, a JSON value or an embedded object, for a row rule that names text, and for a create that names the state its row starts in | a Go API implements those operations by hand; the TypeScript server serves them |

## A table's behavior operations

A DB table may type a field as a behavior, `status: Workflow<{ ... }>`, or
implement a behavior of the whole table, `implements Timers<Ticket, { ...
}>` ([A table's deadlines](#a-tables-deadlines-timers-and-its-worker)),
`implements Reactions<Project, { ... }>` ([A table's
reactions](#a-tables-reactions-and-its-change-queue)), `implements
Approvals<Task, { ... }>` ([A table's sign-offs](#a-tables-sign-offs-approvals))
or `implements Lease<Job, { ... }>` and the work-queue behaviors beside it
([A table's leases, retries, presence and budgets](#a-tables-leases-retries-presence-and-budgets))
(D103). The table
stays a table: the behavior's fields are its columns (`status`,
`status_entered_at`), the generated repositories read them and leave them
out of their create, update and upsert inputs, and only the behavior's
operations change them.

```ts
// shop-db
export abstract class Order {
  @key
  id: AutoGenerate<Identity.UUID>;
  title: string;
  status: Workflow<{
    states: ["draft", "paid", "shipped"];
    initial: "draft";
    transitions: [{ from: "draft"; to: "paid" }, { from: "paid"; to: "shipped"; permission: "orders.ship" }];
  }>;
}
```

An API serves those operations with no code of yours: a class with no
members, marked `@behaviorOperations` with the table, which it imports from
its database, its `authDb` or its one DB dependency.

```ts
// shop-orders
import { behaviorOperations, requirePermission } from "@superschematic/api";
import { Order } from "@acme/shop-db";

@behaviorOperations(Order)
@requirePermission(["orders.write"])
export abstract class OrderActions {}
```

The build adds to the set one operation for each operation of each
behavior the table composes, those it implements first and then those on
its fields, in field order:

| | `Order`'s `status`, `transition` |
| --- | --- |
| Route | `POST /api/order/{id}/status/transition`: the row's key in the path, the operation's parameters as the body, `{ "to": "paid" }` |
| Types | `OrderStatusTransitionInput` (`to`, and an optional `from`) and `OrderStatusTransitionResult` (`from`, `to`, and an optional `unchanged`), typed by the enum of the config's states, `OrderStatusState` |
| SDK | `sdk.order.status.transition(id, { to: OrderStatusState.Paid })` ([Client SDKs](/superschematic/guides/client-sdks/#a-tables-behavior-operations)) |
| MCP tool | `order_status_transition`, with the behavior's invocation policy ([MCP tools](/superschematic/reference/mcp-tools/#a-tables-behavior-operations)) |
| Handler | generated: it runs the operation through the database's repositories and the behaviors' core, in one transaction |

The route and the tool follow the table, the field and the operation, in
kebab and snake case (`shipment/{id}/payment-status/transition`,
`shipment_payment_status_transition`); a behavior the table implements
takes the field's place with its name (`ticket/{id}/timers/fire-timer`,
`ticket_timers_fire_timer`). The SDK methods sit in the set's namespace,
as every set's do ([Operation sets](#operation-sets)), under a member
named for the field, or for the behavior the table implements (`timers`):
name the set `<Table>Actions` to put them under the table's name. The
OpenAPI document, the permission catalog and the tool documents list the
operations as any other, and the document
marks the fields a behavior owns `readOnly`, in the table's own component
and in a `@source` view's that projects one, but for the body of a create
that names [the state its row starts in](#the-state-a-row-starts-in).

The class's decorators guard every route it serves, as a method's guard
its route: `@auth`, `@requirePermission([...])` and `@publicRoute`, which
go on a class only here, `@requireService` and `@allowService`, and
`@rateLimit`, `@bodyLimit` and `@timeout`. `@requireOwnership` does not
go on it, since no implementation of yours runs to check what the caller
owns. A permission the behavior's config names, `orders.ship` on the move
to `shipped`, is the core's to check, against the permissions the caller
holds: a caller with `orders.write` alone moves an order to `paid`, and is
refused the move to `shipped` with a 403 whose detail is the core's. The
core matches by the default rule, a held permission covering itself and
those nested under it (`orders` covers `orders.ship`), and not by a matcher
your server gives its routes (`permissionMatcher`, `identity.WithMatcher`):
a caller such a matcher admits by another rule is refused there. A calling
service with no end user holds no permission there. The permission catalog
lists `orders.ship` under the operation, and `@seedRoles`' coverage counts
it.

A stack's Go server authenticates a caller only for an API that is
`public` or whose `authDb` holds the user model (see
[Auth and permissions](/superschematic/guides/auth-and-permissions/)), so
one whose set needs a caller (`@auth`, `@requirePermission`) is refused
for any other API: the handlers are generated, and would run for anyone.
A Go server you write mounts `RegisterRoutes` behind a middleware of your
own that puts the caller on the request. A set that only services call
(`@requireService`) publishes no tool: its operations' `@mcp` is hidden,
since no end user's agent can call them (D37).

A refusal of the core is the problem every route answers
([Errors](#errors)), with its `code` and, where it has them, `details`:

| Status | `code` | When |
| --- | --- | --- |
| 403 | `forbidden` | the caller lacks a permission the config names: `sam may not move Order <id>'s status from paid to shipped: the transition needs permission orders.ship` |
| 404 | `not_found` | no row holds the key: `Order <id> does not exist` |
| 409 | `vetoed` | the behavior refuses the change, a move no transition leads to, say; `details.vetoCode` names the rule (`transition_not_allowed`; `not_principal` and `stale`, [below](#who-may-move-a-row-and-a-move-that-changes-nothing)) |
| 409 | `conflict` | a row the operation would write collides with one that exists |
| 422 | `invalid_instance` | the behavior's validation refuses the fields the operation would store |
| 503 | `busy` | the row kept changing while the operation ran again, and it gave up; try again |

A malformed key or body is the 400 any route answers, before the core
runs, and any other failure is the server's own 500.

Each server takes the database's repositories and has no method for the
operations in its implementation, nor a scaffold of one; a namespace
whose every operation is a behavior's has no implementation at all:

| Server | What it takes |
| --- | --- |
| Go | `Config.DB`, the ORM of the database, which `Validate` requires |
| TypeScript | `RouterOptions.orm`, the database's `orm.ts` repositories over Postgres, which `buildRouter` requires |
| Rust | the database's pool, the last argument of `Implementations::new`; the handlers call `superschematic-rules-adapter` on it |

An operation a behavior runs on the table as a whole (Pool's `pick`,
Lease's `expireHolder`) is routed at `POST <table>/<member>/<operation>`,
with no key, and runs as a command without a row: Go's handler through
the ORM's method of no key, TypeScript's through the repository's, and
Rust's through the generated `behaviors::run_table_operation`, which calls
the adapter's `postgres::run_table_operation`
([An operation of the table as a whole](#an-operation-of-the-table-as-a-whole)).

A stack's server passes each. The behaviors' core comes with them: the Go
module links the rules module's archive (`[paths] rules_go` in a
checkout), the TypeScript package depends on `@superschematic/rules`, and
the Rust crate depends on `superschematic-rules-adapter` and
`superschematic-rules-behaviors`, which are unpublished, so a Rust server
with behavior operations builds only in a checkout that sets `[paths]
rules_adapter_rust` and `rules_behaviors_rust`
([Naming](/superschematic/reference/naming/#pathsrules_adapter_rust)). The
TypeScript repositories run on Postgres alone, so a database that lists
`sqlite` first has no behavior operations on a TypeScript server yet.

A raw SQL write of an owned column is never refused, so an operator can
repair a row, but it skips the behavior's rules: move a state through its
operation.

### Who may move a row, and a move that changes nothing

A Workflow field's transition may name who makes it (`by`), its config the
permission that moves a caller past that (`overridePermission`), and a
move to the state the row is in may answer as no change (`repeat:
"unchanged"`) (D104,
[Who may move a Workflow field's row](/superschematic/guides/database-tables/#who-may-move-a-workflow-fields-row)).
The route serves them as it serves the rest, the core answering from the
row itself, so an `@auth` set admits any signed-in caller and the row
decides who moves it:

```ts
// questions-api
@behaviorOperations(Question)
@auth
export abstract class QuestionActions {}
```

| Call | Answer |
| --- | --- |
| the subject `askedOf` holds, `{ "to": "answered" }` | 200 `{ "from": "open", "to": "answered" }` |
| another caller, the same body | 409 `vetoed`, `details.vetoCode` `not_principal`, `details.vetoDetails` `{ "from": "open", "to": "answered", "by": ["askedOf"] }`: `behavior Workflow vetoes transition of Question <id>: <subject> may not move Question <id>'s status from open to answered: the transition is made by the subject askedOf holds` |
| a caller holding `questions.moderate`, the same body | 200, as the subject's |
| the same move again, with `repeat: "unchanged"` | 200 `{ "from": "answered", "to": "answered", "unchanged": true }`, nothing written: the row's `_version` and `status_entered_at` stay |
| the same move again, without `repeat` | 409 `vetoed`, `already_in_state` |
| `{ "to": "answered", "from": "answered" }` on an open row | 409 `vetoed`, `stale`, `details.vetoDetails` `{ "from": "answered", "status": "open" }` |
| `{ "to": "answered", "from": "open" }` | 200 when the row is open; once that move is made, the same call again is `stale` with `status` `answered`: the retry landed |

`from` is checked first, before `repeat`, `by` and the permission, and a
repeat checks no `by` or permission, so both answer any caller the route
admits, as a read of the row would. An SDK leaves an unset `from` out of
the body, and every server reads `"from": null` (which the OpenAPI
document and the MCP tools allow, as for any optional member) as no
`from`. The permission catalog lists `overridePermission` under each of
the field's operations, beside the transitions' permissions.

`by` is only as strong as its field: a caller who may write `askedOf` may
set it to itself and then make the move. The build warns when an API, one
that serves the table's behavior operations or any other, has an operation
that updates a row of the table (a `PUT` or a `PATCH`, or another method
but `GET` that takes the table's key, as `questions/{id}/...` does) and
takes a `@source` view of the table carrying a field a `by` names, naming
the API, the operation, the field, the moves and the fix:

```
questions-api: QuestionAdmin.reassignQuestion takes Question.askedOf (QuestionAssignment is @source(Question)), and the Workflow on Question.status names askedOf in by for open to answered and answered to closed: a caller who may call reassignQuestion can set askedOf to itself and then make that move. Keep askedOf out of the operation's input, or freeze it: list it in the fields of Question's Constants (D104)
```

A field the table's Constants lists in `fields` is not warned of, since
no update changes it
([Fields a table keeps, freezes and signs off](/superschematic/guides/database-tables/#fields-a-table-keeps-freezes-and-signs-off)).
A field a StateRules state's `by` names is warned of the same way, since
a caller who sets it to itself may then change what the state freezes:

```
tasks-api: TaskAdmin.reassignTask takes Task.reviewer (TaskAssignment is @source(Task)), and Task's StateRules names reviewer in by for working: a caller who may call reassignTask can set reviewer to itself and then change the fields working freezes. Keep reviewer out of the operation's input, or freeze it: list it in the fields of Task's Constants (D104)
```

It is a warning, not a refusal, and it sees only that: an input of a
plain type, code that calls the repository's update, and an API written in
a data format (JSON or YAML) that reads no database, since it serves no
behavior operations and runs no behavior worker, are yours to keep the
field out of. A create, which takes no key, is not warned of: whoever
creates the row names whom its fields hold. `createdBy`, which the
repositories stamp, is never warned of.

`overridePermission` is matched as any permission is, a held permission
covering itself and each one nested under it, so `questions` overrides
`by` where `questions.moderate` is the override. The build warns when
every permission a set of the table's behavior operations requires covers
the override, since every caller its routes admit then passes `by`:

```
QuestionActions: every caller its routes admit holds questions, which covers questions.moderate, the overridePermission of the Workflow on Question.status, so each moves its rows past every transition's by, which names no one for them; require a permission that does not cover questions.moderate, or name another overridePermission (D104)
```

### A table's sign-offs: Approvals

A table that implements Approvals
([Fields a table keeps, freezes and signs off](/superschematic/guides/database-tables/#fields-a-table-keeps-freezes-and-signs-off))
has three operations, which a `@behaviorOperations` set serves beside its
Workflow field's `transition`; Constants and StateRules add none, and hold
the table's updates and moves instead:

```ts
// tasks-api
@behaviorOperations(Task)
@auth
export abstract class TaskActions {}
```

| Route | Body | Answer |
| --- | --- | --- |
| `POST /api/task/{id}/approvals/sign-off` | `{ "state": "done", "note"?: "...", "version"?: 7 }` | `{ state, subject, note?, at, signedBy, count }`, the gate's subjects that count after it |
| `POST /api/task/{id}/approvals/withdraw-sign-off` | `{ "state": "done" }` | the sign-off taken back, `{ state, subject, note?, at }` |
| `POST /api/task/{id}/approvals/list-sign-offs` | `{ "state"?: "done", "limit"?: 50, "cursor"?: "..." }` | `{ items: [{ state, subject, note?, at, consumedAt? }], next }`, oldest first, the consumed ones included; it writes nothing |

The types are `TaskApprovalsSignOffInput`, whose `state` is
`TaskApprovalsGate`, the enum of the config's gated states, and the rest
of `TaskApprovals*`; the SDK method is `sdk.task.approvals.signOff(id, {
state: "done", version })` and the MCP tool `task_approvals_sign_off`. The
core checks a `signOff`'s caller against the gate's `permission` (403
`forbidden` without it), so an `@auth` set admits any signed-in caller and
the config decides who signs. A sign-off is a
write: it moves the row's `_version`. The permission catalog lists each
gate's permission under the three operations, and Constants' and
StateRules' `permission` under each operation that updates a row of the
table through a `@source` view of it, which the core checks on that
update.

| Call | Answer |
| --- | --- |
| a transition into a gated state with fewer sign-offs than its `count` | 409 `vetoed`, `approvals_missing`, `details.vetoDetails` `{ "state": "proving", "required": 1, "count": 0 }` |
| `signOff` on a `pinned` gate without `version` | 400 `invalid_argument`: `operation signOff of behavior Approvals: /version: is required: the gate on done is pinned, so a sign-off names the row's version its signer read` |
| `signOff` whose `version` is not the row's, on any gate | 409 `vetoed`, `stale`, `details.vetoDetails` `{ "version": 6, "current": 7 }`: `behavior Approvals vetoes signOff of Task <id>: Task <id> is at version 7, not 6` |
| `signOff` with the row's `version` | 200 |
| `signOff` of a state the config does not gate, of the state the row is in, by its creator on a gate that excludes the creator, a second time, or `withdrawSignOff` with no sign-off to take back | 409 `vetoed`: `no_gate`, `in_state`, `creator_cannot_sign`, `already_signed`, `not_signed` |

`version` is checked after the parameters (a malformed `version`, or none
on a pinned gate, is 400 first) and only for a state the config gates (a
`version` on another state is `no_gate`), then before every guard and the
gate's permission, as Workflow's `from` is, so a stale read is answered to
any caller the route admits. The API's types of `Task` carry no
`_version`: read it from a repository's row, or from the `stale` veto's
`current`. The
updates Constants and StateRules refuse answer through the route that
makes them, as any refusal of the core: 409 `vetoed` with `one_way`,
`required_fields` or `frozen_fields`, and 422 `invalid_instance` for a
constant. An authored route's update reaches the core as its caller's
subject alone, holding no permissions, so Constants' and StateRules'
`permission` passes only for an update that names its caller
(`orm.withBehaviorCaller({ subject, permissions })`, Go's
`WithBehaviorCaller`).

## A table's deadlines: Timers and its worker

A table implements `Timers` to hold its rows to named deadlines: a first
answer due four hours after a ticket opens, an invoice overdue after
thirty days, a reminder a day before a visit (D103). The first type
argument is the table itself, the second its config, a type literal or
`typeof` a constant declared `as const`; `Timers` comes from
`@superschematic/db` and, like `User`, adds no members to the class.

```ts
// support-db
import { Identity, Temporal } from "superscalar";
import { AutoGenerate, Timers, Workflow, key } from "@superschematic/db";

export abstract class Ticket implements Timers<Ticket, {
  deadlines: {
    respond: { start: { create: true }; afterMs: 14400000; then: { transition: "escalated" }; until: { leaves: "open" } };
    idle: { start: { enters: "waiting" }; afterMs: 86400000; then: { transition: "closed" } };
    remind: { start: { field: "visitAt" }; afterMs: -86400000 };
  };
  permission: "tickets.timers";
}> {
  @key
  id: AutoGenerate<Identity.UUID>;
  title: string;
  visitAt?: Temporal.DateTime;
  status: Workflow<{
    states: ["open", "waiting", "escalated", "closed"];
    transitions: [
      { from: "open"; to: "waiting" },
      { from: "waiting"; to: "open" },
      { from: "open"; to: "escalated" },
      { from: "open"; to: "closed" },
      { from: "waiting"; to: "closed" },
      { from: "escalated"; to: "closed" }
    ];
  }>;
}
```

Each deadline starts from the row's create (`{ create: true }`), from the
time its status enters a state (`{ enters: "waiting" }`, again at each
entry) or from a date-time field (`{ field: "visitAt" }`, again whenever
the field moves; a field left empty starts nothing), and falls due
`afterMs` milliseconds after it, or before it when negative. When it falls
due it fires, once, and its `then` moves the status to the state its
`transition` names while the status is still in the state the deadline
started in (`from` names others): the outcome is `moved`, or `skipped` for
a row that moved on, and a guard's veto of the move or a permission the
caller lacks records `vetoed` or `forbidden`, the deadline fired all the
same. `until` cancels it while it is pending, when the status leaves a
state (`{ leaves: "open" }`) or enters one of a list (`{ enters: ["closed"]
}`). `enters`, `then` and `until` read a `Workflow`
field: the table's one, or, when it has several, the one `status` names
(`status: "payment"`). `permission` is the permission a caller needs to
reset or snooze a deadline; with none, nobody may. The build holds each
deadline to the table as the core does, in the core's words: the Workflow
and a field start's field are there, and the field holds date-times; an
`enters` state, a `then`'s transition and `from` states and an `until`'s
states are states of the Workflow, with a transition from each `from`
state to the `then`'s; a deadline that starts at a field names its
`then`'s `from` and takes no `until.leaves`, since it is in no state of
its own; and only a field start takes a negative `afterMs`.

The build adds, beside the table:

| | For `Ticket` |
| --- | --- |
| A sub-table | `ticket_timers_deadlines` (`TicketTimersDeadlines`), one row per deadline started on a ticket: `base_at` (what it starts from), `armed_from`, `due_at` (empty once cancelled), `fired`, `fired_at` and `outcome` (`moved`, `skipped`, `vetoed` or `forbidden`), with a foreign key to the ticket, deleted with it |
| A deadline queue | `ticket_deadline_queue` (`TicketDeadline`), one waiting message per ticket and deadline, due when the deadline falls due |
| A change queue | `ticket_change_queue` (`TicketChange`), one message per insert, update and delete of a ticket, whoever makes it, which a trigger on `ticket` writes ([The change queue](#the-change-queue)) |
| Operations | `timers.fireTimer`, `timers.resetTimer` and `timers.snoozeTimer`, which a `@behaviorOperations` set serves as it serves a field's |
| A column | `_version`, the version every write through the behaviors' core holds the row to |

Migrations plan the tables and the trigger as any other. The repositories
have no table or write path of their own for the sub-table: SQL, reports
and projections may read it. A table whose behaviors keep sub-tables or arm deadlines has
no upserts in its repositories, since an upsert applies none of a
behavior's rules.

A create, an update and a delete through the repositories, and each
behavior operation, arm and clear the row's deadlines in the same
transaction: a ticket's create arms `respond`, a move to `waiting` cancels
it by its `until` and arms `idle`, and a delete removes every message of
the row. Every other write is heard after it commits, through the table's
change queue: a raw SQL write (`UPDATE ticket SET visit_at = ...`, `DELETE
FROM ticket ...`, from a script or psql) and the repositories' bulk and
hard writes, which bypass the core (TypeScript's `updateMany`, `deleteMany`
and `hardDeleteOne`, Go's `UpdateMany`, `DeleteMany` and `HardDeleteOne`).
When the worker runs the write's change, Timers reconciles the row: a
`visitAt` an `updateMany` moved re-arms `remind` at its new time, a raw
insert arms `respond` from the insert's time, and a raw delete removes the
row's deadline messages. Until the worker runs it, the old arming stands;
a deadline that falls due first reconciles its row before it fires, so it
is armed again at its new time rather than fired on its old arming. A write
through the core is heard too, and changes nothing more: its deadlines are
already as it left them.

### The worker

An API runs a table's deadlines and its change queue with a class with no
members, marked `@behaviorWorker` with the table, imported from its
database as `@behaviorOperations` imports it:

```ts
// support-api
import { behaviorOperations, behaviorWorker, requirePermission } from "@superschematic/api";
import { Ticket } from "@acme/support-db";

@behaviorOperations(Ticket)
@requirePermission(["tickets.write"])
export abstract class TicketActions {}

@behaviorWorker(Ticket, { concurrency: 2 })
export abstract class TicketTimers {}
```

The class is a worker of the API, as a `@worker` class is
([Queues and workers](/superschematic/guides/queues/#write-a-worker)): a
deployable of kind worker named after the API and the class,
`support-api-ticket-timers`, with a worker's settings, `stack dev`
process, image and gcp worker pool. Its handlers of deadlines and changes
are generated, so your implementation has no method for them: it claims
each message of the table's deadline queue as it falls due, and each
message of its change queue, and runs it through the behaviors' core in one
transaction with the message's completion, one claim loop per queue, the
deadlines first. A table whose behaviors emit events (Schedules' runs, Pool's rechecks)
also has an event queue, its third, whose messages the worker hands to a
method of the API's `Workers` that you write
([A behavior worker's event handlers](/superschematic/guides/queues/#a-behavior-workers-event-handlers));
a table that emits none gives `Workers` no method. It runs as the worker, the subject
`support-api/TicketTimers`, not as a user, holding the permissions the
decorator gives it:

| Option | Default | What it does |
| --- | --- | --- |
| `concurrency` | 1 | how many messages of each of the table's behavior queues an instance handles at a time; an environment's settings change it |
| `grace` | `"8s"` | how long a stopping worker lets its running handlers finish before it gives their messages back |
| `permissions` | none | the permissions the worker's commands hold: a `then` whose transition names a permission the worker lacks still fires, and records `forbidden` |

A deadline re-armed or cancelled while the worker holds its message never
fires on its old arming: the worker finds its claim gone, runs nothing and
logs `deadline ran nothing` with why, `claim lost`. A deadline the fired
command arms again, a status that re-enters `waiting`, survives the
message's completion. A fire that a guard of the table's behaviors vetoes
is released, not failed: the worker logs `deadline ran nothing` with why,
`vetoed`, and the message is due again a minute later, counting no
attempt, for as long as the guard holds it, its sub-table row pending all
the while. A fire that fails otherwise (`busy`, a failure of the database)
fails the message: it is due again after the queue's backoff (30 seconds,
doubling to an hour) and dead after its sixth attempt, for `stack queue
dead|retry|drop <env> support-db.TicketDeadline`. Nothing arms a dead
deadline again: its sub-table row stays pending, unfired, until you retry
the message, a caller with the config's `permission` resets or snoozes it,
or what it starts from moves. A newer arming or a cancel of the same deadline deletes
its dead message, so a retry of every dead message never meets a waiting
one of the same deadline.

One class runs a table's queues per API, and the build refuses one over a
table whose behaviors arm no deadlines, hear no writes and emit no events,
which has nothing to run. Nothing refuses a table whose queues no worker runs: its
deadlines fall due and its changes wait for one, and nothing that hears
them runs until a worker does. An API that serves
`@behaviorOperations(Ticket)` and declares no `@behaviorWorker(Ticket)`
gets a warning; declare one on that API or on another over the same
database. The worker claims on Postgres, as every worker does. A
TypeScript one over a database that lists `sqlite` first is refused, as
the TypeScript repositories run behaviors on Postgres alone, and so is
one an environment places on Cloudflare Workers. A Rust one builds in a
checkout that sets `[paths] rules_adapter_rust` and `rules_behaviors_rust`,
as a Rust server with behavior operations does.

### Its operations

| | `Ticket`'s Timers, `fireTimer` |
| --- | --- |
| Route | `POST /api/ticket/{id}/timers/fire-timer`, the body `{ "deadline": "respond" }` |
| Types | `TicketTimersFireTimerInput` (`deadline`, the enum `TicketTimersDeadline` of the config's deadlines) and `TicketTimersFireTimerResult` (`fired`, `outcome`) |
| SDK | `sdk.ticket.timers.fireTimer(id, { deadline: TicketTimersDeadline.Respond })` |
| MCP tool | `ticket_timers_fire_timer` |

`fireTimer` fires a due deadline now, before the worker does, and spends
its message; one not due, fired already or not started writes nothing and
answers `{ "fired": false }`. `resetTimer` starts a deadline again from
what it starts from and answers its new `dueAt`; `snoozeTimer` moves a
started one to the `dueAt` it is given, and one that fired fires again
then. Both are refused a deadline with no due time to give (`not_armed`),
and both need the
config's `permission` (`tickets.timers`), which the core checks after the
set's own guard: a caller with `tickets.write` alone is refused with a 403
`forbidden`. The permission catalog lists `tickets.timers` under each of
the three, `fireTimer` too, though `fireTimer` never checks it: a caller
needs it only to reset or snooze. A `dueAt` is epoch milliseconds, as the declaration has it,
not a date-time. No route, SDK method or tool reads a row's deadlines yet;
the operations' results and the sub-table are what there is.

## A table's reactions and its change queue

A table implements `Reactions` to move Workflow statuses when its rows, or
the rows that point at it, are written (D103): a project that becomes
active when a task starts, done once every task is done, failed once one
fails, a task that starts when it is marked urgent. Each rule is one `when`
and one `then`:

```ts
// projects-db
import { Identity } from "superscalar";
import { AutoGenerate, Reactions, Relation, Workflow, key } from "@superschematic/db";
import { projectFlow, taskFlow } from "./flows";

export abstract class Project implements Reactions<Project, {
  rules: [
    { when: { allTerminal: { schema: "Task"; link: "project"; outcomes: ["success"] } }; then: { transition: "done" } },
    { when: { anyTerminal: { schema: "Task"; link: "project"; outcomes: ["failure"] } }; then: { transition: "failed" } }
  ];
}> {
  @key
  id: AutoGenerate<Identity.UUID>;
  name: string;
  status: Workflow<typeof projectFlow>;
}

export abstract class Task implements Reactions<Task, {
  rules: [
    { when: { enters: "doing" }; then: { link: "project"; transition: "active" } },
    { when: { changes: { field: "priority"; to: "urgent" } }; then: { transition: "doing" } }
  ];
}> {
  @key
  id: AutoGenerate<Identity.UUID>;
  title: string;
  priority?: string;
  project: Relation<Project>;
  status: Workflow<typeof taskFlow>;
}
```

`projectFlow` and `taskFlow` are Workflow configs declared `as const`,
whose terminal states each name an `outcome` (`success`, `failure` or
`neutral`), which `allTerminal` and `anyTerminal` read.

| `when` | Fires when |
| --- | --- |
| `{ enters: "doing" }` | the write moved the row's status into the state: a create or insert that leaves it there, or an update that left it in another state (or in the same one entered again) |
| `{ changes: { field, to?, from? } }` | the write moved the field's value, to `to` and from `from` when given; an insert moves a field from empty, and a delete moves nothing. `field` names a field of the table: an own field, a to-one relation (`project`), or a field typed as a behavior (`status`), whose value it hears |
| `{ allTerminal: { schema, link, outcomes? } }` | a write of a row of `schema`, the table whose to-one relation `link` points at this one, left every such row pointing here in a terminal state, at least one, each with an outcome the list holds (any outcome without one) |
| `{ anyTerminal: { schema, link, outcomes } }` | a row of `schema` that points here through `link` entered a terminal state whose outcome the list holds, or was pointed here while in one |

`then: { transition }` moves the row's own status to the state, and `then: {
link, transition }` the status of the row its to-one relation `link` points
at, through Workflow's `transition`, whose guards and permissions run. A
rule acts only where it can: a target already in the state, one with no
transition from where it is to the state, one whose guards veto the move,
one that is gone, and a row that has moved on from the state its rule
entered (or the value its `changes` rule named) are left as they are, and
the write it heard is not refused. A move refused because the worker lacks
a transition's permission fails the change's message, which the worker
tries again after the queue's backoff. `status` names the Workflow field
the rules read and move when the table has several (`status: "payment"`);
with one, it is implied. A table may hold any number of rules; the build
checks each against the table, its relations and the tables they name
(`schema` a table of the same database, `link` its to-one relation to this
one, each with one Workflow, a `then`'s state one of its target's), and
the rest of the config (a state the Workflow lacks, a transition that
cannot lead there, rules that move a row round its states for ever) is
the core's to refuse at the first command on the table. `holds` and
`revised`, which the engine's Reactions takes, are refused on a table until
Rollups, Revisions and Branches come to it, and so are a dotted field
name, a binary, vector or geometric field (a `Geo.Location`, which a
write's image leaves out), and Workflow's `statusEnteredAt`, which every
move of the status moves. Reactions has no operations: no route, SDK
method or tool comes from it.

### The change queue

A table whose writes a behavior hears gets a change queue in its database:
a table that implements `Timers` or `Reactions`, and a table another
table's Reactions names in `allTerminal` or `anyTerminal` (`Task`, which
`Project`'s rules hear through `task.project`).

| | For `Task` |
| --- | --- |
| A change queue | `task_change_queue` (`TaskChange`), keyed by the row's key and claimed one message of a row at a time, in the order they were written: `row_key`, `write` (`insert`, `update` or `delete`), `at` (epoch milliseconds, the database's clock), and the row's columns `before` and `after` the write, as JSON |
| A trigger | on `task`, after each insert, update and delete of a row, whoever makes it: the repositories, a raw SQL write, a script, psql. An update that changes none of the columns the behaviors read (`updated_at` alone, say) writes no message; a soft delete or a restore, which changes `deleted_at` alone, writes one |

The trigger never refuses a write. The table's `@behaviorWorker` runs the
queue beside its deadline queue, with no other decorator: a change of a
`Task` runs `Task`'s own rules, then `Project`'s `allTerminal` and
`anyTerminal` on the project the task points at, now, after the write and
before it. So declare a worker for each table with a change queue, even
one that only another table's rules hear; the build warns an API that
serves `Project`'s operations and declares no worker of `Task`:

```ts
// projects-api
@behaviorWorker(Project)
export abstract class ProjectReactions {}

@behaviorWorker(Task, { concurrency: 2 })
export abstract class TaskReactions {}
```

A rule runs after the write commits, when the worker claims its change: a
raw `UPDATE task SET status = 'doing'` moves the task's project to
`active` as a move through the API does, a moment later. A rule that moves
another table's row runs as the worker of the table whose write it heard
(`TaskReactions` moves a project), with that worker's `permissions`. A
change of a row that is gone completes its message, and the change of a
row a repository already wrote changes nothing that write did not set off.
A soft delete is heard as the row going: its deadlines go, and the rules
that read the rows pointing at a project no longer count it. A change
refused for any other reason, or a failure of the database, fails its
message, which is due again after the queue's backoff and dead after its
last attempt (about fifteen minutes); the row's later changes wait behind
it, so one row's changes always run in the order they were written. Nothing
refuses a table whose change queue no worker runs: its messages wait, and
no rule runs and no raw write's deadline moves until a worker claims them.
On a database that lists `sqlite` first, and on D1, no behavior worker
claims yet, so a hearing table's change queue grows by a message per
write, each holding the row's columns, until one does; an operator may
delete them, and the writes they held then go unheard. A table's rows
written before its trigger existed have no messages; their deadlines
reconcile at their next write.

## A table's leases, retries, presence and budgets

A table that implements Lease, Retries, Presence or Budget
([Rows a worker leases, retries, beats and meters](/superschematic/guides/database-tables/#rows-a-worker-leases-retries-beats-and-meters))
has their operations, which a `@behaviorOperations` set serves beside its
Workflow field's `transition`, and deadlines, which a `@behaviorWorker`
runs (D104):

```ts
// agents-api
import { auth, behaviorOperations, behaviorWorker } from "@superschematic/api";
import { Account, Job, Session } from "@acme/agents-db";

@behaviorOperations(Job)
@auth
export abstract class JobActions {}

@behaviorWorker(Job)
export abstract class JobDeadlines {}

@behaviorOperations(Session)
@auth
export abstract class SessionActions {}

@behaviorWorker(Session, { permissions: ["jobs.override"] })
export abstract class SessionPresence {}

@behaviorOperations(Account)
@auth
export abstract class AccountActions {}
```

| Table | Routes, under `POST /api/<table>/{id}/` | Deadlines the worker runs |
| --- | --- | --- |
| `Job`'s Lease | `lease/acquire`, `lease/heartbeat`, `lease/release`, `lease/expire`, `lease/direct`, `lease/acknowledge`, `lease/reset-expiries` | `expire`, when a lease lapses: `onExpiry` moves the job, the token advances |
| `Job`'s Retries | `retries/record-attempt` | `retry`, when a backoff ends: `then` moves the job back |
| `Session`'s Presence | `presence/beat`, `presence/miss` | `miss`, at the session's deadline: `onMissed` moves it, and the leases its principal holds on the tables `releaseLeases` names expire |
| `Account`'s Budget | `budget/reserve`, `budget/check-reserve`, `budget/record-usage`, `budget/settle`, `budget/set-limit`, `budget/observe`, `budget/reserve-for`, `budget/settle-for`, `budget/record-usage-for` | none |

The SDK methods and MCP tools follow the behavior's name, as Timers' do
(`sdk.job.lease.acquire(id, {})`, `job_lease_acquire`;
`sdk.account.budget.observe(id, { meter: "tokens", used, resetsAt })`,
`account_budget_observe`). The types are typed by the config:
`recordAttempt`'s `failure` is `JobRetriesClass`, the config's classes,
and every Budget operation's `meter` is `AccountBudgetMeter`, its meters.
Lease's `expireHolder` runs on the table as a whole, at `POST
/api/job/lease/expire-holder` with no key, for a caller holding
`overridePermission`
([An operation of the table as a whole](#an-operation-of-the-table-as-a-whole)):
`sdk.job.lease.expireHolder({ holder: "w-7" })` answers `{ expired,
reasons, ids }`, `job_lease_expire_holder`. A Budget scope's
operations (`reserveFor` and the rest) are the core's calls from a row
inside it; a route serves them, and the core refuses one from a row that
does not draw the meter from the scope. A table's API has no update or
delete route of its own, so its updates and deletes present a token
through the repositories.

The core checks the configs' permissions on each call, against the
caller's: `observe` needs `observePermission`, `setLimit`
`limitPermission`, `resetExpiries` and another holder's `release` or
`expire` Lease's `overridePermission`, so an `@auth` set admits any
signed-in caller and the config decides the rest. The refusals are the
vetoes the database guide lists, 409 `vetoed` with
`details.vetoCode` (`held_by_another`, `token_stale`, `token_required`,
`backing_off`, `throttled`, `exhausted`, `not_principal`, `over_limit`,
and the rest), and 403 `forbidden` for a permission the caller lacks. The
permission catalog lists each permission under the operations that need
it, and Lease's `overridePermission`, Retries' `limitsPermission` and
Budget's `limitPermission` under each operation that updates a row of the
table through a `@source` view of it, as the core checks them on that
update.

### A precondition: the lease's token

A Lease's fencing token is a precondition of the call
([Rows a worker leases](/superschematic/guides/database-tables/#rows-a-worker-leases-retries-beats-and-meters)):
the caller asserts what it holds, and the core checks it before it reads
the row. On a table one of whose uses takes a precondition, every
behavior operation's input has a member `preconditions`, keyed by the
use, `Lease` for a table's Lease, in the body beside the parameters:

```http
POST /api/job/{id}/lease/heartbeat
Content-Type: application/json

{ "preconditions": { "Lease": { "token": 3 } } }
```

| | Presenting `Job`'s token |
| --- | --- |
| HTTP | the body's `preconditions`, `{ "Lease": { "token": 3 } }`, beside the operation's parameters (`{ "to": "running", "preconditions": ... }`) |
| Types | `JobPreconditions`, whose `Lease` is `JobLeasePrecondition` (`token`, an integer of at least 0); every input of the table's behavior operations has it, optional |
| SDK | `sdk.job.lease.heartbeat(id, { preconditions: { Lease: { token } } })`, `sdk.job.status.transition(id, { to: "running", preconditions: { Lease: { token } } })` |
| MCP tool | the tool's `preconditions` argument, `job_lease_heartbeat` with `{ id, preconditions: { Lease: { token: 3 } } }` |
| Repositories | TypeScript's `updateOne(id, update, { preconditions })`, `deleteOne(id, { preconditions })`; Go's `orm.WithPreconditions(ctx, ...)`; Rust's `ExecuteOptions.preconditions` |

It is a member of the body rather than a header, so an SDK's call and an
MCP tool carry it as any other member, and the build refuses a parameter
named `preconditions` on such a table. The generated handlers take it out
of the body and hand it to the core. A token that is not the lease's is
409 `vetoed`, `token_stale`, `{ token, current }`; a write under
`requireToken` that presents none is `token_required`; a malformed one is
the route's 400 before the core runs (the TypeScript and Go SDKs check it
before they send it); and one for a use whose behavior takes none, or a use the table
lacks, is 400 `invalid_argument` from the core, class
`PreconditionsError` (`preconditions of Job: /Retries: behavior Retries
takes no precondition`). An engine type's routes read the token from the
`Preconditions` header instead
([Work queues](/superschematic/guides/work-queues/#lease)).

### Their worker

A table whose behaviors arm deadlines needs a `@behaviorWorker` on an API
over its database ([The worker](#the-worker)): Lease's expiry, Retries'
`then` and Presence's miss each fall due on its deadline queue,
`job_deadline_queue` and `session_deadline_queue`, and nothing moves the
row until a worker runs them. The worker runs each as itself, the subject
`agents-api/SessionPresence`, holding the permissions its decorator lists:
a miss that expires another principal's leases through `releaseLeases`
needs that table's Lease `overridePermission`, so the worker lists it,
and the build warns of one that does not. A fire that another
principal's active lease vetoes (a Timers fire, a Presence miss on a table
that also implements Lease) is released and falls due a minute later, as
every vetoed fire is; list the operation in Lease's `exempt`
(`"Timers.fireTimer"`, `"Presence.miss"`) to let it through. Budget arms nothing and needs no worker.

## A table's seats and observations

A table that implements Seats, or types a field as a Reconcile
([A row's seats, and a field that follows observations](/superschematic/guides/database-tables/#a-rows-seats-and-a-field-that-follows-observations)),
has their operations, which a `@behaviorOperations` set serves beside its
Workflow field's `transition`; Reconcile's stale deadline needs a
`@behaviorWorker` (D104):

```ts
// seats-api
import { auth, behaviorOperations, behaviorWorker } from "@superschematic/api";
import { Problem, Sandbox } from "@acme/seats-db";

@behaviorOperations(Problem)
@auth
export abstract class ProblemActions {}

@behaviorOperations(Sandbox)
@auth
export abstract class SandboxActions {}

@behaviorWorker(Sandbox)
export abstract class SandboxDeadlines {}
```

| Route | Body | Answer |
| --- | --- | --- |
| `POST /api/problem/{id}/seats/take-seat` | `{ "seat": "accountable", "subject"?: "..." }` | `{ seat, subject, displaced, unchanged? }` |
| `POST /api/problem/{id}/seats/leave-seat` | `{ "seat": "handles", "subject"?: "..." }` | `{ seat, subject, unchanged? }` |
| `POST /api/problem/{id}/seats/list-seats` | `{ "seat"?: "responsible" }` | `{ items: [{ seat, subject, seatedAt, seatedBy, fromField }] }`; it writes nothing |
| `POST /api/sandbox/{id}/observed/observe` | `{ "state": "running", "at": 1790790700324 }` | `{ observed, observedAt, status, moves: [{ from, to }], drift?, unchanged? }` |

The types are typed by the config: every Seats operation's `seat` is
`ProblemSeatsSeat`, the enum of the config's seats, and `observe`'s
`state`, its result's states and `moves` are `SandboxObservedState`, the
states of the Workflow `status` names. The SDK methods and MCP tools
follow the use, as Workflow's do: `sdk.problem.seats.takeSeat(id, { seat:
"accountable" })`, `problem_seats_take_seat`;
`sdk.sandbox.observed.observe(id, { state: "running", at })`,
`sandbox_observed_observe`. The core checks the seat's `take` and
`assign` and Reconcile's `observePermission` against the caller's, so an
`@auth` set admits any signed-in caller and the config decides the rest;
the permission catalog lists a seat's `take` and `assign` under each Seats
operation and `observePermission` under `observe`.

| Call | Answer |
| --- | --- |
| a take of `accountable` by a caller holding `problems.own` | 200 `{ "seat": "accountable", "subject": "<caller>", "displaced": [] }`; the next caller's take answers `displaced: ["<caller>"]` |
| the same take again | 200, `unchanged: true`, nothing written |
| a take without the seat's `take`, or another's seat without `assign` | 403 `forbidden` |
| a sixth `handles` | 409 `vetoed`, `seat_full`, `details.vetoDetails` `{ "seat": "handles", "max": 5, "seated": [...] }` |
| a leave of `responsible` by the row's `agent` | 409 `vetoed`, `held_by_field`, `{ "seat": "responsible", "subject": "<agent>", "field": "agent" }` |
| a `seat` the table's Seats lacks | 400: the route's `bad_request`, since the input types `seat` by the table's seats; the core's own `invalid_argument` answers a repository's or the adapter's call |
| `{ "to": "working" }` by a caller seated in no seat the transition's `by` names | 409 `vetoed`, `not_principal`, `{ "from": "open", "to": "working", "by": ["seat:responsible"] }` |
| an observation of `running` on a pending sandbox | 200, `moves` `[{ "from": "pending", "to": "starting" }, { "from": "starting", "to": "running" }]`, the stale deadline armed five minutes after `at` |
| an observation of `stopped` by an observer without `sandboxes.stop` | 200, `status` `running`, `drift` `{ "status": "running", "observed": "stopped", "code": "forbidden" }` |
| an observation no newer than the last | 200, `unchanged: true`, nothing written |
| `observe` without `observePermission` | 403 `forbidden` |
| a `state` the Workflow lacks | 400: the route's `bad_request`, since the input types `state` by the Workflow's states; the core's own `invalid_argument` answers a repository's or the adapter's call |

A refused step of an observation is no refusal of the call: the
observation is recorded, the steps before it are made, and the result's
`drift` says where the path stopped. Each step is a `transition` made as
the caller, so its `by`, its permission and every other behavior's rule
hold it as they hold the caller's own move.

The worker runs the stale deadline as itself, the subject
`seats-api/SandboxDeadlines`, holding the permissions its decorator lists:
when no observation has reached a sandbox for `staleAfterMs`, it moves the
row to `unreachable`, and a step its permissions or a rule refuse records
drift. A table whose Reconcile gives no `staleAfterMs` still gets a
deadline queue, which nothing arms, and Seats arms nothing.

## A table's schedules and their events

A table that implements Schedules
([A row's schedules](/superschematic/guides/database-tables/#a-rows-schedules))
has its operations, which a `@behaviorOperations` set serves, and a
deadline queue, a change queue and an event queue, which a
`@behaviorWorker` runs (D104). The worker hands each run's event to your
`Workers` method:

```ts
// schedules-api
import { auth, behaviorOperations, behaviorWorker } from "@superschematic/api";
import { Problem } from "@acme/schedules-db";

@behaviorOperations(Problem)
@auth
export abstract class ProblemActions {}

@behaviorWorker(Problem, { permissions: ["problems.schedule"] })
export abstract class ProblemWakeUps {}
```

| Route | Body | Answer |
| --- | --- | --- |
| `POST /api/problem/{id}/schedules/set-schedule` | `{ "name": "standup", "cron": "0 9 * * MON-FRI", "timeZone"?: "Europe/London" }`, or `"after"` or `"every"` in milliseconds | the schedule, `{ name, kind, spec, timeZone?, state, setAt, nextAt, runs, replaced?, unchanged? }` |
| `POST /api/problem/{id}/schedules/pause-schedule` | `{ "name": "standup" }` | the schedule, `state: "paused"` |
| `POST /api/problem/{id}/schedules/resume-schedule` | `{ "name": "standup" }` | the schedule, `state: "active"` |
| `POST /api/problem/{id}/schedules/cancel-schedule` | `{ "name": "standup" }` | the schedule, `state: "finished"`, `endedBy: "cancel"` |
| `POST /api/problem/{id}/schedules/report-run` | `{ "name": "standup", "run": 3, "attempt"?: 1, "outcome": "told" }` | `{ name, run, outcome, retryAt?, unchanged? }` |
| `POST /api/problem/{id}/schedules/list-schedules` | `{ "name"?: "standup" }` | `{ items: [...] }`, by name; it writes nothing |

The inputs are typed by the config: `setSchedule`'s input carries only
the kinds `kinds` names (`timeZone` beside `cron`), and `reportRun`'s
`outcome` is `ProblemSchedulesOutcome`, the config's outcomes. What a
call answers keeps the declaration's types, so it reads a schedule that a
later config narrowed: a schedule's `kind`, `state` and `endedBy` are
enums of every value (`ProblemSchedulesKind`, `ProblemSchedulesState`,
`ProblemSchedulesEndedBy`), as the event's `kind` is, and a schedule's
`lastOutcome` and `reportRun`'s answered `outcome` are strings, since a
schedule of a kind a new config dropped keeps running and an outcome it
dropped stays recorded. The SDK methods and MCP tools follow the use:
`sdk.problem.schedules.setSchedule(id, { name: "standup", cron: "0 9 * *
MON-FRI" })`, `problem_schedules_set_schedule`. The core checks the
config's `permission` against the caller's, so an `@auth` set admits any
signed-in caller and the config decides the rest; the permission catalog
lists it under each of the six operations.

| Call | Answer |
| --- | --- |
| `setSchedule` of `{ "name": "nudge", "after": 300000 }` by a caller holding `problems.schedule` | 200, `state: "active"`, `nextAt` five minutes on, its deadline armed then |
| the same again | 200, `unchanged: true`, nothing written |
| `setSchedule` by a caller without `problems.schedule` | 403 `forbidden` |
| a delay under `minMs`, two kinds at once, or a cron line with a seconds field | 400 `invalid_argument`, at `/after`, `""` or `/cron` |
| an eleventh live name | 409 `vetoed`, `schedule_limit`, `details.vetoDetails` `{ "max": 10, "live": [...] }` |
| `reportRun` of a run the schedule has not had | 409 `vetoed`, `no_run`, `{ "name": "nudge", "run": 2, "runs": 1 }` |
| `reportRun` of an older run, or of the outcome recorded | 200, `unchanged: true` |
| `reportRun` of `missed`, `retry`'s outcome | 200, `retryAt` five minutes on, the run armed again then as its next attempt |
| `setSchedule` on a problem that is `done` | 409 `vetoed`, `schedules_ended`, `{ "status": "done" }` |
| `pauseSchedule` of a finished schedule | 409 `vetoed`, `schedule_finished` |

The worker runs each schedule's deadline as itself, the subject
`schedules-api/ProblemWakeUps`, holding the permissions its decorator
lists: it records the run, writes its event, and arms the next run, all in
the deadline's transaction, and then claims the event from
`problem_event_queue` and hands it to `problemWakeUpsSchedulesRun`
(`ProblemWakeUpsSchedulesRun` in Go, `problem_wake_ups_schedules_run` in
Rust) in the transaction that completes it. The method reports the run
through that transaction as the worker, which `permissions` lets do so:

```go
func (w *workers) ProblemWakeUpsSchedulesRun(ctx context.Context, tx orm.TxInterface, event types.ProblemSchedulesRunEvent) error {
	id, err := dbtypes.ParseIdentityUUID(event.Key.String())
	if err != nil {
		return err
	}
	_, err = tx.GetProblemRepository().Schedules().ReportRun(ctx, id, orm.ProblemSchedulesReportRunParams{
		Name: event.Payload.Name, Run: int64(event.Payload.Run), Outcome: "told",
	})
	if rules.IsNotFound(err) {
		return nil // the problem is gone: complete the event
	}
	return err
}
```

A method's error fails the event, which is due again after the queue's
backoff, the row's later events waiting behind it; a method that returns
completes it, its writes with it. A table whose writes Schedules hears
through its change queue has a raw SQL write of the status heard too:
when it enters a state `endOn` names, the worker finishes the row's
schedules. An API that serves `@behaviorOperations(Problem)` and declares
no `@behaviorWorker(Problem)` is warned, naming what waits (`deadlines
(Schedules), changes (Schedules) and events (Schedules: run)`).

## A table's pool and its rechecks

A table that implements Pool
([A pool of members](/superschematic/guides/database-tables/#a-pool-of-members))
has its operations, which a `@behaviorOperations` set serves, one of them
on the table as a whole, and a deadline queue and an event queue, which a
`@behaviorWorker` runs (D104). The worker hands each recheck's event to
your `Workers` method, which asks the provider and reports:

```ts
// pool-api
import { auth, behaviorOperations, behaviorWorker } from "@superschematic/api";
import { Account } from "@acme/pool-db";

@behaviorOperations(Account)
@auth
export abstract class AccountActions {}

@behaviorWorker(Account, { permissions: ["accounts.pool"] })
export abstract class AccountRechecks {}
```

| Route | Body | Answer |
| --- | --- | --- |
| `POST /api/account/pool/pick` | `{ "match"?: { "owner": "..." }, "prefer"?: { "vendor": "anthropic", "kind": "account" }, "exclude"?: ["..."] }` | `{ member: { key, availability, order, preferred } }`, or `{ member: null, until? }`; it writes nothing |
| `POST /api/account/{id}/pool/mark-out` | `{ "until"?: 1772325000000, "reason": "rate limited" }` | `{ availability: "out", outUntil, outReason, unchanged? }` |
| `POST /api/account/{id}/pool/report-room` | `{ "room": true, "near"?: true }`, or `{ "room": false, "resetsAt"?: 1772326800000, "reason"?: "quota" }` | `{ availability, checkedAt, outUntil?, outReason?, opened? }` |

`pick`'s `match` and `prefer` are `AccountPoolMatch`, a member per own
field of the table but the key, each typed by the JSON value its field
holds (`owner`, a UUID, and `kind`, an enum, are strings; `rank` is an
integer). A null member is absent, as every optional value's null is, on
every server and in every SDK, so a pick matches a field's value, never
its absence: `{ "match": { "owner": "...", "rank": null } }` keeps the
owner's accounts whatever their rank. `pick`'s `key` is the
member's key as its routes take it, a UUID in base62. The SDK methods
and MCP tools follow the use: `sdk.account.pool.pick({ match: { owner }
})`, with no id, and `sdk.account.pool.markOut(id, { reason })`;
`account_pool_pick`, whose input takes no id, `account_pool_mark_out`.
The core checks the config's `permission` at `markOut` and `reportRoom`
against the caller's, so an `@auth` set admits any signed-in caller to
`pick` and the config decides the rest; the permission catalog lists it
under each of the three operations.

| Call | Answer |
| --- | --- |
| `pick` of `{ "match": { "owner": "..." } }` with an open account | 200, the open account lowest by `rank`, `preferred: true` |
| `pick` with every account out | 200, `{ "member": null, "until": ... }`, the soonest time one may be back |
| `markOut` by a caller holding `accounts.pool` | 200, `outUntil` thirty minutes on, the recheck armed then |
| the same again, or an earlier `until` for the same reason | 200, `unchanged: true`, nothing written |
| `reportRoom` with room before `outUntil` | 200, `availability: "out"`, `checkedAt` set |
| `markOut` or `reportRoom` by a caller without `accounts.pool` | 403 `forbidden` |
| `pick` whose `match` names a field the table lacks | 400 |
| `pick` of more than 2,000 members `match` keeps | 409 `vetoed`, `pool_too_large`, `details.vetoDetails` `{ "max": 2000 }` |

The worker runs each recheck as itself, the subject
`pool-api/AccountRechecks`, holding the permissions its decorator lists:
it writes the event and arms the next recheck in the deadline's
transaction, then claims the event from `account_event_queue` and hands
it to `accountRechecksPoolRecheck` (`AccountRechecksPoolRecheck` in Go,
`account_rechecks_pool_recheck` in Rust) in the transaction that
completes it:

```go
func (w *workers) AccountRechecksPoolRecheck(ctx context.Context, tx orm.TxInterface, event types.AccountPoolRecheckEvent) error {
	id, err := dbtypes.ParseIdentityUUID(event.Key.String())
	if err != nil {
		return err
	}
	room, err := askProvider(ctx, id) // your provider's figure, code of your own
	if err != nil {
		return err // due again after the queue's backoff
	}
	_, err = tx.GetAccountRepository().Pool().ReportRoom(ctx, id, orm.AccountPoolReportRoomParams{
		Room: room.Room, ResetsAt: room.ResetsAt,
	})
	if rules.IsNotFound(err) {
		return nil // the account is gone: complete the event
	}
	return err
}
```

An event may come twice; the row's key and `dueAt` say which fire it is.
A check with room made at or after the account's `outUntil` opens it and
clears the recheck; one without room moves it. An API that serves
`@behaviorOperations(Account)` and declares no `@behaviorWorker(Account)`
is warned, naming what waits (`deadlines (Pool) and events (Pool:
recheck)`).

## An operation of the table as a whole

An operation a behavior declares on the table as a whole (D104: Pool's
`pick`, Lease's `expireHolder`) is served at the row's route with its
`{id}` segment gone, `POST /api/<table>/<member>/<operation>`, and its
input takes no id and no preconditions. Each server runs it as a command
without a row through the behaviors' core: TypeScript's router calls the
repository's member method with no key, Go's handler the ORM's
(`Pick(ctx, params)`, through `runTableBehaviorOperation`), and Rust's
the generated `behaviors::run_table_operation`, which runs the adapter's
`postgres::run_table_operation` in one transaction. Its answer and its
refusals are a row operation's. The build refuses a set whose added
table route an operation of the API also matches, by the same method,
with a path parameter in a segment's place (`account/{id}/pick` matching
`account/pool/pick`), so no router's precedence decides: rename one, or
serve the table's operations from code of your own. An operation a
behavior declares on a namespace as a whole (Comments') is not served,
and the build warns of it.

## OpenAPI

The build writes `api/<service>/openapi.json`, and every server serves it
at `GET /api/openapi.json` as `application/json`, with a browsable
[RapiDoc](https://rapidocweb.com/) page at `GET /api/docs`. Each
schema comment becomes a description, and each constraint the matching
JSON Schema keyword: `minLength`, `pattern`, `minimum`, and `minItems` and
`maxItems` for `listMin` and `listMax`.

The served document states version `1.0.0` and one server,
`http://localhost:8080`, unless the service says otherwise. The Rust and
TypeScript routers can also serve neither route:

| Server | Version | Server URL | Neither route |
| --- | --- | --- | --- |
| Go | `Config.OpenAPIVersion` | `Config.OpenAPIBaseURL` | always served |
| Rust | `RouterOptions.openapi_version` | `RouterOptions.openapi_base_url` | `serve_openapi: false` |
| TypeScript | `openAPIVersion` | `openAPIBaseURL` | `serveOpenAPI: false` |

The TypeScript package embeds the document in `openapi.ts`, so serving it
reads no file, on Bun, Node.js and Workers alike. It still exports
`openapi.json` as `<package>/openapi.json`. A server that serves several
APIs answers both routes from the first API's router.

With `outputs.api.mcp` on, a TypeScript API also serves its MCP tools at
`POST /api/mcp`
([An API's MCP endpoint](/superschematic/reference/mcp-tools/#an-apis-mcp-endpoint)).
A tool whose `@mcp` says `invocationPolicy: "ask"` runs there only once
the person confirms the call, by MCP elicitation or a two-step token, so
the API's config names the secret the endpoint signs confirmations with,
`outputs.api.mcpConfirmationKey`
([Confirming a tool that asks](/superschematic/reference/mcp-tools/#confirming-a-tool-that-asks)).
The endpoint asks only about a call the tool's route would run: a call
the route refuses, for its arguments or for its caller, gets the route's
error at once.

## The Rust server
