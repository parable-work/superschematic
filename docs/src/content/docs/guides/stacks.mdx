A Stack service declares which of your services run, how they group into
servers and databases, and the environments they run in. Its build wires
each server to its database and to the APIs it calls, checks the result
offline, and writes three things: each environment as `environment.json`,
an entrypoint and Dockerfile for each Go, TypeScript and Rust server and
each Go and TypeScript job and worker, and a
scaffold of each API implementation that is missing. Wiring the schemas already say,
such as an API's database or the address of an API another one calls, is
derived and never written by hand.

`superschematic stack dev` runs an environment on your machine, with
Postgres and a storage emulator in Docker and each server as a process. The `stack` commands
bootstrap, plan and deploy the cloud environments, and the gcp target
lowers them to Cloud Run, Cloud Scheduler, Cloud SQL, Secret Manager, load
balancer and DNS resources that the Pulumi provisioner applies.

## Start a stack

In a tree that already has API services, `stack init` writes a Stack
service over them. It writes files and nothing else:

```sh
superschematic stack init --gcp-project acme-staging --region us-east1 --ci github
```

Over acme-shop's services, before its stack was written, it writes
`schemas/services/shop-stack/`, with the `@stack` acme-shop declares by
hand: a
`package.json` and `tsconfig.json` like its siblings', `schema.config.ts`
with `outputs: { ci: { github: {} } }`, `src/gcp-target.ts`, and
`src/stack.schema.ts`:

```ts
// schemas/services/shop-stack/src/stack.schema.ts
import { ShopApi } from "@acme/shop-api";
import { ShopOrders } from "@acme/shop-orders";
import { ShopStorefront } from "@acme/shop-storefront";
import { ShopWeb } from "@acme/shop-web";
import { environment, stack } from "@superschematic/stack";

// Written by superschematic stack init. ...
@stack({ deploy: [ShopApi, ShopOrders, ShopStorefront, ShopWeb], expose: [ShopApi, ShopOrders, ShopStorefront] })
export abstract class Shop {}

// This machine: ...
@environment({ target: "local" })
export abstract class Dev {}

// Google Cloud: ...
@environment({ target: "gcp", gcp: { project: "acme-staging", region: "us-east1" } })
export abstract class Staging {}
```

- **`deploy`** lists every API and every site of the tree. The databases
  and buckets they reach through `authDb`, DB dependencies and `buckets`
  come with them.
- **`expose`** lists each API an end user or a third party calls: one
  with an operation that is not `@requireService`, by its own clause or
  its set's. An API whose every operation is `@requireService`, or that
  has none, only other servers call, and stays internal. Each API a site
  calls is exposed too, since a browser calls it. `--expose shop-api`
  names the list in its place, and `--expose none` exposes nothing.
- **`Dev`** runs on the local target, which `stack dev` runs. Given a
  project and a region, a second environment runs on gcp, `Staging`
  unless `--environment` names it, and `src/gcp-target.ts` types its
  values and settings for tsc ([Type a target's values](#type-a-targets-values)).
  Given a Cloudflare account's id instead, `--cloudflare-account <id>`,
  it runs on [cloudflare](#deploy-to-cloudflare), with
  `src/cloudflare-target.ts`. Only the installed binary links gcp and
  cloudflare; the core alone refuses either.
- **The name** is `--name`, else the first word the deployed services'
  names share and `-stack`, else the naming file's `npm_scope`, else the
  project's directory.

It also adds the stack's ignore rules to the `.gitignore` that covers the
schemas root, the nearest one at or above it in the repository, or a new
`schemas/.gitignore`: the output root's contents but its
[lockfile](#the-generated-server), and `.superschematic`, which holds this
machine's local secrets:

```gitignore
/dist/*
!/dist/bun.lock
/.superschematic/
```

A `/dist/` rule there becomes `/dist/*`. Where a broader rule such as a
repository's `dist/` still hides the lockfile, init adds `!/dist/` to take
the directory back. Running init again adds nothing.

At a terminal it asks for each value no flag gives: the name, whether to
add a gcp environment, its name, project and region, or else a cloudflare
one and its account, CI, and what to expose, each with a default from the tree or from `gcloud config`.
Without a terminal it takes the flags and the defaults, so `stack init`
alone writes `Dev` alone. A tree with a Stack service already needs
`--force`, which replaces the stack of the same name or writes another
beside it.

Last, it loads the stack, resolves each environment as a build would, and
prints what it decided, anything that does not resolve yet, and the
commands to run next:

```
Wrote the Stack service shop-stack in ./schemas/services/shop-stack:
  ...
It deploys shop-api, shop-orders, shop-storefront and shop-web; the databases and buckets they reach come with them.
  shop-api         exposed: Account.login is not @requireService
  shop-orders      exposed: OrderQueries.getOrder is not @requireService
  shop-storefront  exposed: StorefrontProbes.getHealth is not @requireService
  A site is always exposed: shop-web.
...
Next:
  superschematic stack dev --environment Dev
  superschematic stack bootstrap Staging
```

A required config field that nothing binds, for instance, is a problem
only you can fix: set it in the environment's `settings`, as
[Declare a stack](#declare-a-stack) shows. From there the stack is yours
to edit; init does not run again over it unless `--force` replaces it.
The [CLI reference](/superschematic/reference/cli/#stack-init-services-root)
lists the flags.

## The model

A stack has three tiers:

- **Schemas** are your DB and API services, as they are today.
- **Deployables** are what runs. A database hosts DB schemas, a server
  serves API schemas, a job runs one of an API's `@job` classes to
  completion, a worker handles the messages of a queue for one of an API's
  `@worker` classes until it is stopped, a site serves a Site service's
  built files, and a bucket keeps a Bucket service's objects. With nothing
  declared, each API service is one server, each of its jobs one job, each
  of its workers one worker, each DB service one database, each Site
  service one site, and each Bucket service an API lists one bucket.
- **Environments** place the deployables on a target and set the values
  only a person decides: a project, a region, a domain, instance sizes and
  settings.

An edge is a need one deployable has of another. The schemas already say
most of them:

| Edge | From | To | Comes from |
| --- | --- | --- | --- |
| sql | a server, a job or a worker | a database | each served API's `authDb`, or its one DB-kind dependency |
| http | a server, a job or a worker | a server | `calls` in the config of each API the calling server serves |
| site | a site | an exposed server | `calls` in a Site service's config ([static sites](/superschematic/guides/static-sites/)) |
| bucket | a server or a job | a bucket | `buckets` in the config of each API the server serves |

A server's edges are the union of its APIs' edges, so grouping two APIs on
one server restates nothing. A job's are its API's, and so are a worker's.

## Wire the services

`calls` is the one wiring fact you write, because no schema says that one
API's implementation calls another. It sits in the API's config beside
`authDb`, as handles:

```ts
// schemas/services/shop-orders/schema.config.ts
import { ShopApi } from "@acme/shop-api";
import { ShopDb } from "@acme/shop-db";
import { defineConfig, SchemaKind, TargetLanguage } from "@superschematic/schema-config";

export default defineConfig({
  name: "shop-orders",
  kind: SchemaKind.API,
  authDb: ShopDb,
  dependencies: [ShopDb],
  calls: [ShopApi],
  outputs: {
    types: { [TargetLanguage.Go]: { enabled: true } },
    api: { enabled: true }
  }
});
```

`buckets`, beside it, lists the Bucket services the implementation keeps
objects in ([Buckets](/superschematic/guides/buckets/)).

`calls` takes only API handles, so tsc refuses a DB handle there and
discovery refuses one in any form. The callee must generate a Go SDK, and
the database Go types, or the caller's build refuses them. A call is a
build-order edge for the caller's API server only: each callee's SDK
builds before the servers that call it, so two APIs may call each other.
The [CLI reference](/superschematic/reference/cli/#build-all-services-root)
has the ordering rules.

A server's settings come from the API's `@envVars` class, which may sit in
the API's own schema:

```ts
// schemas/services/shop-orders/src/config.schema.ts
import { Default, Secret } from "@superschematic/schema";
import { envVars } from "@superschematic/schema-config";

export abstract class PaymentsSecrets {
  STRIPE_KEY: Secret<string>;
}

@envVars
export abstract class OrdersConfig extends PaymentsSecrets {
  FULFILLMENT_REGION: string;
  MAX_LINE_ITEMS: Default<number, 50>;
}
```

A secret is identified by the type that declares the field and the
field's name. When `shop-api`'s config extends the same `PaymentsSecrets`,
both servers read one `PaymentsSecrets.STRIPE_KEY` in each environment.

Each API's build writes its handle to `src/service.generated.ts`. An API's
handle carries its kind and its `@envVars` class as type parameters
(`service<"API", OrdersConfig>(...)`), which is how a stack types the
`env` it sets for that API.

## What an API gets from its edges

Each edge adds a typed field to the Go API's config. The API package's
`EnvConfig` embeds the `@envVars` type and adds a field per edge, and
`LoadEnvConfig` reads them all, reporting every missing or invalid one:

```go
type EnvConfig struct {
	OrdersConfig

	// ShopDbDatabase is the connection to shop-db, the API's database.
	ShopDbDatabase stackconfig.Database

	// ShopApiService is the endpoint of shop-api, which the API calls.
	ShopApiService stackconfig.Service
}
```

`stackconfig` is a package of the Go HTTP runtime. A `Database` is a
connection string or a Cloud SQL connector configuration (instance
connection name, database and IAM user). A `Service` is the callee's base
URL and, optionally, the source of the service credential to send and the
headers that carry it.

A platform sets each derived field as one environment variable per member
of its value: the field's name, an underscore and the member's path in
upper snake case.

| Field | Variables |
| --- | --- |
| `SHOP_DB_DATABASE` | `SHOP_DB_DATABASE_URL`, or `SHOP_DB_DATABASE_CLOUD_SQL_INSTANCE`, `_CLOUD_SQL_DATABASE` and `_CLOUD_SQL_USER` |
| `SHOP_API_SERVICE` | `SHOP_API_SERVICE_URL`; with a credential, `SHOP_API_SERVICE_CREDENTIAL_SOURCE` and the members that source reads (`_AUDIENCE`, `_TOKEN_FILE`, `_ISSUER`, `_KEY`), and `_HEADERS`, joined by commas |
| `SHOP_MEDIA_BUCKET` | `SHOP_MEDIA_BUCKET_NAME`, and `SHOP_MEDIA_BUCKET_ENDPOINT` for a bucket an emulator serves |

On Cloudflare Workers a field also names the binding a Worker reaches its
database, callee or bucket through: `SHOP_DB_DATABASE_D1_BINDING` and
`_D1_DATABASE` in place of a URL, `SHOP_API_SERVICE_BINDING_NAME` and
`_BINDING_WORKER` beside the callee's URL, and `SHOP_MEDIA_BUCKET_BINDING`
with `_R2_ACCOUNT`, `_R2_ACCESS_KEY_ID` and `_R2_TOKEN`, the credential
that signs the bucket's URLs. Only the TypeScript runtime reads them; the
Go and Rust readers refuse them.

The names come from the naming file's
[`[derived_fields]`](/superschematic/reference/naming/#derived_fields)
templates, `{SERVICE}_DATABASE`, `{SERVICE}_SERVICE` and
`{SERVICE}_BUCKET` by default. The
loader refuses an `@envVars` field named after a derived field, or after
one plus an underscore. `values-schema.json` lists each derived field
under `x-superschematic.envVars` with `derived`, `service` and
`variables`, and the callers field of an API with `@requireService` or
`@allowService` with `callersOf`, `variables` and `variablePatterns`,
whose patterns are its `patternProperties`: a deployment outside a stack
sets it ([Service callers](/superschematic/guides/auth-and-permissions/#service-callers)). The TypeScript API package's `loadEnvConfig()` and the
Rust API crate's `config::load_env_config()` read them too, through the
HTTP runtimes' readers.

The API package also gets `deps.go`, with what the implementation is built
from and the signature of its constructor:

```go
type Deps struct {
	Config  EnvConfig              // the @envVars settings and the derived fields
	DB      orm.DatabaseInterface  // the ORM of the API's database
	ShopApi *shopapisdk.ShopApiSDK // a Go SDK client per calls entry
	Logger  *zap.Logger
}

type Constructor func(deps Deps) (Implementations, error)
```

A field is left out when the API has nothing for it. An API that lists a
bucket also gets it, `ShopMedia bucket.Bucket`, the runtime's
provider-neutral interface, which the entrypoint opens on GCS or on the
local emulator ([Buckets](/superschematic/guides/buckets/)). The generated
server entrypoint fills `Deps` and calls your `New`.

## Declare a stack

A stack is a service of kind `Stack`. Its config names it and lists no
`dependencies`: the handles in its schema reference the services.

```ts
// schemas/services/shop-stack/schema.config.ts
import { defineConfig, SchemaKind } from "@superschematic/schema-config";

export default defineConfig({
  name: "shop-stack",
  kind: SchemaKind.Stack,
  outputs: {}
});
```

Its schema declares the stack, any deployable that differs from the
defaults, and the environments, one class each. Every class carries one of
the four decorators of `@superschematic/stack` and no fields.

```ts
// schemas/services/shop-stack/src/stack.schema.ts
import { ShopApi } from "@acme/shop-api";
import { ShopDb } from "@acme/shop-db";
import { ShopOrders } from "@acme/shop-orders";
import { environment, server, stack } from "@superschematic/stack";

@stack({ deploy: [ShopApi, ShopOrders], expose: [ShopApi] })
export abstract class Shop {}

@server({ serves: [ShopOrders] })
export abstract class Orders {}

@environment({
  target: "local",
  settings: [{ of: Orders, env: { FULFILLMENT_REGION: "us" } }]
})
export abstract class Dev {}

@environment({
  target: "gcp",
  gcp: { project: "acme-staging", region: "us-east1" },
  domain: "staging.acme.dev",
  dns: { "gcp.clouddns": { zone: "acme-dev" } },
  settings: [{ of: Orders, env: { FULFILLMENT_REGION: "us" } }]
})
export abstract class Staging {}

@environment({
  target: "gcp",
  gcp: { project: "acme-prod", region: "us-east1", production: true, telemetry: { sampleRatio: 0.25 } },
  domain: "acme.dev",
  settings: [
    { of: ShopDb, tier: "db-custom-2-7680", highAvailability: true },
    { of: ShopApi, minInstances: 1, env: { LOG_LEVEL: "warn" } },
    { of: Orders, memory: "1Gi", env: { FULFILLMENT_REGION: "us" } }
  ]
})
export abstract class Production {}

@environment({
  parameters: ["pr"],
  settings: [{ of: ShopApi, env: { PREVIEW_ID: { parameter: "pr" } } }]
})
export abstract class Preview extends Staging {}
```

- **`@stack({ deploy, expose })`** declares the stack, once per schema.
  `deploy` names the entry points, API and DB handles; every service they
  reach through `authDb`, DB dependencies and `calls` joins the stack, so
  `shop-db` needs no mention. `expose` names what is reachable from
  outside the environment, an API's handle or an `@server` class.
  Everything else is internal.
- **`@server({ serves })`** declares one server for the listed APIs in
  place of their default servers. Here `Orders` serves `shop-orders`, and
  takes its edges from it: `shop-db` through `authDb`, `shop-api` through
  `calls`. **`@database({ hosts })`** puts several DB schemas on one
  database in the same way.
- **`@environment({...})`** declares an environment.
  [Environments](#environments) covers its keys.

The stack takes its service's name, `shop-stack`. A server takes its name
in the stack: a declared server's class name (`Orders`), or the API a
default server serves (`shop-api`). The schema files import their
siblings' handles from the siblings' packages, as a config does, and
`build` writes any missing sibling handle first. A stack may not import
`@superschematic/api` or `@superschematic/db`.

### Type a target's values

tsc checks a stack in the editor, and the loader reports tsc's errors, so
a value tsc refuses fails the build at its line. `target` takes a key of
the `Targets` interface of `@superschematic/stack`, which lists the core's
`local`. No package augments it for gcp yet. `stack init` writes the
augmentation into `src/gcp-target.ts`, from the JSON Schemas the gcp
target and its platforms register; a stack written by hand declares it
in a file of the stack's `src/` that its `tsconfig.json` includes:

```ts
// schemas/services/shop-stack/src/gcp-target.ts
export {};

declare module "@superschematic/stack" {
  interface Targets {
    gcp: {
      values: {
        project: string;
        projectNumber?: string;
        region: string;
        production?: boolean;
        telemetry?: {
          endpoint?: string;
          sampleRatio?: number;
        };
      };
      server: {
        minInstances?: number;
        maxInstances?: number;
        concurrency?: number;
        cpu?: string;
        cpuAlwaysAllocated?: boolean;
        memory?: string;
        telemetry?: boolean;
      };
      database: {
        tier?: string;
        highAvailability?: boolean;
        version?: "POSTGRES_15" | "POSTGRES_16" | "POSTGRES_17";
        deletionProtection?: boolean;
        diskSize?: number;
      };
      job: {
        cpu?: string;
        memory?: string;
        telemetry?: boolean;
      };
      bucket: {
        versioning?: boolean;
        deleteAfterDays?: number;
      };
      worker: {
        cpu?: string;
        memory?: string;
        telemetry?: boolean;
      };
    };
  }
}
```

The loader checks the same values again against the JSON Schemas the gcp
target registers, so these types are the early warning, not the rule.
`internal/generator/stackgen/testdata/services/shop-stack` does the same
for a test target.

### The data forms

A stack has the JSON and YAML forms every schema has. A class is a type
and its decorator a key of the type. A handle is `{ name, kind }`; an
`expose` entry or a settings `of` is `{ service: { name, kind } }` or
`{ deployable: Orders }`; the target's values sit under `values`, platform
settings under each element's `values`, and an `env` value is `{ value }`
or `{ parameter }`. An environment's `order` is its place among the
stack's environments, from 1, which TypeScript takes from where the class
is declared:

```yaml
# schemas/services/shop-stack/src/stack.schema.yaml (excerpt)
kind: Stack
types:
  Production:
    name: Production
    role: EmbeddedStruct
    environment:
      order: 3
      target: gcp
      values: { project: acme-prod, region: us-east1, production: true }
      domain: acme.dev
      settings:
        - of: { service: { name: shop-db, kind: DB } }
          values: { tier: db-custom-2-7680, highAvailability: true }
        - of: { deployable: Orders }
          values: { memory: 1Gi }
          env: { FULFILLMENT_REGION: { value: us } }
```

`internal/generator/stackgen/testdata/yaml/shop-stack` is a whole stack in
YAML, `extends` included, and builds to the same `environment.json` as its
TypeScript twin.

## Environments

| Key | What it sets |
| --- | --- |
| `target` | the target that places every deployable no setting places elsewhere: `local`, or `gcp` in the installed binary |
| `<target>` | the target's values, under the target's name: `gcp: { project, projectNumber, region, production, telemetry }`, or `local: { postgresImage, postgresPort, storageImage, storagePort }` |
| `domain` | where exposed servers are reached; each gets the host `<server>.<domain>` |
| `dns` | the DNS platform that holds the domain's records and its values, as its one key: `{ "gcp.clouddns": {...} }` or `{ cloudflare: {...} }`. Without it, the target's default |
| `settings` | per deployable: `of` a handle, a Bucket's among them, or an `@server` or `@database` class, platform settings as the other keys, `env`, and optionally `platform` to place it on another platform than the target's. A job's element names the job beside its API's handle, `{ of: ShopOrders, job: "ShipOrders" }`, and takes `schedule`, `timeZone` and `enabled` too ([Jobs](#jobs)); a worker's names the worker, `{ of: ShopOrders, worker: "FulfilOrders" }`, and takes `instances`, `concurrency` and `enabled` ([Queues and workers](#queues-and-workers)); an engine's runner's names it beside its database's handle, `{ of: ShopDb, runner: true }`, and takes `enabled` ([The engine's runner](#the-engines-runner)) |
| `parameters` | makes the environment a family, one member per value |

`env` binds the server's `@envVars` fields, each to a literal or to
`{ parameter }`. tsc types the keys from the handle's config: a
`Secret<T>` field takes no literal, and a `Default<T, V>` field takes a
`T`. An `@server` or `@database` class takes either kind's settings and
any `env` key, since tsc cannot see what it serves; the loader checks
them.

An `@environment` class may extend another. It inherits the parent's
target, values and settings, which merge key by key, and adds its own
parameters to the parent's. `Preview` above inherits Staging's project and
domain, and each of its members is named with the value of `pr` at deploy
time. A parameter's value is never written into a generated file.

The environments keep the order the schema declares them in: its schema
files in path order, and the classes of a file in source order. Above,
that is Dev, Staging, Production and Preview. In a data form each
environment's `order` gives it, and one without comes after those with
one, by name; two environments with one order fail the build.

## Jobs

A job is background work of an API: a run to completion, on a schedule or
on demand, with the API's connections and clients. Declare one with `@job`
on a class of the API's schema, which holds no fields:

```ts
// schemas/services/shop-orders/src/jobs.schema.ts
import { job } from "@superschematic/api";

// The warehouse's pick run: it ships every order FulfilOrders fulfilled.
@job({ schedule: "*/15 * * * *", timeout: "5m", retries: 1 })
export abstract class ShipOrders {}
```

Every argument is optional:

| Argument | What it sets |
| --- | --- |
| `schedule` | a five-field cron: minute, hour, day of the month, month and day of the week. Without one the job runs only on demand |
| `timeZone` | the IANA time zone the schedule is read in; UTC unless set |
| `timeout` | how long one run may take, as `90s`, `10m` or `1h30m`; ten minutes unless set |
| `retries` | how many times a failed run is run again; none unless set |

The API's Go package gets `Jobs`, a method per job, and the signature of
the constructor your implementation writes beside `New`:

```go
type Jobs interface {
	ShipOrders(ctx context.Context) error
}

type JobsConstructor func(deps Deps) (Jobs, error)
```

A TypeScript API's `deps.ts` declares the same, with a signal for Go's
context, which SIGTERM aborts:

```ts
export interface Jobs {
  shipOrders(signal: AbortSignal): Promise<void>;
}

export type JobsConstructor = (deps: Deps) => Jobs | Promise<Jobs>;
```

The scaffold writes `NewJobs`, or exports `createJobs` in TypeScript, and
each method returns the not-implemented error, or throws it, until you
write it. Your `NewJobs` takes the same `Deps` as `New`, and your
`createJobs` as `create`. Since the build never writes into a package
that exists, an API whose implementation predates its jobs fails the
stack's build, which says what to add.

In a stack each job is a deployable of its own, named after its API and
its class in kebab case: `shop-orders-ship-orders`. Its edges are its
API's, so it connects to the same database and calls the same APIs, as a
caller of its own that serves its API: an operation whose `from` lists
`ShopOrders` admits the job too. It reads its API's config, with the
`env` its API's server is given.

An environment changes a job's schedule, or turns it off, in its
settings:

```ts
@environment({
  target: "gcp",
  gcp: { project: "acme-staging", region: "us-east1" },
  settings: [{ of: ShopOrders, job: "ShipOrders", schedule: "0 * * * *", timeZone: "America/New_York" }],
})
export abstract class Staging {}

@environment({ parameters: ["pr"] })
export abstract class Preview extends Staging {}
```

`job` takes only a job the API declares, which its handle names, and
`enabled: false` turns the schedule off. A member of a parameterized
environment, such as a preview, runs no schedule unless its settings turn
it on with `enabled: true`. Each job's resolved deployable records what
runs in the environment: its schedule, empty for none, its time zone,
timeout and retries, and whether it runs on every deploy.

### Run a job on every deploy

`onDeploy: true` runs a job once on every deploy of the environment, with
or without a schedule. Use it for work that must follow each rollout: a
backfill of what the new servers write, a cache to warm, reference rows
to bring up to date.

```ts
// schemas/services/shop-orders/src/jobs.schema.ts
// Fills each order's total_cents, which this release adds and its servers
// write, for the orders placed before it.
@job({ timeout: "30m", retries: 2 })
export abstract class BackfillTotals {}

// schemas/services/shop-stack/src/stack.schema.ts
@environment({
  target: "gcp",
  gcp: { project: "acme-staging", region: "us-east1" },
  settings: [{ of: ShopOrders, job: "BackfillTotals", onDeploy: true }],
})
export abstract class Staging {}
```

The deploy runs it in a step of its own after the last rollout wave,
when every server of the new version runs, and before the `contract`
phase, so the job can still read a column the contract drops, and a
column the contract makes `NOT NULL` is filled first: the expand,
backfill, contract order a renamed or tightened column needs. The deploy
waits for the run, its retries included, and when its last try fails it
stops there with that try's error, runs no `contract` step, and records
the failure in the manifest; the next deploy runs the job again. Every
deploy runs it, one that changes nothing included, so write it to be run
twice. `stack plan` lists the jobs a deploy runs.

`onDeploy` merges over the `extends` chain as any setting does, so a
preview member of an environment that sets it runs the job too, unlike a
schedule; `onDeploy: false` in the member turns it off. Only a job takes
it. A target that runs no job on demand cannot run one on a deploy, and
its deploy is refused before anything changes.

### Run a job

The build writes each job an entrypoint module beside the servers',
`server/shop-stack/shop-orders-ship-orders/`, whose `main` builds the
API's `Deps`, calls your `NewJobs`, runs the job's method once with a
context that SIGTERM cancels, and exits 1 when it returns an error. A
TypeScript job's is a package with a `main.ts` that does the same on Bun
with your `createJobs`, and a Rust job's a crate whose `main.rs` does it
on tokio with your `create_jobs` and a `Shutdown` that SIGTERM cancels
([Rust servers](#rust-servers)). A job serves no request, so it is given
no callers field: where its API has one, the TypeScript job loads the
API's config with `loadBackgroundEnvConfig()`, and the Rust job with
`load_background_env_config()`, which leave the field without issuers.
Its Dockerfile builds an image as a server's does, and `stack build` and
`stack deploy` build and pin it beside the servers'.

`stack dev` builds each job with the servers and runs it on its schedule
while the environment runs, never two runs at once, each line of a run's
output with the job's name in front:

```text
job shop-orders-ship-orders runs on * * * * * (UTC)
...
job shop-orders-ship-orders: start the run due at 2026-10-07T12:01:00Z, try 1 of 2
[shop-orders-ship-orders] {"level":"info",...,"msg":"shipped the fulfilled orders",...,"orders":1}
job shop-orders-ship-orders: the run due at 2026-10-07T12:01:00Z, try 1 of 2 succeeded in 412ms
```

A run that outlives the job's timeout is stopped, a failed run is run
again up to its retries, and a run's failure never stops the environment.
A job that runs on every deploy runs once when `stack dev` starts, after
the last rollout wave, and `stack dev` waits for it before it prints where
each server is:

```text
job shop-orders-backfill-totals runs once the environment is up, as on every deploy
...
job shop-orders-backfill-totals: start the run after the rollout, try 1 of 3
job shop-orders-backfill-totals: the run after the rollout, try 1 of 3 succeeded in 1.2s
```

To run a job once, now, run `stack run` from another terminal:

```sh
superschematic stack run Dev shop-orders-ship-orders
```

Locally it runs against the environment `stack dev` runs, with its
values, secrets and keys. It builds no schema, but builds a Go job's
binary again, runs a TypeScript job's `main.ts` after an install, or
builds a Rust job's crate again with cargo, so a change to your job's code
is in the run. It exits
non-zero when the run's last try fails, refuses an environment that is
not running, and waits for no schedule: while its run goes on, the
schedule skips the job's runs, and while a scheduled run goes on, it
refuses to start. On a cloud environment it runs the deployed job, with
the image the last deploy rolled out, through the target: on gcp, an
execution of the job's Cloud Run job ([Deploy to Google
Cloud](#deploy-to-google-cloud)). The cloudflare target runs a job only
on its Cron Trigger, and `stack run` refuses it ([Jobs on Cron
Triggers](#jobs-on-cron-triggers)).

## Queues and workers

A queue is a table of a DB service's database, and a worker is a
deployable that handles its messages with an API's `Deps`.
[Queues and workers](/superschematic/guides/queues/) walks both; in short:

```ts
// shop-db: the message, whose fields are columns of the queue's table
@queue({ retries: 5, backoff: "30s" })
export abstract class OrderPlaced {
  orderId: Identity.UUID;
}

// shop-orders: handles each message, four at a time
@worker({ queue: OrderPlaced, concurrency: 4 })
export abstract class FulfilOrders {}
```

Your code enqueues a message in the transaction that writes what caused
it, `orm.EnqueueOrderPlaced(ctx, tx, msg)`, and implements the worker's
method of the API's generated `Workers`, `FulfilOrders(ctx, msg)`, beside
`NewWorkers(deps)`. In TypeScript it enqueues with the HTTP runtime's
`enqueue(client, orderPlacedQueue, msg)`, over the definition the
database's TypeScript types export from `./queues`, and implements
`fulfilOrders(message, signal)` beside `createWorkers(deps)`. In Rust it
enqueues with the runtime's `queue::enqueue(&tx, &definition, &msg)`,
over the descriptor the database's Rust types hold
(`database_types::ORDER_PLACED_QUEUE`), and implements
`fulfil_orders(message)` beside `create_workers(deps)`. In a stack each
worker is a deployable of its own,
named as a job is, `shop-orders-fulfil-orders`, with its API's edges,
config and identity. It rolls out after its callees, and an environment
sets how many instances run and how many messages each handles at a time:

```ts
settings: [{ of: ShopOrders, worker: "FulfilOrders", instances: 2, concurrency: 8 }]
```

`instances` is one unless set, and `enabled: false` runs none. The
queue must be a queue of the database the API connects to, which the
environment runs on Postgres. On gcp a worker is a Cloud Run worker
pool, scaled by hand to its instances ([Deploy to Google
Cloud](#deploy-to-google-cloud)).

## The engine's runner

A DB service whose types compose behaviors is an engine database: every
server, job and worker of an API that connects to it opens the
[engine](/superschematic/guides/engine/) on it. Its runner, which runs the
reactions that follow a commit, the schedules, Timers' deadlines and the
event log's retention, is a deployable of its own, `<db>-engine-runner`,
in the language of the first API, by name, that connects to it. It runs
one instance, which runs while it holds the runner's lock on Postgres, so
a second would only wait. An element names it beside its database's
handle:

```ts
settings: [{ of: ShopDb, runner: true, enabled: false }]
```

It takes `enabled`, a `platform` and the platform's settings, and no
`instances` or `env`. A runner that is off runs no instance: no reaction,
schedule, Timers deadline or retention pass runs until it is on again,
when each reaction reads on from its cursor, a schedule that came due runs
once and every overdue deadline fires. On gcp it is a Cloud Run worker
pool of one instance, and on `local` a process with no port.

## Static sites

A Site service is a static site: its config names the APIs its browser
code calls and how it builds, and a stack that deploys it serves the
files its build writes, always exposed, with a config per environment
that holds each API's public address. Each API a site calls must be
exposed, and answers CORS for the site's origin, which its CORS field,
`<API>_CORS`, lists:

```ts
@stack({ deploy: [ShopApi, ShopOrders, ShopStorefront, ShopWeb], expose: [ShopApi, ShopOrders, ShopStorefront] })
export abstract class Shop {}
```

`stack dev` builds the site once and serves it on a port of its own, and
`stack deploy` builds it, publishes its files and its config through the
target, and records their digest. [Static
sites](/superschematic/guides/static-sites/) is the guide.

## Build a stack

Build the stack like any service. A single build loads the services it
reaches from its siblings:

```sh
superschematic build schemas/services/shop-stack
superschematic build-all schemas/services
```

Under the output root, `schemas/dist` by default, the build writes:

- `stack/shop-stack/<environment>/environment.json` for each environment;
- `server/shop-stack/<server>/`, a Go module for each Go server, holding
  `main.go`, `go.mod`, a `Dockerfile` and `Dockerfile.dockerignore`, one
  the same for each job and each worker of a Go API, under its name, and a package
  for each TypeScript server, job and worker, holding `main.ts`,
  `package.json`, `tsconfig.json`, a `Dockerfile` and
  `Dockerfile.dockerignore`, a member of the output root's Bun workspace,
  and a crate for each Rust server, holding `Cargo.toml`, `src/main.rs`, a
  `Dockerfile` and `Dockerfile.dockerignore`, a member of the output
  root's Cargo workspace, `Cargo.toml` beside `schemas/dist/Cargo.lock`
  ([Rust servers](#rust-servers));
- `impl/<service>/`, a copy of each implementation a Rust server builds
  against ([Rust servers](#rust-servers)), and, in an output root other
  than `schemas/dist`, of each one a TypeScript server builds against and
  of each site, which builds there
  ([The generated server](#the-generated-server)).

The build also scaffolds each implementation a TypeScript server serves
that is missing, at the `typescript` template (`typescript/{service}`), as
[TypeScript](/superschematic/install/typescript/#serve-a-generated-api)
describes, each one a Rust server serves, at the `rust` template
(`rust/{service}`), as [Rust](/superschematic/install/rust/#the-implementation-crate)
describes, and each one a Go server serves: `implementation.go` at the naming file's
[`[implementation_paths]`](/superschematic/reference/naming/#implementation_paths)
`go` template (`go/{service}` from the parent of the schemas root), whose
`New` has the `Constructor` signature and whose every method answers 501
until you implement it. Where the API's generated `Config` takes them, it
also writes `AuthMiddleware(deps)`, which refuses every request with 401
until it verifies your end users, `PayloadDecryptor(deps)`, which
refuses every encrypted payload, and `NewManualRoutes(deps)`, with a
handler per `@manualRouteRegistration` operation that answers 501. An API over the user model takes the
identity service instead of an auth middleware, or a TypeScript
implementation's `authenticate`, which the entrypoint builds over its
database and its identity config field, `<API>_IDENTITY`; a job's
entrypoint builds none. When no `go.mod` holds the package, it writes
one beside it. It never writes into a directory that holds a Go file, so
the package is yours from then on. Outside a stack,
`build --scaffold` writes the same scaffold for each Go API built. This
is a different stub from `outputs.api.scaffoldsOutputDir`
([API routes](/superschematic/guides/api-routes/#operation-sets)), which
writes one per route.

No `environment.json` is written unless every environment resolves. A
failure names the stack, the environment and each problem with its code:

```
stack shop-stack environment Production does not resolve:
  unbound-field: server Orders: required config field FULFILLMENT_REGION of OrdersConfig has no binding and no default
```

The installed `superschematic` links the gcp target, so a stack with gcp
environments builds with it. The core alone registers only `local`, and a
stack on a target the binary does not link fails with `unknown-target`.

### What is checked offline

Resolution needs no credentials and no network. It stops at the end of the
first stage that fails, so every model problem reports before anything is
lowered:

| Code | Refuses |
| --- | --- |
| `unbound-field` | a required config field with no binding and no default |
| `unknown-env-key` | an `env` key that is not a field of the server's `@envVars`, or an `env` on a database |
| `secret-literal` | a literal or a parameter for a `Secret<T>` field |
| `kind-mismatch` | a handle whose kind is not the kind of the service it names, or a handle in a place that does not take its kind |
| `unrealizable` | a deployable its platform cannot run, such as a job on a target with no job platform, or a server whose APIs are in two languages |
| `no-connector` | an edge no connector realizes between the two platforms. Between platforms of two providers, such as a server placed on another target's platform with a settings `platform`, the core's generic connector serves an http or a site edge |
| `cross-provider-unexposed` | an http edge between deployables of two providers to a server the stack does not expose: the generic connector reaches a server only at its public address |
| `expose-not-server` | an exposed deployable that is not a server |
| `unreachable-edge` | a `calls` edge to an API none of whose operations admits the calling server |
| `ambiguous-database` | an API with several DB dependencies and no `authDb` |
| `call-cycle` | servers that call each other, which no callee-first rollout serves |
| `field-collision` | a config field two types declare for one server, or one a derived field takes |
| `invalid-values`, `invalid-settings` | target, DNS or platform values that fail their JSON Schema |
| `lowering` | an error a platform, connector or DNS platform returned, such as a bucket whose name GCS refuses |
| `graph` | a dangling or cyclic dependency, an undeclared parameter, properties that fail the schema of their resource type, or an inherited node the parent lacks |
| `policy` | a target's policy rule |

`invalid-stack`, `unknown-service`, `unknown-deployable`,
`unknown-target`, `unknown-platform` and `unknown-parameter` cover
malformed declarations and names nothing registers.

## Run it locally

`stack dev` runs an environment on the core's `local` target and stays in
the foreground until Ctrl-C. Give each secret a value first; `stack dev`
refuses a secret that has none and names the file it reads:

```sh
superschematic stack secrets set Dev --stack schemas/services/shop-stack
superschematic stack dev schemas/services/shop-stack
```

It needs Docker, Go, [Bun](https://bun.sh) for a stack with a TypeScript
server, cargo for a stack with a Rust server, and the migration runner, `superschematic-migrate`, on `PATH` or
named by `SUPERSCHEMATIC_MIGRATE`
([Schema migrations](/superschematic/reference/migrations/#the-runner)
says how to install it). It then:

1. builds the stack and every service it reaches, each with its
   dependencies;
2. starts one Postgres container for the environment, published on
   127.0.0.1 only, and creates a database per DB schema; and, when the
   stack has a bucket, one fake-gcs-server container, with a bucket per
   Bucket service. A DB schema that lists `sqlite` first is instead a
   SQLite file under the environment's state directory, which needs no
   Docker ([Databases on D1](#databases-on-d1));
3. migrates each database from the model it recorded to its schema's,
   expand and contract back to back;
4. builds each Go server's entrypoint module with `go build`, runs `bun
   install` once at the output root for the TypeScript servers, which
   writes `schemas/dist/bun.lock` or brings it up to date, as your own
   install would, builds each Rust server's crate with `cargo build
   --release --locked`, frozen to `schemas/dist/Cargo.lock`, which the
   build of step 1 brought up to date, starts each server with its
   resolved config and `PORT`, callees first, a TypeScript one as `bun
   main.ts`, and waits until it answers `/readyz`. Each line a server
   prints carries its name;
5. builds each worker's entrypoint module the same way, or runs a
   TypeScript one as `bun main.ts`, and starts it with the servers of its
   wave, a process with no port;
6. builds each job's entrypoint module the same way, a TypeScript one
   with nothing to build, and runs each job with a schedule on it until
   Ctrl-C ([Run a job](#run-a-job)).

Ctrl-C stops the servers, callers first, and the containers, which keep
their data for the next run, as the SQLite files stay; `--remove-data`
removes them and the SQLite files instead.

A Go server, job or worker links superscalar's static archive through
cgo. In a project whose naming file names no superscalar checkout
([`[paths] scalar_go`](/superschematic/reference/naming/#pathsscalar_go)),
a release of superschematic fetches the static archives it ships for your
machine before the Go builds, checks them against the digest it names,
keeps them in your cache directory, and builds with `CGO_LDFLAGS`
pointing at them, after any you set; `stack run` does the same.
`eval "$(superschematic env)"` sets the same `CGO_LDFLAGS` for a `go
build` you run yourself ([`env`](/superschematic/reference/cli/#env-variable)).

A server, job, worker or engine runner on an engine database whose types
compose the work queue's behaviors or an extension's opens the engine
built from the project's engine crate, which the database's build writes
under `dist/engine/rust/<db>`. `stack dev` builds it with cargo first, the
static archive for a Go one, which the Go build links in the core's place,
and the Node-API addon for a TypeScript one, which its process loads
through `SUPERSCHEMATIC_ENGINE_ADDON`; you set neither. It keeps cargo's
work in the program's directory, so a later run rebuilds only what
changed. The crate builds against a checkout's engine crates, which the
naming file's `[paths]` engine keys name, since a release ships none yet.

Each checkout of the repository runs an environment with containers and
ports of its own, so two worktrees run `stack dev` on one stack at once.
The containers are named after the stack, the environment and the
checkout: `superschematic-shop-stack-dev-3f9a2c-postgres` and
`superschematic-shop-stack-dev-3f9a2c-storage`, where `3f9a2c` is a hash
of the path of the environment's state directory,
`<schemas-root>/.superschematic/local/<stack>/<environment>`. A checkout
keeps them from run to run, but a checkout moved elsewhere starts new
ones. `--remove-data` removes the checkout's containers and no other's.
A container an older superschematic created for the environment,
`superschematic-shop-stack-dev-postgres`, names no checkout: `stack dev`
leaves it and its data, and prints the `docker rm` that removes it.

| Stack concept | On `local` |
| --- | --- |
| server | a Go process, built from its entrypoint module, a TypeScript one, whose `main.ts` Bun runs, or a Rust one, built from its crate with cargo |
| job | a Go process per run, built from its entrypoint module, or a TypeScript one, whose `main.ts` Bun runs, with its API's config and no `PORT`; on its schedule while `stack dev` runs, and once with `stack run` |
| worker | a Go process, built from its entrypoint module, or a TypeScript one, whose `main.ts` Bun runs, with its API's config, no `PORT` and `WORKER_CONCURRENCY`; one whatever its `instances`, none when it is off. Its exit stops the environment, as a server's does |
| database | a database on the checkout's one Postgres container for the environment, `postgres:16-alpine` unless `postgresImage` names another; for a DB schema that lists `sqlite` first, a SQLite file, `<schemas-root>/.superschematic/local/<stack>/<environment>/databases/<database>.sqlite` |
| bucket | a bucket on the checkout's one fake-gcs-server container for the environment, `fsouza/fake-gcs-server:1.56.1` unless `storageImage` names another |
| bucket edge | `SHOP_MEDIA_BUCKET_NAME=shop-media` and `SHOP_MEDIA_BUCKET_ENDPOINT=http://127.0.0.1:<port>`, the emulator's address |
| sql edge | `SHOP_DB_DATABASE_URL=postgres://postgres@127.0.0.1:<port>/shop_db?sslmode=disable`, or for a SQLite file `REVIEWS_DB_DATABASE_URL=sqlite:<state directory>/databases/reviews_db.sqlite` |
| http edge | the callee's `http://127.0.0.1:<port>`, with a `signed-token` credential signed by an Ed25519 key pair per calling and called server |
| secret | a line in `<schemas-root>/.superschematic/local/<stack>/<environment>/secrets.env`: `PaymentsSecrets.STRIPE_KEY=sk_test_...` |
| port | a server's `port` setting and the `postgresPort` and `storagePort` values, the same in every checkout; otherwise a hash of the stack, the environment and the server, which the checkout shifts, the same on every run |

`stack secrets set` writes the secrets file, or you edit it by hand. The
`.superschematic` directory ignores itself in git, and holds the key
pairs too; no secret or private key reaches the output root or
`environment.json`. A local environment refuses a domain, parameters and
two listeners on one port. The
[CLI reference](/superschematic/reference/cli/#stack-dev-stack-service-dir)
lists the flags.

A process gets nothing else of your shell's environment but its
OpenTelemetry variables, `OTEL_SERVICE_NAME` aside. Export a collector's
address, `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318`, before
`stack dev`, and every server, job and worker sends it its traces;
without it, none starts an exporter.
[Traces](/superschematic/guides/traces/) shows a collector to run and what
each deployable sends.

## What environment.json holds

The resolved environment is what a provisioner reads, and it is stable:
fields in a fixed order and map keys sorted, so a wiring change reads as a
diff in review. Its top-level keys are `stack`, `environment`, `extends`,
`target`, `provisioner`, `values`, `parameters`, `domain`, `dns`,
`deployables`, `edges`, `secrets`, `resources` (the resource graph) and
`deployOrder`.

Each deployable carries its platform, its name and address in the
environment, and a binding for every config field, from one of four
sources: `literal`, `secret`, `derived` or `parameter`. A value may
reference a node's output (`$output`), a parameter (`$parameter`), or
both joined (`$concat`). These are the `Orders` server's bindings in
Staging on gcp:

```json
"bindings": [
  { "field": "FULFILLMENT_REGION", "source": "literal", "value": "us" },
  { "field": "MAX_LINE_ITEMS", "source": "literal", "value": "50", "default": true },
  {
    "field": "SHOP_API_SERVICE",
    "source": "derived",
    "value": {
      "credential": {
        "audience": { "$output": { "resource": "shop-api.service", "name": "uri" } },
        "source": "google-id-token"
      },
      "url": { "$output": { "resource": "shop-api.service", "name": "uri" } }
    },
    "edge": "http:Orders->shop-api"
  },
  {
    "field": "SHOP_DB_DATABASE",
    "source": "derived",
    "value": {
      "cloudSql": {
        "database": { "$output": { "resource": "shop-db.database.shop-db", "name": "name" } },
        "instance": { "$output": { "resource": "shop-db.instance", "name": "connectionName" } },
        "user": "orders@acme-staging.iam"
      }
    },
    "edge": "sql:Orders->shop-db"
  },
  { "field": "STRIPE_KEY", "source": "secret", "secret": "PaymentsSecrets.STRIPE_KEY" }
]
```

Each node of the resource graph has an ID, a type token, its properties,
`dependsOn`, its phase (`infrastructure`, `rollout` or `exposure`), its
owners, and `inherited` when a parameterized member reads it from the
parent environment. `deployOrder` lists the steps: infrastructure; the
migrations' `expand` phase; the rollout in waves, callees before their
callers; the jobs that run on every deploy, in a `jobs` step that holds
no nodes; the migrations' `contract` phase; then exposure.

## The generated server

Each Go server's `main.go` reads its whole configuration from the
environment. It loads each served API's `EnvConfig`, opens one pgx pool
per database, shared by the APIs on it and connecting on first use, and
builds one Go SDK client per API called, which sends the service
credential its endpoint names and forwards the request's end user. It
calls each implementation's `New` with its `Deps`, and its
`NewManualRoutes(deps)` where an operation is `@manualRouteRegistration`,
whose handlers `RegisterRoutes` mounts behind the auth, traffic controls
and request log of their routes, routes each request to the API that
registers its method and path, answers `GET /healthz` and `GET /readyz`,
listens on `$PORT` (8080 when unset), logs JSON, and drains on SIGTERM.
The build refuses two served APIs that register one method and path, a
manual route included.

A server whose database some environment of the stack places on Cloud
SQL links the Cloud SQL Go connector and logs in with IAM database
authentication; every other server links no Google module. A server
whose API has a `@requireService` or `@allowService` clause verifies each
calling server's credential against the API's callers field,
`<API>_CALLERS`, which the connector of each http edge to it derives
([Service callers](#service-callers)).

A TypeScript server's package, beside the Go servers' modules, holds a
`main.ts` that does the same on [Bun](https://bun.sh): it loads each API's
config with `loadEnvConfig()`, opens one `pg` Pool per database, or for
a database whose DB service lists `sqlite` first the SQLite file its
`sqlite:` URL names ([Databases on D1](#databases-on-d1)), builds
one TypeScript SDK client per API called with the credential its endpoint
names, calls each implementation's `create(deps)`, its
`authenticate(deps)` where a route needs an end user, and its
`createManualRoutes(deps)` where an operation is
`@manualRouteRegistration`, mounts each API's router on one Hono app,
with the service authenticator over its callers field where an operation
has a service clause and those handlers as its `manualRoutes`, answers
`/healthz` and `/readyz`, and drains on SIGTERM. The package is a member of the output
root's Bun workspace, so `bun install` there links it to the API packages,
the SDKs and the implementations. Its Dockerfile builds superscalar's Node
addon in a Rust stage, from the checkout the naming file's `[paths]
scalar_typescript` names, installs the workspace on `oven/bun`, frozen to
its lockfile, and runs `main.ts` as a non-root user.

Your implementations, and your sites, are members of `schemas/dist`'s
workspace alone, so their `node_modules` link to it, and your editor and
their own `tsc` work against it. A build into another output root
(`stack dev --out`, `build-all --out`) copies each implementation its
TypeScript servers, jobs and workers build against into
`<output-root>/impl/<service>/`, and that root's workspace lists the
copies, `impl/*`, and none of your packages, so an install there leaves
your `node_modules` as they were. The copy keeps the package's name, so
the server resolves it as it would the package, and its `package.json`
re-bases each dependency on a path for where the copy sits. It holds the
package's files but `node_modules`, `.git`, a lockfile beside its
`package.json`, and what its `.gitignore` files leave out, and a build
rewrites only the files that changed. Edit the package, not the copy: the
next build into that root, which `stack dev` runs, brings the copy up to
date. A site is copied the same way, to `<output-root>/impl/<site>/`, and
builds there, against that root's install, so its `dist` is the copy's and
your package's is left as it is.

Commit the workspace's lockfile, `schemas/dist/bun.lock`, which `bun
install` in `schemas/dist` writes, so the image, the
[generated CI](#generated-ci) and every engineer install the same
versions. Write it after `build-all`, which builds every service, so it
names every package; `stack dev` brings it up to date as you change the
schemas. An output root built for one stack, as `stack dev --out` builds
a fresh one, holds only that stack's packages: its workspace leaves out
each implementation or site that needs a package the root lacks, and its
install leaves the lockfile as it is. The rest of `schemas/dist` stays ignored, but git cannot take
back a file under an ignored directory, so ignore the output root's
contents, not the directory:

```gitignore
schemas/dist/*
!schemas/dist/bun.lock
```

Where a broader rule such as `dist/` already ignores the directory, take
it back first in `schemas/.gitignore` with `!/dist/`, then `/dist/*` and
`!/dist/bun.lock`. [`stack init`](#start-a-stack) writes these rules. A
stack's build prints one line naming the rule that hides the lockfile,
and leaves your ignore files as they are. An image built without the
lockfile resolves the workspace afresh and says so.

### Rust servers

A server whose APIs are Rust (`api: { language: "RUST" }`) gets a crate,
`schemas/dist/server/<stack>/<server>/`, whose binary is the server's
name and whose `src/main.rs` does what the Go server's `main.go` does on
tokio: it loads each API's `EnvConfig` with `load_env_config()` and stops,
naming every variable missing, when one fails; opens one Postgres pool
per database, which reaches Cloud SQL over the socket Cloud Run mounts, so
a Rust server needs no connector; builds one Rust SDK client per API
called with the credential its endpoint names; calls each implementation's
`create(deps)`, and its `create_manual_routes(deps)` where an operation is
`@manualRouteRegistration`, whose handlers it mounts with
`build_router_with_manual_routes`; builds an API's identity service over
its database's pool from `<API>_IDENTITY`, and its service authenticator
from `<API>_CALLERS`; and joins them with the handlers through
`Implementations::new`. It hands
each request to the API whose operations take it, answers the site CORS
of an API a site calls, serves `/healthz` and `/readyz`, logs JSON lines,
and drains for ten seconds on SIGTERM.

A Rust API's jobs and workers get crates beside it,
`schemas/dist/server/<stack>/<job>/`, each named after its deployable
and building a binary of that name (D65). A job's `main.rs` builds the
API's `Deps` as the server's does, calls your `create_jobs(deps)`, runs
the job's method once with a `Shutdown` that SIGTERM cancels, and exits 1
when it fails; a worker's calls your `create_workers(deps)` and runs the
runtime's claim loop over the queue's descriptor in the database's Rust
types, with `WORKER_CONCURRENCY` or the decorator's concurrency, and on
SIGTERM gives the running methods the worker's grace, then drops them and
gives their messages back. Neither builds an identity service or a
router, so neither is given the callers, identity or CORS field: they
load the API's config with `load_background_env_config()`, which leaves
the callers field without issuers, where the API has one. Their lines
name them `"job"` or `"worker"`, as Go's and TypeScript's do.

Each Rust server's, job's and worker's crate is a member of the Cargo
workspace whose root, `schemas/dist/Cargo.toml`, the stack's build writes.
Commit its lockfile, `schemas/dist/Cargo.lock`, beside `bun.lock`: each
build of the stack brings it up to date with `cargo update --workspace`,
which pins nothing afresh that it pinned already, and the image and the
generated CI build with `--locked` from it.

```gitignore
schemas/dist/*
!schemas/dist/bun.lock
!schemas/dist/Cargo.lock
```

The build says in one line when git ignores the lockfile, when cargo is
not on `PATH`, and when cargo cannot resolve the workspace, as in a build
of the stack before its services are built.

The implementation's `Cargo.toml` names the API crate by its path under
the output root the scaffold was written for, which your editor and the
crate's own `cargo test` build against. The server builds against a copy:
each build of the stack mirrors each implementation into
`schemas/dist/impl/<service>/`, its path dependencies re-based there and
the API crate's naming that output root's, so `stack dev --out` builds
anywhere, and the image needs no implementation directory. The copy holds
the crate's files but its `Cargo.lock`, `target/` and any crate inside it,
and what its `.gitignore` files or `[package] exclude` leave out, and a
build rewrites only the files that changed, so cargo rebuilds only what
did. Edit the crate, not the copy: the next build, which `stack dev`
runs, brings the copy up to date. A crate that inherits from a workspace
(`workspace = true`) is refused, since the copy belongs to none.

image, `stack dev` and `superschematic env` fetch the same archives for
your machine ([Run it locally](#run-it-locally)).

## Deploy to Google Cloud

The gcp target is `extensions/gcp`, linked in the installed binary. Its
values are `project` and `region`, which are required, `production`,
`projectNumber`, the project's number, which `stack bootstrap` records
and the [generated CI](#generated-ci) signs in with, and `telemetry`,
which sends every server's, job's and worker's traces to Cloud Trace, or
to a collector its `endpoint` names
([Traces](/superschematic/guides/traces/#on-google-cloud)). Only an
account whose deployable exports to Cloud Trace holds the Cloud Trace
agent role: the next deploy removes it from every other, so code of your
own that calls Cloud Trace directly turns its deployable's `telemetry`
on. `stack bootstrap` enables the Telemetry and Cloud Trace APIs for
every environment with Cloud Run.

| Stack concept | On gcp |
| --- | --- |
| server | a Cloud Run service with its own service account; its config in environment variables, a derived field as one variable per member |
| job | a Cloud Run job with its own service account, named after the job (`shop-orders-ship-orders`), with its API's config, secrets and connections; one task, with the job's timeout for each try and its retries, at most 10 |
| schedule | a Cloud Scheduler job, named as the job is, on the job's cron in its time zone, that runs the Cloud Run job through the Cloud Run Admin API as the job's own account, which may run that job and no other. A job whose schedule is off has none, and runs only on demand |
| worker | a Cloud Run worker pool with its own service account, named after the worker (`shop-orders-fulfil-orders`), with its API's config, secrets and connections and `WORKER_CONCURRENCY`; no port and no URL, scaled by hand to the worker's `instances`, zero when it is off. A `grace` of ten seconds or more is refused, since Cloud Run stops an instance ten seconds after SIGTERM |
| runner | a Cloud Run worker pool with its own service account, named after the runner (`shop-db-engine-runner`), with its database's connection as its one config; scaled by hand to one instance, zero when it is off |
| database | a Cloud SQL for Postgres instance (Enterprise edition, IAM database authentication on, connections only through a Cloud SQL connector) and a database per hosted DB schema |
| bucket | a Cloud Storage bucket `<project>-<stack>-<bucket>` in the region, with uniform bucket-level access and public access prevention enforced |
| sql edge | `roles/cloudsql.client` and `roles/cloudsql.instanceUser` for the server's or job's account, held to the instance by an IAM condition, and an IAM database user, which the migration job gives read and write privileges on the DB service's tables. On an engine database it also grants the user a role of the database's own, `<database>_engine`, which owns the engine's schema, `engine`, so each deployable that opens the engine, as its own user, may change what another created there; and it creates the `unaccent` extension the engine's Search needs. The derived value is the Cloud SQL connection, with no password, which a Rust server dials over the socket the service mounts at `/cloudsql` |
| http edge | `roles/run.invoker` on the callee for the caller's account. The derived value is the callee's `run.app` URL with a Google ID token for it as the service credential, sent in `Service-Authorization` and, to an internal callee, also in `X-Serverless-Authorization`. | bucket edge | `roles/storage.objectUser` on the bucket and `roles/iam.serviceAccountTokenCreator` on its own account for the server's, job's or worker's account, so it signs URLs as itself, in Go, TypeScript or Rust. The derived value is the bucket's name |
| internal server | internal ingress only, with Cloud Run's invoker check on |
| calling server or job | Direct VPC egress through the environment's network: a VPC, a subnet with Private Google Access, a router and Cloud NAT |
| exposed server | with a domain, a global external Application Load Balancer and a Certificate Manager certificate for its host, authorized by a DNS record, with the service taking traffic from the load balancer only; without one, its public `run.app` URL |
| site | a Cloud Storage bucket, `<project>-<site>`, readable by `allUsers`, and a backend bucket with Cloud CDN behind a load balancer of its own, whose URL map serves the files of the build the deploy switched to; with a domain at `https://<site>.<domain>`, without one over HTTP at the load balancer's address ([Static sites](/superschematic/guides/static-sites/#on-google-cloud)) |

A server's CPU is allocated only while an instance handles a request, so
Cloud Run bills its instances for the requests they handle. A server that
works between requests, in goroutines of its own or on the warm instances
`minInstances` keeps, sets `cpuAlwaysAllocated: true`, and Cloud Run
bills each instance for its whole life and takes no `cpu` below 1.

Backups are on, with point-in-time recovery in production. Two policy
rules run over every gcp environment: `production-databases-highly-available`
refuses a zonal instance when `production` is set, and
`nothing-public-unless-exposed` refuses an internal server that takes
outside traffic or turns its invoker check off, a load balancer for
anything but an exposed server or a site, a grant to `allUsers` or
`allAuthenticatedUsers`, a job's included, but a site's bucket's, and an
instance open to `0.0.0.0/0`; `buckets-never-public` refuses a Bucket
service's bucket without uniform bucket-level access or public access
prevention, and a grant of one to the public on behalf of any deployable.
Every
resource type is pinned at pulumi-gcp 9.37.1 in `extensions/gcp/schemas`,
and resolution checks each node's properties against it.

### The commands

Each command resolves the environment as the build does, without writing
a build. They reach Google Cloud with application default credentials,
and all but `secrets set`, `run` and `unlock` run the `pulumi` CLI, which must be on `PATH`:

```sh
superschematic stack bootstrap Staging
superschematic stack secrets set Staging
superschematic stack plan Staging
superschematic stack deploy Staging
superschematic stack outputs Staging --out outputs.json
superschematic stack run Staging shop-orders-ship-orders
superschematic stack unlock Staging
```

- **`bootstrap`** runs once per project with an owner's credentials, and
  is safe to run again. It enables the APIs, creates the state bucket
  `<project>-superschematic-state` and its KMS key, gives the bucket a
  lifecycle rule that deletes build contexts and migration job documents
  after 30 days, and applies the
  Artifact Registry repository named after the stack, the
  `<stack>-deployer` and read-only `<stack>-planner` accounts, the
  `builder` account Cloud Build runs as, the `migrator` account the
  migration job runs as, and Workload Identity Federation for the GitHub
  repository of the git remote. It enables Cloud Scheduler when the
  environment runs a job's schedule, and gives `deployer` Cloud
  Scheduler's admin role to apply it, and Storage Admin to create the
  buckets and set their grants. `--repository owner/name` names another
  repository, and `--repository ""` leaves the federation out, for a
  project no CI deploys to. Last, it records the project's number,
  which the generated CI's Workload Identity Federation needs, as
  `projectNumber` beside `project` in the environment that sets
  `project`: Staging's, when you bootstrap Preview. It writes the value
  when the schema has none, writes it again when it differs, leaves the
  file alone when it matches, and prints a line for each:

  ```text
  projectNumber 123456789012: recorded on Staging in src/stack.schema.ts
  ```

  A TypeScript schema changes in that property alone, comments and
  layout kept. A JSON or YAML schema is not edited: bootstrap prints the
  property to add. Commit the change with the rest of the stack.
- **`secrets set`** asks for each secret that has no value and stores it
  in Secret Manager. On a fresh environment, deploy first: its
  infrastructure step creates each secret's storage, and the deploy then
  asks for the missing values at a terminal.
- **`plan`** changes nothing: the provisioner's plan of every resource,
  each database's migration plan, the secrets with no value and the
  servers and jobs with no image.
- **`build`** builds the image of each server and job whose build context
  changed, on Cloud Build, and prints each as a `--image` flag. It
  deploys nothing.
- **`deploy`** first builds, as `build` does, each server and job whose
  context changed and that `--image` names no image for. It then runs the deploy
  order: infrastructure, each database's `expand` phase, the servers wave
  by wave, callees first, the `contract` phase, then exposure. Each
  migration phase runs as an execution of the stack's Cloud Run job,
  `<stack>-migrate`, which also gives each server that connects to a
  database its privileges. An execution that fails stops the deploy with
  the runner's error, which the deploy reads from the execution's logs in
  Cloud Logging, and the next deploy runs the phase again. A job that runs
  on every deploy runs after the last wave as one execution of its Cloud
  Run job, as `run` runs it, and the deploy waits for it; its last try
  failing stops the deploy before the `contract` phase with the job's
  error from Cloud Logging. The deploy
  records a manifest in the state bucket after every step, and refuses a
  migration hazard no `--allow` acknowledges. It holds the run's deploy
  lock throughout, an object of the state bucket, from before it reads
  the manifest until it ends, whether it succeeds or fails: a second
  deploy or a destroy of the run meanwhile fails at once and says who
  holds the lock, on which machine, and since when. Ctrl-C stops the
  step under way, records the failure and releases the lock.
- **`unlock`** removes a lock a deploy left when its process was killed,
  a CI job cancelled hard or a laptop closed mid-deploy. The lock has no
  expiry, so nothing else removes it: check that the deploy it names no
  longer runs, then type the run's name, or pass `--yes`. Each run has a
  lock of its own, so `--param pr=123` names a preview member's.
- **`run`** runs a deployed job once: an execution of its Cloud Run job
  as the last deploy left it. It refuses a job whose Cloud Run job runs
  another image than the manifest records, as during a deploy, waits for
  the execution to end, retries included, and when it fails exits
  non-zero with the last try's error, the error of its `job failed` line
  or its panic, which it reads from the execution's logs in Cloud
  Logging. Cloud Run starts an execution each time a schedule fires, even
  while the last one runs, so a job whose run may outlast its interval
  keeps its runs apart itself.
- **`destroy`** removes a run's resources and its manifest, after you
  type the run's name, or with `--yes`, holding the run's lock as a
  deploy does. What the stack's runs in the
  project share stays: bootstrap's resources, the stack's images, its
  migration job `<stack>-migrate`, and the build contexts and job
  documents in the state bucket, until its lifecycle rule deletes them.
  **`outputs`** prints the applied outputs.

A build's context is the repository root, or the directory the naming
file's
[`[paths] build_context`](/superschematic/reference/naming/#pathsbuild_context)
names, cut down by the `Dockerfile.dockerignore` beside each server's
Dockerfile. A context that lacks a directory the ignore file takes in,
such as a superscalar checkout a CI runner never made, or that holds one
under a symbolic link, is refused before anything is uploaded. `--image
<server>=...` takes a server's image by digest instead of building it,
and `--no-build` builds nothing. A deploy keeps the image the manifest
records for a server whose context did not change. A parameterized
member takes its values with `--param pr=123`.

A deploy runs your project's code: its sidecar documents through Bun,
the install of `schemas/dist`'s workspace, each site's build and each
bundle's. Each of those processes gets an environment with no
credential in it, so an install script cannot read
`GOOGLE_APPLICATION_CREDENTIALS`, `CLOUDFLARE_API_TOKEN` or
`PULUMI_CONFIG_PASSPHRASE`; to hand one a variable it needs, such as a
private registry's token, list its name in `SUPERSCHEMATIC_CHILD_ENV`.
gcloud's credentials file stays readable on disk to any process you run.
To keep your project's code away from your credentials altogether, run
it first in a shell that holds none, then deploy what it made:

```sh
superschematic stack prepare Staging          # no credentials needed
superschematic stack deploy Staging --prepared schemas/dist/prepared/shop-stack
```

`stack prepare` evaluates the documents, writes each image's build
context and builds each site and bundle into the directory; `stack plan`,
`build`, `deploy` and `destroy` given `--prepared` read them from it and
start no Bun, no install and no build. The generated CI works this way.

The migration job's image is built once per release of the runner. A
binary built from a checkout names no release, so set
`SUPERSCHEMATIC_MIGRATE_IMAGE` to an image of `superschematic-migrate`, by
digest, in the stack's repository. After `bootstrap`, the checkout's
`scripts/migrate-dev-image.sh` builds one from its `runtime/migrate/go` on
Cloud Build, as the stack's `builder` account, and prints it:

```sh
export SUPERSCHEMATIC_MIGRATE_IMAGE="$(scripts/migrate-dev-image.sh acme-staging us-east1 shop-stack)"
```

A deploy with a migration to run finds or builds the runner's image, or
checks that the one `SUPERSCHEMATIC_MIGRATE_IMAGE` names exists, before it
changes anything, and stops there, saying what to set, when it has none.

acme-shop has run this way on a fresh project (milestone 3 of the stack
model). A failed migration fails its step with the job execution's name
and the URL of its logs, where the runner's error is. The
[CLI reference](/superschematic/reference/cli/#stack-deploy-environment)
has every flag, the hazard gate and the manifest.

## Deploy to Cloudflare

The cloudflare target is `extensions/cloudflare`, linked in the installed
binary beside its DNS platform (D64). An environment on it runs on one
Cloudflare account, which its values name:

```ts
@environment({
  target: "cloudflare",
  cloudflare: { accountId: "0123456789abcdef0123456789abcdef" },
  domain: "staging.acme.dev",
  dns: { cloudflare: { zone: "acme.dev", zoneId: "023e105f4ecef8ad9ca31a8372d0c353" } },
})
export abstract class Staging {}
```

`accountId` is 32 hexadecimal digits, from the dashboard. `stack
bootstrap` records `workersSubdomain`, the account's workers.dev
subdomain, and `secretsStoreId`, its Secrets Store's, beside it, and you
may correct either by hand. A domain must be on the `cloudflare` DNS
platform, the target's default: the rule `domain-on-cloudflare` refuses
any other. On this target the DNS platform names no credential, since the
run's own token reaches the zone. `stack init --cloudflare-account <id>`
writes the environment and `src/cloudflare-target.ts`.

The target places TypeScript servers on Workers
([Servers on Workers](#servers-on-workers)), which call each other
through service bindings ([Calls between Workers](#calls-between-workers)),
buckets on R2 ([Buckets on R2](#buckets-on-r2)), databases on D1
([Databases on D1](#databases-on-d1)), TypeScript jobs on Cron Triggers
([Jobs on Cron Triggers](#jobs-on-cron-triggers)) and sites on Workers'
static assets ([Sites on Workers](#sites-on-workers)). What every deploy
goes through:

- **The token and the passphrase.** Every `stack` command reads the API
  token from `CLOUDFLARE_API_TOKEN` and the state's passphrase from
  `PULUMI_CONFIG_PASSPHRASE`, in the shell, as gcp's commands read
  application default credentials; `stack bootstrap` also reads its own
  passphrase from `SUPERSCHEMATIC_BOOTSTRAP_PASSPHRASE`. None is ever
  written to a file. The run's AWS session token, profile and shared
  files are kept from the state's S3 backend.
- **Names.** One account may hold several stacks and environments, so
  each Worker, D1 database, R2 bucket and bucket token is named
  `<stack>-<env>-<name>` in kebab case, `acme-shop-staging-shop-api`,
  with each parameter's name and value after it in a member of a
  parameterized environment. A name too long for Cloudflare is refused,
  naming its longest part to shorten.
- **The state.** One R2 bucket per account, `superschematic-state`, holds
  Pulumi's state for every stack in it, through Pulumi's S3 backend on
  `https://<accountId>.r2.cloudflarestorage.com`, region `auto`,
  path-style. Each run verifies the token, and hands the provisioner the
  token's S3 credentials, its id and the SHA-256 of its value, and the
  passphrase, which encrypts the secrets in the state. A run without a
  token or a passphrase is refused before Pulumi starts. The deploy
  manifests are in the same bucket under
  `superschematic/manifests/<stack>/`, each written twice, as
  `<run>.json` and as a copy under `<run>/` named by the time it was
  written, since R2 keeps no versions. A deploy or a destroy holds the
  run's deploy lock, `superschematic/locks/<stack>/<run>.json` in the
  same bucket, and `stack unlock` removes one a killed deploy left.
- **Secrets.** Each secret is one in the account's Secrets Store per
  environment, `<Stack>-<Environment>-<Type>-<FIELD>`, which the members
  of a parameterized environment share. `stack secrets set` writes it,
  and needs no deploy first, only bootstrap. Nothing reads a value back:
  the Secrets Store gives it only to a Worker that binds it.

`stack bootstrap <environment>` runs once per account with your own token,
one that reads the account, creates R2 buckets and account API tokens,
and creates or reads the Secrets Store. It is safe to run again:

1. it verifies the token, an account token or a user token;
2. it creates the state bucket and `superschematic-bootstrap`, where it
   keeps its own state, the CI's tokens among its secrets;
3. on the account's first bootstrap, it generates two passphrases, 32
   random bytes each, and prints each once: the state's, which you set
   in `PULUMI_CONFIG_PASSPHRASE` from then on and the CI holds too, and
   the bootstrap's own, which you set in
   `SUPERSCHEMATIC_BOOTSTRAP_PASSPHRASE` to bootstrap again and no CI job
   ever holds. Keep both in your password manager. Each later run checks
   each passphrase in the shell against `superschematic/passphrase-check`
   in its bucket, a key PBKDF2-SHA256 derives from it, and refuses
   another. Set a passphrase of your own before the first run to have it
   take that one instead. Two first runs at once cannot both write a
   check: the one that loses is refused;
4. it finds the account's Secrets Store, or creates it;
5. it applies three account tokens for the CI in the Pulumi project
   `<stack>-bootstrap`, a stack per account: `<stack>-deployer`, which
   edits the account's Workers scripts, D1, R2, Secrets Store and account
   API tokens and the Workers routes and DNS of its zones;
   `<stack>-planner`, which reads Workers scripts, D1, the Secrets Store's
   names, account tokens, routes and DNS, and writes the objects of the
   state bucket alone, since a preview takes the stack's lock; and
   `<stack>-preview`, which deploys and destroys a pull request's member
   and writes no secret's value. For an environment with a bucket, it
   first checks that the account lists the permission group each bucket
   edge's token holds, by the id Cloudflare publishes. An account whose
   bootstrap state an earlier release kept in the state bucket is
   refused, with the tokens to delete and the objects to remove before
   it runs again;
6. with `--github`, it sets the tokens the environment's jobs read and the
   state's passphrase as the repository's GitHub Actions secrets with
   `gh`, at the scopes the [generated CI](#generated-ci) reads them from,
   and creates the deploy job's GitHub environment when it is missing.
   Without `gh` on PATH, signed in, it prints the `gh secret set` commands
   and each token once;
7. it records `secretsStoreId` and `workersSubdomain` beside `accountId`.
   An account with no workers.dev subdomain yet is told to choose one in
   the dashboard.

### Servers on Workers

A TypeScript server on the cloudflare target is a Worker of
`cloudflare.workers`, named after the stack, the environment and the
deployable, `acme-shop-staging-shop-api`, with a suffix per parameter in
a member of a parameterized environment. Its artifact is a
bundle, not an image: a deploy runs `bun bundle.ts <dir>` in the server's
package after the workspace's frozen install, and keeps the files in the
state bucket under `superschematic/bundles/<stack>/<deployable>/<hex>/`
when their digest is new. The Worker is three nodes: the `worker`, in
infrastructure; a `workerVersion` per rollout, which uploads `main.js`,
`main.js.map` and `superscalar_wasm_bg.wasm` from beside the program, each with
its pinned SHA-256; and a `workersDeployment` that sends it all traffic.
`--bundle shop-storefront=sha256:...` rolls the server back to an earlier
bundle with no build.

Its settings:

| Setting | Default | |
| --- | --- | --- |
| `logs` | `true` | Workers Logs |
| `compatibilityDate` | the extension's, `2026-09-15` | the Workers runtime's compatibility date |
| `cpuMs` | Cloudflare's | the CPU time a request may take, in milliseconds |
| `placement` | none | `"smart"` for Smart Placement |

The server's config reaches it as bindings: each setting and derived
variable as plain text, a `Secret<T>` field as a binding to its Secrets
Store secret, a signing key as a secret text binding from the deploy's
state. An exposed server under a domain gets a custom domain,
`<server>.<domain>`, whose record and certificate Cloudflare writes; one
without a domain is at `https://<worker>.<workersSubdomain>.workers.dev`,
its Worker's name, which needs bootstrap's `workersSubdomain`. An internal
server has no route at all. The rule `nothing-public-unless-exposed`
refuses workers.dev, preview URLs, a Worker that leaves both to
Cloudflare's defaults, a custom domain or a route for a server that is
not exposed.

The stack's build writes `fetch.ts`, the Worker's entrypoint, `bundle.ts`
and `workers.d.ts` beside the server's `main.ts`, which `stack dev` still
runs on Bun. `fetch.ts` reads each API's config from the bindings when
Cloudflare loads the version, so a config the API refuses fails the
upload; builds the APIs on an isolate's first request, and again after a
failure; and gives the runtime the client's address from
`CF-Connecting-IP`. An isolate's memory is its own, and Cloudflare runs
many: the storefront's carts live per isolate. `bundle.ts` bundles for
workerd with Bun, and fails on a `node:` import, Bun's global, or a
WebAssembly module other than superscalar's; `bun bundle.ts --check`,
which the generated CI's `check` runs, bundles into a temporary
directory. Resolution refuses a Go or Rust server, a name over 63
characters and an API over the user model on Workers, whose runtime has
no argon2.

### Calls between Workers

A server on Workers reaches a server it calls through a service binding,
exposed or not, so an internal callee needs no route. The caller's
`SHOP_PRICING_SERVICE` holds the callee's address, `https://<callee's
Worker>`, the host the binding's requests carry; the binding, named after
the field, to the callee's Worker; and a signed token, as the generic
connector's: the binding admits the caller, and the token identifies it.
Each edge has an Ed25519 key, a `tls` `PrivateKey` node in the deploy's
state. Its private key reaches the caller as a secret text binding, and
its public key goes into the callee's callers field, with the caller as
its issuer and subject, the callee as the audience, EdDSA, and tokens that
live at most 300 seconds. No runtime reads a service binding's
`ctx.props`.

The callee's Worker is in infrastructure, and the caller's version names
it through the Worker node's output, so the callee exists before the
caller binds it, and the rollout waves put the callee's version first.
The caller's Worker depends on the callee's, so a destroy removes the
caller, with its bindings, before the callee. A call between two APIs one
server serves stays in process: `fetch.ts` hands it to the server's own
app, with no binding and no credential from the connector. When the
callee has a service clause, the client sends the server's loopback
credential, a key the isolate generates as it builds the server, which
the callee accepts beside its callers field, as `main.ts` does on Bun
([service callers](#service-callers)).

### Buckets on R2

A bucket on the cloudflare target is a private R2 bucket of
`cloudflare.r2`, `<stack>-<env>-<bucket>`, with a suffix per parameter in a
member of a parameterized environment, which gets a bucket of its own.
Its settings:

| Setting | Default | |
| --- | --- | --- |
| `locationHint` | none | `wnam`, `enam`, `weur`, `eeur`, `apac` or `oc`: where R2 places the bucket |
| `storageClass` | `Standard` | `InfrequentAccess` for new objects |
| `deleteAfterDays` | none | a lifecycle rule deletes each object that many days after it was written |

There is no `jurisdiction`: a jurisdiction's bucket is reached at another
S3 host, which the R2 credential does not carry yet, and no `versioning`,
which R2 lacks.

Each server that lists the bucket gets an `r2_bucket` binding named after
its field, `SHOP_MEDIA_BUCKET`, through which it puts, gets, deletes and
lists objects, and an account token of its own, minted by the edge, that
holds Workers R2 Storage Bucket Item Write on that bucket's objects alone.
The token's id and value reach the server as `_R2_ACCESS_KEY_ID` and
`_R2_TOKEN`, the value as a secret text binding, and the runtime's
`signedUrl` presigns S3 URLs at
`https://<accountId>.r2.cloudflarestorage.com/<bucket>/<object>` with
them. The rule `buckets-never-public` refuses an r2.dev managed domain or
a custom domain on a bucket.

`stack destroy` of a member of a parameterized environment empties its
buckets first, since Cloudflare deletes only an empty bucket. Any other
environment's bucket keeps its objects, and its destroy fails on one that
holds some. `stack dev` keeps the bucket on the storage emulator, through
the same `Bucket` interface.

### Databases on D1

A database on the cloudflare target is on `cloudflare.d1`, in SQLite: a
D1 database per DB service it hosts, named `<stack>-<env>-<db>`, with each
parameter's name and value after it in a member of a parameterized
environment, so each preview migrates databases of its own. A DB service
that does not list `sqlite` is refused there. Its settings:

| Setting | |
| --- | --- |
| `locationHint` | where the primary lives: `wnam`, `enam`, `weur`, `eeur`, `apac` or `oc` |
| `jurisdiction` | where the data stays: `eu`, `fedramp` or `us`. D1 ignores the location hint under a jurisdiction, so setting both is refused |

List `sqlite` first for a DB service a TypeScript API on Workers uses:

```ts
// schemas/services/reviews-db/schema.config.ts
export default defineConfig({
  name: "reviews-db",
  kind: SchemaKind.DB,
  outputs: {
    types: { [TargetLanguage.TypeScript]: { enabled: true } },
    sql: { dialects: ["sqlite", "postgres"] }
  }
});
```

The API's `Deps.db` is then the HTTP runtime's `SqlDatabase`, D1's
interface: `prepare(sql).bind(...).first()`, `all()`, `run()` and
`raw()`, `batch([...])`, which runs its statements in one transaction,
and `exec(script)`. Placeholders are `?` and `?N`. D1 has no interactive
transaction, so write what must be atomic as one `batch`. `bind` refuses
`undefined`, so bind an optional field as `value ?? null`, and a BLOB
reads back as an array of its bytes, under `stack dev` as on D1. On Workers the
server's `fetch.ts` takes it from the Worker's d1 binding, which the sql
edge's connector derives as `{type: "d1", name: "REVIEWS_DB_DATABASE",
id: <the database's uuid>}`, and `/readyz` pings it. The same code
runs under `stack dev`, where the database is a SQLite file under the
environment's state directory, `databases/<database>.sqlite`, and the
server opens the `sqlite:` URL its edge derives with the runtime's
`openSqlite`. Resolution refuses a TypeScript API whose database runs in
another dialect than its first, a Go or Rust API on a SQLite database,
and a TypeScript API over the user model on a sqlite-first one.

A deploy migrates each D1 database from your machine, or the CI job's,
between its steps: it finds `superschematic-migrate` on `PATH`, or where
`SUPERSCHEMATIC_MIGRATE` says, reads the database's uuid from the outputs
of what the deploy applied, and runs the runner's job at `d1://<accountId>/<uuid>` with the run's
`CLOUDFLARE_API_TOKEN`. The expand phase runs before the rollout and the
contract phase after it, as on gcp. D1 has no roles, so every Worker
bound to a database reads and writes all of it; the runner gives no
privileges, a deploy that only changes which servers connect needs
neither the runner nor a token for it, and the D1 driver's lease keeps
two deploys apart. The
generated CI's deploy and preview jobs install `superschematic-migrate`
from the release, checked against `SHA256SUMS`.

The D1 driver has run against a fake of D1's REST API, not yet against
D1. To check it against a real database, make a scratch one and run
`go test -run TestRealD1 -v .` in `runtime/migrate/go` with
`SUPERSCHEMATIC_MIGRATE_TEST_D1_URL=d1://<account id>/<database uuid>` and
a `CLOUDFLARE_API_TOKEN` that may edit D1.

`examples/acme-shop`'s `wishlist-stack` runs a D1-backed API this way:
`shop-wishlist`, a TypeScript API over `shop-wishlist-db`, which lists
`sqlite` first and holds a shopper's kept products:

with no Docker, over a SQLite file it creates and migrates, and the

### Jobs on Cron Triggers

A TypeScript job on the cloudflare target is a Worker of its own on
`cloudflare.cron`, named as a server's is, `acme-shop-staging-shop-storefront-sweep-carts`,
never exposed. Its bundle is built and kept as a server's is, from
`scheduled.ts`, which the stack's build writes in the job's package with
`bundle.ts` and `workers.d.ts`, beside the `main.ts` that `stack dev`
still runs. A schedule the environment runs is a Cron Trigger on the
Worker, `<job>.schedule`; a job with no schedule, or one its environment
turns off, has the Worker and no trigger.

| Setting | Default | |
| --- | --- | --- |
| `logs` | `true` | Workers Logs |
| `cpuMs` | Cloudflare's, 30 seconds | the CPU time a run may take, in milliseconds, up to 300000 |

A job's edges are its API's, as a server's are on Workers: it calls
another server through a service binding with a key of its own, which
the callee's callers field admits, even an API the server of its own API
serves, since a job has no app to call in process; it reaches a bucket
through an `r2_bucket` binding and a token of its own; and its database,
on D1, through its d1 binding.

At each firing, the Worker's `scheduled` handler runs the job's tries one
after the other, as `stack dev` does: each builds the API's `Deps` from
the Worker's bindings, as a server's `fetch.ts` does, calls your
`createJobs`, and runs the job's method with a signal that aborts at the
job's timeout. It logs `job started`, then `job done` or `job failed`
with how long the try took, and throws after the last failure, so
Cloudflare records the run as failed.

Cloudflare reads every schedule in UTC and stops a Cron Trigger's run
after 15 minutes. So resolution refuses a job whose schedule runs in
another time zone, and one whose timeout times its tries is over 15
minutes: give such a job a shorter timeout or fewer retries, since the
default timeout, ten minutes, leaves no room for a retry. The target runs
no job on demand, so `stack run` refuses it.

### Sites on Workers

A site on the cloudflare target is a Worker of `cloudflare.sites`, named
as a server's is, that serves the site's build as static assets. A
deploy builds the site after the workspace's frozen install, keeps its
files in the state bucket under
`superschematic/sites/<stack>/<site>/<hex>/` when their digest is new,
and places them beside the program, from which the Worker's version
uploads them; `--site shop-web=sha256:...` serves an earlier build with
no build, its files fetched back from R2. The version also holds:

- `SITE_CONFIG`, the site's config for the environment: each API it calls
  with its public address, which the target composes from names, so the
  graph holds it and no step writes it;
- `SITE_FALLBACK`, the site's `fallback`, when it has one;
- a script the extension embeds, the same in every release, which
  Cloudflare runs for a path that names no file.

The script answers `/__superschematic/config.json` with the config,
`no-store`, even when the build holds a file there; a directory, `/`
among them, with its `index.html`; and any other path with the fallback
at 200, or 404 without one. Files are served with Cloudflare's asset
caching, which revalidates each by its ETag.

A site is always exposed: under a domain at `https://<site>.<domain>`, a
custom domain whose record and certificate Cloudflare writes, and
without one at `https://<worker>.<workersSubdomain>.workers.dev`, its
Worker's name, which needs bootstrap's `workersSubdomain`. That address is the site's origin
in the CORS field of each API it calls, each of which must be a server on
Workers, exposed.

## Generated CI

A stack opts in to a generated CI workflow in its config, under the name
of the renderer that writes it. The core's is `github`, GitHub Actions:

```ts
// schemas/services/shop-stack/schema.config.ts
export default defineConfig({
  name: "shop-stack",
  kind: SchemaKind.Stack,
  outputs: { ci: { github: { branch: "main" } } }
});
```

| Option | Default | What it sets |
| --- | --- | --- |
| `branch` | `main` | the branch pull requests target and a push deploys from: a branch name, not a pattern |
| `install` | `.github/workflows` | the directory under the repository root the build installs the workflow into |

Only a Stack service takes `ci`, and one naming a renderer the binary
does not register fails to build. The build writes the workflow to
`ci/shop-stack/github/shop-stack.yml` under the output root, and copies it
into the install directory when that directory exists. Without the
directory, or outside a git repository, it logs why and installs nothing,
so an example in a repository with CI of its own adds no workflow. A stack
without `outputs.ci` gets none. Commit the installed file, and build again
after changing the stack.

The workflow:

- **On a pull request to the branch**, `check` installs superschematic,
  the static archives its release ships for the runner, which a Go server
  links, and the schemas root's packages (`bun install --frozen-lockfile`
  for a `bun.lock`, `npm ci` for a `package-lock.json`), runs `build-all`,
  which resolves every environment and checks its graph, and compiles
  each Go server's, job's and worker's entrypoint module with `go build
  -mod=mod`. It needs no credentials, and no Rust or superscalar checkout
  for a stack with no Rust server, job or worker. For a stack with one it
  sets up the Rust release `tools.env` pins before the build, fails when
  `schemas/dist/Cargo.lock` is not committed or the build changed it, and
  compiles each Rust server, job and worker with `cargo check --locked`;
  `prepare` sets up the same release before its build. For a stack with a
  TypeScript server, job or worker it then installs `schemas/dist`'s Bun
  workspace with `bun install --frozen-lockfile`, failing when
  `schemas/dist/bun.lock` is not committed or no longer matches the
  packages the build wrote, and type-checks each TypeScript server's,
  job's and worker's package and the implementation each imports with
  `tsc --noEmit`. For a stack with a
  [static site](/superschematic/guides/static-sites/) it installs the same
  workspace and builds each site with its build script, as `stack deploy`
  does, so a site that does not build fails the pull request. Every job
  that sets up Bun installs the release a TypeScript server's image runs
  on, and every job of a project that installs with npm sets up the
  Node.js release superschematic's own CI runs on, so `npm ci` runs on
  the same release from run to run.
- Beside it, `prepare` runs all of your project's code the cloud jobs
  need, with no credentials: the install, the build, the workspace's
  install, and `stack prepare` for every environment with a cloud job,
  which evaluates the sidecar documents, writes each image's build
  context and builds each site and bundle. It uploads the result as the
  artifact `prepared`. When a pull request with a preview closes, it
  prepares the documents alone, for the destroy.
- After both, `plan-<environment>` runs `stack plan` for each cloud
  environment without parameters, as the environment's `planner`
  account, and `preview-<environment>` runs `stack deploy <environment>
  --param <parameter>=<pull request number>` for each environment with one
  parameter, as `deployer`. When the pull request closes, the preview job
  runs `stack destroy` of that member instead.
- A pull request from a fork runs `check` alone: GitHub gives its jobs
  no identity token.
- **On a push to the branch**, `deploy-<environment>` deploys each cloud
  environment without parameters in the order the stack declares them,
  each after the one before, in the GitHub environment of its name. Give
  the `Production` environment required reviewers in the repository's
  settings, and each production deploy waits for their approval.
  `workflow_dispatch` runs the same on demand from the branch.
- Every cloud job downloads `prepared`, installs the schemas root's
  packages with `--ignore-scripts`, and runs its `stack` command with
  `--prepared`: it runs no build, no Bun and no package's script.
  `prepare` set up Bun, even when the schemas root installs with npm, and
  built the sites and bundles. Jobs, workers and buckets need nothing
  more: the deploy builds a job's or a worker's image on the target from
  its prepared context, as it builds a server's, and a bucket is a
  resource of the environment's graph.
- One deploy runs at a time per environment, and one preview job per
  member.

A local environment has no job, since `stack dev` runs it on your
machine, and neither has an environment with several parameters. The
workflow's header names each environment it leaves out and why.

Each cloud job signs in through its target. On gcp that is Workload
Identity Federation, through the pool `stack bootstrap` creates for the
GitHub repository of the git remote, as `<stack>-planner` or
`<stack>-deployer`, with `google-github-actions/auth`, whose credentials
file gives superschematic and Pulumi application default credentials.
A job signs in last, right before its `stack` command, and runs none of
your project's code: GitHub lets any step of a job with `id-token: write`
ask for an identity token, so the pull request's lockfiles, their
packages' install scripts, the build, the sites' and bundles' builds and
the sidecar documents run in `prepare`, which has no identity token and
no secret. A pull request from the repository can still change the
workflow itself, so treat its author as able to act as the job's
account; what this stops is code its dependencies bring.
The provider's name holds the project's number, `projectNumber` in the
environment's `gcp` values, which bootstrap records and you may enter by
hand. An environment that extends another inherits it. Until it is set,
the environment has no cloud job, and the header names the bootstrap to
run:

```ts
gcp: { project: "acme-staging", projectNumber: "123456789012", region: "us-east1" }
```

On cloudflare a job signs in with a long-lived account token, since
Cloudflare offers no federation, and the state's passphrase, each a
GitHub Actions secret `stack bootstrap --github` sets. No action signs
in: the `env` of each step that runs a `stack` command, and of no other
step, reads them into `CLOUDFLARE_API_TOKEN` and
`PULUMI_CONFIG_PASSPHRASE`, so a pull request's package install never
sees them, and the job asks GitHub for no identity token.

| Job | Token | Passphrase |
| --- | --- | --- |
| a plain environment's deploy job | `CLOUDFLARE_DEPLOYER_TOKEN_<STACK>_<ENV>`, a secret of the GitHub environment of its name: the deployer's | `PULUMI_CONFIG_PASSPHRASE_<STACK>_<ENV>`, in the same GitHub environment |
| a plan job | `CLOUDFLARE_PLANNER_TOKEN_<STACK>_<ENV>`, a repository secret: the planner's | `PULUMI_CONFIG_PASSPHRASE_<STACK>_<ENV>`, a repository secret |
| a preview job | `CLOUDFLARE_PREVIEW_TOKEN_<STACK>_<ENV>`, a repository secret: the preview's | `PULUMI_CONFIG_PASSPHRASE_<STACK>_<ENV>`, a repository secret |

`<STACK>` and `<ENV>` are the stack's and the environment's names in
upper case, their words joined by underscores: `acme-shop`'s `Staging` is
`ACME_SHOP_STAGING`, so two stacks of one repository never set each
other's secrets. A plan job's credentials decrypt the
state, and so every secret in it, so they are as sensitive as the
deployer's.

The cloud jobs also install the tools the environment's provisioner runs:
the `pulumi` CLI at the release of the Pulumi SDK the binary links.

The workflow installs the release of superschematic that generated it,
from the project's release page, and checks it against the release's
`SHA256SUMS`, so a repository's CI changes only when you build with
another release. It checks the static archives against the digest the
binary that generated it names. A binary built from a checkout names no release: its
workflow's install step fails and says to generate the workflow again
with a released superschematic. Every action is pinned by commit, and
nothing in the file depends on when it was generated.

## DNS

An environment with a `domain` writes two records per exposed server on
gcp: the host's A record and the certificate's `_acme-challenge` CNAME.
Its DNS platform turns them into resources, in the same provisioner run.

- **Cloud DNS**, `gcp.clouddns`, is the gcp target's default. It writes
  into a managed zone that already holds the domain: `zone` names it,
  defaulting to the domain with its dots as hyphens, and `project` names
  the zone's project when it is not the environment's.
- **Cloudflare DNS**, `cloudflare`, writes into a Cloudflare zone. Its
  values are `zone` (the zone's name), `zoneId` (its 32-character id from
  the zone's Overview page, which is not a secret) and `proxied`, false by
  default.

```ts
@environment({
  target: "gcp",
  gcp: { project: "acme-staging", region: "us-east1" },
  domain: "staging.acme.dev",
  dns: { cloudflare: { zone: "acme.dev", zoneId: "023e105f4ecef8ad9ca31a8372d0c353" } }
})
export abstract class Staging {}
```

Cloudflare records are `cloudflare:index/dnsRecord:DnsRecord` nodes of
pulumi-cloudflare 6.22.0, pinned and checked offline like gcp's. They are
DNS-only with a TTL of 300 seconds, unless `proxied` proxies each host's
A, AAAA and CNAME records. A TXT record, or a name whose first label
begins with an underscore, is never proxied. A domain or record outside
the zone is refused. Resolution writes the API token the provider reads,
`CLOUDFLARE_API_TOKEN`, into `environment.json` under `dns.credentials`
as a secret name (`<stack>-cloudflare-dns-<zone>`, dots as underscores),
never a value.

The installed binary links the Cloudflare extension, with its provider
pin. `stack bootstrap` asks for the token and stores it in the target's
secret store, and `plan`, `deploy`, `destroy` and `outputs` set
`CLOUDFLARE_API_TOKEN` from it for each run. An environment on the
[cloudflare target](#deploy-to-cloudflare) names no such credential: the
token in the shell, or CI's, reaches the zone. A distribution of your own
links it the same way:

```go
cli.New(cli.Config{Name: "superschematic"},
	gcp.Extension{},
	cloudflare.Extension{},
	pulumi.Extension{ProviderVersions: map[string]string{
		"gcp":              gcp.ProviderVersion,
		cloudflare.Package: cloudflare.ProviderVersion,
	}},
)
```

## The Pulumi provisioner

`extensions/pulumi` is the provisioner the gcp target names, and the cloud
commands drive it. It renders an environment's graph as `Pulumi.yaml` in
`<schemas-root>/dist/program/<stack>/<environment>`: one resource per
node, keyed and named by the node's ID, with `dependsOn`,
`${node.output}` references and the provider version pinned for each
package. The same environment renders the same bytes, so you can review
the program. The Pulumi project is the stack's name in kebab case, and
each run is a Pulumi stack of it: `staging`, or `preview.pr-123` for a
member of a parameterized environment, which reads the nodes it inherits
from its parent's stack through a stack reference.

Each step of the deploy order is one targeted `up` of that program, and
the last step that holds nodes updates the whole program, which deletes
what the graph dropped. Migrations, and the jobs that run on every
deploy, run between steps, outside the graph.
The release pins the `pulumi` CLI at the Go SDK's version,
`PULUMI_VERSION` in `tools.env`.

## Typed bindings

`extensions/pulumi/bindings` writes a Go package over a stack's outputs,
for scripts and for hand-written Pulumi programs that need a resource the
vocabulary lacks. It has no command: call it from Go with each
environment's `environment.json` and the outputs file `stack outputs --out`
wrote, which `bindings.UnmarshalOutputs` reads and checks the version of.

```go
env, err := stack.Unmarshal(environmentJSON)
if err != nil {
	return err
}
outputs, err := bindings.UnmarshalOutputs(outputsJSON)
if err != nil {
	return err
}
err = bindings.Write("internal/shopstack", "shopstack",
	[]bindings.Environment{{Resolved: env, Outputs: outputs}})
```

It writes two packages:

- `shopstack`, with an `Environment` type that has a field per deployable
  and a value per applied environment: `shopstack.Staging.ShopAPI.Address`,
  or a node's outputs under the node it comes from. DNS records sit in a
  field of their own.
- `shopstack/pulumi`, package `shopstackpulumi`, with the same types over
  Pulumi outputs and a function per environment that reads one through a
  stack reference: `shopstackpulumi.Staging(ctx)`, or
  `shopstackpulumi.Preview(ctx, "123")` for a member.

Generate the binding again after each deploy.

## Service callers

An API decides which servers may call each operation with
`@requireService` and `@allowService`
([Service callers](/superschematic/guides/auth-and-permissions/#service-callers)).
A stack's `calls` edges must agree: every edge from a server to an API
must reach at least one operation that admits that server, or resolution
fails with `unreachable-edge`. A handle in `from` that names a service the
stack does not deploy is not an error, since one API is written once and
deployed in many stacks.

The connector of each http edge to an API with a service clause derives
the issuer its caller's credential comes from, and the build merges them
into the API's callers field, `<API>_CALLERS`, which its server's
authenticator verifies each credential against. On `local`, the calling
server signs a short-lived token with an Ed25519 key pair `stack dev`
makes for the edge, and the callee's field holds its public key. In the
acme shop, `shop-orders`' server, its worker and its job each have an
edge to `shop-stock`, since each holds a client of it in its `Deps`, so
`SHOP_STOCK_CALLERS` lists all three, each serving `shop-orders`.
