The other guides generate code from a schema. `@superschematic/engine`
runs a schema with no generated code. Your server hands it the schema as
JSON while it runs; the engine versions the schema, keeps its instances
and an event log in one SQLite file, and serves them over HTTP, a
server-sent event stream and MCP. A type in the schema composes
behaviors: code that adds fields, operations, checks and storage to it,
such as a state machine, a conversation or reviewed revisions.

This guide builds `examples/engine-notes`, a notes server. A note moves
from draft through review to published, holds a conversation and keeps its
revisions, and a reader can propose a change for an editor to approve.
CI runs the example's end-to-end test on Node.js and on Bun in the
release candidate run on `main` twice a day. The
[engine README](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md)
is the reference for everything below: every route, status, option and
rule.

## What the engine is

- The Rust library every server links (D58), which `@superschematic/engine`
  loads as a Node-API addon on Node.js 24 and Bun. Your server opens it in
  its own process; the engine has no server or process of its own.
- One SQLite file, through the SQLite the engine bundles, or a schema of a
  Postgres database ([On Postgres](#on-postgres)). On SQLite there is no
  database server.
- One process writes the file. The engine caches each schema version's
  validator and behaviors in the process and announces new events in the
  process, and nothing coordinates either across processes. Run one server
  process per file.
- A schema is one JSON document of kind `General`, with no `imports` and
  no operation sets. Every schema has the operations `create`, `get`,
  `list`, `update` and `delete`, one with a unique field `lookup`, and
  its behaviors add their own.
- It has no roles and no default policy. Your server says who each caller
  is and what each caller may do.

It is not a database server of its own: on SQLite one server process
owns the file, and on Postgres each instance of your server opens its own
engine on one schema of the database. D16 and D58 in
[docs/DECISIONS.md](https://github.com/parable-work/superschematic/blob/main/docs/DECISIONS.md)
record the design, what is built and what is still to come.

## Set up

Nothing is published yet, so the example links the engine from the
checkout. From the repository root, after
[setting up the checkout](/superschematic/start/prerequisites/#set-up-the-checkout)
with `make setup`:

```sh
examples/engine-notes/scripts/check.sh
```

It builds the HTTP runtime and the engine (`bun install --frozen-lockfile`
and `bun run build` in each), and the engine's Node-API addon with cargo
when the engine has none (`scripts/engine-napi.sh`), links them into the
example's `node_modules` (`scripts/link.sh`), type-checks the example, and
runs its end-to-end test with `node --test` and with `bun test`. The last
line it prints is `engine-notes: ok`.

`@superschematic/engine` loads its addon when the first engine opens,
from the first of these:

- the file the engine option `addon` names, or, for every engine the
  process opens, the environment variable `SUPERSCHEMATIC_ENGINE_ADDON`:
  a project's own addon, built over its own behaviors
  ([Your own behaviors](#your-own-behaviors)). Nothing else is tried when
  it does not load;
- the checkout's `runtime/engine/typescript/native/`, which
  `scripts/engine-napi.sh` builds, as here;
- the published platform package `@superschematic/engine-<target>`, for
  `darwin-arm64`, `darwin-x64`, `linux-x64-gnu` or `linux-arm64-gnu`, an
  optional dependency of `@superschematic/engine` that npm installs for
  its host.

`scripts/link.sh` links `@superschematic/engine`, and, from the engine's
own install, the packages the example imports: `@superschematic/http-runtime`,
`hono`, `@hono/node-server` and `@modelcontextprotocol/client`, and
TypeScript and the Node.js types for the type-check. Each resolves to the
engine's copy, so the engine and the example share one Hono. The engine
needs `@superschematic/http-runtime` beside it, and `superscalar`, which
the HTTP runtime imports; its build links both into its own
`node_modules`. Its `./http` and `./mcp` entry points also need `hono`.
The engine speaks MCP itself, so `./mcp` needs no MCP SDK, and its
`Branches` behavior runs the version graph's Rust engine inside the
addon, so nothing else needs building.

## The schema

The engine reads a schema in the JSON data form of a schema file, the form
[`superschematic format --to=json`](/superschematic/reference/cli/) writes
from a TypeScript or YAML schema file. The notes schema:

<Snippet example="engine-notes" file="schemas/notes.schema.json" />

- `name` keys the schema's versions and names it in every route and tool.
- The instance type, the one whose instances the engine stores, is the
  type named like the schema or, as here, the only type.
- A field's type is a builtin primitive, a scalar, or an enum or type of
  the document, alone, as a list or as a list of lists. The engine
  refuses a union or a map, which the schema runtime does not check.
- `behaviors` lists what `Note` composes, with each one's config.
  `Workflow` keeps a `status`, and when it last moved in `enteredAt`,
  and moves it only along the listed transitions; moving a note from review to published, or from published
  to archived, needs the permission `notes.publish`. `Comments` keeps
  a conversation on the note: messages, each top-level or a reply in a
  thread. `Revisions` records a revision at every change,
  and its `review` config lets a caller propose a change that someone
  holding `notes.review` approves or rejects.

The engine checks a document with the strict loader of the schema
runtime's Rust crate, against the core binary's
[`json-schema`](/superschematic/reference/cli/) output by default, which
admits the core's behaviors, the
[work-queue behaviors](/superschematic/guides/work-queues/) included
(those run once the server names them in the engine's `behaviors`
option).
A deployment whose binary registers more behaviors passes that binary's
output as the `metaSchema` option.

You can also write the schema in TypeScript, composing each behavior with
`@behavior(name, config)`, and convert it with `format --to=json`;
[Engine behaviors](/superschematic/guides/engine-behaviors/#compose-a-behavior)
shows both forms.

## Open the engine and publish the schema

<Snippet example="engine-notes" file="src/server.ts" symbol={['notesSchema', 'deployer', 'openNotes']} />

`openEngine` takes the file's path and the access policy (next section),
creates the file if it is absent and brings it up to the engine's
migrations. `define` stores the document as the draft of its name, and
`publish` makes the draft the next live version. Publishing a draft
identical to the live version mints nothing, so the server publishes its
schema file every time it starts.

### The compatibility rule

A new version may change a schema only in ways every instance the live
version accepts still satisfies. A new optional field, a new enum value, a
looser bound and a required field made optional are allowed. A removed or
renamed field, a new required field, a tighter bound and another type are
refused: the engine throws `IncompatibleChangeError`, and the HTTP API
answers 409 `incompatible_change`. To make such a change, publish it under
a new schema name. Each behavior decides which changes to its own config a
new version may make. A new `@unique` field is allowed while no two
stored instances hold the same value, and refused while two do. The README's
[compatibility rule](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md#the-compatibility-rule)
has the full table.

The end-to-end test restarts the server on the same file, first with a
schema that drops `tags`, then with one that adds an optional `pinned`:

<Snippet example="engine-notes" file="test/notes.test.ts" from="// Removing a field" to="engine = openNotes(path, withPinned);" />

The first is refused and the server would not start; the second becomes
version 2, and every stored note stays as it was. The same rule holds for
a draft defined over HTTP; see
[Change the schema over HTTP](#change-the-schema-over-http).

### On Postgres

`openEngine` is synchronous: each call returns its result, which suits a
SQLite file in the server's own process. A server on Postgres, where a
call waits on the network, opens the engine with `openEngineAsync`, whose
`AsyncEngine` returns a promise from every call:

```ts
import { openEngineAsync } from '@superschematic/engine';

const engine = await openEngineAsync({ postgres: { url: process.env.DATABASE_URL! }, policy: 'permission' });
await engine.schemas.define(deployer, notesSchema);
await engine.schemas.publish(deployer, 'notes');
```

`postgres` names the database's `url` and the Postgres `schema` the
engine's tables live in, `engine` by default, with the pool's options
beside them (`PostgresOptions`); a `path` in its place opens a SQLite file
the same way. Its calls run off the JavaScript thread, so its options are
data alone: the policy is `allowAll`, `permissionPolicy()` (or its name,
`'permission'`) or `{ rules }`, a list of rules the first match of which
decides. A behavior's namespace operation (below) is decided only by a
rule that names `behavior` (`true`, or the behaviors' names): a rule
without it, such as `{ service: ["shop-orders"], action: ["read",
"write"], allow: true }`, does not reach Comments' `inbox` or
`claimDeliveries`, and with no rule that names `behavior` the call is
refused. `{ behavior: ["Comments"], action: "read", allow: true }`
allows its reads, and `{ behavior: true, action: "write", require:
"{behavior}.{operation}" }` its writes to a caller holding
`Comments.claimDeliveries`, as `'permission'` does. It takes no policy of your own written as a function, no
permission matcher but the HTTP runtime's `hasAnyPermission`, no id
function and no behavior written in TypeScript.
Every instance of the server opens its own engine on the one schema; the
README's
[several instances on one Postgres database](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md#several-instances-on-one-postgres-database)
has what the engine holds across them. `engineApp` and `engineMcp` serve
either engine.

## Callers and the access policy

<Snippet example="engine-notes" file="src/auth.ts" symbol={['callers', 'authenticate', 'policy']} />

- The HTTP runtime's authentication gate calls `authenticate` on every
  route. It returns the caller, a principal with a `subject` and
  `permissions`, or `null`, which answers 401. A real server verifies a
  signed token or looks a session up; the example reads a fixed table.
- The engine asks `policy` before every read and write, with the
  principal, the action (`read`, `write`, `define` or `publish`), the
  namespace, the schema and, for a behavior operation, the operation's
  name. Only `true` allows; anything else is 403 `forbidden`. The policy
  runs synchronously. There is no default: `allowAll` is there for tests.
- Making, archiving and listing namespaces asks the action `manage`,
  with the namespace, no schema, and the operation (`create`, `archive`,
  `unarchive` or `list`). This example makes no namespace while it runs,
  so its policy refuses `manage`.
- A behavior operation asks `write` when it writes and `read` when it only
  reads. This policy lets a reader post in a note's conversation, edit
  and delete her messages, react, and `propose`, and nothing else that
  writes.
- An operation that writes only its caller's own state, and appends no
  event, declares `"asks": "read"`, and the policy is asked `read` for
  it: Comments' `markRead` and `follow`. A reader marks what she has read
  and follows a thread with no write permission, and an archived
  namespace lets both run.
- A behavior's namespace operation, which runs across every schema of
  the namespace that composes the behavior, names no schema. The policy
  is asked `{ principal, action, namespace, behavior, operation }`, with
  `action` `read` or `write` as the operation declares, so a policy that
  builds a permission from `schema` checks `behavior` first, as this one
  does. Its rows are those of the schemas the caller may read, which the
  engine asks `read` of one schema at a time and skips when refused, so
  this policy lets every read one through, and a writing one only to a
  caller holding `<behavior>.<operation>` (`Comments.claimDeliveries`).
  `permissionPolicy()` answers both the same way. In a `{ rules }`
  policy, only a rule that names `behavior` answers them.
- Where a behavior limits who may do something, its config names a
  permission and the behavior asks the engine's permission matcher. That
  is the HTTP runtime's `hasAnyPermission` unless you pass another, so
  `notes` covers `notes.publish` and `notes.review`. Workflow and
  Revisions check those after the policy has allowed the write. A server
  that replaces the matching rule passes the same `permissionMatcher` to
  `openEngine` and to the HTTP options.
- Another service in a stack can call the engine too (D37). Pass the HTTP
  runtime's `authenticateService` beside `authenticate`, and the
  principal carries the verified caller in `service`. A service that
  forwards an end user's token acts as that end user. One that sends no
  `Authorization` header stands in for an end user, as
  `service:<deployable>` with no permissions, so the policy decides what
  it may do by `principal.service.deployable`, and a transition behind a
  permission stays closed to it. The README's
  [service callers](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md#service-callers)
  section has the rules.
- An agent or a service that works for a person acts for that person
  (D77): its principal carries `actingFor: { subject }`, and stays its
  own. The event a call acting for someone writes names the agent as
  `actor` and the person as `for`, Provenance records both (`by` and
  `for`), and Comments records the person as the message's `for`
  ([Acting for someone](#acting-for-someone)). Acting for someone grants
  nothing: every permission check answers for the principal's own.
  Over HTTP and MCP a client sends the subject in the `Acting-For`
  header, which a mount honors only when the host opts in with
  `engineApp`'s and `engineMcp`'s `actingFor` option: `false`, the
  default, ignores the header, `true` honors it for any caller the
  runtime authenticated, and a function, `(principal, subject, request)
  => boolean`, decides per request, so a host that trusts only its
  agents' tokens to act for anyone says so there. The Go binding's
  `enginehttp.Options.ActingFor` is that function
  (`enginehttp.HonorActingFor` for `true`).
- The policy sees `principal.actingFor` on every question and decides.
  `permissionPolicy()` refuses a principal acting for someone unless it
  holds `actFor`, and then answers as for its own permissions: an agent
  holding `notes.write` and `actFor` may write notes for anyone, and
  nothing else. In a `{ rules }` policy a rule matches on `actingFor`:
  `true` for a principal acting for any subject, `false` for one acting
  for none, or a subject or a list of them; a rule that leaves it out
  matches only a principal acting for no one, so rules written before it
  let nobody act for anyone. `{ "actingFor": true, "require":
  "{schema}.{action}" }` lets a principal act for anyone within its own
  permissions. A policy of your own reads `principal.actingFor` first,
  as this example's does: its callers act only as themselves, and its
  server honors no `Acting-For` header. A subject that is the caller's
  own is 400 `invalid_argument`, and so is one beside the end user a
  service brings: a service that forwards an end user's token already
  acts for that user. A service standing in, `service:<deployable>`,
  may act for a subject, and the engine's runner acts for no one.

## Serve it

<Snippet example="engine-notes" file="src/server.ts" symbol={['notesApp', 'listen']} />

- `engineApp` serves the HTTP API and the event stream. Its routes carry
  the namespace and the schema name as path parameters and look them up
  per request, so publishing a version mounts nothing. Every route goes
  through the HTTP runtime: the request id, the rate limit, the timeout,
  the body limit, the authentication gate, the `{data, meta}` envelope and
  RFC 9457 problem documents.
- `engineMcp` serves the MCP endpoint at `/namespaces/{namespace}/mcp`,
  with the same options.
- There is one namespace, `default`, unless you configure more with the
  `namespaces` option or make one while the server runs
  (`POST /api/namespaces`, `create_namespace`), as the policy allows. An
  archived namespace is read as it was and refuses every write (409
  `namespace_archived`).

Start the server from the example's directory:

```sh
cd examples/engine-notes
node src/main.ts
```

```
engine-notes: http://127.0.0.1:8787/api, database notes.db
```

`bun src/main.ts` runs the same server on Bun. Ctrl-C stops it. The
commands below run in a second terminal, from `examples/engine-notes`, and
print JSON with `jq`. The live schema:

```sh
API=http://127.0.0.1:8787/api/namespaces/default
curl -s $API/schemas -H 'authorization: Bearer carol-token' | jq .data
```

[
  {
    "namespace": "default",
    "name": "notes",
    "liveVersion": 1,

## Instances

Create a note as alice, an author:

```sh
curl -s $API/schemas/notes/instances \
  -H 'authorization: Bearer alice-token' -H 'content-type: application/json' \
  -d '{"id": "launch", "data": {"title": "Launch", "tags": ["launch"]}}' | jq
```

```json
{
  "data": {
    "namespace": "default",
    "schema": "notes",
    "id": "launch",
    "schemaNamespace": "default",
    "version": 1,
    "seq": 1,
    "data": {
      "title": "Launch",
      "tags": [
        "launch"
      ]
    },
    "behaviors": {
      "Workflow": {
        "status": "draft",
        "enteredAt": 1790790700324
      },
      "Comments": {
        "messages": 0,
        "threads": {
          "open": 0,
          "resolved": 0
        },
        "composing": [],
        "unread": 0
      },
      "Revisions": {
        "revision": 1,
        "pendingProposals": 0
      }
    },
    "createdAt": 1790790700324,
    "createdBy": "alice",
    "updatedAt": 1790790700324,
    "updatedBy": "alice"
  },
  "meta": {
    "requestId": "0ab67d9c-70d3-442b-b5f2-7c9377174d23"
  }
}
```

The response is 201. The note's `data` holds its own fields, and
`behaviors` the fields its behaviors add, under each behavior's name:
Workflow's `status` and `enteredAt`, Comments' `messages`, `threads` and
`composing`, and Revisions' `revision` and `pendingProposals`. They never collide with the note's own fields,
which could hold a `status` of their own. Only a behavior's operations
change its fields: a create or an update writes `data`, and a name it
does not declare there is 422. `seq` is the sequence of the note's last
event, and the response sends it as the `ETag`, `"1"`. Without an `id`, the
engine makes a random UUID. The fields come back as the engine stores
them: each scalar value in the canonical form its scalar defines (an
email lowercased, a color as `#RRGGBBAA`), and each absent field that
declares a default with it, on a create; an update fills no default. A
body may also carry `behaviors`, the
parameters a create gives the note's behaviors by name, such as the links
and blockers it holds from its create;
[create parameters](/superschematic/guides/engine-behaviors/#create-parameters)
has them.

carol, a reader, may not create one:

```sh
curl -s $API/schemas/notes/instances \
  -H 'authorization: Bearer carol-token' -H 'content-type: application/json' \
  -d '{"data": {"title": "Mine"}}' | jq
```

```json
{
  "type": "about:blank",
  "title": "Forbidden",
  "status": 403,
  "detail": "carol may not write notes in namespace default",
  "code": "forbidden",
  "requestId": "4dd339ca-b651-4f99-9256-f3d958e8fddb"
}
```

An update is a JSON merge patch (RFC 7386): a member replaces the note's
member, a nested object merges, `null` removes the member, and a list
replaces the list. `If-Match` names the sequence you last read; the engine
checks it inside the write, and answers 412 `seq_mismatch` when the note
has moved on since.

```sh
curl -s -X PATCH $API/schemas/notes/instances/launch \
  -H 'authorization: Bearer alice-token' -H 'content-type: application/merge-patch+json' \
  -H 'if-match: "1"' -d '{"body": "Ships in the fall.", "tags": null}' | jq -c '.data | {data, behaviors}'
```

```json
{"data":{"title":"Launch","body":"Ships in the fall."},"behaviors":{"Workflow":{"status":"draft","enteredAt":1790790700324},"Comments":{"messages":0,"threads":{"open":0,"resolved":0},"composing":[],"unread":0},"Revisions":{"revision":2,"pendingProposals":0}}}
```

`GET $API/schemas/notes/instances` lists notes in creation order, a page
at a time (`limit`, and the `next` cursor as `cursor`), `GET` on a note
reads it, and `DELETE` removes it.

A field whose JSON is longer than 64 KiB, a long body or a step's result
document, is stored once in the engine's value store, under the SHA-256
of its canonical JSON, and the note's row keeps a small ref in its place:
a write that leaves the field alone, and a lease's heartbeat, never
rewrites it. Reads return the value as they always do. Add
`?valueRefs=true` to a list or a get to receive the ref instead,
`{"$value": "<hash>", "bytes": <n>}`, with the pointers to the refs in
the instance's `valueRefs`, and read a value when you need it from
`GET $API/values/<hash>`, which answers a caller who may read the note's
schema. The engine's README, `runtime/engine/README.md` ("The value
store"), has the rules.

`where` filters a list by equality, a JSON object in the query: each
member a note's own field that holds a string, a number or a boolean, by
its name, or a behavior's field a list filters on, by its qualified name,
the behavior's name, a dot and the field's, such as `Workflow.status`,
with a value or a list of values any of which the note holds, `null`
meaning none:

```sh
curl -s -G $API/schemas/notes/instances -H 'authorization: Bearer carol-token' \
  --data-urlencode 'where={"Workflow.status": ["review", "published"]}' | jq '.data.items[].id'
```

A page keeps creation order. A filter an index serves, `Workflow.status`
or a unique field, reads only the notes that match; another
reads at most 1000 notes past the cursor per page, so its page can hold
fewer notes than `limit`, even none, while `next` is not null. Read on
until `next` is null.

### Unique fields and lookups

`@unique` or `@key` on a field of the instance type, or a unique
`@index` over several, makes the engine refuse a second instance with the
same value in the namespace: the create or the update is 409 `conflict`,
with the fields in `details.fields`. An instance that lacks the field
does not count, so any number of instances can lack it. A field like
that is a string, a number or a boolean; the engine refuses `@unique` on
a list or an object when you define the schema.

`GET $API/schemas/{name}/lookup?key=<JSON>` returns the instance whose
unique fields hold the key's values, or 404. The key is a JSON object in
the query, never part of the path, so a value may hold a slash. For a
`models` schema whose `slug` is `@unique`:

```sh
curl -s -G $API/schemas/models/lookup -H 'authorization: Bearer carol-token' \
  --data-urlencode 'key={"slug": "openai/gpt-5"}' | jq .data.id
```

A client that syncs an outside collection looks each item up by its key
and creates the ones it does not find; a create that races another for
the same key is 409, after which a lookup finds it.

## Behaviors

Each behavior operation on an instance is a route:
`POST .../instances/{id}/operations/{operation}`, with the operation's
parameters as the body, an optional `If-Match`, and an optional
`Preconditions` header for the behaviors that check one, such as a
lease's token
([refusals and preconditions](/superschematic/guides/engine-behaviors/#refusals-and-preconditions)).
A few operations run
on the whole schema instead, such as `Search`'s `search` and `Queue`'s
`claimNext`, at `POST .../schemas/{name}/operations/{operation}`
([schema-level operations](/superschematic/guides/engine-behaviors/#schema-level-operations)).
And a few run across the namespace, on the behavior's own tables in every
schema that composes it, such as Comments' `inbox`, at
`POST /namespaces/{namespace}/behaviors/{behavior}/operations/{operation}`.
They are the behavior's, not a type's: no schema's routes, describe
document or typed client has them
([namespace operations](/superschematic/guides/engine-behaviors/#namespace-operations)).
The README's
[core behaviors](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md#core-behaviors)
section lists every operation, guard and config change of each.

This example uses three behaviors. The core also declares
`Dependencies`, `Links` and `Rollups`, which reach other instances,
`Search`, full-text search over a type's text fields and, optionally,
vector search over embeddings an outside embedder computes, `Reactions`,
whose rules the engine's [runner](/superschematic/guides/engine-behaviors/#the-runner)
applies after a change commits, `Constants` and `Variants`, which keep
fields as their create set them and type a JSON field by another field's
value, `Branches`, which makes each instance the root of a version
graph whose drafts merge into its primary line, and the behaviors for
business records: `Timers`, deadlines that move an instance on when
nobody does, `StateRules`, which holds fields to the Workflow state an
instance is in, `Numbering`, which gives each instance a number a person
reads, and `Approvals`, sign-offs a move of its status waits for;
[Engine behaviors](/superschematic/guides/engine-behaviors/) covers them. [Work queues](/superschematic/guides/work-queues/) covers
`Lease`, `Assignment`, `Queue`, `Presence`, `Blueprint`, `Budget` and
`Retries`, which make instances claimable work.

### Workflow

alice sends the note to review:

```sh
curl -s $API/schemas/notes/instances/launch/operations/transition \
  -H 'authorization: Bearer alice-token' -H 'content-type: application/json' \
  -H 'if-match: "2"' -d '{"to": "review"}' | jq .data
```

```json
{
  "from": "draft",
  "to": "review"
}
```

The move from review to published names `notes.publish`, which alice does
not hold. The policy lets her write, and Workflow refuses the move:

```sh
curl -s $API/schemas/notes/instances/launch/operations/transition \
  -H 'authorization: Bearer alice-token' -H 'content-type: application/json' \
  -d '{"to": "published"}' | jq
```

### Comments

```sh
curl -s $API/schemas/notes/instances/launch/operations/post \
  -H 'authorization: Bearer carol-token' -H 'content-type: application/json' \
  -d '{"body": "Which fall?"}' | jq .data
```

```json
{
  "id": 1,
  "author": "carol",
  "state": "posted",
  "body": "Which fall?",
  "blocks": [],
  "mentions": [],
  "reactions": {},
  "createdAt": 1790790700450,
  "postedAt": 1790790700450,
  "edits": 0,
  "pinned": false,
  "replies": 0,
  "participants": [
    "carol"
  ]
}
```

A post is beside the note: it writes the conversation's own tables, so
the note's `seq`, ETag and `updatedAt` stay where they were, and a lease
on the note does not stop a reply. Every message is top-level, a thread
of its own, or a reply in one: `thread` names the top-level message, and
threads are one level deep. A message may carry `mentions` and
`blocks` beside its Markdown `body`: a `ref` to another instance the
poster may read, an `action` card with a title and a status, a `code`
block anchored at lines of a file, or an `attachment` that describes a
file the deployment stores ([Code blocks and
attachments](#code-blocks-and-attachments)). Its
author edits it (`edit`, whose earlier text `listEdits` keeps) and
deletes it (`deleteMessage`, which keeps its place in the thread);
anyone who may write reacts to it with an emoji (`react`, `unreact`),
pins it (`pin`, `unpin`), and the thread's author resolves the thread
(`resolve`, `reopen`). `listMessages` reads a page of the top-level
messages, or with `thread` of a thread's replies, with `before`,
`after` or `around` a message id, `getMessage` reads one, and
`listPinned` the pinned ones ([Search and pinned
messages](#search-and-pinned-messages)). The config
narrows who may do what: `editWindowMs`, `maxBodyLength`, `blocks` and
`attachments`, and `moderatePermission`, `pinPermission`,
`resolvePermission` and `anchorPermission` for a caller who acts on
another's message.

A reply that is written as it goes, a model's or a person's typing it
out, is streamed instead of posted. `begin` takes the message's id and
its place in the thread at once, `composing`, with an empty `body`. Its
author adds text with `appendDraft`, `{ message, text }`, which appends
no event and returns where the text went, `{ message, offset, length }`
in code points, and posts it with `finish`, which takes the draft as the
body, or a `body` in its place, and `blocks` and `mentions` as a post
does. The message's `postedAt` is then when it was finished, its
`createdAt` still the `begin`, so it keeps its place.
[Typed wrappers](#typed-wrappers-for-your-schemas) streams one from
TypeScript.

A reader that reads the message meanwhile gets the draft so far as its
`body`. One whose author stops says `interrupt`, which keeps what it
wrote, `interrupted`; one whose author appends nothing for the config's
`composeTimeoutMs` (a minute by default) is interrupted by the runner. A
caller may have `maxDrafts` messages composing on a note at once (five
by default); `begin` refuses the next one `too_many_drafts`.

The note's Comments fields count the conversation: `messages`, the
messages that stand, posted or interrupted; `lastMessageAt`, the latest
one's `postedAt`; `threads`, `{open, resolved}`; and `composing`, who is
writing one now. A post moves them without moving the note, so the event
it appends carries the message rather than a patch.

Comments also declares three signals, messages about the note that the
engine hands to the event streams open on it and keeps nowhere
([signals](#signals) has the route): `typing`, `{ thread? }`, and
`viewing`, `{}`, which a client sends every few seconds while its person
types or looks at the conversation, and `draft`, `{ message, offset,
text }`, which `appendDraft` sends with each chunk, so a reader shows a
streamed reply as it is written without reading it again.

#### Code blocks and attachments

A `code` block points at lines of a file at a revision, and carries the
text of those lines as the poster captured it, so a reader sees it with
no repository:

```json
{ "kind": "code", "repo": "github.com/acme/shop", "path": "src/orders.rs", "revision": "9c1f2e7", "lines": [40, 48], "snippet": "fn place(order: &Order) {" }
```

`path` is relative: no leading or trailing `/`, no `\`, and no empty,
`.` or `..` part. `lines` are the first and the last, counted from 1, the
first at most the last, and the `snippet` holds at most 8000 code
points. The engine knows no repository. When the code moves, a caller
that does, a git extension after a push say, moves the block to the same
code at the new revision with `moveAnchor`, `{ message, block, revision,
lines }`, `block` its index in the message's blocks. A move is no edit:
it changes nothing the author wrote, so it is not held to
`editWindowMs`, and `edits`, `editedAt` and `listEdits` stay as they
were. The block keeps the anchor it was given with in `original`, and
records the last move:

```json
{ "kind": "code", "repo": "github.com/acme/shop", "path": "src/orders.rs", "revision": "e41b07c", "lines": [44, 52],
  "snippet": "fn place(order: &Order) {", "original": { "revision": "9c1f2e7", "lines": [40, 48] },
  "moves": 2, "movedAt": 1790790900000, "movedBy": "service:git-anchors" }
```

Its author may move it, and so may a caller holding the config's
`anchorPermission`, which suits a bot that should hold nothing else, or
`moderatePermission`. Comments vetoes `no_block` for an index past the
message's blocks, `not_code` for a block of another kind, and
`anchor_unchanged` for the anchor it already has. An edit that gives a
code block back unchanged at its index keeps its moves; one that changes
it starts it over.

An `attachment` block describes a file the deployment stored through an
upload route of its own, in a [bucket](/superschematic/guides/buckets/)
say. The engine keeps the description, never the bytes:

```json
{ "kind": "attachment", "uri": "https://files.acme.test/7c1e", "name": "trace.txt", "mediaType": "text/plain", "bytes": 2048, "sha256": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08" }
```

The config's `attachments` says what one may describe: `schemes`, the
URI schemes its `uri` may use, `["https"]` when absent and always the
whole list, so `["bucket"]` refuses `https`; `mediaTypes`, each
`type/subtype` or `type/*`; and `maxBytes`. A block outside them is
vetoed `attachment_not_allowed`, its details `{ block, member, value,
allowed }`. An `https` URI must name a host. A config narrowed later
leaves posted blocks as they are, and an edit that gives such a block
back is not held to it again.

What an attachment block is, and is not:

- The `uri` is what the poster wrote. The engine never fetches it and
  never checks the `sha256` against anything; it checks the scheme, the
  media type and the size the poster gave, nothing more.
- No config may list `javascript`, `vbscript`, `data`, `file`, `blob` or
  `about`, the schemes that run code or carry the bytes themselves.
  Still, a client links a `uri` only by a scheme it knows, `https` or a
  scheme of your own it resolves itself (`bucket:shop-files/7c1e`), and
  shows any other as text: never put an unchecked `uri` in an `href` or
  a `src`, since a message posted before the config changed keeps its
  blocks.
- The `name` is the poster's too: show it as text, and name a download
  yourself rather than write it to a path.
- Downloads go through your route, which decides who may read the file.
  A reader who may read the message is not thereby allowed the file, and
  the engine asks nothing of a bucket. A reader that downloads it can
  check the bytes against `sha256`.

#### Search and pinned messages

`listPinned`, `{ limit?, cursor? }`, reads a note's pinned messages,
top-level and replies, in the conversation's order, each the record
`getMessage` returns. Only a message that stands is pinned:
`deleteMessage` unpins one.

`searchMessages` finds messages by the words of their bodies across the
namespace. Like `inbox` it is a namespace operation, asked of the policy
as `read`, and it finds only messages of the schemas the caller may
read: a `schema` it may not read finds nothing, rather than a refusal
that would say the schema is there.

```sh
curl -s $API/behaviors/Comments/operations/searchMessages \
  -H 'authorization: Bearer alice-token' -H 'content-type: application/json' \
  -d '{"query": "fall", "schema": "notes"}' | jq .data
```

```json
{
  "items": [
    {
      "schema": "notes",
      "instanceId": "launch",
      "message": 1,
      "author": "carol",
      "state": "posted",
      "postedAt": 1790790700450,
      "rank": 1,
      "snippet": [
        { "text": "Which ", "match": false },
        { "text": "fall", "match": true },
        { "text": "?", "match": false }
      ]
    }
  ],
  "next": null
}
```

The query is plain words, all of which a message must hold: the first
eight count, and quotes, `AND`, `OR`, `NOT`, `NEAR` and `*` are words
like any other. `instanceId` (with `schema`) and `thread` (with
`instanceId`, the top-level message and its replies) narrow it. Only the
body of a message that stands, posted or interrupted, is searched: never
a draft, a deleted message or the text before an edit, and never its
blocks. Each hit gives its place in the order, `rank`, from 1 across
pages, and a few words around its matches in parts; it ranks as the
database's full-text index does, so SQLite and Postgres may order hits
differently, and a search reaches its first 1000 hits. Matching ignores
case, and on SQLite accents too, so `cafe` finds `Café`. On Postgres it
ignores accents only where the migration that made Comments' index found
the `unaccent` extension, or could create it: on a database without it,
the index folds case but keeps accents, so `cafe` does not find `Café`,
and an `unaccent` added later changes no index made before. The MCP tool
is `comments_search_messages`.

#### Acting for someone

A message posted or begun by a caller [acting for
someone](#callers-and-the-access-policy) records that subject as its
`for`; the caller is still its `author`. An edit, a reaction and a
resolve each record the caller's own `for` too, in `listEdits`,
`listReactions` and `resolved.for`. It is an attribution, never a grant:
a check that only the author passes compares the caller's own subject,
so an agent acting for alice may not edit or delete alice's messages,
nor alice the agent's, and what a call writes for its caller, a read
marker, a follow, a reaction's `mine`, a draft, is the caller's.

The person a message was written for follows its thread, so replies
reach her, and gets no delivery of the message itself, as its author
does not. Her inbox and her `unread` count it as another's message until
she reads it. An inbox item and a delivery carry the message's `for`, so
a notifier can say "the reviewer agent, for alice".

#### Read state and follows

Each caller has a read marker on a note's conversation and one on each
thread. `markRead`, `{ upTo, thread? }`, moves the caller's marker past
the messages up to an id, on the top-level messages or with `thread` on
that thread's replies, and never moves it back. alice has read carol's
question:

```sh
curl -s $API/schemas/notes/instances/launch/operations/markRead \
  -H 'authorization: Bearer alice-token' -H 'content-type: application/json' \
  -d '{"upTo": 1}' | jq .data
```

```json
{
  "readUpTo": 1,
  "unread": 0
}
```

Markers count in stands, not ids. A message's `stand` is its place in
the order the conversation's messages came to stand, given when it is
posted, finished or interrupted, so a streamed reply that began before a
message alice read and finished after it is still unread to her.
`listMessages` returns the caller's marker as `readUpTo`, absent until
there is one, and a client shows a message of another as unread when its
`stand` is above it. The note's `unread` field is the reader's own count
of the top-level messages of others above her conversation marker: two
callers read two values, and a conversation she has never marked read,
nor posted in, counts 0 for her rather than everything.

A caller follows each thread it posts in and each it is mentioned in.
`follow`, `{ thread, on }`, follows another or stops, until the caller
posts there or is mentioned again. Neither call appends an event or moves
the note, and both ask the policy `read`, so carol, a reader, may call
them.

#### The inbox and deliveries

Comments declares three [namespace
operations](/superschematic/guides/engine-behaviors/#namespace-operations),
which run on its tables across every schema of the namespace that
composes it. `inbox`, `{ kinds?, unread?, limit?, cursor? }`, is the
caller's, newest first: each message that mentions it, each thread it
follows that has replies of others, and each conversation it has marked
read that has top-level messages of others since, over the schemas it
may read. Each item names the latest such message and how many the
caller has not read; one with none unread is done. Had carol mentioned
alice in a reply, alice's inbox would hold it:

```sh
curl -s $API/behaviors/Comments/operations/inbox \
  -H 'authorization: Bearer alice-token' -H 'content-type: application/json' \
  -d '{"unread": true}' | jq .data
```

```json
{
  "items": [
    {
      "kind": "mention",
      "schema": "notes",
      "instanceId": "launch",
      "message": 2,
      "thread": 1,
      "author": "carol",
      "postedAt": 1790790700610,
      "excerpt": "@alice the first week of October?",
      "unread": 1
    }
  ],
  "next": null
}
```

A mention is done once alice's marker passes it, the thread's for a
reply. The MCP tool is `comments_inbox`, in every list whose caller may
read a schema that composes Comments.

The engine sends nothing. When a message comes to stand, Comments records
a delivery for each subject that should hear of it: each subject it
mentions, a person's, an agent's (`agent:reviewer`) or a group's
(`role:editors`), with the reason `mention`, and each follower of its
thread but its author, with the reason `reply`; a subject both is one
delivery with both reasons. Something outside the engine claims them
with `claimDeliveries`, `{ subjects?, prefix?, limit?, ttlMs? }`, under a
token that lapses after `ttlMs`, so two claimers never send one twice,
and settles each with `settleDeliveries`, `{ token, ids, outcome }`:
`sent`, `dropped`, or `failed`, which makes it due again after a backoff
until the config's `maxAttempts`. A delivery whose subject has read its
message by the time it is claimed is dropped instead of returned.
Deliveries are claimed only for a schema whose Comments config names a
`deliverPermission`, `{ "name": "Comments", "config": {
"deliverPermission": "notes.deliver" } }` say, by a caller holding it,
and the policy is asked `write` for both operations
(`Comments.claimDeliveries` and `Comments.settleDeliveries` under
`permissionPolicy()`). Without one the deliveries still feed the inbox;
the runner removes each after the config's `deliveryRetentionMs`,
thirty days by default. This example's notes name none, so a claim is
409 `vetoed` with the code `not_configured` until they do.

Check the recipient before you send a body. Comments records a delivery
for every subject a message mentions, and every follower, whether or not
that subject may read the schema. A claim returns up to 4000 code points
of the message's body to the claimer, and says nothing of what the
recipient may see. Before a notifier sends the
body, it checks that the recipient may read the instance:

- read the instance as the recipient: `engine.instances.get` with a
  principal of the recipient's subject and their permissions from your
  identity store, which asks the policy as their own read would; or
- ask your policy the same question with the recipient's permissions,
  `<schema>.read` under `permissionPolicy()`.

For a group subject (`role:editors`), check each member you send to. A
recipient who may not read it gets no body: settle the delivery
`dropped`, or send a notice with a link and no text, where signing in
decides.

A deployment runs two claimers: a notifier that claims people's
deliveries and sends them to chat, mail or a phone, and an agent
dispatcher that claims `prefix: "agent:"` and hands each to its agent,
which answers with `begin`, `appendDraft` and `finish`. A dispatcher
acts on `mention` reasons only. An agent mentioned once follows the
thread like anyone, so every later reply in it by someone else is a
`reply` delivery to it; one that answered each would answer every
message of a busy thread, and two agents in one thread would answer
each other without end. It drops those. With the typed client
from [Typed wrappers](#typed-wrappers-for-your-schemas):

```ts
import { commentsNamespaceClient, isCommentsNamespaceVeto, type CommentsDelivery } from './notes.client.ts';

const comments = commentsNamespaceClient(client, 'default');

async function dispatch(ask: (agent: string, delivery: CommentsDelivery) => Promise<void>): Promise<void> {
  const { token, items } = await comments.claimDeliveries({ prefix: 'agent:', limit: 20, ttlMs: 60_000 });
  if (token === null) return;                                           // nothing due
  const sent: string[] = [];
  const failed: string[] = [];
  const ignored: string[] = [];
  for (const delivery of items) {
    if (!delivery.reasons.includes('mention')) {
      ignored.push(delivery.id);                                        // a reply in a thread it follows
      continue;
    }
    try {
      await ask(delivery.subject, delivery);                            // queue the agent's turn
      sent.push(delivery.id);
    } catch {
      failed.push(delivery.id);
    }
  }
  for (const [ids, outcome] of [[sent, 'sent'], [failed, 'failed'], [ignored, 'dropped']] as const) {
    if (ids.length === 0) continue;
    try {
      await comments.settleDeliveries({ token, ids, outcome });
    } catch (error) {
      // The claim lapsed and another claimer took them: they are its now.
      if (!isCommentsNamespaceVeto(error, ['token_stale', 'not_claimed'])) throw error;
    }
  }
}
```

A delivery carries what the agent needs with no other read: the schema,
the instance and the message, its thread, its author, and its body as it
is now. The dispatcher's principal holds the schema's `deliverPermission`
and, under `permissionPolicy()`, `Comments.claimDeliveries` and
`Comments.settleDeliveries`. A mention does not mean the agent may read
the instance: anyone who may post can mention `agent:reviewer`. Before
`ask` hands the agent the body, the dispatcher checks that the agent may
read the instance, as a notifier checks a person (above), by reading it
as the agent's principal or asking the policy with the agent's
permissions, and drops the delivery when it may not. Run the agent as
its own principal, so what it reads next is held to the same policy.

### Your own behaviors

An extension adds a behavior in two halves. The compiler half is a JSON
declaration its Go package registers; the binary's
[`behaviors --out`](/superschematic/reference/cli/) command copies it into
the crate that implements it. The engine half is that crate: a Rust type
that implements the engine's `Behavior` trait, with a parsed config and
its hooks, a handler per operation, a reader per field, guards (which may
refuse a create too), an `initialize` that gets the parameters a create
gives it, and migrations for its own storage, and optionally config
checks, a `validate` that judges the fields a write stores (with
`checked_types` and `instance_schema`), `after_change`, schema-level
operations, reactions and schedules for the runner, and hooks that run
when an instance it references changes. A guard's veto carries a code the
declaration lists, at a create as at any other change, and a caller can
send a behavior a precondition with a write, which its guard checks:
`Lease`'s token is one (`Preconditions` header over HTTP).

The behavior's registration names its crate, and a build of a schema
whose types compose the behavior writes the project's engine crate, which
compiles the core's behaviors and the extension's into the engine, with a
Node-API addon over them as its `napi/` member. A TypeScript server loads
that addon in place of the core's, with the engine option `addon` or
`SUPERSCHEMATIC_ENGINE_ADDON`, names the behavior in `behaviors`
(`behaviors: ['acme.Rating']`), and passes the extension binary's
`json-schema` output, which declares it, as `metaSchema`, and its
invocation policy and vendor keys as `tools`. A generated TypeScript
server does all of it itself: its image's engine stage builds the addon
and names it, and `stack dev` builds it and names it for the server's
process, with nothing set by hand. `acme.Rating`
in `examples/acme-schematic` is the worked example, and
[Write an extension](/superschematic/extending/write-an-extension/#a-behavior)
walks through it. A behavior written in TypeScript, with
`@superschematic/engine/testing`'s `defineBehavior`, runs only on the
engine's test addon (`scripts/engine-napi.sh --js-behaviors`), through
its bridge, and the shipped addon refuses it: it is for tests and
fixtures, not a deployment.

A behavior's hooks reach the instance they run on, the behavior's own
columns and tables, and the rest of the namespace as the caller: they
read other instances and change them through their operations, and the
access policy is asked at each step. Beyond one instance, a behavior
reads its own columns across every instance of its schema with SQL, on a
read-only relation the engine names (`sql().instances()`) and a migration
can index; creates instances wherever it may invoke a writing operation
(`instances().create`), with their behaviors' create parameters, so a
parent's children commit with it, linked and blocked; and runs
schedules at an interval its schema's config can set, or turn off. A
behavior that keeps values of the schema's other types in its own
tables reads those types' fields in `parse_config` (`target.types()`),
which holds them to the schema's checks and its compatibility rule, and
checks a value against one with `validate(type, value)`. Which types a
config reads may depend on the config and the document only, not on the
other schemas, since a version is checked against the next with no other
schema in reach; a define or publish refuses a config whose reads do. A
behavior that keeps an object with large members in its own tables, a
copy of the instance's fields say, keeps it through the value store
(`values().stow`, `load` and `release`), as Revisions does, so the value
is stored once however many rows hold it. A schedule's
run may write the behavior's own tables directly, but only what no
operation returns, history nothing pins say; a change a read shows goes
through an operation it invokes. The README's
[behaviors](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md#behaviors)
section has the whole interface.

## The event log

Every write appends one event in its own transaction: a create, an update,
a delete, a behavior operation that writes, a publish, and the define of
a draft. The cursor orders the whole log:

```sh
curl -s "$API/events?after=0" -H 'authorization: Bearer carol-token' \
  | jq -c '.data.events[] | [.cursor, .kind, .actor, .change.operation]'
```

```
[1,"define","engine-notes",null]
[2,"publish","engine-notes",null]
[3,"create","alice",null]
[4,"update","alice",null]
[5,"operation","alice","transition"]
[6,"operation","bob","transition"]
[7,"operation","carol","post"]
[8,"operation","carol","propose"]
[9,"operation","bob","approve"]
```

A page is `{events, next, more}`; read on with `after` set to `next`.
`schema` and `instanceId` narrow it, and events of schemas the caller may
not read are left out. An event's `change` is the instance for a create,
`{data, behaviors}`, a merge patch of that for an update, and `{behavior,
operation, params, patch}` for an operation, its `patch` the same, so
applying the changes in order gives the note as a read returns it. An
operation beside the note, such as carol's post, appends an event with
`seq` null and `beside: true`, whose change is `{behavior, operation,
params, result}`; applying the others skips it. An
operation whose behavior said where the values it wrote came from adds
`attribution`, by field: the behavior and the confidence and source it
gave. A define's is `{hash}`, the draft's hash: a reviewer
watching the log learns a draft waits, and reads it from the draft route.
A member of a change longer than 64 KiB is a ref to the value store, and
the event lists the pointers to its refs in `valueRefs`, so the log never
copies a large field; read the value from `GET $API/values/<hash>`.

Three filters narrow a page further, each a list, repeated or
comma-separated: `kind` keeps those kinds, `behavior` keeps the
operations of those behaviors, and `exclude` drops operations by name.
`?kind=operation&exclude=post` is every operation but posts, and
`beside=false` drops the events of operations beside their instance. A page
still scans its limit of events, so one whose events were all dropped is
empty, and its `next` is past them. `after=head` starts at the last
event: no events, and `next` to read on from.

A write that reaches other instances, such as a delete that clears the
links pointing at it or a create that stamps children, appends an event
on each instance it changes, all in the same transaction. An event the
[runner](/superschematic/guides/engine-behaviors/#the-runner) writes
also carries `cause`, the behavior and the event or schedule that set it
off. An event a principal [acting for
someone](#callers-and-the-access-policy) wrote carries `for`, that
subject, beside `actor`.

With `Accept: text/event-stream` the same route streams. It replays from
`after` (or `Last-Event-ID`, which a reconnecting `EventSource` sends),
sends a `ready` event with the cursor once it has caught up, then waits
and sends each event as it commits:

```sh
curl -sN "$API/events?after=6" -H 'accept: text/event-stream' -H 'authorization: Bearer carol-token'
```

`ready` is a named event, so `EventSource.onmessage` does not receive
it; `addEventListener('ready', ...)` does, and its id is where a
reconnect resumes. `after=head` skips the replay: `ready` comes at once,
then only what commits. The filters work as on the JSON page; when they
drop the last events the stream read, a message with only an `id:` keeps
the client's place, which `EventSource` records without an event. While
it waits it sends a `: keepalive` comment every five seconds. Stop it
with Ctrl-C. The end-to-end test reads the stream from a cursor, then
posts a reply and receives its event.

### Signals

A signal is a message about one instance that the engine hands to the
streams open on it and keeps nowhere: who is typing, who is looking, the
next chunk of a reply being written. It appends no event and moves no
cursor, and a reader that was not connected has missed it. A behavior
declares its signals, each with the schema of its data and who may send
it: a caller who may read the schema, one who may write it, or only the
behavior's own operations, as `appendDraft` sends Comments' `draft`.

A stream opened with `signals=1` also sends the signals of the instances
its `schema`, `instanceId` and `behavior` filters keep, after `ready`, as
named `signal` events with no `id:`, so a reconnect never replays one.
In one terminal:

```sh
curl -sN "$API/events?after=head&schema=notes&instanceId=launch&signals=1" \
  -H 'accept: text/event-stream' -H 'authorization: Bearer alice-token'
```

and in another, carol says she is typing a reply in thread 1:

```sh
curl -s -o /dev/null -w '%{http_code}\n' \
  $API/schemas/notes/instances/launch/signals/Comments/typing \
  -H 'authorization: Bearer carol-token' -H 'content-type: application/json' \
  -d '{"thread": 1}'
```

```
204
```

```
event: signal
data: {"namespace":"default","schema":"notes","instanceId":"launch","behavior":"Comments","name":"typing","data":{"thread":1},"from":"carol","at":1790790703012}
```

The send checks that the behavior declares the signal, asks the access
policy its access with the operation `signal:typing`, and checks the
data against the signal's schema, at most 4096 bytes of JSON. Each
caller may send 20 signals a second on one instance, the engine option
`signals.perSecond`; past it the send is 429 `rate_limited` with
`Retry-After: 1`, and a client sends again later rather than retrying. A
signal arrives at most once and in no order with the events, so a
client shows a typing indicator for a few seconds after the last one,
and a `draft` may arrive after the `finish` event of its message. The
MCP endpoint has no tool that sends one. The README's
[signals](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md#signals)
section has the rules.

This server keeps every event. One that passes `retention` to
`openEngine`, `{ maxAgeMs }`, `{ maxEvents }` or both, has its runner
prune the oldest, each namespace's apart, a count being each namespace's
own, and never one a subscription has yet to handle; `maxHoldMs` bounds
how long a halted subscription, or one in an archived namespace, holds
them. A read from the start, with no `after` or
`after=0`, reads what is kept, from the oldest event. A read or a
stream's resume from a cursor retention has pruned past is 410
`cursor_expired`, whose `details` carry the `floor` to read on from,
taking the gap, and the `head` to start again from. The README's
[retention](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md#retention)
section has the rules.

## Call it from TypeScript

`@superschematic/engine/client` is a typed client of the HTTP API. It
imports nothing of the engine's server side or of Node.js, so it runs in
a browser and a worker runtime as well as in another server:

```ts
import { EngineClient, isVeto } from '@superschematic/engine/client';

const client = new EngineClient({
  baseUrl: 'http://127.0.0.1:8787/api',
  auth: { token: 'alice-token' },
});

const note = await client.instances.create('notes', { title: 'Launch' }, { id: 'launch' });
await client.instances.update('notes', note.id, { body: 'Ships in the fall.' }, { expectedSeq: note.seq });
try {
  await client.instances.invoke('notes', note.id, 'transition', { to: 'published' });
} catch (error) {
  if (isVeto(error, 'Workflow', 'transition_not_allowed')) {
    // a refusal to branch on, with error.vetoDetails
  } else {
    throw error;
  }
}
```

- The calls follow the engine's: `namespaces` (`list`, `create`,
  `archive`, ...), `schemas` (`define`, `publish`,
  `describe`, ...), `instances` (`create` with `behaviors`, `get`, `list`
  with `where`, `lookup`, `update`, `delete`, `invoke` and the
  schema-level `invokeSchema`),
  `events`, `behaviors`, `tools()` and `search()`. A write's
  `expectedSeq` is sent as `If-Match` and its `preconditions` as the
  `Preconditions` header.
- A refusal is an `EngineProblem` with the status, the problem's `code`
  and `issues` at their paths; a behavior's veto is an `EngineVeto` with
  `behavior`, `vetoCode` and `vetoDetails`.
- Credentials are a generated SDK's: an end user's token with
  `refreshToken` on a 401, and a calling service's `serviceCredential`,
  which the HTTP runtime's token sources fill. A 401
  `service_unauthorized` asks the service source for a fresh token once
  and never refreshes the end user.
- `actingFor`, the client's or a call's, is sent as the `Acting-For`
  header: the subject an agent or a service works for. A call's `null`
  sends none. The mount honors it only when its host opts in.
- `client.events.subscribe({ after: 'head' })` is the event stream as an
  async iterable of events and a `ready` per connection. It resumes after
  a dropped connection with `Last-Event-ID`, so it neither repeats nor
  skips an event. With `signals: true` it also hands out each signal as
  `{ type: 'signal', signal }`, and `client.signals.send({ schema,
  instanceId, behavior, name, data })` sends one; a 429 `rate_limited`
  is not retried.
- `reconcile(client, { handle, cursor })` runs a handler per event, in log
  order, from the cursor its store keeps, retrying a failing event rather
  than skipping it: a controller's loop.

The README's
[client](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md#the-client)
section has every call and option, and
[Work queues](/superschematic/guides/work-queues/#write-a-worker) builds a
worker on it.

### Typed wrappers for your schemas

The client is generic over schema names: `create` takes any object and an
operation any parameters, so a misspelled field, state or link name
reaches the server and comes back as a refusal. `superschematic
engine-client` writes a module that types the client for your schemas,
from their documents and the behaviors' declarations:

```sh
superschematic engine-client --out src/notes.client.ts schemas/notes.schema.json
```

```ts
import { EngineClient } from '@superschematic/engine/client';
import { isNoteVeto, notesClient } from './notes.client.ts';

const client = new EngineClient({ baseUrl: 'http://127.0.0.1:8787/api', auth: { token: 'alice-token' } });
const notes = notesClient(client);

const note = await notes.create({ title: 'Launch' }, { id: 'launch' });   // data: NoteFields
note.behaviors.Workflow.status;                                           // 'draft' | 'review' | 'published' | 'archived'
await notes.transition('launch', { to: 'review' });                       // { to: 'publshed' } fails to compile
await notes.post('launch', { body: 'Ships in the fall.' });               // returns a NoteCommentMessage
await notes.propose('launch', { patch: { body: 'Ships on the first.' } }); // patch: NotePatch
try {
  await notes.transition('launch', { to: 'review' });
} catch (error) {
  if (!isNoteVeto(error, 'Workflow', 'already_in_state')) throw error;   // codes Workflow lists
}
```

The module types the signals too. Each signal a behavior declares has a
type for its data, `NoteTypingSignal`, `NoteViewingSignal` and
`NoteDraftSignal`, and `isNoteSignal` tells a note's signals from the
other messages of a stream and types their data. Each signal a caller
may send has a method, `sendTyping` and `sendViewing`; `draft` has none,
since only `appendDraft` sends it. A streamed reply, and a reader that
follows it:

```ts
import { isNoteSignal, type NoteDraftSignal } from './notes.client.ts';

// The reader opens the stream before it reads, so it misses no chunk.
const drafts = new Map<number, string>();
const stream = client.events.subscribe({ after: 'head', schema: 'notes', instanceId: 'launch', signals: true });
void (async () => {
  for await (const message of stream) {
    if (isNoteSignal(message, 'Comments', 'draft')) {
      const { message: id, offset, text }: NoteDraftSignal = message.signal.data;
      const held = drafts.get(id) ?? '';
      if (offset === Array.from(held).length) drafts.set(id, held + text);    // offsets count code points
      else if (offset > Array.from(held).length) drafts.set(id, (await notes.getMessage('launch', { message: id })).body);
    }
  }
})();

// The writer.
const reply = await notes.begin('launch', { thread: 1 });                // a NoteCommentMessage, state 'composing'
await notes.sendTyping('launch', { thread: 1 });                         // { thread: '1' } fails to compile
await notes.appendDraft('launch', { message: reply.id, text: 'The first week ' });
await notes.appendDraft('launch', { message: reply.id, text: 'of October.' });
await notes.finish('launch', { message: reply.id });                     // state 'posted', its body the draft
```

A reader also takes the record from a `finish`, `interrupt`,
`deleteMessage` or `purge` event and drops the draft it held, and
ignores a `draft` whose offset is below what it holds, one the read
before it already had.

`markRead`, `follow`, `moveAnchor` and `listPinned` are a note's
operations, typed as any other. A message's blocks are typed twice: what
`post`, `finish` and `edit` give is a `NoteCommentBlock`, of the kinds
the config allows, and what a record holds is a `NoteCommentPostedBlock`,
whose code block may also hold `moveAnchor`'s `original`, `moves`,
`movedAt`, `movedBy` and `movedFor`; an attachment that leaves out its
`sha256`, or a code block under a config that allows none, fails to
compile. Every method takes the client's per-call options, `actingFor`
among them:

```ts
const posted = await notes.post('launch', {
  body: 'The total rounds twice.',
  blocks: [{ kind: 'code', repo: 'github.com/acme/shop', path: 'src/orders.rs', revision: '9c1f2e7', lines: [40, 48], snippet: 'fn place(order: &Order) {' }],
}, { actingFor: 'alice' });                                             // posted.for === 'alice'
const moved = await notes.moveAnchor('launch', { message: posted.id, block: 0, revision: 'e41b07c', lines: [44, 52] });
const block = moved.blocks[0];                                          // NoteCommentPostedBlock
if (block?.kind === 'code') block.original;                             // { revision: '9c1f2e7', lines: [40, 48] }
```

A behavior's namespace operations are no schema's, so the module types
them once, named after the behavior: `CommentsInboxParams` and
`CommentsInboxResult` for each, the items `CommentsInboxItem`,
`CommentsSearchHit`, `CommentsDelivery` and `CommentsSettledDelivery`,
`CommentsNamespaceOperations`, `isCommentsNamespaceVeto`, and
`commentsNamespaceClient(client, namespace?)`, whose `inbox`,
`searchMessages`, `claimDeliveries` and `settleDeliveries` call them in
that namespace, the client's own when none is given. `notes.inbox` and
`notes.searchMessages` fail to compile:

```ts
import { commentsNamespaceClient } from './notes.client.ts';

const comments = commentsNamespaceClient(client);
const { items } = await comments.inbox({ unread: true, kinds: ['mention'] });
for (const item of items) {                                             // CommentsInboxItem
  if (item.schema !== 'notes') continue;
  // A mention is read once the marker of its listing passes it: the thread's for a reply.
  await notes.markRead(item.instanceId, item.thread === undefined ? { upTo: item.message } : { upTo: item.message, thread: item.thread });
}
const found = await comments.searchMessages({ query: 'rounds twice', schema: 'notes' });
for (const hit of found.items) {                                        // CommentsSearchHit
  console.log(hit.rank, hit.instanceId, hit.snippet.map((part) => (part.match ? `[${part.text}]` : part.text)).join(''));
}
```

The behaviors' configs narrow the types: a `Workflow`'s states, the names
of a `Links` config with each required link required at create, the
schemas a `Dependencies` blocker may come from, the kinds of block a
`Comments` config lets a post give, and with `Variants` the type of the
field for each value of the one that picks it. An operation's
method takes its declaration's parameters and returns its result, and a
write's `preconditions` take only the behaviors that declare one (Lease's
`token`). The module imports the client and nothing else, so it runs in
a browser too. The example commits `src/notes.client.ts` and uses it in
its end-to-end test; regenerate it when the schema changes, and run
`engine-client --check` in CI to keep it current.

## MCP tools

The MCP endpoint serves one tool per operation of every live schema the
caller may read, `lookup` for a schema with a unique field among them,
one per namespace operation of each behavior they compose, and ten
engine tools: `list_schemas`, `describe_schema`
and `define_schema`, `list_behaviors` and `describe_behavior`, which
list the behaviors the engine runs and return one's declaration, its
config's JSON Schema included, `get_value`, which reads a value of
the value store by its hash, and `list_namespaces`, `create_namespace`,
`archive_namespace` and `unarchive_namespace`. A tool's name is the schema's and the operation's,
in snake case: `notes_create`, `notes_transition`, `notes_list_messages`.
`notes_list` takes `where`, as the route does, as a JSON object.
A tool the policy refuses the caller is left out of the caller's list, so
carol, a reader, sees these:

```sh
curl -s $API/mcp -H 'authorization: Bearer carol-token' -H 'content-type: application/json' \
  -H 'accept: application/json, text/event-stream' \
  -d '{"jsonrpc": "2.0", "id": 1, "method": "tools/list"}' \
  | sed -n 's/^data: //p' | jq -r '.result.tools[].name'
```

`notes_mark_read` and `notes_follow` ask `read`, so a reader has them.
`comments_inbox` is one of the tools of the namespace operations of the
behaviors the caller's schemas compose, named after the behavior; the
policy's question for each, with `listing: true`, decides whether the
caller sees it, so carol, who holds no `Comments.claimDeliveries`, does
not see `comments_claim_deliveries` or `comments_settle_deliveries`.

`define_schema` and the namespace tools name their schema or namespace
only when called, so the list asks the policy whether the caller may
`define`, or `manage` namespaces, at all: this policy gives `define` to
`schemas.define` alone and refuses every caller `manage`, so carol sees
neither, and a call she makes all the same is still refused. The tools
that only read are in every list, each answering with what the caller
may read; the behavior tools ask the policy nothing, since the behaviors
are the server's code. `engineMcp`'s `tools` option narrows a caller's
list further, a session limited to one schema's tools say. Where a schema
composes `Search`, one more tool, `search`, searches every such schema the
caller may read ([Engine behaviors](/superschematic/guides/engine-behaviors/#searching-every-schema)).
No tool publishes: a draft that `define_schema` stores goes live only
through the HTTP publish route.

Each tool's `_meta` carries guidance under
`superschematic/operation-guidance`, in the members an SDK tool's
`@docs` fills: when to call it, when to call another, what it returns,
and the vetoes it can meet with the usual correction. The engine
computes it from the behaviors' configs. `notes_transition`'s `useWhen`
reads "Use to move status from draft to review; from review to draft or
published; from published to archived. The moves review to published
and published to archived need permission notes.publish; without it the
call is forbidden.", and `notes_propose`'s names `notes.review`, the
permission an approval needs.

An MCP client connects to `http://127.0.0.1:8787/api/namespaces/default/mcp`
with the header `Authorization: Bearer <token>`. The end-to-end test uses

## Change the schema over HTTP

dana holds `schemas`, so the policy lets her define drafts
(`POST $API/schemas`, the document as the body) and publish them
(`POST $API/schemas/notes/publish`). A draft that adds a required field is
refused, since a note the live version accepts need not have it:

```sh
jq '.types.Note.fields += [{"name": "owner", "typeRef": {"name": "string"}, "required": true}]' schemas/notes.schema.json \
  | curl -s $API/schemas -H 'authorization: Bearer dana-token' -H 'content-type: application/json' -d @- \
  | jq '{status, code, changes: .details.changes}'
```

```json
{
  "status": 409,
  "code": "incompatible_change",
  "changes": [
    {
      "path": "Note.owner",
      "message": "field Note.owner is added as required"
    }
  ]
}
```

Before writing a draft, `GET /api/behaviors` lists the behaviors the
engine runs, and `GET /api/behaviors/Workflow` returns one's declaration:
the JSON Schema of its config, its operations and the codes its vetoes
carry. A draft the rule allows is stored, with a `define` event in the
log, and the publish route makes it the live version. This server publishes its schema file each time it starts,
so change the file rather than the live version: after a version with a
field the file lacks goes live over HTTP, the next start refuses the file.
