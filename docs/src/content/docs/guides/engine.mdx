The other guides generate code from a schema. Development mode runs a
schema with no generated code. Your server hands the handler the schema as
JSON while it runs; the handler keeps each version of it and its rows in
one SQLite file, and serves them over HTTP, a server-sent event stream and
MCP. A type in the schema composes behaviors: rules that add fields,
operations and checks to it, such as a state machine, a conversation or
reviewed revisions.

This guide builds `examples/engine-notes`, a notes server. A note moves
from draft through review to published, collects comments, and keeps its
revisions; a reader can propose a change that an editor approves. Every
code block that names a file is quoted from the example, which CI
type-checks and tests on Node.js and Bun, so what you read here runs.
[Development mode](/superschematic/guides/development-mode/) is the
reference: every request, route, rule of the access policy and answer.

## What development mode is

A project's schemas run in one of three modes (D117 in
[docs/DECISIONS.md](https://github.com/parable-work/superschematic/blob/main/docs/DECISIONS.md)).
Development keeps rows as JSON in fixed tables, so a publish takes effect
at once and may rename, retype, remove and tighten. Runtime gives each
type its own table, whose DDL a publish plans. Compiled is the build. The
schemas are the same in all three.

- **The handler is the behaviors' core.** `@superschematic/rules-handler`
  is the Rust request handler built for WebAssembly
  (`runtime/rules-handler/typescript`). The behaviors run in the core it
  embeds, the Rust library every language's adapter embeds, so a note's
  Workflow is the same rules a table's is.
- **The server is yours.** The handler does no I/O. The library runs it
  over a store, a SQLite connection here, and answers the Fetch API's
  `Request` with a `Response`, so any server that takes a Fetch handler
  serves it. The example listens with `@hono/node-server`, on Node.js and
  on Bun.
- **Nothing in a schema names the mode.** The notes schema is a General
  schema in the JSON data form; the same document publishes in runtime
  mode, and its class (`format --to=ts`) builds as a table.

`superschematic-dev` serves the same handler from Rust, a server you run
with no code of your own; the example's smoke serves the SQLite file the
TypeScript host wrote with it.

## Set up

Nothing is published yet, so the example builds from the checkout. From
the repository root, after `make setup`:

```sh
examples/engine-notes/scripts/check.sh
```

It builds the HTTP runtime and `@superschematic/rules-handler`, which
needs cargo and the `wasm32-unknown-unknown` target, builds
`superschematic-dev`, links them into the example's `node_modules`,
type-checks the example, and runs its tests under Node.js 24 and Bun. The
last line it prints is `engine-notes: ok`.

## The schema

The schema is a General schema in the JSON data form, one file:

<Snippet example="engine-notes" file="schemas/notes.schema.json" />

- **`Note` is the type.** A route names it: `/schemas/Note`. A row's key is
  `id`, which a create may give.
- **The fields** are the note's own: a required `title` of at most 200
  characters, a `body` and a list of `tags`. A write is held to them.
- **The behaviors** add to a note. `Workflow` gives it a status that moves
  only along the listed transitions, two of them behind the
  `notes.publish` permission. `Comments` gives it a conversation.
  `Revisions` keeps a revision at every change, and with its `review`
  config a reader can propose a change for a holder of `notes.review` to
  approve.

`superschematic format --to=json` writes this form from a TypeScript
class with `@behavior`.

## Open the store and publish the schema

`openNotesDev` opens the handler over a SQLite connection, `bun:sqlite`'s

first time:

<Snippet example="engine-notes" file="src/dev.ts" symbol={['notesSchema', 'openNotesDev']} />

A define keeps the document as the type's draft, and a publish makes the
draft its next version. Every publish is a new version, so the server
publishes only when `Note` is not live: a restart over the same file keeps
the notes and the version they are at.

### The compatibility rule

There is none. A version may rename, retype, remove and tighten, and a
stored note the new version no longer describes fails the publish, which
changes nothing and answers `409 conflict` with each failing row. The
example's restart test adds a required field the stored note lacks:

<Snippet example="engine-notes" file="test/notes.dev.test.ts" from="// A required field the stored note lacks" to="assert.ok(refused.body.details.rows.length > 0);" />

Publish again with `?discard=true` to delete the rows it fails
([Publishing with no compatibility rule](/superschematic/guides/development-mode/#publishing-with-no-compatibility-rule)).

## Callers and the access policy

The host keeps authentication: `authenticate` reads a request's caller,
and a request it reads none from is `401`. The handler asks the access
policy before every request a caller makes, and the policy is data:

<Snippet example="engine-notes" file="src/dev.ts" symbol={['callers', 'authenticate', 'devPolicy']} />

- **Permissions are dotted names**, and one covers every permission
  nested under it: bob's `notes` covers `notes.read`, `notes.write`, and
  the `notes.publish` and `notes.review` the schema's behaviors name.
- **The first rule that matches decides.** A rule matches on `action`,
  `operation`, `schema` and `subject`; in `require`, `{action}` and
  `{schema}` stand for the question's. A question no rule matches is
  refused, `403 forbidden`.
- **A reader may comment.** A post, a reaction, a streamed reply and a
  proposal are writes beside the note, which the second rule lets a
  holder of `notes.read` make. Marking the conversation read is asked as a
  read.
- **The behaviors' own permissions still apply.** The policy lets alice
  call `transition`; Workflow refuses her the move to `published`, which
  names `notes.publish`.

| Token | Subject | Permissions | May |
|---|---|---|---|
| `alice-token` | alice | `notes.read`, `notes.write` | read and write notes, and move them between draft and review |
| `bob-token` | bob | `notes` | everything under `notes`: publish, archive, approve and reject proposals |
| `carol-token` | carol | `notes.read` | read notes, post, reply and react, and propose changes |
| `dana-token` | dana | `schemas` | define and publish schemas; read no notes |

A deployment verifies a signed token or a session in `authenticate`
instead of a table. A server that only its developer reaches may read the
caller from headers with the library's `devCallers()`, as
`superschematic-dev` does.

## Instances

The routes of a type are under `/namespaces/default/schemas/{type}`. A
success is the envelope `{ "data", "meta": { "requestId" } }`, and a
refusal an RFC 9457 problem with the refusal's `code`:

```sh
TOKEN='authorization: Bearer alice-token'
curl -X POST http://127.0.0.1:8787/namespaces/default/schemas/Note/instances \
  -H "$TOKEN" -H 'content-type: application/json' \
  -d '{"id": "launch", "data": {"title": "Launch", "tags": ["launch"]}}'
curl http://127.0.0.1:8787/namespaces/default/schemas/Note/instances/launch -H "$TOKEN"
curl -X PATCH http://127.0.0.1:8787/namespaces/default/schemas/Note/instances/launch \
  -H "$TOKEN" -H 'content-type: application/merge-patch+json' -d '{"body": "Ships soon."}'
curl 'http://127.0.0.1:8787/namespaces/default/schemas/Note/instances?filter[workflowStatus]=draft&sort=-title' -H "$TOKEN"
```

- **A row is flat.** Its own fields sit beside its behaviors' fields, each
  named after its behavior: `workflowStatus`, `commentsMessages`,
  `revisionsRevision`. Only the behaviors' operations change those.
- **A row carries its version** as `_version` and as its `ETag`. A create
  answers `201`; the test's create reads `"1"`, and after two transitions
  the note is at `"3"`.
- **An update is a merge patch.** A delete is `DELETE` on the row.
- **A list filters and sorts** in the query string, as the generated
  servers read them: `filter[title]=Launch`, `filter[title][contains]=aun`,
  `sort=-title`, `limit` and `cursor`
  ([Routes](/superschematic/guides/development-mode/#routes)).

### Unique fields and lookups

A field marked `unique` refuses a second holder with `409 conflict`, as a
table's unique column does. A route that reads a row by a unique field,
the engine's lookup, waits; until then a list filters on it.

## Behaviors

A behavior's operation of a row is a `POST` to
`.../instances/{id}/operations/{operation}`, its parameters the body. It
answers what the operation returns.

### Workflow

`transition` moves the status along a listed transition:

```sh
curl -X POST http://127.0.0.1:8787/namespaces/default/schemas/Note/instances/launch/operations/transition \
  -H 'authorization: Bearer alice-token' -H 'content-type: application/json' -d '{"to": "review"}'
```

It answers `{ "from": "draft", "to": "review" }`. A move with no
transition, or behind a permission the caller lacks, is refused: alice's
move to `published` is `403 forbidden`, and bob's is taken. The row's
`workflowStatus` filters a list.

### Comments

A conversation on the note, every write beside it: a post leaves the
note's version as it was.

- `post` (`{ body }`) answers the message, with its `id`, its `author` and
  its `state`, `posted`; a reply names its `thread`. Edits, deletes,
  reactions, pins and resolving a thread are operations too.
- The note reads its conversation: `commentsMessages`,
  `commentsLastMessageAt`, `commentsThreads` (`{ open, resolved }`) and
  `commentsComposing`, who is writing a reply.
- **A reply may stream as it is written.** `begin` (`{ thread }`) holds
  its place as a message in the `composing` state, `appendDraft` adds to
  its draft, and `finish` posts it. A reader reading midway gets the draft
  so far with `getMessage`, and `commentsComposing` names its author.
- **Each reader has a marker.** `markRead` (`{ upTo }`) moves it,
  `commentsUnread` counts what came after it for the caller, and `follow`
  follows a thread or stops.

### Revisions

Every change keeps a revision, and `revisionsRevision` is the latest. With
`review` in its config, a reader proposes a change rather than making it:

```sh
curl -X POST http://127.0.0.1:8787/namespaces/default/schemas/Note/instances/launch/operations/propose \
  -H 'authorization: Bearer carol-token' -H 'content-type: application/json' \
  -d '{"patch": {"body": "Ships on the first."}, "note": "Adds the date."}'
```

The proposal answers `pending`, with its `id`. `approve` (`{ proposal }`)
needs `notes.review`: bob's writes the patch to the note as its next
revision, and alice's is `403`. `listRevisions` lists them.

## The event stream

`GET /namespaces/default/events` reads the events the behaviors emit, in
order, as a page or, with `Accept: text/event-stream`, as a stream of
server-sent events, which sends a `ready` event once it has caught up.
Workflow, Comments and Revisions emit none, so the notes' stream is
quiet; a behavior such as Schedules writes its runs there
([The event stream](/superschematic/guides/development-mode/#the-event-stream)).

### Signals

A signal is a message about one row that a server delivers to the streams
open on it and keeps nowhere: a streamed reply's next chunk, or a reader
typing. A stream opened with `signals=1` receives them. Comments' `typing`
is a caller's, sent with `POST .../instances/{id}/signals/Comments/typing`;
its `draft` is `appendDraft`'s alone, and a caller's send of one is `403`.

`superschematic-dev` publishes signals to the streams open in its
process; the TypeScript host does not yet. The example's smoke shows them
on `superschematic-dev`, over the file the TypeScript host wrote:

## Call it from TypeScript

In the server's own process, `dev.request(caller, request)` runs a request
as a caller, typed by its kind, and rejects with a `RefusalError` whose
`refusal` carries the code:

```ts
const alice = callers.get('alice-token')!;
const note = await dev.request(alice, { kind: 'get', type: 'Note', id: 'launch' });
const page = await dev.request(alice, { kind: 'list', type: 'Note', limit: 10 });
```

A client in another process calls the routes over HTTP with its bearer
token, as the example's test does with `fetch`.

## MCP tools

`POST /namespaces/default/mcp` is an MCP endpoint over the streamable HTTP
transport, stateless. The handler makes its tools from the live types:
`note_create`, `note_get`, `note_list`, `note_update` and `note_delete`,
one per operation the behaviors declare, such as `note_transition` and
`note_propose`, and `list_schemas`, `describe_schema`, `define_schema` and
`publish_schema`. A caller lists only the tools the policy lets them call.

## Change the schema over HTTP

A holder of `schemas.define` and `schemas.publish` changes the schema while
the server runs:

```sh
TOKEN='authorization: Bearer dana-token'
curl -X POST http://127.0.0.1:8787/namespaces/default/schemas \
  -H "$TOKEN" -H 'content-type: application/json' --data-binary @schemas/notes.schema.json
curl -X POST http://127.0.0.1:8787/namespaces/default/schemas/Note/publish -H "$TOKEN"
```

The publish answers the new version, which the next request reads.
