The other guides generate code from a schema. `@superschematic/engine`
runs a schema with no generated code. Your server hands it the schema as
JSON while it runs; the engine versions the schema, keeps its instances
and an event log in one SQLite file, and serves them over HTTP, a
server-sent event stream and MCP. A type in the schema composes
behaviors: code that adds fields, operations, checks and storage to it,
such as a state machine, comments or reviewed revisions.

This guide builds `examples/engine-notes`, a notes server. A note moves
from draft through review to published, collects comments and keeps its
revisions, and a reader can propose a change for an editor to approve.
CI runs the example's end-to-end test on Node.js and on Bun in the
release candidate run on `main` twice a day. The
[engine README](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md)
is the reference for everything below: every route, status, option and
rule.

## What the engine is

- A TypeScript library for Node.js 24 and Bun. Your server opens it in
  its own process; the engine has no server or process of its own.
- One SQLite file, through the runtime's built-in `node:sqlite` or
  `bun:sqlite`. There is no native addon and no database server.
- One process writes the file. The engine caches each schema version's
  validator and behaviors in the process and announces new events in the
  process, and nothing coordinates either across processes. Run one server
  process per file.
- A schema is one JSON document of kind `General`, with no `imports` and
  no operation sets. Every schema has the operations `create`, `get`,
  `list`, `update` and `delete`, one with a unique field `lookup`, and
  its behaviors add their own.
- It has no roles and no default policy. Your server says who each caller
  is and what each caller may do.

It is not a database server that several processes share, and it does not
run on Postgres. D16 in
[docs/DECISIONS.md](https://github.com/parable-work/superschematic/blob/main/docs/DECISIONS.md)
records the design, what is built and what is still to come.

## Set up

Nothing is published yet, so the example links the engine from the
checkout. From the repository root, after
[setting up the checkout](/superschematic/start/prerequisites/#set-up-the-checkout)
with `make setup`:

```sh
examples/engine-notes/scripts/check.sh
```

It builds the schema runtime, the HTTP runtime, the version graph and
the engine (`bun install --frozen-lockfile` and `bun run build` in each),
links them into the example's `node_modules` (`scripts/link.sh`),
type-checks the example, and runs its end-to-end test with `node --test`
and with `bun test`. The version graph's build compiles its core to
WebAssembly, so it needs cargo and the `wasm32-unknown-unknown` target.
The last line it prints is `engine-notes: ok`.

`scripts/link.sh` links `@superschematic/engine`, and, from the engine's
own install, the packages the example imports: `@superschematic/http-runtime`,
`hono`, `@hono/node-server` and `@modelcontextprotocol/client`, and
TypeScript and the Node.js types for the type-check. Each resolves to the
engine's copy, so the engine and the example share one Hono. The engine
needs `@superschematic/schema-runtime`, `@superschematic/schema-ir`,
`@superschematic/http-runtime` and `superscalar` beside it, which its build
links into its own `node_modules`. It depends on
`@superschematic/versiongraph`, whose engine and SQLite adapter run the
`Branches` behavior over the version graph's WebAssembly core. Its `./http`
entry point also needs `hono`, and its `./mcp` entry point `hono` and
`@modelcontextprotocol/server`.

## The schema

The engine reads a schema in the JSON data form of a schema file, the form
[`superschematic format --to=json`](/superschematic/reference/cli/) writes
from a TypeScript or YAML schema file. The notes schema:

<Snippet example="engine-notes" file="schemas/notes.schema.json" />

- `name` keys the schema's versions and names it in every route and tool.
- The instance type, the one whose instances the engine stores, is the
  type named like the schema or, as here, the only type.
- A field's type is a builtin primitive, a scalar, or an enum or type of
  the document, alone, as a list or as a list of lists. The engine
  refuses a union or a map, which the schema runtime does not check.
- `behaviors` lists what `Note` composes, with each one's config.
  `Workflow` keeps a `status` and moves it only along the listed
  transitions; moving a note from review to published, or from published
  to archived, needs the permission `notes.publish`. `Comments` keeps
  comments on the note. `Revisions` records a revision at every change,
  and its `review` config lets a caller propose a change that someone
  holding `notes.review` approves or rejects.

The engine checks a document with the strict loader of
`@superschematic/schema-runtime`, against the core binary's
[`json-schema`](/superschematic/reference/cli/) output by default, which
admits the core's behaviors, the
[work-queue behaviors](/superschematic/guides/work-queues/) included
(those run once the server registers `@superschematic/engine-workqueue`).
A deployment whose binary registers more behaviors passes that binary's
output as the `metaSchema` option.

You can also write the schema in TypeScript, composing each behavior with
`@behavior(name, config)`, and convert it with `format --to=json`;
[Engine behaviors](/superschematic/guides/engine-behaviors/#compose-a-behavior)
shows both forms.

## Open the engine and publish the schema

<Snippet example="engine-notes" file="src/server.ts" symbol={['notesSchema', 'deployer', 'openNotes']} />

`openEngine` takes the file's path and the access policy (next section),
creates the file if it is absent and brings it up to the engine's
migrations. `define` stores the document as the draft of its name, and
`publish` makes the draft the next live version. Publishing a draft
identical to the live version mints nothing, so the server publishes its
schema file every time it starts.

### The compatibility rule

A new version may change a schema only in ways every instance the live
version accepts still satisfies. A new optional field, a new enum value, a
looser bound and a required field made optional are allowed. A removed or
renamed field, a new required field, a tighter bound and another type are
refused: the engine throws `IncompatibleChangeError`, and the HTTP API
answers 409 `incompatible_change`. To make such a change, publish it under
a new schema name. Each behavior decides which changes to its own config a
new version may make. A new `@unique` field is allowed while no two
stored instances hold the same value, and refused while two do. The README's
[compatibility rule](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md#the-compatibility-rule)
has the full table.

The end-to-end test restarts the server on the same file, first with a
schema that drops `tags`, then with one that adds an optional `pinned`:

<Snippet example="engine-notes" file="test/notes.test.ts" from="// Removing a field" to="engine = openNotes(path, withPinned);" />

The first is refused and the server would not start; the second becomes
version 2, and every stored note stays as it was. The same rule holds for
a draft defined over HTTP; see
[Change the schema over HTTP](#change-the-schema-over-http).

## Callers and the access policy

<Snippet example="engine-notes" file="src/auth.ts" symbol={['callers', 'authenticate', 'policy']} />

- The HTTP runtime's authentication gate calls `authenticate` on every
  route. It returns the caller, a principal with a `subject` and
  `permissions`, or `null`, which answers 401. A real server verifies a
  signed token or looks a session up; the example reads a fixed table.
- The engine asks `policy` before every read and write, with the
  principal, the action (`read`, `write`, `define` or `publish`), the
  namespace, the schema and, for a behavior operation, the operation's
  name. Only `true` allows; anything else is 403 `forbidden`. The policy
  runs synchronously. There is no default: `allowAll` is there for tests.
- Making, archiving and listing namespaces asks the action `manage`,
  with the namespace, no schema, and the operation (`create`, `archive`,
  `unarchive` or `list`). This example makes no namespace while it runs,
  so its policy refuses `manage`.
- A behavior operation asks `write` when it writes and `read` when it only
  reads. This policy lets a reader call `comment` and `propose`, and
  nothing else that writes.
- Where a behavior limits who may do something, its config names a
  permission and the behavior asks the engine's permission matcher. That
  is the HTTP runtime's `hasAnyPermission` unless you pass another, so
  `notes` covers `notes.publish` and `notes.review`. Workflow and
  Revisions check those after the policy has allowed the write. A server
  that replaces the matching rule passes the same `permissionMatcher` to
  `openEngine` and to the HTTP options.
- Another service in a stack can call the engine too (D37). Pass the HTTP
  runtime's `authenticateService` beside `authenticate`, and the
  principal carries the verified caller in `service`. A service that
  forwards an end user's token acts as that end user. One that sends no
  `Authorization` header stands in for an end user, as
  `service:<deployable>` with no permissions, so the policy decides what
  it may do by `principal.service.deployable`, and a transition behind a
  permission stays closed to it. The README's
  [service callers](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md#service-callers)
  section has the rules.

## Serve it

<Snippet example="engine-notes" file="src/server.ts" symbol={['notesApp', 'listen']} />

- `engineApp` serves the HTTP API and the event stream. Its routes carry
  the namespace and the schema name as path parameters and look them up
  per request, so publishing a version mounts nothing. Every route goes
  through the HTTP runtime: the request id, the rate limit, the timeout,
  the body limit, the authentication gate, the `{data, meta}` envelope and
  RFC 9457 problem documents.
- `engineMcp` serves the MCP endpoint at `/namespaces/{namespace}/mcp`,
  with the same options.
- There is one namespace, `default`, unless you configure more with the
  `namespaces` option or make one while the server runs
  (`POST /api/namespaces`, `create_namespace`), as the policy allows. An
  archived namespace is read as it was and refuses every write (409
  `namespace_archived`).

Start the server from the example's directory:

```sh
cd examples/engine-notes
node src/main.ts
```

```
engine-notes: http://127.0.0.1:8787/api, database notes.db
```

`bun src/main.ts` runs the same server on Bun. Ctrl-C stops it. The
commands below run in a second terminal, from `examples/engine-notes`, and
print JSON with `jq`. The live schema:

```sh
API=http://127.0.0.1:8787/api/namespaces/default
curl -s $API/schemas -H 'authorization: Bearer carol-token' | jq .data
```

```json
[
  {
    "namespace": "default",
    "name": "notes",
    "liveVersion": 1,
    "hasDraft": false
  }
]
```

## Instances

Create a note as alice, an author:

```sh
curl -s $API/schemas/notes/instances \
  -H 'authorization: Bearer alice-token' -H 'content-type: application/json' \
  -d '{"id": "launch", "data": {"title": "Launch", "tags": ["launch"]}}' | jq
```

```json
{
  "data": {
    "namespace": "default",
    "schema": "notes",
    "id": "launch",
    "schemaNamespace": "default",
    "version": 1,
    "seq": 1,
    "data": {
      "title": "Launch",
      "tags": [
        "launch"
      ],
      "status": "draft",
      "commentCount": 0,
      "revision": 1,
      "pendingProposals": 0
    },
    "createdAt": 1790790700324,
    "createdBy": "alice",
    "updatedAt": 1790790700324,
    "updatedBy": "alice"
  },
  "meta": {
    "requestId": "0ab67d9c-70d3-442b-b5f2-7c9377174d23"
  }
}
```

The response is 201. The note's `data` holds its own fields and, after
them, the fields its behaviors add: Workflow's `status`, Comments'
`commentCount` and Revisions' `revision` and `pendingProposals`. Those
are read-only; a create or an update that sets one is 422. `seq` is the sequence of the note's last
event, and the response sends it as the `ETag`, `"1"`. Without an `id`, the
engine makes a random UUID. A body may also carry `behaviors`, the
parameters a create gives the note's behaviors by name, such as the links
and blockers it holds from its create;
[create parameters](/superschematic/guides/engine-behaviors/#create-parameters)
has them.

carol, a reader, may not create one:

```sh
curl -s $API/schemas/notes/instances \
  -H 'authorization: Bearer carol-token' -H 'content-type: application/json' \
  -d '{"data": {"title": "Mine"}}' | jq
```

```json
{
  "type": "about:blank",
  "title": "Forbidden",
  "status": 403,
  "detail": "carol may not write notes in namespace default",
  "code": "forbidden",
  "requestId": "4dd339ca-b651-4f99-9256-f3d958e8fddb"
}
```

An update is a JSON merge patch (RFC 7386): a member replaces the note's
member, a nested object merges, `null` removes the member, and a list
replaces the list. `If-Match` names the sequence you last read; the engine
checks it inside the write, and answers 412 `seq_mismatch` when the note
has moved on since.

```sh
curl -s -X PATCH $API/schemas/notes/instances/launch \
  -H 'authorization: Bearer alice-token' -H 'content-type: application/merge-patch+json' \
  -H 'if-match: "1"' -d '{"body": "Ships in the fall.", "tags": null}' | jq .data.data
```

```json
{
  "title": "Launch",
  "body": "Ships in the fall.",
  "status": "draft",
  "commentCount": 0,
  "revision": 2,
  "pendingProposals": 0
}
```

`GET $API/schemas/notes/instances` lists notes in creation order, a page
at a time (`limit`, and the `next` cursor as `cursor`), `GET` on a note
reads it, and `DELETE` removes it.

A field whose JSON is longer than 64 KiB, a long body or a step's result
document, is stored once in the engine's value store, under the SHA-256
of its canonical JSON, and the note's row keeps a small ref in its place:
a write that leaves the field alone, and a lease's heartbeat, never
rewrites it. Reads return the value as they always do. Add
`?valueRefs=true` to a list or a get to receive the ref instead,
`{"$value": "<hash>", "bytes": <n>}`, with the pointers to the refs in
the instance's `valueRefs`, and read a value when you need it from
`GET $API/values/<hash>`, which answers a caller who may read the note's
schema. The engine's README, `runtime/engine/README.md` ("The value
store"), has the rules.

`where` filters a list by equality, a JSON object in the query: each
member a note's own field that holds a string, a number or a boolean, or
a behavior's field a list filters on, such as Workflow's `status`, with
a value or a list of values any of which the note holds, `null` meaning
none:

```sh
curl -s -G $API/schemas/notes/instances -H 'authorization: Bearer carol-token' \
  --data-urlencode 'where={"status": ["review", "published"]}' | jq '.data.items[].id'
```

A page keeps creation order. A filter an index serves, Workflow's
`status` or a unique field, reads only the notes that match; another
reads at most 1000 notes past the cursor per page, so its page can hold
fewer notes than `limit`, even none, while `next` is not null. Read on
until `next` is null.

### Unique fields and lookups

`@unique` or `@key` on a field of the instance type, or a unique
`@index` over several, makes the engine refuse a second instance with the
same value in the namespace: the create or the update is 409 `conflict`,
with the fields in `details.fields`. An instance that lacks the field
does not count, so any number of instances can lack it. A field like
that is a string, a number or a boolean; the engine refuses `@unique` on
a list or an object when you define the schema.

`GET $API/schemas/{name}/lookup?key=<JSON>` returns the instance whose
unique fields hold the key's values, or 404. The key is a JSON object in
the query, never part of the path, so a value may hold a slash. For a
`models` schema whose `slug` is `@unique`:

```sh
curl -s -G $API/schemas/models/lookup -H 'authorization: Bearer carol-token' \
  --data-urlencode 'key={"slug": "openai/gpt-5"}' | jq .data.id
```

A client that syncs an outside collection looks each item up by its key
and creates the ones it does not find; a create that races another for
the same key is 409, after which a lookup finds it.

## Behaviors

Each behavior operation on an instance is a route:
`POST .../instances/{id}/operations/{operation}`, with the operation's
parameters as the body, an optional `If-Match`, and an optional
`Preconditions` header for the behaviors that check one, such as a
lease's token
([refusals and preconditions](/superschematic/guides/engine-behaviors/#refusals-and-preconditions)).
A few operations run
on the whole schema instead, such as `Search`'s `search` and `Queue`'s
`claimNext`, at `POST .../schemas/{name}/operations/{operation}`
([schema-level operations](/superschematic/guides/engine-behaviors/#schema-level-operations)).
The README's
[core behaviors](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md#core-behaviors)
section lists every operation, guard and config change of each.

This example uses three behaviors. The core also declares
`Dependencies`, `Links` and `Rollups`, which reach other instances,
`Search`, full-text search over a type's text fields and, optionally,
vector search over embeddings an outside embedder computes, `Reactions`,
whose rules the engine's [runner](/superschematic/guides/engine-behaviors/#the-runner)
applies after a change commits, `Constants` and `Variants`, which keep
fields as their create set them and type a JSON field by another field's
value, and `Branches`, which makes each instance the root of a version
graph whose drafts merge into its primary line; [Engine behaviors](/superschematic/guides/engine-behaviors/)
covers them. [Work queues](/superschematic/guides/work-queues/) covers
`Lease`, `Assignment`, `Queue`, `Presence`, `Blueprint`, `Budget` and
`Retries`, which make instances claimable work.

### Workflow

alice sends the note to review:

```sh
curl -s $API/schemas/notes/instances/launch/operations/transition \
  -H 'authorization: Bearer alice-token' -H 'content-type: application/json' \
  -H 'if-match: "2"' -d '{"to": "review"}' | jq .data
```

```json
{
  "from": "draft",
  "to": "review"
}
```

The move from review to published names `notes.publish`, which alice does
not hold. The policy lets her write, and Workflow refuses the move:

```sh
curl -s $API/schemas/notes/instances/launch/operations/transition \
  -H 'authorization: Bearer alice-token' -H 'content-type: application/json' \
  -d '{"to": "published"}' | jq
```

```json
{
  "type": "about:blank",
  "title": "Forbidden",
  "status": 403,
  "detail": "alice may not move notes launch from review to published: the transition needs permission notes.publish",
  "code": "forbidden",
  "requestId": "f6949e8e-dea0-4968-a8d3-6a3d386bf177"
}
```

bob, an editor, holds `notes`, which covers it:

```sh
curl -s $API/schemas/notes/instances/launch/operations/transition \
  -H 'authorization: Bearer bob-token' -H 'content-type: application/json' \
  -d '{"to": "published"}' | jq .data
```

```json
{
  "from": "review",
  "to": "published"
}
```

A transition the config does not list is 409 `vetoed`, with
`details.behavior` `Workflow` and `details.code` `transition_not_allowed`
for a client to branch on, and a state it does not name is 400
`invalid_argument`.

### Revisions

carol cannot change the note, but she can propose a change. The proposal
is checked as the update would be, and changes none of the note's fields
yet; `pendingProposals` counts it:

```sh
curl -s $API/schemas/notes/instances/launch/operations/propose \
  -H 'authorization: Bearer carol-token' -H 'content-type: application/json' \
  -d '{"patch": {"body": "Ships on October 1."}, "note": "Adds the date."}' | jq .data
```

```json
{
  "id": 1,
  "patch": {
    "body": "Ships on October 1."
  },
  "note": "Adds the date.",
  "base": 2,
  "state": "pending",
  "createdBy": "carol",
  "createdAt": 1790790700466
}
```

bob's `notes` covers `notes.review`, so he may approve it. The approval
applies the patch with the same validation and guards as an update, and
records revision 3 with the proposal's id:

```sh
curl -s $API/schemas/notes/instances/launch/operations/approve \
  -H 'authorization: Bearer bob-token' -H 'content-type: application/json' \
  -d '{"proposal": 1}' | jq .data
```

```json
{
  "id": 1,
  "patch": {
    "body": "Ships on October 1."
  },
  "note": "Adds the date.",
  "base": 2,
  "state": "approved",
  "createdBy": "carol",
  "createdAt": 1790790700466,
  "reviewedBy": "bob",
  "reviewedAt": 1790790700481,
  "revision": 3
}
```

```sh
curl -s $API/schemas/notes/instances/launch -H 'authorization: Bearer carol-token' | jq .data.data
```

```json
{
  "title": "Launch",
  "body": "Ships on October 1.",
  "status": "published",
  "commentCount": 1,
  "revision": 3,
  "pendingProposals": 0
}
```

`reject` settles a proposal without applying it, `listProposals` and
`listRevisions` page through them, `getRevision` reads one revision by
its number, and a revision's `data` is the note's own fields as that
change left them. A proposal may cite `evidence`, instances the proposer
may read, each optionally at a revision, which the reviewer reads with
the proposal.

### Your own behaviors

An extension adds a behavior in two halves. The compiler half is a JSON
declaration its Go package registers; the binary's
[`behaviors --out`](/superschematic/reference/cli/) command copies it into
the npm package that implements it. The engine half is a
`BehaviorImplementation`, built with `defineBehavior`: a handler per
operation, a reader per field, guards (which may refuse a create too),
an `initialize` that gets the parameters a create gives it, and
migrations for its own storage, and optionally config checks, a
`validate` that judges the fields a write stores (with `checkedTypes`
and `instanceSchema`), `afterChange`, schema-level operations,
reactions and schedules for the runner, and hooks that run when an
instance it references changes. A guard's veto carries a code the
declaration lists, at a create as at any other change, and a caller can
send a behavior a precondition with a write, which its guard checks:
`Lease`'s token is one (`Preconditions` header over HTTP). A server
registers it with `openEngine({ behaviors, metaSchema })`, where
`metaSchema` is the extension binary's `json-schema` output, which
declares it. `acme.Rating` in `examples/acme-schematic` is the worked
example, and
[Write an extension](/superschematic/extending/write-an-extension/#a-behavior)
walks through it.

A behavior's functions reach the instance they run on, the behavior's own
columns and tables, and the rest of the namespace as the caller: they
read other instances and change them through their operations, and the
access policy is asked at each step. Beyond one instance, a behavior
reads its own columns across every instance of its schema with SQL, on a
read-only relation the engine names (`sql.instances()`) and a migration
can index; creates instances wherever it may invoke a writing operation
(`instances.create`), with their behaviors' create parameters, so a
parent's children commit with it, linked and blocked; and runs
schedules at an interval its schema's config can set, or turn off. A
behavior that keeps values of the schema's other types in its own
tables reads those types' fields in `parseConfig` (`target.types`),
which holds them to the schema's checks and its compatibility rule, and
checks a value against one with `validate(type, value)`. Which types a
config reads may depend on the config and the document only, not on the
other schemas, since a version is checked against the next with no other
schema in reach; a define or publish refuses a config whose reads do. A
behavior that keeps an object with large members in its own tables, a
copy of the instance's fields say, keeps it through the value store
(`values.stow`, `load` and `release`), as Revisions does, so the value
is stored once however many rows hold it. A schedule's
run may write the behavior's own tables directly, but only what no
operation returns, history nothing pins say; a change a read shows goes
through an operation it invokes. The README's
[behaviors](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md#behaviors)
section has the whole interface.

## The event log

Every write appends one event in its own transaction: a create, an update,
a delete, a behavior operation that writes, a publish, and the define of
a draft. The cursor orders the whole log:

```sh
curl -s "$API/events?after=0" -H 'authorization: Bearer carol-token' \
  | jq -c '.data.events[] | [.cursor, .kind, .actor, .change.operation]'
```

```
[1,"define","engine-notes",null]
[2,"publish","engine-notes",null]
[3,"create","alice",null]
[4,"update","alice",null]
[5,"operation","alice","transition"]
[6,"operation","bob","transition"]
[7,"operation","carol","comment"]
[8,"operation","carol","propose"]
[9,"operation","bob","approve"]
```

A page is `{events, next, more}`; read on with `after` set to `next`.
`schema` and `instanceId` narrow it, and events of schemas the caller may
not read are left out. An event's `change` is the instance for a create,
the merge patch for an update, and `{behavior, operation, params, patch}`
for an operation, so applying the changes in order gives the note as a
read returns it. A define's is `{hash}`, the draft's hash: a reviewer
watching the log learns a draft waits, and reads it from the draft route.
A member of a change longer than 64 KiB is a ref to the value store, and
the event lists the pointers to its refs in `valueRefs`, so the log never
copies a large field; read the value from `GET $API/values/<hash>`.

Three filters narrow a page further, each a list, repeated or
comma-separated: `kind` keeps those kinds, `behavior` keeps the
operations of those behaviors, and `exclude` drops operations by name.
`?kind=operation&exclude=comment` is every operation but comments. A page
still scans its limit of events, so one whose events were all dropped is
empty, and its `next` is past them. `after=head` starts at the last
event: no events, and `next` to read on from.

A write that reaches other instances, such as a delete that clears the
links pointing at it or a create that stamps children, appends an event
on each instance it changes, all in the same transaction. An event the
[runner](/superschematic/guides/engine-behaviors/#the-runner) writes
also carries `cause`, the behavior and the event or schedule that set it
off.

With `Accept: text/event-stream` the same route streams. It replays from
`after` (or `Last-Event-ID`, which a reconnecting `EventSource` sends),
sends a `ready` event with the cursor once it has caught up, then waits
and sends each event as it commits:

```sh
curl -sN "$API/events?after=6" -H 'accept: text/event-stream' -H 'authorization: Bearer carol-token'
```

```
: open

id: 7
data: {"cursor":7,"kind":"operation","namespace":"default","schema":"notes","instanceId":"launch","seq":5,"version":1,"actor":"carol","at":1790790700450,"change":{"behavior":"Comments","operation":"comment","params":{"body":"Which fall?"},"patch":{"commentCount":1}}}

id: 8
data: {"cursor":8,"kind":"operation","namespace":"default","schema":"notes","instanceId":"launch","seq":6,"version":1,"actor":"carol","at":1790790700466,"change":{"behavior":"Revisions","operation":"propose","params":{"patch":{"body":"Ships on October 1."},"note":"Adds the date."},"patch":{"pendingProposals":1}}}

id: 9
data: {"cursor":9,"kind":"operation","namespace":"default","schema":"notes","instanceId":"launch","seq":7,"version":1,"actor":"bob","at":1790790700481,"change":{"behavior":"Revisions","operation":"approve","params":{"proposal":1},"patch":{"body":"Ships on October 1.","revision":3,"pendingProposals":0}}}

event: ready
id: 9
data: {"cursor":9}

: keepalive
```

`ready` is a named event, so `EventSource.onmessage` does not receive
it; `addEventListener('ready', ...)` does, and its id is where a
reconnect resumes. `after=head` skips the replay: `ready` comes at once,
then only what commits. The filters work as on the JSON page; when they
drop the last events the stream read, a message with only an `id:` keeps
the client's place, which `EventSource` records without an event. While
it waits it sends a `: keepalive` comment every five seconds. Stop it
with Ctrl-C. The end-to-end test reads the stream from a cursor, then
adds a comment and receives its event.

This server keeps every event. One that passes `retention` to
`openEngine`, `{ maxAgeMs }`, `{ maxEvents }` or both, has its runner
prune the oldest, each namespace's apart, and never one a subscription
has yet to handle. A read from the start, with no `after` or
`after=0`, reads what is kept, from the oldest event. A read or a
stream's resume from a cursor retention has pruned past is 410
`cursor_expired`, whose `details` carry the `floor` to read on from,
taking the gap, and the `head` to start again from. The README's
[retention](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md#retention)
section has the rules.

## Call it from TypeScript

`@superschematic/engine/client` is a typed client of the HTTP API. It
imports nothing of the engine's server side or of Node.js, so it runs in
a browser and a worker runtime as well as in another server:

```ts
import { EngineClient, isVeto } from '@superschematic/engine/client';

const client = new EngineClient({
  baseUrl: 'http://127.0.0.1:8787/api',
  auth: { token: 'alice-token' },
});

const note = await client.instances.create('notes', { title: 'Launch' }, { id: 'launch' });
await client.instances.update('notes', note.id, { body: 'Ships in the fall.' }, { expectedSeq: note.seq });
try {
  await client.instances.invoke('notes', note.id, 'transition', { to: 'published' });
} catch (error) {
  if (isVeto(error, 'Workflow', 'transition_not_allowed')) {
    // a refusal to branch on, with error.vetoDetails
  } else {
    throw error;
  }
}
```

- The calls follow the engine's: `namespaces` (`list`, `create`,
  `archive`, ...), `schemas` (`define`, `publish`,
  `describe`, ...), `instances` (`create` with `behaviors`, `get`, `list`
  with `where`, `lookup`, `update`, `delete`, `invoke` and the
  schema-level `invokeSchema`),
  `events`, `behaviors`, `tools()` and `search()`. A write's
  `expectedSeq` is sent as `If-Match` and its `preconditions` as the
  `Preconditions` header.
- A refusal is an `EngineProblem` with the status, the problem's `code`
  and `issues` at their paths; a behavior's veto is an `EngineVeto` with
  `behavior`, `vetoCode` and `vetoDetails`.
- Credentials are a generated SDK's: an end user's token with
  `refreshToken` on a 401, and a calling service's `serviceCredential`,
  which the HTTP runtime's token sources fill. A 401
  `service_unauthorized` asks the service source for a fresh token once
  and never refreshes the end user.
- `client.events.subscribe({ after: 'head' })` is the event stream as an
  async iterable of events and a `ready` per connection. It resumes after
  a dropped connection with `Last-Event-ID`, so it neither repeats nor
  skips an event.
- `reconcile(client, { handle, cursor })` runs a handler per event, in log
  order, from the cursor its store keeps, retrying a failing event rather
  than skipping it: a controller's loop.

The README's
[client](https://github.com/parable-work/superschematic/blob/main/runtime/engine/README.md#the-client)
section has every call and option, and
[Work queues](/superschematic/guides/work-queues/#write-a-worker) builds a
worker on it.

### Typed wrappers for your schemas

The client is generic over schema names: `create` takes any object and an
operation any parameters, so a misspelled field, state or link name
reaches the server and comes back as a refusal. `superschematic
engine-client` writes a module that types the client for your schemas,
from their documents and the behaviors' declarations:

```sh
superschematic engine-client --out src/notes.client.ts schemas/notes.schema.json
```

```ts
import { EngineClient } from '@superschematic/engine/client';
import { isNoteVeto, notesClient } from './notes.client.ts';

const notes = notesClient(new EngineClient({ baseUrl: 'http://127.0.0.1:8787/api', auth: { token: 'alice-token' } }));

const note = await notes.create({ title: 'Launch' }, { id: 'launch' });   // data: NoteFields
note.data.status;                                                         // 'draft' | 'review' | 'published' | 'archived'
await notes.transition('launch', { to: 'review' });                       // { to: 'publshed' } fails to compile
await notes.comment('launch', { body: 'Ships in the fall.' });
await notes.propose('launch', { patch: { body: 'Ships on the first.' } }); // patch: NotePatch
try {
  await notes.transition('launch', { to: 'review' });
} catch (error) {
  if (!isNoteVeto(error, 'Workflow', 'already_in_state')) throw error;   // codes Workflow lists
}
```

The behaviors' configs narrow the types: a `Workflow`'s states, the names
of a `Links` config with each required link required at create, the
schemas a `Dependencies` blocker may come from, and with `Variants` the
type of the field for each value of the one that picks it. An operation's
method takes its declaration's parameters and returns its result, and a
write's `preconditions` take only the behaviors that declare one (Lease's
`token`). The module imports the client and nothing else, so it runs in
a browser too. The example commits `src/notes.client.ts` and uses it in
its end-to-end test; regenerate it when the schema changes, and run
`engine-client --check` in CI to keep it current.

## MCP tools

The MCP endpoint serves one tool per operation of every live schema the
caller may read, `lookup` for a schema with a unique field among them,
and ten engine tools: `list_schemas`, `describe_schema`
and `define_schema`, `list_behaviors` and `describe_behavior`, which
list the behaviors the engine runs and return one's declaration, its
config's JSON Schema included, `get_value`, which reads a value of
the value store by its hash, and `list_namespaces`, `create_namespace`,
`archive_namespace` and `unarchive_namespace`. A tool's name is the schema's and the operation's,
in snake case: `notes_create`, `notes_transition`, `notes_list_comments`.
`notes_list` takes `where`, as the route does, as a JSON object.
A tool the policy refuses the caller is left out of the caller's list, so
carol, a reader, sees these:

```sh
curl -s $API/mcp -H 'authorization: Bearer carol-token' -H 'content-type: application/json' \
  -H 'accept: application/json, text/event-stream' \
  -d '{"jsonrpc": "2.0", "id": 1, "method": "tools/list"}' \
  | sed -n 's/^data: //p' | jq -r '.result.tools[].name'
```

```

define_schema
list_behaviors
describe_behavior
get_value

unarchive_namespace
notes_get
notes_list

notes_get_revision

```

The engine's tools name no schema until they are called, so everyone
lists them and the policy answers the call; the behavior tools ask it
nothing, since the behaviors are the server's code, and this policy
refuses every caller the namespace tools' `manage`. Where a schema
composes `Search`, one more tool, `search`, searches every such schema the
caller may read ([Engine behaviors](/superschematic/guides/engine-behaviors/#searching-every-schema)).
No tool publishes: a draft that `define_schema` stores goes live only
through the HTTP publish route.

Each tool's `_meta` carries guidance under
`superschematic/operation-guidance`, in the members an SDK tool's
`@docs` fills: when to call it, when to call another, what it returns,
and the vetoes it can meet with the usual correction. The engine
computes it from the behaviors' configs. `notes_transition`'s `useWhen`
reads "Use to move status from draft to review; from review to draft or
published; from published to archived. The moves review to published
and published to archived need permission notes.publish; without it the
call is forbidden.", and `notes_propose`'s names `notes.review`, the
permission an approval needs.

An MCP client connects to `http://127.0.0.1:8787/api/namespaces/default/mcp`
with the header `Authorization: Bearer <token>`. The end-to-end test uses
the official TypeScript client:

## Change the schema over HTTP

dana holds `schemas`, so the policy lets her define drafts
(`POST $API/schemas`, the document as the body) and publish them
(`POST $API/schemas/notes/publish`). A draft that adds a required field is
refused, since a note the live version accepts need not have it:

```sh
jq '.types.Note.fields += [{"name": "owner", "typeRef": {"name": "string"}, "required": true}]' schemas/notes.schema.json \
  | curl -s $API/schemas -H 'authorization: Bearer dana-token' -H 'content-type: application/json' -d @- \
  | jq '{status, code, changes: .details.changes}'
```

```json
{
  "status": 409,
  "code": "incompatible_change",
  "changes": [
    {
      "path": "Note.owner",
      "message": "field Note.owner is added as required"
    }
  ]
}
```

Before writing a draft, `GET /api/behaviors` lists the behaviors the
engine runs, and `GET /api/behaviors/Workflow` returns one's declaration:
the JSON Schema of its config, its operations and the codes its vetoes
carry. A draft the rule allows is stored, with a `define` event in the
log, and the publish route makes it the live version. This server publishes its schema file each time it starts,
so change the file rather than the live version: after a version with a
field the file lacks goes live over HTTP, the next start refuses the file.
