A bucket is private object storage: product images, exports, uploads. It
is a service of the core kind `Bucket`, and an API that keeps objects in
it lists it in its config, as it lists the APIs it `calls`. A stack that
deploys the API deploys the bucket too, and the API's implementation gets
it in `Deps`, behind an interface that names no provider. The design is
section 8.9 of
[docs/stack-model.md](https://github.com/parable-work/superschematic/blob/main/docs/stack-model.md),
and D54 in the [decision log](https://github.com/parable-work/superschematic/blob/e8e685a5149a8897001153fb6cca1100ac90d0c0/docs/DECISIONS.md) records the decision.

| Built | Not built yet |
| --- | --- |
| the `Bucket` kind, `buckets` in an API's config, and the `bucket` deployable and edge | |
| `Deps` gains a bucket per listed bucket, in Go, TypeScript and Rust, implemented over GCS, and in TypeScript over an R2 binding on Workers | a bucket on another provider from Go or Rust |
| signed URLs to upload or download an object directly | |
| `stack dev` runs fake-gcs-server with a bucket per Bucket service | |
| on gcp, a private Cloud Storage bucket per Bucket service, with its grants | |
| on cloudflare, a private R2 bucket per Bucket service, with a token of its own per edge ([buckets on R2](/superschematic/guides/stacks/#buckets-on-r2)) | |
| a bucket's [CORS rules](#let-a-page-reach-the-bucket) on gcp and on cloudflare, which a browser's upload to a signed URL needs | CORS rules per bucket on `stack dev`'s emulator, which answers every origin |

## Declare a bucket

A Bucket service's config is all it has: a name, the kind and an empty
`outputs`. It has no schema files and generates nothing, but its build
writes a handle, `src/service.generated.ts`, which the APIs that use it
import:

<Snippet file="schemas/services/shop-media/schema.config.ts" />

An API lists the buckets it uses in `buckets`, beside `authDb` and
`calls`. Several APIs may list one bucket:

<Snippet file="schemas/services/shop-api/schema.config.ts" />

`buckets` takes only Bucket handles, so tsc refuses another kind's there,
and discovery refuses one in any form. In a data form the list is
`{ name, kind }` pairs, `buckets: [{ name: shop-media, kind: Bucket }]`.
A bucket is private: its config takes no `public`, no `authDb`, no
`dependencies` and no outputs. It may say `contentAddressed: true`, with
`maxBytes` ([below](#name-objects-by-their-content)).

## What an API gets

The API's config gains a field per bucket, which the stack derives:
the bucket's name, and locally the emulator's endpoint. It holds no
credential, since the workload's own identity reaches the bucket.

| Field | Variables |
| --- | --- |
| `SHOP_MEDIA_BUCKET` | `SHOP_MEDIA_BUCKET_NAME`, and `SHOP_MEDIA_BUCKET_ENDPOINT` when an emulator serves the bucket |

The name comes from the naming file's
[`[derived_fields] bucket`](/superschematic/reference/naming/#derived_fieldsbucket)
template, `{SERVICE}_BUCKET` by default. `Deps` gains the bucket itself,
named after the service: `ShopMedia bucket.Bucket` in Go, from
`runtime/http/go/bucket`, `shopMedia: Bucket` in TypeScript, from
`@superschematic/http-runtime`, and `shop_media: Arc<dyn Bucket>` in Rust,
from the Rust HTTP runtime's `bucket` module. All three have these
methods:

| Go | TypeScript | Rust | Does |
| --- | --- | --- | --- |
| `Put(ctx, name, body, opts)` | `put(name, body, options)` | `put(name, body, options)` | writes the object from a stream, replacing any, with an optional content type |
| `Put` with `IfAbsent: true` | `put` with `ifAbsent: true` | `put` with `PutOptions::default().if_absent()` | writes only when no object has the name, and says whether it did ([below](#put-only-when-absent)) |
| `Head(ctx, name)` | `head(name)` | `head(name)` | what the bucket holds of the object, its size, content type and time, without its bytes, or nothing when there is none |
| `Get(ctx, name)` | `get(name)` | `get(name)` | opens the object as a stream, with its size, content type and time; the caller closes it, or in Rust drops it |
| `Delete(ctx, name)` | `delete(name)` | `delete(name)` | removes the object |
| `List(ctx, opts)` | `list(options)` | `list(options)` | a page of the objects whose names begin with a prefix, in name order, and the token of the next page |
| `SignedURL(ctx, name, opts)` | `signedUrl(name, options)` | `signed_url(name, options)` | a URL that lets its holder `GET` the object or `PUT` it, with no other credential, until it expires |

A missing object is `bucket.ErrNotFound` in Go, an
`ObjectNotFoundError` in TypeScript and `BucketError::NotFound` in Rust.
Object names are slash-separated paths such as `products/7b0e/image.png`;
a bucket has no directories. In Rust, a `Body` is bytes, text, or a
stream of chunks such as an axum request's `into_data_stream()`, and a
`Reader` is a stream an axum handler answers with as
`Body::from_stream(reader)`.

## Put only when absent

`put` replaces an object of the same name. With `ifAbsent` it writes only
when no object has the name, and its result says which happened:

```ts
const put = await deps.shopMedia.put(name, body, { contentType: "image/png", ifAbsent: true });
if (!put.created) {
  // put holds the object that was already there: its size and content type.
}
```

```go
put, err := deps.ShopMedia.Put(ctx, name, body, bucket.PutOptions{ContentType: "image/png", IfAbsent: true})
if err == nil && !put.Created {
	// put.Object is the one that was already there.
}
```

```rust
let put = deps
    .shop_media
    .put(&name, body, PutOptions::content_type("image/png").if_absent())
    .await?;
if !put.created {
    // put.object is the one that was already there.
}
```

The provider checks and writes in one step, so of two puts of one name at
once, one creates the object and the other finds it. A `head` followed by
a `put` does not do that: two callers interleave. On GCS it is the
precondition `ifGenerationMatch=0`, and on R2 the binding's conditional
write, `onlyIf` with `If-None-Match: *`. A put that found an object reads
it back for its result. If the object is deleted between the two, the put
fails and says to put it again.

Every `put` answers `created`, in TypeScript beside the object's members,
in Go as `PutResult{Object, Created}` and in Rust as
`PutResult { object, created }`: `true` for a put without `ifAbsent`,
which always writes.

## Name objects by their content

A Bucket service whose config says `contentAddressed: true` stores each
file once, under the hash of its bytes:

```ts
export default defineConfig({
  name: "shop-blobs",
  kind: SchemaKind.Bucket,
  contentAddressed: true,
  maxBytes: 8 * 1024 * 1024,
  outputs: {},
});
```

An API that lists it gets a content bucket in its `Deps`, in place of the
plain one: `ShopBlobs *bucket.ContentBucket` in Go,
`shopBlobs: ContentBucket` in TypeScript and `shop_blobs: ContentBucket`
in Rust, from the Rust HTTP runtime's `bucket` module.

| Go | TypeScript | Rust | Does |
| --- | --- | --- | --- |
| `Put(ctx, body, opts)` | `put(body, { contentType })` | `put(body, options)` | reads the body whole, up to `maxBytes`, names the object `sha256/<hex>` by the SHA-256 of its bytes, and writes it if absent; answers `{ hash, size, created }` |
| `Has(ctx, hash)` | `has(hash)` | `has(hash)` | whether the bucket holds those bytes |
| `Missing(ctx, hashes)` | `missing(hashes)` | `missing(hashes)` | the hashes it does not hold, each once, in the order given |
| `Get(ctx, hash)` | `get(hash)` | `get(hash)` | opens the bytes as a stream |
| `SignedURL(ctx, hash, expires)` | `signedUrl(hash, { expiresInSeconds })` | `signed_url(hash, expires)` | a URL that lets its holder `GET` the bytes |
| `Raw()` | `raw` | `raw()` | the plain bucket, whose names are `sha256/<hex>` |

```ts
const { hash, created } = await deps.shopBlobs.put(await request.arrayBuffer().then(bytes => new Uint8Array(bytes)), { contentType: "application/pdf" });
const missing = await deps.shopBlobs.missing(manifest.hashes);
```

- A hash is 64 lowercase hex digits. Every method refuses anything else,
  so no caller's text reaches an object's name.
- `maxBytes` is 32 MiB when the config names none. `put` holds the body
  in memory to hash it before it writes, since a name is known only once
  the last byte is read. A longer body is `bucket.ErrContentTooLarge` in
  Go, a `ContentTooLargeError` in TypeScript and `BucketError::TooLarge`
  in Rust, and nothing is written.
  Send a larger file to a plain bucket through a signed URL.
- It has no delete, and it signs no upload: an object is written only by
  `put`, which hashes it, so the bytes under a hash are always the bytes
  of that hash. `raw` is the plain interface for the caller that needs
  one, to list, or to delete an object nothing refers to any more.
- `missing` asks about sixteen objects at a time.
- `created` is false when the bucket already held the bytes. Two puts of
  the same bytes at once store one object, and one of them says it
  created it.
- The Go, TypeScript and Rust content buckets name and answer alike
  (`runtime/http/testdata/content_bucket_parity.json`).

## Hand a browser a signed URL

A browser uploads or downloads an object straight to or from the bucket,
through a URL the API signs, so the file's bytes never pass through the
server, and a large one is not held to Cloud Run's 32 MiB request limit.
A signed URL lives at most seven days, and one for a `PUT` names the
content type the upload must send. The acme shop's `shop-api` hands out
the upload of a product's image and records the object's name on the
product:

<Snippet file="go/shop-api/products.go" symbol="Products.CreateProductImageUpload" />

In Rust, an implementation signs one the same way:

```rust
use std::time::Duration;
use superschematic_http_runtime::bucket::SignedUrlOptions;

let upload = deps
    .shop_media
    .signed_url(
        &format!("products/{id}/image.png"),
        SignedUrlOptions::put(Duration::from_secs(15 * 60)).with_content_type("image/png"),
    )
    .await?;
```

A Rust URL's expiry is a whole number of seconds, as TypeScript's is.

The browser then sends the file with the content type it asked for:

```sh
curl -X PUT -H 'Content-Type: image/png' --data-binary @tea.png "$UPLOAD_URL"
```

## Let a page reach the bucket

A page's script that sends that `PUT`, or reads an object with `fetch`,
is a cross-origin request: the browser first asks the bucket whether the
page's origin may send it, and sends nothing when the bucket does not
answer. So a bucket's settings in an environment take `cors`, a list of
rules, the same on gcp and on cloudflare (D148):

```ts
@environment({
  target: "gcp",
  gcp: { project: "acme-prod", region: "us-east1", production: true },
  settings: [
    {
      of: ShopMedia,
      cors: [
        {
          origins: ["https://shop.acme.dev"],
          methods: ["GET", "PUT"],
          headers: ["content-type"],
          exposeHeaders: ["etag"],
          maxAge: "1h"
        }
      ]
    }
  ]
})
export abstract class Production {}
```

| Key | Holds |
| --- | --- |
| `origins` | the origins the rule answers, each a scheme and a host with no path (`https://shop.acme.dev`, `http://localhost:5173`), or `*` alone for any origin |
| `methods` | the methods it admits from them: `GET`, `HEAD`, `PUT`, `POST` and `DELETE` |
| `headers` | the request headers a page may send, `content-type` for an upload that names its type; `*` is any |
| `exposeHeaders` | the response headers the page's script may read beside the ones every browser exposes, `etag` say |
| `maxAge` | how long a browser may keep the bucket's answer before it asks again, a duration of whole seconds (`10m`, `1h`), a day at most |

A rule that admits `PUT` from `*` is refused. The bucket is private, and a
page writes to it only through a URL an API signed, so the rule names the
origins of the pages that upload. `*` is taken for `GET` and `HEAD`, as
for a signed download any page may fetch. A bucket with no `cors` answers
no preflight, which is right for one only servers reach.

gcp writes the rules as the Cloud Storage bucket's `cors`. Cloud Storage
keeps one list of headers per rule, which it both allows in a request and
exposes in the response, so a rule's `headers` and `exposeHeaders` are
joined there. cloudflare writes them as the R2 bucket's CORS rules, a node
of their own beside the bucket.

## Run it locally

`superschematic stack dev` runs
[fake-gcs-server](https://github.com/fsouza/fake-gcs-server), which speaks
GCS's API, in a container beside Postgres, one per environment and
checkout, and
creates a bucket per Bucket service, named after it. The bucket field's
endpoint points at it, so the same GCS implementation reaches it, with no
credential, in Go, TypeScript and Rust alike. It signs URLs too: against
an emulator, a V4 URL for the emulator's host signed with a key the
process makes, which the emulator takes and does not check. A process
with `STORAGE_EMULATOR_HOST` set reaches that emulator the same way.

The container keeps its objects between runs; `stack dev --remove-data`
removes them with the containers. The environment's `storageImage` and
`storagePort` values change its image, `fsouza/fake-gcs-server:1.56.1`,
and its host port, which is otherwise a hash of the stack and the
environment, shifted by the checkout
([Run it locally](/superschematic/guides/stacks/#run-it-locally)):

```ts
@environment({ target: "local", local: { storagePort: 54443 } })
export abstract class Dev {}
```

The emulator answers a browser's preflight for every bucket alike, from
any origin, so a page of a local site uploads to a signed URL with no
`cors` setting, and a local bucket takes none. It allows the request
headers `Content-Type`, `Content-Encoding`, `Range` and `Content-Range`.
A page that sends another, an `x-goog-meta-` header say, names it in the
environment's `storageCorsHeaders` value, as it names it in `headers` on
gcp and cloudflare:

```ts
@environment({ target: "local", local: { storageCorsHeaders: ["x-goog-meta-owner"] } })
export abstract class Dev {}
```

The acme shop's `go/stack_dev_test.go` runs it: it asks `shop-api` for an
upload URL, `PUT`s an image through it to the emulator, and reads it back
from the bucket. `TestStackDevRunsRustJobsAndWorkers` runs a Rust API's
job, which puts objects in its bucket on the emulator, its worker, which
reads and deletes them, and its server, which lists the rest and signs a
URL that downloads one.

## On Google Cloud

A server, job or worker whose APIs list a bucket links GCS's Go client,
depends on its Node client, or in Rust turns on the HTTP runtime's `gcs`
feature, and no other does. The Rust one links no Google library: it calls
Cloud Storage's JSON API with an access token for its account from the
metadata server. On Cloud Run each reaches the bucket as its own service
account, and signs a URL as that account through IAM's `signBlob`.

The gcp target places each Bucket service on the `gcp.storage` platform:
a Cloud Storage bucket in the environment's region, named
`<project>-<stack>-<bucket>` since bucket names are global, with uniform
bucket-level access and public access prevention enforced. Each server,
job or worker whose APIs list it, in any language, gets:

- `roles/storage.objectUser` on that bucket alone, to read, write, list
  and delete its objects;
- `roles/iam.serviceAccountTokenCreator` on its own service account,
  which signing a URL through `signBlob` needs.

The derived field holds the bucket's name alone. A member of a
parameterized environment gets a bucket of its own, which its destroy
empties; any other bucket keeps its objects, and a destroy of a bucket
that holds some fails.

| Setting | Default |
| --- | --- |
| `versioning` | false: an object's earlier versions are not kept |
| `deleteAfterDays` | none: an object stays until it is deleted |
| `cors` | none: the bucket answers no browser's preflight ([Let a page reach the bucket](#let-a-page-reach-the-bucket)) |

```ts
@environment({
  target: "gcp",
  gcp: { project: "acme-prod", region: "us-east1", production: true },
  settings: [{ of: ShopMedia, versioning: true }]
})
export abstract class Production {}
```

The `buckets-never-public` policy rule refuses a bucket that is not
private, and any grant of one to `allUsers` or `allAuthenticatedUsers`,
an exposed server's included. `stack bootstrap` gives the `deployer`
account Storage Admin, to create the buckets and set their grants.
