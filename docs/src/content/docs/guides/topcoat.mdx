[Topcoat](https://github.com/tokio-rs/topcoat) is a Rust web framework for
server-rendered pages. Its pages run in the same process as a service's
Rust implementations. It leaves validation and authentication to the app,
and a Rust API already has both, for each route. The Topcoat extension
writes a crate that lets a page call an operation directly, by the route's
rules. For the operations a page can call, the crate also has a form per
input type, nested objects and lists included, and per operation's other
arguments, a filter for a GET, and a record per result type, with
components that render each record, and it mounts the JSON API beside the
pages.

The acme shop's `topcoat/` app is a small shop over `shop-orders`, on
the implementations its [Rust server](/superschematic/guides/api-routes/#the-rust-server)
serves, which keep the shop in memory or in a SQLite file, with the
shop's users in SQLite. A shopper signs in with their password, writes a
review at `/reviews`, places an order at `/orders/new`, picking each
line's product from the catalog `shop-orders` lists, filters their orders
at `/orders` and pages through them, and cancels one from its page,
`/orders/{id}`, each page's input taken through a form the crate builds.
The crate also generates a console of the shop's resources at `/console`
([Generated pages](#generated-pages)), with a back office beside them:
`shop-db`'s engine types at `/console/engine` ([Engine
pages](#engine-pages)) and the shop's users and roles ([Sign-in and admin
pages](#sign-in-and-admin-pages)). The pages and the console show a
shopper their own orders alone, since the implementations list, read
and cancel no other customer's, and staff, who hold `orders.any`, every
customer's. They show the shop's amounts as money, `GBP 39.98`
([Money](#money)).

## Build the crate

The extension is a Go module of its own, `extensions/topcoat`. The
installed `superschematic` binary does not link it, since Topcoat is
before 1.0; `superschematic-topcoat` is the installed binary with it
linked beside the official extensions, so it builds and deploys
everything `superschematic` does: {/* verify: b4 */}

```bash
cd extensions/topcoat && go build -o superschematic-topcoat ./cmd/superschematic-topcoat
```

The crate needs the Rust server. A service turns it on with
`outputs.topcoat: { enabled: true }` in its config, or by being listed in
`superschematic.toml`. A binary without the extension, `superschematic`
included, never reads that table, so the same configs still build there:

<Snippet file="schemas/superschematic.toml" from="[extension.topcoat]" to="services" />

Then build the service with its server in Rust:

```bash
superschematic-topcoat build --with-deps --api-language RUST --out schemas/dist-rust schemas/services/shop-orders
```

The crate, `acme-shop-orders-topcoat`, lands in
`schemas/dist-rust/topcoat/shop-orders`, beside the API crate it builds
on. A service whose server is in another language skips the crate and
says why in the build log, so the same config also builds the Go server.
The crate pins Topcoat 0.10, which needs Rust 1.98 or newer.

The crate's forms, records, procedures and display components, below,
are on by default. In `outputs.topcoat`, `forms: false` leaves out both
kinds of form, `procedures: false` the procedures, `views: false` the display
components, and `records: false` the records with the procedures and the
display components, which are built on records. Its
[generated pages](#generated-pages) are off until a config asks for them.

## Mount it

`shop_orders` keeps the API's `Implementations` for the in-process calls
and mounts the JSON API at `/api`, giving its routes the client's address
as Topcoat reads it, by which their rate limits count clients. It also
takes a `PageAuthenticator`, which establishes a page's caller. The shop's
users are the core user model's, so the crate offers
`IdentityPageAuthenticator::of(&implementations)`, which reads a page's
caller from the session cookie or bearer token as the JSON API does. One
sign-in serves the pages and the JSON API, and a refused cookie is cleared
on the page's response. An app whose users are its own writes a
`PageAuthenticator` instead, over a Topcoat session, say.

<Snippet file="topcoat/src/lib.rs" symbol={['app', 'SignInForm', 'sign_in']} />

`shop-orders` serves no login route (`shop-api` does), so the sign-in page
calls the identity service in process: `login` with a cookie session,
after the cross-origin check a cookie login passes, then the session
cookie on the page's response. Where the mounted API serves
`@userSessions`, the browser can post JSON to `/api/auth/login` with
`session: "cookie"` instead. The app serves plain HTTP locally, so its
identity config turns the cookie's `Secure` off. Topcoat's origin policy
runs before the identity check, so an origin the identity config trusts
must be one the app's `OriginPolicy` trusts too.

The API's own authenticator still decides whether a caller's permissions
cover an operation's. A page and the JSON API therefore admit the same
callers. The app names the crate, so the linker keeps it and `.discover()`
finds its procedures.

### Several services in one app

`[extension.topcoat] services` lists the services one Topcoat app hosts.
Each crate's `<service>(implementations, page_authenticator)` mounts its
JSON API at `/api/{*rest}`, a route Topcoat refuses twice as the app
builds, so an app that hosts several services sets one up that way and
the others with `<service>_without_api`, which keeps the implementations
for the in-process calls and adds the crate's pages', procedures' and
pickers' controls, with a registry of limiters of its own, but mounts no
JSON API. The app serves at most one service's JSON API at `/api`:

```rust
Router::builder()
    .discover()
    .fixture_console_api(console, Clerk)
    .fixture_console_suppliers_api_without_api(suppliers, Clerk)
    .build()
```

An app links the crates of every service its crates depend on, and
`.discover()` registers their pages, set up or not. A call into a crate
the app did not set up answers with a 500 that names the setup it lacks,
`the app does not host fixture-console-suppliers-api: ...`, not a panic,
so a page that names one of its items shows the item's id instead.

When the table lists a service and an API dependency of it, a reference
whose options are the dependency's own operation calls the dependency's
crate in-process ([Choices from references](#choices-from-references)).
The service's crate then depends on it, at `../<dependency>`, which
`build --with-deps` builds first.

A page whose operation would refuse a caller who is not signed in shows a
Sign in button. It opens the sign-in page with the page to come back to
(`next`), which the sign-in form sends along, and a sign-in goes back
there only when `next` is a path of the app, never another host's:

## Call an operation from a page

`operations::<namespace>_<operation>(cx, args)` runs an operation as its
route does:

1. the caller, admitted by the route's rule (401 without one, 403 without a
   permission it lists);
2. the arguments, checked by the router's rules (the same 400);
3. the implementation.

`can_<namespace>_<operation>(cx)` admits the caller alone, for a page that
shows or hides what the operation does. An operation only a service may
call (`@requireService`) has no such call, so a page cannot call it for a
reader, and its guard refuses one 401 `service_unauthorized`, as its route
refuses a request without a service credential. A page that acts as a
service calls it, and any operation with a service clause, through
`operations::as_service(&caller)`, the caller one it names with
`ServiceCaller::in_process(deployable, serves)` and holds to the route's
`from`
([Calling an operation in-process](/superschematic/install/rust/#calling-an-operation-in-process)).
The acme pages ask the guard whether to show the sign-in button above a
form:

## Forms

The crate's `forms` module has a form for what a page submits to an
operation, of two kinds that share their controls, their decoding and
their errors. An **input form** holds an input type's fields, parsed by
the type's rules. An **argument form** holds an operation's arguments,
in its path, its query or its body, parsed by the route's own rules
(`Args::check`), and embeds the input's form when the operation takes
one. A form holds each field as the browser sends it, so a refused form
renders again exactly as it was sent.

### An input form

An input type gets a form when an operation a page can call takes it and
the service declares it; the build log names any other and why. The user
model's operations are not among them: the identity runtime serves them,
so login's input has no form, and a page signs a user in through the
identity service ([Mount it](#mount-it)).
`forms::WriteReviewInputForm` holds `WriteReviewInput`'s fields, each an
`Option<String>`. `parse()` reads them by the type's rules, and
`FormErrors::from_api` turns the operation's refusal into the same field
messages:

<Snippet file="topcoat/src/lib.rs" symbol="post_review" />

`write_review_input_fields` renders the form's fields with the attributes
the input type's rules give them: `required`, `min` and `max` on the
rating, `maxlength` on the title. A browser checks them before it sends the
form, and `parse()` checks every rule again. A field is labeled by its
`@docs` title, else by its name in words, a number at the end of a word
a word of its own: the shipping address's `line1` reads "Line 1". An
enum's member, a select's option or a checkbox's label, is labeled by its
title, a JSDoc `@title` on the member, else by its name in words: `OnHold`
reads "On hold".

### Nested objects and lists

A control is named by its field's path in the input, so a form holds an
input of any shape. `shop-orders`' `PlaceOrderInput` has a nested
`shippingAddress` and a list of `lines`, each a product and a quantity:
`place_order_input_fields` renders the address in a `<fieldset>` whose
controls are `shippingAddress.city` and the rest, and each line in a
fieldset of its own, `lines[0].productId` and `lines[0].quantity`.
`PlaceOrderInputForm` holds them as `ShippingAddressForm` and a
`Vec<PlaceOrderLineForm>`, and `Form<PlaceOrderInputForm>` decodes a post
into it, a list's rows in the order of their indexes. An error, `parse`'s
or the operation's, is keyed by the same path, so it renders at its
control: a quantity over 99 on the second line is shown on
`lines[1].quantity`.

A new form, `PlaceOrderInputForm::new()` and the component's default,
holds each field's `@default` and each list's first rows: `listMin`, or
one for a required list. A list of an enum's members is a group of
checkboxes, and an optional nested object is sent only when one of its
fields is, so none of its controls is required.

### Rows without JavaScript

A list's rows are added and removed by submit buttons named `_action`:
`add:lines` after the rows, until the list holds its `listMax`, or 1000
rows for a list without one, and `remove:lines[1]` in each row while it
holds more than its `listMin`. The
form keeps the button pressed, and `apply_action()` applies it and says
whether a row button submitted the form, in which case the page renders
the form again, 200, without calling the operation. The acme app's
`POST /orders/new` does that, then places the order and goes to its page,
or renders the form again with each error at its control:

<Snippet file="topcoat/src/lib.rs" symbol="place_order" />

A page answers with one view, so the row action and a refusal set the
status, and both render the same `place_order_page` component. The
buttons skip the browser's checks (`formnovalidate`), so a row can be
added before the others are valid, and a list within a row has buttons
of its own, named under the row. Enter in a text field presses a form's
first submit button, so the component renders a hidden one ahead of
every row button, which submits the form with no `_action`, and the page
puts its own button after the component, in the one `<form>` around it.
The extension's tests check every page they render for that order
without a browser, through `extensions/topcoat/testdata/enter.rs`. The
file ships with neither the extension nor the crate, so an app's tests
copy it from the superschematic repository to use it too.

The page answers a refusal with its status, through a `Refusal` of
`forms`, the status and the errors the form renders again with:
`Refusal::from(errors)` for a form `parse` refused, 422, and
`Refusal::from_api(&err)` for the operation's refusal, with the route's
status, so a shopper who is signed out gets 401. An argument form's
`submit` returns one ([An argument form](#an-argument-form)).

A form reads no more than a browser could send it. It reads one row past
a list's limit, which `parse` refuses at the list, and at most 5000 names
and values, past which it reads none and `parse` refuses the form. A post
of 20,000 `lines[n]` renders the form again with 51 lines, not 20,000.

The row type's `@display` names the rows and the add button: each row is
numbered by its `noun` ("Line 1"), else by the list's label, and the add
button says its `createLabel` ("Add a line"), else "Add". A field's
`@docs` title is its label, so the line's product reads "Product":

### An argument form

An operation a form submits gets `<Namespace><Operation>ArgsForm`, named
after its `Args` struct: a GET operation with a query argument, whose
form is a filter, and any other operation with an argument beside its
input. A GET whose path carries its only arguments, `getOrder(id)`, is a
link and has none. The form holds each argument, a list's every value,
and `input`, the input's form, when the operation takes one, so one
`<form>`, one `parse()` and one component cover the arguments and the
input's fields. `parse()` writes each argument as the JSON a request
carries, decodes it into the `Args` struct and checks it as the router
checks a request's, so a value the JSON API would refuse with 400 is that
argument's error. `submit(cx)` parses the form and makes the in-process
call. Its refusal is a `Refusal`: the status the page answers with, 422
for a form `parse` refused and the route's status for the operation's
refusal (401, 403, 404, 409, ...), and the errors the form renders again
with.

`<namespace>_<operation>_args_fields(form, errors)` renders each argument
with the control an input field of its type gets: a `<select>` for an
enum, a group of checkboxes for a list of an enum, an input per value for
any other list, `min` and `max` on a number, `maxlength` on a string. An
argument is labeled by its name in words, and its description is a hint
under the label. A path argument is a hidden input: `new(id)` builds the
form of one resource, such as the order a cancel button cancels.

The acme order page renders `order_cancel_order_args_fields` under the
order's detail while the order is placed. `POST /orders/{id}/cancel`
takes the id from its route, not from the hidden input, which a reader
can change, then submits the form. It goes back to the order's page
(303), or renders the page again with the form as sent and the refusal's
status: 422 for an over-long reason, its message at the reason, and the
operation's 409, for an order no longer placed, its message the form's
own:

<Snippet file="topcoat/src/lib.rs" symbol="cancel_order" />

`path_param!(id: types::IdentityUUID, error = not_found)` declares the
route's id, so a path that holds no id is a 404.

A GET operation's form is a filter. Its `METHOD` is `"get"`, and a page
reads it from the query with Topcoat's `Form<T>`, which reads the query on
GET, or with `from_query(cx)`, so the controls show the filters in effect.
A list's values are repeated keys, `statuses=placed&statuses=shipped`, and
a comma-separated value is split as the router splits it. A blank field is
absent, or its declared default. A filter's boolean is a `<select>` of Yes
and No after a blank option, so a filter can leave a flag out, ask for
false, or turn off a flag whose default is true; a new form selects the
default. Any other form's boolean is a checkbox, as an input's is:
unchecked is false, whatever the argument's default, which only checks
the box of a new form.

An operation whose input is optional takes it only when one of its fields
is sent, so a blank form calls it without one.

The acme orders page answers with the status `submit` keeps, as the JSON
API would: a caller the route refuses gets its 401 and the sign-in
button, and a filter the route's rules refuse gets 422 and the message
at its control. `listOrders` pages, so the page shows the orders a page
at a time ([A paged list and a search box](#a-paged-list-and-a-search-box)):

<Snippet file="topcoat/src/lib.rs" symbol="show_orders" />

### A paged list and a search box

A `@paginated` operation's call takes the page it asks for in its `Args`,
`page`, and returns a page: its items and `next`, the cursor of the
following page, none after the last
([Pages](/superschematic/guides/api-routes/#pages)). Its argument form, which every paged
operation has, holds `cursor` and `limit` as the query sends them and
renders a control for neither. `page()` reads them by the route's rules,
so a cursor outside the base64url alphabet or a limit past the route's
maximum is the router's 400, which `submit` answers with, and
`query_pairs()` is the query the form holds, its filters and the limit
but never the cursor, from which a page builds its links. The acme orders
page links the next page with them and `cursor`, the page's `next`, and
the first page with them alone, after a later page:

<Snippet file="topcoat/src/lib.rs" symbol={['orders_href', 'pager']} />

Its errors are the form's, so a cursor no page gave, `/orders?cursor=e30`,
answers 400 with "cursor: not a cursor this operation returned" above the
filter, and a limit past `listOrders`' 100 "limit: must be at most 100";
the page still links the first page.

A `SearchQuery` argument is its form's first control, an
`<input type="search">` labeled "Search", with its rules' attributes, and
a page that pages the list carries it in its links. `listReviews`' `q` is
the first control of the console's reviews filter
([Generated pages](#generated-pages)).

A sorted operation, one with a `SortBy` argument
([Pages](/superschematic/guides/api-routes/#pages)), reads its order in
`page.sort`. Its form holds the sort as it holds the limit, `sort` as the
query sends it, with no control of its own: `page()` reads it by the
route's rules, a sort the route does not offer being its 400, and
`query_pairs()` keeps it before the limit, so a page's links keep the
order. The in-process call unbinds the cursor from the sort before the
implementation reads it, and binds the page's `next` to it after, as the
router does: a cursor from the JSON API pages the call, one from the call
pages the JSON API, and one returned under another sort is the 400 at
`cursor`. A sorted operation's procedure takes `sort` beside `cursor` and
`limit`.

### Typed controls

A `Temporal.Date` field or argument is `type="date"` and a
`Temporal.Time` one `type="time"`. A `Temporal.DateTime` one is
`type="datetime-local"`, which carries no offset, so the form reads it as
UTC and its label says so, and a value held with an offset renders in
UTC. Long text, a text field or argument whose `maxLength` is 500 or
more, such as a cancel's reason or a review's body, is a `<textarea>`
with the same `minlength` and `maxlength`; its pattern, which a textarea
does not take, is checked by `parse()`. A field's multiline hint
overrides the 500 rule either way: `@display({ multiline: true })` makes
its text a textarea whatever its `maxLength`, a note without a bound,
and `@display({ multiline: false })` keeps it one line at any bound. The
hint applies only where the control would be text: an email, URL, phone,
date or time keeps its control, and the build log says it ignored the
hint. An argument takes no decorator, so it keeps the 500 rule. A
review's body says `@display({ multiline: true })`, which its
`maxLength` of 5000 would decide alone. A number
field holding a whole number reads any a browser sends, `1e1` and `2.0`
too. A `@secret` field is `type="password"` and is never rendered with
its value, so a refused form asks for it again. A record leaves the
field out, but a form holds what a reader types. A value no control
holds, a union, any JSON value or a map, is a `<textarea>` of its JSON
text.

### Errors

A form's errors are keyed by its controls' names, so each renders at its
control: `parse`'s, and an operation's refusal through
`FormErrors::from_api`, which also places a refused parameter's error,
which the router's 400 names, on that argument's control. A message no
rendered control shows, such as a hidden path argument's, is shown with
the form's own messages, named by its field.

### Choices the app supplies

A page can say what a field's value names with `Choices`, which either
kind of component takes and which turns the text or number fields it
names into a `<select>`: `lines.productId` for every line's product, or
`lines[0].productId` for one line's:

```rust
let choices = Choices::new().with("lines.productId", [(anvil_id.to_string(), "Anvil")]);
view! { place_order_input_fields(form: form, errors: errors, choices: choices) }
```

A choice's value is the id as the API sends it, its compact text, which
is what a record holds and what the select sends back. The display
components take the same `Choices` and show a value's label in its place
([Display components](#display-components)). An API that declares what
the id refers to, as `shop-orders` does, needs none of the app's: the
crate lists the items itself, and the app's choices win where they name
a field.

### Choices from references

An API that declares what an id refers to, `productId: RefersTo<Identity.UUID, ProductView>`
([References and search](/superschematic/reference/references-and-search/#refersto-a-value-that-names-an-item)),
needs no choices for it: the
crate writes `references`, with a function per form that holds one,
`<form>_choices(cx, form, choices)`, and per record, `<record>_labels(cx,
records, choices)`. The first gives each such control the target's items
as options, from the one operation that lists them, called once a request
as the page's caller, its first page when it pages; when more items
follow than the page holds, the control stays a text input, since a
select would hide them. The second names each value the records hold by
its item's label, through the listing operation's lookup argument, the
list argument that narrows it to given values, called with the records'
values in chunks of the lesser of its `listMax` and, when the listing
pages, its `maxLimit`, at most ten calls a target each time. Both
answer under the app's choices, which win where they name a field, and
for which no call is made. The acme new-order page gives no choices of
its own, and `listProducts` searches the products by name, so each line's
product is a search picker, below, of the products it finds, each by its
name. The page passes the form it renders, the one posted after a
"Find", so the picker lists what that text finds:

<Snippet file="topcoat/src/lib.rs" from="let choices = references::place_order_input_form_choices" to="place_order_input_fields(form" />

A caller the listing operation refuses gets a text input and the id, and
the page renders as it did. A reference whose listing operation has no
in-process call, a webhook's, is left out, and the build log says why.

When the listing operation searches, with a `SearchQuery` argument, the
control is a search picker instead, however many items there are: a
search box, `_find.<control>`, labeled after the target's plural and
with the search's rules' attributes, a "Find" button, and the select of
the first page of the items the box's text finds, at the listing's
`defaultLimit`, with a note when more match. The value held is always an
option, named through the lookup. `<form>_choices` reads the texts from
the form it is given, which holds them in `finds`, and every picker
searches its text, so its box always says what its select lists. Each
distinct text is one listing a request, and a request searches at most
ten distinct texts through one listing operation, every picker it lists
counted together; a picker past them lists the first page and says to
search again. A filter's "Find" sends its query, so the matches show
beside the list. A post's posts the form with `_action=find:<control>`,
as a row button does, and the page renders the form again as sent, 200,
without the operation, that picker's text searched past the ten; the
hidden submit ahead of every "Find" is still the one Enter presses. A row
button's post and a refused one render each picker's text searched too,
and a removed line's text goes with it. A text the search refuses shows
the route's message. The app's choices win, with no picker and no call,
and a caller the listing refuses gets the plain control.

Each picker is a Topcoat shard, at
`/_superschematic/<service>/_pick/<target>`. Without Topcoat's runtime it
renders in place. With it, the picker renders again as the reader types
and each time the reader presses "Find", the same text too, the value the
select holds kept, and its requests meet the listing's rate limit and
timeout, as a page that calls it does: past the limit, the shard answers
the route's 429 with `Retry-After`.

A target that an API dependency declares
([Options from an API dependency](/superschematic/reference/references-and-search/#options-from-an-api-dependency))
is listed by the API's own operation when it has one, else by the
dependency's. One app that hosts both, by the table
([Several services in one app](#several-services-in-one-app)), calls the
dependency's crate for its items, under its rules and its setup, and a
page that does meets the dependency's rate limit. Otherwise the reference
is left out, and the build log gives the reason: the table does not list
both, the dependency's config generates no API server, its server is not
Rust, its config or its API cannot be read, or its crate is not built.
The extension reads a dependency's API only for a reference that calls
it, so a dependency no reference calls fails no build. When both APIs
authenticate with the identity runtime, the crate's `identity-*` features
turn on the dependency's crate's too.

## Records

`records` mirrors each type a page's call returns, and the types it
nests, as a Topcoat record, which a page hands the browser, here through a
shard:

<Snippet file="topcoat/src/lib.rs" symbol="review_card" />

A record holds the type's JSON as the API sends it. UUIDs, timestamps and
enums are strings, a map is its entries, and an `@uiHidden` or secret
field is left out, since a record reaches the browser. A webhook's result
reaches no page, so it has no record ([Procedures](#procedures)), and the
user model's routes have none, since a page does not call them in-process.
A paged operation's page is a page record, `<Element>PageRecord`, its
items' records and `next`.

## Display components

`views` renders each record two ways: `<type>_detail(record)` as a
description list, a label and a value per field, and `<type>_table(rows)`
as a table with a row per record. The shard above renders a review with
`review_view_detail`, an order's page renders the order with
`order_view_detail`, and the orders page renders the shopper's orders
with `order_view_table`. A table's cells are the records' values, with no
links, so the page lists a link to each order's page after it:

<Snippet file="topcoat/src/lib.rs" symbol="order_list" />

A field is labeled as its form field is: its `@docs` title, else its name
in words. A value renders by its type:

- an enum's value is its member's title, else its name in words, in a
  `<data>` element whose `value` is the one the API sends: shop-db titles
  `OrderStatus.Fulfilled` with `/** @title Picked and packed */`, so a
  fulfilled order reads "Picked and packed" in the tables and the
  filters, and a placed one "Placed". `<enum>_label` gives the same label
  for a page's own markup;
- a date, a time or a date-time is a `<time>` element whose `datetime`
  is the value the API sends and whose text a reader reads, the same for
  every reader: "9 Oct 2026", "14:30", and a date-time in UTC to the
  minute, "9 Oct 2026, 14:30 UTC";
- a boolean is "Yes" or "No";
- a nested record is its own detail, and in a table cell its title when
  its type declares one;
- a list of records is their table, any other list a `<ul>`, and a map a
  `<dl>` of its entries;
- a union or any JSON value is its JSON text in a `<pre>`;
- an absent optional value leaves its cell empty.

columns, which are otherwise every field. `titleField` names a detail for
assistive technology (`aria-label`, the noun when the title is empty) and
heads each row. `plural` captions a table. `ReviewView` declares all four:

## Money

An amount in a schema is a whole number of a currency's minor units:
acme's prices are pence, in `Generic.Int64` fields named `*Cents`. A
field says which currency it holds with `@display({ currency })`
([Currency](/superschematic/reference/documentation/#display-currency--on-a-field)):
a code, `"GBP"`, or another field of the same type that holds one.
`shop-orders` gives a literal code to its products' prices, its orders'
totals and lines and its refunds, and a checkout's payment names its
own currency field:

<Snippet file="schemas/services/shop-orders/src/checkouts.schema.ts" symbol="CheckoutPayment" />

A display component then shows the amount as money: the code, then the
amount over its minor units with that many decimals and its whole part
grouped in threes, in a `<data>` whose `value` is the amount as the API
sends it, `<data value="3998">GBP 39.98</data>`. A currency field is read
per record, so each row of a table shows its own. A `Finance.Money` field
without the hint whose type has one `Finance.Currency` field takes it.
The text is the same for every reader, and needs no locale: the minor
units come from superscalar, the scalar crate the types already link,
which the crate's `Cargo.toml` names when it shows money.
`views::money_text(amount, currency)` writes it for a page's own markup.
An amount whose currency is unknown, or not an active ISO 4217 code,
shows as a number, and the build log names each amount a component shows
that way, and why.

A form's amount in a literal currency is a decimal control, labeled with
its code (`Deposit (GBP)`), with `inputmode="decimal"` and a pattern of at
most the currency's decimals. Its reader writes the minor units, so
`4.50` posts 450, and refuses at the control text that is no amount, a
third decimal for GBP or any for JPY, a sign the field's bounds refuse,
and a value past `i64`. An edit page fills the control with `4.50`, not
`450`. The app's choices do not apply to it, since a choice's value is
in minor units. An amount whose currency is another field stays a
whole-number input, with the hint "In minor units of Currency", since
the other field may change in the same form, and it refuses `12.00`,
which a number input would send for twelve pounds.

## Generated pages

An app over an API whose operations list, read, create, edit, delete and
act on records can have a page for each without writing one. The pages
are off by default. A service's config turns them on, under a prefix of
their own, `/console` unless it names another:

```ts
topcoat: { enabled: true, pages: { enabled: true, prefix: "/console" } },
```

The acme shop builds its configs with the installed binary, which does
not link `extensions/topcoat` and refuses `outputs.topcoat`, so it sets `pages_prefix` beside `services` in
`superschematic.toml`'s `[extension.topcoat]` instead:

<Snippet file="schemas/superschematic.toml" from="[extension.topcoat]" to="pages_prefix" />

A path serves the one service the table lists. With more,
`pages_prefix` is a table of each service whose pages are on and its
prefix, `{ "shop-orders" = "/console" }`, since two consoles one app links
cannot share a path or nest one inside the other.

The pages need the forms, the records and the display components, and a
prefix under `/api` or `/_superschematic`, which the crate serves itself,
is refused.

The crate reads the resources from the operations' REST paths and
results. A GET of a collection that returns a list is its list, and a GET
of an item that returns one record its item's page; either makes the
collection a resource. A POST to the collection is its new page, a PUT or
PATCH of an item with an input its edit page, a DELETE of an item its
delete, and a POST, PUT or PATCH of a word after an item, one that names
no collection, an action, a form on the item's page. A collection under an item, `products/{productId}/reviews`,
is nested: its pages live under the item's, and its list and its new link
are a section of the item's page when the parent has one. Any other
operation gets no page, and the build log says why: a PUT or DELETE of a
whole collection among them, which no page does, and a DELETE of a word
after an item, which an action's form would do without asking first. So
does a collection whose pages would be served at the console's own: a
list at `orders/new`, beside the orders' new page, or one named `edit` or
`delete` under an item that has an edit or a delete page, since
Topcoat's router refuses a page registered twice. Each resource is
named by its type's `@display` (`noun`, `plural`, `createLabel`,
`titleField`) where it declares them. Else the collection is titled by
its path's last word as the path gives it, `shelves` Shelves, and an item
by its type's name in words, `Shelf`, never by a singular guessed from
the plural. A collection whose path extends another's, `orders/archived`
beside `orders`, is titled by its own words, Archived.

`shop-orders` gives the acme shop this console:

| Page | Path |
| --- | --- |
| The index of the resources the shopper may list | `/console` |
| The orders, a page at a time, with their filter and a link to each | `/console/orders` |
| The new order, each line's product a picker of the products, and the POST that places it | `/console/orders/new` |
| An order: its detail, its lines by their products' names, and the cancel form | `/console/orders/{order_id}` |
| The cancel's POST | `/console/orders/{order_id}/cancel` |
| The products, a page at a time, their `ids` lookup a product select, and a link to each | `/console/products` |
| A product: its detail and its reviews' first page, with a link to the next | `/console/products/{product_id}` |

`listProducts` admits anyone, so the index and the nav list the products
to a shopper who is not signed in too, and each row links to its
product's page, which `getProduct` reads, since its `productId` refers to
`ProductView`; the trail names a product by its title. An API whose
operations edit or delete an item gets `/edit` and `/delete` pages under
it too, the edit form filled from the item and the delete confirmed on a
page of its own before its POST.

Every page calls its operation in-process, so the route's caller rule and
argument checks hold, and takes its input through the [forms](#forms).
Its request meets the route's rate limit, body limit and timeout too, in
the route's order, through a layer `shop_orders` adds at the prefix: a
post the controls of the operation it submits, a list's page or an
item's those of the operation it shows, and every page the rate limit and
timeout of the listing operations its
[references](#choices-from-references) call. `placeOrder` allows a client
60 a minute, and the console's new-order post takes from the same budget
as `POST /api/orders` and the operation's procedure: `shop_orders` makes
one limiter per operation, keyed by the client's address, and the JSON
API, the procedures and the pages all take from it. A
refusal is the route's 429 with `Retry-After`, 413 or 504, as the pages'
refusal section without the layout, since the page did not run. A
route's values come from the page's path, never from the form's hidden
inputs, and one its argument does not decode is no page (404). A post
that succeeds redirects (303): to the item after a create, an edit or an
action, and to the list after a delete. A refused post answers with its
`Refusal`: the form again with each error at its control, 422 for what
the form's rules refuse and the route's status for what the operation
refuses, a conflict's message (409) as the form's own. A refused caller
keeps the route's status on a page of its own: 403, 404, and 401 with a
link to the app's sign-in page that comes back to the page.

A layout at the prefix puts each page in `<main>`, after a nav of the
resources the caller may list, the current one marked with
`aria-current`, each after its type's icon when its `@display` names one
(`<span class="ss-icon" data-icon="receipt" aria-hidden="true">`, which
the app's stylesheet draws, since the crate ships no icon set: acme's
`ProductView` and `OrderView` name `package` and `receipt`), and a
breadcrumb trail from the index to the page, an
item by its title where its type declares one. Else an item is named by
the label of what its route's value refers to, when every operation whose
route holds that value refers to one target by one value, so a supplier's
products at `suppliers/{supplierId}/products` name their supplier though
no operation reads one; else by its noun and id. A list whose path extends
another's, `orders/archived` beside `orders/{id}`, is its own in both,
never an order named archived. List rows link to their items through the
`hrefs` prop each `<type>_table` takes, a row without a title by its noun
and id. A render asks the app's `PageAuthenticator` for its caller once,
and the nav's guards are permission checks of that caller. The markup has
the display components' `ss-` classes and no styles.

The app's `.discover()` registers the pages, as it registers the
procedures. The app tells them its site's title, its sign-in page and
any choices of its own through `pages::Settings` in its app context. The
acme app gives its title and sign-in page and no choices: the console
names what an order's lines refer to through `listProducts`, so the

A paged list's page renders the page's items, then a `<nav
class="ss-pager">`: "First page" on a later page, "Previous page"

`role="search"` form. Every form a page renders

detail whose path parameter refers to its own type, `products/{productId}`.

### Live lists

With `live: true` beside `enabled` in `outputs.topcoat.pages`, or
`pages_live = true` beside `pages_prefix` in the table, each list with a
filter, or that pages, renders through a Topcoat shard at a path of its own,
`/console/_live/orders`. Without Topcoat's runtime in the browser nothing
changes: the filter is a GET form and its submit loads the page. With
it, the submit sends the form's query to the shard, which renders the
list again in place, and puts the query in the address bar. A shard's
request meets no page's guard, so the shard reads the query as the page
does and calls the list through the in-process call, which admits the
caller and checks the filter, with the route's status for a refusal. The
runtime applies only a 200, so a refusal leaves the table as it was
until a reload. A paged list's links set the shard's query too, so a list
pages in place, back and forth, with or without a filter, and its size
form sets the query as the filter does. A sorted list's header links set
it as well, and the headers follow the order the shard renders. An action's form keeps its
POST-redirect-GET.

## Engine pages

When the API's database is an engine database ([The
engine](/superschematic/guides/engine-behaviors/)), and the crate's pages
are on and a route of the API authenticates a caller, the console pages
the engine's types under `<prefix>/engine`, with no code of the app's:

| Page | Path |
| --- | --- |
| The engine's types the caller may read | `/console/engine` |
| A type's instances, a page at a time, and the type's own operations | `/console/engine/{schema}` |
| An instance: its fields, a panel per behavior, and its operations | `/console/engine/{schema}/{id}` |
| An operation of a type or an instance: a read's GET, a write's POST | `.../operations/{operation}` |

Every page calls the engine in-process, as the page's caller, the one
the `PageAuthenticator` establishes, so the engine's policy decides what
each page shows and what each form may do. No page acts as the engine's
system principal, so a signed-out caller is 401, with a link to sign in.
A post another site sent is refused (403). The
pages read each type's describe document, so a type published after the
build has its pages too. A list is paged as the console's lists are, by
the engine's cursor, with its title and summary fields as columns. An
instance's page shows its own fields, an amount as money in the
currency its `@display` names, then a section per behavior, then the
operations no section shows.

An operation's form is built from its parameters' JSON Schema. A write
sends the instance's `expectedSeq`, so a page read before another write
is 409 rather than a write over what the reader did not see. A read
renders its result on the page. A refusal renders as the console's do: a
parameter at its control (422), a behavior's veto as its code and
message (409, `approvals_missing: Refund needs 2 sign-offs for approved,
and has 1`), an operation the caller's policy refuses 403, and one the
deployment hides from its tools 404.

A behavior the crate knows has a panel:

- **Workflow**: the state by its display label, a button for each move
  the display labels, and a select of the other moves the caller may
  make.
- **Approvals**: each gate's sign-offs against its count, who signed,
  and the caller's own sign-off or withdrawal.
- **Branches**: the refs, a ref's history 50 commits at a time, a diff of
  two commits, the release log, and the branch, save, commit, merge and
  discard forms.
- **Stock**: on hand, held, available and low, the receive, adjust and
  count forms, and the movements.
- **Calendar**: the time zone, the opening hours as a week, the closures,
  and the bookings of a range of dates.
- **Holds**: the items with their unit prices, and the total, as money.
- **Payments**: what is due, authorized, captured and refunded, as money
  in the payment's currency, the attempts, and how the instance is
  refunded: a link to the type whose sign-offs refund it, or a refund
  form.

Any other behavior, a project's own among them, gets a generic panel: its
fields as the read returns them, and its operations as forms.

## Procedures

Each operation is also a procedure on
`/_superschematic/shop-orders/<namespace>/<operation>`, which browser code
calls with its arguments as a record. It answers the result's record, or a
`ProblemRecord` with the route's status, code and detail and each refused
field's path, rule and message, since a procedure's `Err` would reach the
browser as a bare 500. `call_<namespace>_<operation>(cx, args)` is the
procedure's body as a plain function, for Rust code and tests: Topcoat
turns the procedure itself into a value Rust cannot call. A paged
operation's procedure takes `cursor` and `limit` beside its arguments and
answers its page record.

A procedure is a second route to its operation, which any browser can
reach, so an operation gets one only where a browser's request can meet
its route's rules. A webhook (`@webhook`, `@hmacVerified`) has neither an
in-process call nor a procedure: a third party calls it, and its route
checks the signature before anything else. Nor has an operation the
service mounts itself (`@manualRouteRegistration`). An operation only a
service may call (`@requireService`) has no procedure, since a browser
holds no service credential, and no end user's call, only a service's
(`operations::as_service`); an `@allowService` one keeps both, since its
route admits an end user too.
Each guard's or call's doc says why, and so does the build log. The
result of an operation without a call reaches no page, so it has no
record and no display components, and its input has no form.

A procedure keeps its route's traffic controls, in the route's order, and
refuses as the route does, as a `ProblemRecord`: `placeOrder`'s procedure
allows a client 60 calls a minute (429 with `Retry-After`), a body of a
megabyte (413) and ten seconds (504). `shop_orders` puts a layer with
them on the procedure's path. Its limiter is the operation's one, which
the JSON API's route and the console's pages share, and counts clients by
the IP address Topcoat reads for them, so a client has 60 a minute
through the route, the procedure and the console's pages together. A
page's in-process call applies none of them, nor does a call as a
service: the page is a route of the app, under the controls the app gives
it. The [generated
pages](#generated-pages) apply them to their own requests.

```bash
superschematic migrate plan schemas/services/shop-db --dialect sqlite --out shop-db.sqlite.plan.json
superschematic-migrate apply --plan shop-db.sqlite.plan.json --database-url sqlite:shop.db
cd topcoat && DATABASE_URL=sqlite:../shop.db cargo run
```

The runner records the model it applied, so a later version of `shop-db`
plans `--from` it ([Adopt a database built from
create.sql](/superschematic/reference/migrations/#adopt-a-database-built-from-createsql)
shows the commands). `Review`'s search fields give the SQLite table its
`search_text` column, `VIRTUAL`, without the trigram index Postgres
builds.

An order stores its total, `totalCents`, so the orders table sorts by
it. `shop-db`'s plan adds `total_cents` as a required column with no
default and no backfill: a schema's `Default` fills in the decoders'
value, not the column's, and a backfill is a migration written by hand.
So a database that already holds orders cannot take the column, in
SQLite or in Postgres; the step fails on its first order. Delete a
`shop.db` made before it and plan it anew. Purge a `Dev` environment
made before it with `superschematic stack dev --remove-data` once, which
removes its containers and their data as it stops, after the failed
migration too, then run `stack dev` again.

## Run the app in a stack

The app above keeps its shop outside any stack, in memory or in a SQLite
file. A Topcoat app can instead run in a [stack](/superschematic/guides/stacks/#apps)
beside its API's server, over the stack's database, with the API's
identity and its engine on Postgres: an app the API declares (D78).
Declare it on an empty class of the API, naming the extension its build
needs:

```ts
import { app } from "@superschematic/api";

@app({ extensions: ["topcoat"] })
export abstract class Backoffice {}
```

The API must be Rust, and its build must link the extension: run the
stack's commands with `superschematic-topcoat`. The core binary still
plans and inits the stack, and refuses to build it, saying to run
`superschematic-topcoat`.

The app's program is a library crate at the naming file's
[`[implementation_paths] rust_app`](/superschematic/reference/naming/#implementation_pathsrust_app),
`apps/{app}` by default, with `{app}` the class in kebab case. It
exports one function, which the app's generated entrypoint calls once the
API's `Deps`, its implementations and its engine are ready:

```rust
pub async fn serve(parts: <api crate>::apps::<App>Parts) -> std::io::Result<()>
```

`<App>Parts`, which the API crate's `apps` module declares, holds the
API's `deps`, its `implementations`, with the authenticator its router
takes, the `engine` of its engine database, open on the stack's database,
and `addr`, every interface at `PORT`, 8080 when it is unset. The first
build that finds no crate there writes one, whose `serve` listens on
`parts.addr` and answers every request with 501 Not Implemented and
`app Backoffice of shop-stock does not serve yet: write its serve`. The
stack runs it, ready, until you write yours. The crate is yours from then
on, and the build never writes it again.

The Topcoat crate of an API that declares an app has one more setup
method, `<service>_with_parts(parts)`. It sets the crate up from the
parts as `<service>` would from them: the implementations, the engine
the entrypoint opened, in place of `engine::open` on a SQLite file, and,
for an API on the identity runtime, `IdentityPageAuthenticator::of` over
the implementations. An API whose users are its own passes its
`PageAuthenticator` after the parts. It mounts the JSON API at `/api` and
the engine at `/engine`, as `<service>` does.

on the container's loopback and never pass its startup probe. acme's
