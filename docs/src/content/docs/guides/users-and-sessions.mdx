A project's users can be a core model it turns on in its schemas. One DB
table takes the `User` trait and, for roles, one takes the `UserRole` trait.
The build adds the tables that hold sessions, password hashes and role
grants. An API serves the routes users sign in and out with, and every
server, Go, TypeScript or Rust, and the engine, authenticate those sessions
the same way. [Auth and permissions](/superschematic/guides/auth-and-permissions/)
covers what a route requires; this page covers who the caller is.
[D50](https://github.com/parable-work/superschematic/blob/e8e685a5149a8897001153fb6cca1100ac90d0c0/docs/DECISIONS.md)
records the design.

## Turn it on

The traits come from `@superschematic/db`. `User` names the field a user
signs in with, and `name` the field their display name comes from, the
login when it is left out. `shop-db` declares both:

<Snippet file="schemas/services/shop-db/src/shop.schema.ts" symbol={['User', 'Role']} />

The rules, which the build checks in every schema form:

- A DB schema has at most one `User` table and one `UserRole` table, and a
  `UserRole` table needs a `User` table beside it.
- The login is a `@unique`, required field typed by a scalar superscalar
  declares case-insensitive, such as `Contact.Email` or `Identity.Slug`. The
  scalar folds case and its column is `CITEXT` (`TEXT COLLATE NOCASE` on
  SQLite), so `Ada@Example.com` and `ada@example.com` are one login.
- A role table has a `@unique` text `name` and a `permissions` list of
  strings.
- Both tables have one `@key`.
- Registration and the administration routes write a user's key, login
  and name alone, so every other field of the `User` table is optional,
  generated, a timestamp the DDL defaults to now, or has a `Default<T, V>`
  its column carries: text, a number, a boolean or an enum member, such as
  `active: Default<boolean, false>`
  ([Columns](/superschematic/guides/database-tables/#columns)).

A schema without the traits builds exactly as before.

## What the build adds

Beside a `User` table, the build adds four tables the core owns. They go
through the DDL, the ORM, the types and migrations like any other table:

| Table | Columns |
| --- | --- |
| `Session` | `id`, `user`, `tokenHash` (the SHA-256 of the session's token, never the token), `createdAt`, `expiresAt`, `lastSeenAt`, `revokedAt`; indexed on `user` |
| `UserCredential` | `id`, `user` (unique), `passwordHash` (an argon2id PHC string), `passwordChangedAt`, `disabledAt`, `pendingAt` (set while a user waits for approval) |
| `UserApiKey` | `id`, `user`, `name`, `tokenHash` (the SHA-256 of the key's token, never the token), `permissions` (the subset the key was made with, null for all), `createdAt`, `expiresAt`, `lastUsedAt`, `revokedAt`; indexed on `user` ([API keys](#api-keys)) |
| `UserRoleGrant`, with a `UserRole` table | `id`, `user`, `role`, `grantedAt`; unique on `user` and `role` |

A role grant raises an event as any write does: the `UserRole` class
declares an `@enqueueOnChange` of its grants with `of: "grants"`, whose
`fields`, `when` and `message` name `UserRoleGrant`'s columns, and the
build copies it onto `UserRoleGrant` (#625). Granting a role and revoking
it then enqueue the message whatever writes the grant, the identity
store's routes or a script:

```ts
@enqueueOnChange(RoleGrantChanged, { of: "grants", on: ["insert", "delete"], message: { user: "user", role: "role", grant: "id" } })
export abstract class Role extends Auditable implements UserRole { ... }
```

A declaration without `of` enqueues on the role table's own writes, a
role's rename or a change of its permissions.

It also writes the identity descriptor, `identity/<schema>.json` beside the
Go types and a constant in the Go, TypeScript and Rust types
(`IdentityDescriptor`, `identityDescriptor`, `IDENTITY_DESCRIPTOR`). The
runtimes' stores read it to find these tables and the user table's
columns.

## Serve the session routes

An API whose config's `authDb` names that schema serves the routes with
two decorators from `@superschematic/api`, each on a class with no
methods. `shop-api` serves both:

<Snippet file="schemas/services/shop-api/src/account.schema.ts" />

`@userSessions({ path?, login?, register?, registration?, defaultRoles?,
firstUser?, apiKeys? })` serves these, under `auth` by default:

| Operation | Route | Rule |
| --- | --- | --- |
| `login` | `POST auth/login`, `{ login, password, session? }`, answers `{ user, expiresAt, token? }` | anyone; 10 a minute |
| `logout` | `POST auth/logout`, revokes the session and clears the cookie | a caller |
| `me` | `GET auth/me`, answers the user, their roles and their permissions | a caller |
| `capabilities` | `GET auth/capabilities`, answers which of the API's operations the caller may call | a caller |
| `changePassword` | `POST auth/password`, `{ current, password }`, revokes the user's other sessions | a caller; 10 a minute |
| `register`, with `register: true` | `POST auth/register`, answers as `login`, or as [Approve new users](#approve-new-users) says under `registration: "approval"` | anyone; 5 a minute |

`@userSessions({ login: false })` serves `me` and `capabilities` alone,
for an API whose users sign in through another. `apiKeys: true` adds the
routes a user makes, lists and revokes [API keys](#api-keys) with.
`@userAdministration({ path?, apiKeys? })` serves the routes that create, list,
disable, enable and approve users and set their passwords; create, list,
update and delete roles; and grant and revoke them, under `auth/admin`.
They need `identity.users.read` or `.write` and `identity.roles.read` or
`.write`; the naming file's `identity_permission_prefix` renames
`identity`. `GET auth/admin/users?pending=true` lists the users who wait
for approval alone, and `?pending=false` the others.

These are ordinary operations in the OpenAPI document, every SDK and the
tool manifest, but the runtime implements them: the implementation you
write has no method for them. The routes that carry a password publish no
MCP tool, and neither does `createApiKey`, whose answer is a credential.

Every server of an API whose `authDb` has a `User` table authenticates
with the identity runtime, whether or not it serves these routes, so
`shop-orders` accepts the sessions `shop-api`'s login starts.

## Run it

Each server takes the identity service, built over a store of the
`authDb`'s tables and an identity config:

| Server | It takes | Built with |
| --- | --- | --- |
| Go | `Config.Identity`, which `Validate` requires | the generated `NewIdentity(store, cfg)` over `identity.NewSQLStore(db, identity.Postgres, []byte(IdentityDescriptor))` |
| TypeScript | `buildRouter(implementations, { identity })`, which refuses `authenticate` beside it | the generated `identityService()` over `postgresIdentityStore(pool, identityDescriptor)`, `sqliteIdentityStore(...)`, or `sqlDatabaseIdentityStore(db, identityDescriptor)` over the SQLite file a server's repositories share (D116) |
| Rust | `Implementations.authenticator`, an `Arc<IdentityAuthenticator>` | the crate's `identity::store(client)` and `identity::service(store, config)`, with its `identity-postgres` or `identity-sqlite` feature |

[Auth and permissions](/superschematic/guides/auth-and-permissions/#say-who-the-caller-is-go)
shows the Go wiring in `shop-orders`. The generated
constructor hands the runtime how the API's `register` admits users
(`IdentityRegistration`, `identityRegistration`, `registration()`), so a
server wires nothing for it. A stack's
entrypoints build it for you, reading each API's config as JSON from
`<API>_IDENTITY` (`SHOP_API_IDENTITY`); a job, which serves no request,
builds none. A Rust server whose `authDb` lists `sqlite` first keeps its
users, their sessions and their API keys in the database's SQLite file
(D116), as under `stack dev`: its entrypoint builds the store with the
crate's `identity::store_on_file`, on a connection of the store's own to
the file. A stack's Go or TypeScript server over the user model runs on
Postgres. On Cloudflare Workers a TypeScript server serves the user
model when its `authDb` is a Postgres database on Hyperdrive, and hashes
passwords with the runtime's own argon2id, which writes the same hashes
as `node:crypto`'s
([Databases on Hyperdrive](/superschematic/guides/stacks/#databases-on-hyperdrive)).
The config, which the three runtimes read alike:

| Member | Default | Meaning |
| --- | --- | --- |
| `sessionTtlSeconds` | 1209600 (14 days) | how long a session lasts after login |
| `idleTimeoutSeconds` | 0 (off) | ends a session not seen for this long |
| `touchIntervalSeconds` | 60 | how often a session's `lastSeenAt`, and an API key's `lastUsedAt`, is written |
| `apiKeyMaxTtlSeconds` | 31536000 (365 days) | the longest an API key lives, and its lifetime when a create names none |
| `cookie.name` | `__Host-session` | `__Secure-session` with a `domain`, `session` without `secure` |
| `cookie.domain` | none | shares the cookie across sibling hosts |
| `cookie.secure` | true | false only on plain HTTP; the `local` target sets it |
| `cookie.sameSite` | `Lax` | |
| `trustedOrigins` | none | the other origins a browser app is served from |
| `password.argon2` | 19456 KiB, 2 passes, 1 lane | the hash's cost; a login rehashes a password whose cost differs |

## Sign in from an SDK

A client chooses its session's transport per login. A bearer session
returns its token, which the SDK sends as `Authorization: Bearer`:

```go
result, err := client.AccountNamespace.Login(ctx, types.LoginInput{
	Login:    types.ContactEmail("ada@example.com"),
	Password: types.AuthPassword(password),
})
client.SetToken(result.Token)
```

A browser app takes a cookie session. The TypeScript SDK passes
`credentials` to `fetch`, and a login with session `cookie` sets an
`HttpOnly` cookie and returns no token, so no script on the page reads it:

```typescript
const sdk = new ShopApiSDK({ baseUrl: 'https://api.example.com', credentials: 'include' });
await sdk.account.login({ login: 'ada@example.com', password, session: SessionTransport.Cookie });
```

A server reads `Authorization` first and the cookie only without one, and
an `Authorization` that fails is 401 with no fallback. A cookie login, and
every cookie request but `GET`, `HEAD` and `OPTIONS`, from an origin the
config does not trust is refused with 403 `cross_origin`, the check Go's
`net/http.CrossOriginProtection` makes; a bearer request skips it. A
server answers preflights from the trusted origins. A session has no
refresh: after a 401, sign in again.

### A site on the API's origin

A browser app a stack deploys as a [site](/superschematic/guides/static-sites/)
calls the API on another origin unless the stack puts them on one:
`origins: [{ site: ShopWeb, apis: [ShopApi] }]` in `@stack` serves the API
under `/api/shop-api` on the site's own address, in `stack dev` and on
every target ([one origin](/superschematic/guides/static-sites/#one-origin)).
The defaults then serve a cookie session: the API sees the browser's
`Host`, so the cross-origin check passes a same-origin login with no
trusted origin, and the `__Host-session` cookie, with no `Domain`, is the
site's host's alone. Leave `trustedOrigins` and `cookie.domain` unset,
and give `loadApis()`'s client `credentials: 'include'` or
`'same-origin'`. Without an origin, a site on `app.example.com` calling an
API on `api.example.com` needs `trustedOrigins: ["https://app.example.com"]`
set per environment, and both hosts under one registrable domain for the
`SameSite=Lax` cookie to travel with its calls.

Every failed login is 401 `invalid_credentials`, whether the login is
unknown, the password wrong or the user disabled, and an unknown login
takes as long to refuse as a wrong password. The one exception is a user
who waits for approval: once their password verifies, login refuses them
with 403 `pending_approval`, so a sign-in page can say why.

## Approve new users

By default `register` signs the new user in at once. Three members of
`@userSessions` change that
([D81](https://github.com/parable-work/superschematic/blob/e8e685a5149a8897001153fb6cca1100ac90d0c0/docs/DECISIONS.md)),
each needing `register: true`:

```ts
@userSessions({
  register: true,
  registration: "approval",
  defaultRoles: ["member"],
  firstUser: { role: "admin", permissions: ["identity", "finances"] },
})
export class Account {}
```

- **`registration: "approval"`** creates the user pending: the credential's
  `pendingAt` is set, apart from `disabledAt`, so an administrator tells a
  pending user from a disabled one. `register` answers `RegisterResult` in
  place of `LoginResult`: 202 with `{ pending: true, user }`, no session and
  no cookie. Login refuses the user with 403 `pending_approval` until an
  administrator calls `approveUser`, `POST auth/admin/users/{id}/approve`
  (`identity.users.write`), which answers the user with `pending` false, and
  409 `not_pending` for a user who is not waiting. The administration
  routes' `IdentityUser` carries `pending` beside `disabled`.
- **`defaultRoles`** names the roles each new user holds. Register creates
  a role no role has the name of, with no permissions, for an
  administrator to fill in, unless the `authDb` seeds it
  ([Seed the roles](#seed-the-roles)). Under approval the roles are granted with the
  pending user, who can neither sign in nor hold a session, so they take
  effect at approval, and `approveUser` works from any API of the same
  `authDb`. Since approving gives the user those roles, the approver's
  permissions must cover theirs, as they must to enable a user.
- **`firstUser`** makes the registration that finds no role grant, the
  state in which `identity bootstrap` still runs, the database's first
  administrator: active even under approval, signed in (200 with
  `pending: false` and a session), and holding `role`, created with
  `permissions` when no role has the name, beside the default roles. Two
  registrations at once make one administrator: on Postgres the first
  locks the grants table until it commits, and SQLite lets one transaction
  write at a time. A self-hosted app then needs no bootstrap step.

`defaultRoles` and `firstUser` need a `UserRole` table in the `authDb`.
Open registration, the default, grants the default roles too, and its
`register` keeps answering `LoginResult`.

### Seed the roles

A default role that register creates has no permissions, so a user an
administrator approves can do nothing until someone fills the role in.
`@seedRoles` on the `UserRole` table declares the roles every database
holds from its first migration on
([D88](https://github.com/parable-work/superschematic/blob/e8e685a5149a8897001153fb6cca1100ac90d0c0/docs/DECISIONS.md)):

```ts
@seedRoles([{ name: "member", permissions: ["finances.read", "finances.write"] }])
export abstract class Role implements UserRole {
  @key id: AutoGenerate<Identity.UUID>;
  @unique name: Identity.Slug;
  permissions: string[];
}
```

`create.sql` inserts each role, so on an empty database the first
registrant is the administrator (`firstUser`), the second waits, and once
approved holds `member` and calls a `finances.read` route at once. A
migration plan inserts a seed it adds, and gives a role of its name that
has no permissions, as one an earlier registration created, the seed's;
a role of its name with permissions keeps them. A seed whose permissions
change is a `destructive` step, since it replaces whatever an
administrator gave the role: in `expand` when the role only gains
permissions, in `contract` when it loses one. A plan never deletes a role
a seed no longer names.

The seeds are the `authDb`'s, beside its tables, so every API of it
shares them. An API whose `authDb` seeds roles checks them when it
loads, and warns when a default role is not seeded, when a seeded
permission covers none the API requires (a misspelling grants nothing),
and, under approval, when the first administrator's role does not cover a
default role's permissions, since `approveUser` needs the approver's to
cover them. A seed of `firstUser`'s role holds over `firstUser`'s
permissions.

## Roles and capabilities

Roles are rows, which the administration routes edit at run time, and a
user holds any number of them. A user's permissions are their roles',
with the same dotted rule `@requirePermission` uses. No one grants what
they do not hold: writing a role's permissions, or granting a role, needs
the caller's own permissions to cover each one given, or it is 403 with
the uncovered permissions in `details.permissions`. Nor does anyone take
over a user who holds more than they do: setting a user's password,
disabling them and enabling them need the caller's permissions to cover
every permission the user holds through their roles, or it is 403
`forbidden` with the uncovered ones. A user with no roles is anyone's
who holds `identity.users.write`.

`capabilities` answers, for each operation of the API, keyed by its OpenAPI
operation id, whether the route admits the caller, by the router's own
rule, so a UI shows or hides an action without restating it. An
`@requireOwnership` operation answers whether a caller is admitted;
whether they own a resource is still the implementation's.

Each API with permissions also gets `permissions.json` beside its OpenAPI
document: every permission its operations name, with the operations that
need it. A role editor can read it.

## Create the first administrator

An empty database has no roles, so the first administrator comes from a
command, or from the first registration when `@userSessions` names a
`firstUser` ([above](#approve-new-users)). It reads the password from standard input, never a flag, and
refuses once any role has been granted:

```bash
superschematic identity bootstrap schemas/services/shop-db --database-url "$DATABASE_URL" --login ada@example.com --permission identity --permission orders --permission products
```

The compiler builds the descriptor and hands the write to
`superschematic-identity`, the runner in the HTTP runtime's release, so no
database driver is in the compiler. A deploy job runs the runner itself,
with the descriptor the build wrote and the password from a secret on
standard input. See [CLI](/superschematic/reference/cli/).

## The engine

An engine server takes `identity` in place of `authenticate`, and serves
the session routes under `/auth`. A behavior's permission, such as a
Workflow transition's, is then a role's like any other, and the opt-in
`permissionPolicy()` allows an action to a caller holding
`<schema>.<action>`, a behavior's namespace operation that reads to any
caller, since its rows are only those of schemas the caller may read, and
one that writes to a caller holding `<behavior>.<operation>`
(`Comments.claimDeliveries`). A caller acting for another user, an
agent that works for her, also needs `actFor`, a role's permission like
any other ([acting for
someone](/superschematic/guides/engine/#callers-and-the-access-policy)).
See the engine README's Users section.

## Pages with Topcoat

A [Topcoat app](/superschematic/guides/topcoat/#sign-in-and-admin-pages)
over an API whose users are the core model's gets pages for them with its
console: sign-in, which comes back to the page that sent the caller
there, sign-out, an account page that changes the password, and, for a
caller who holds `identity.users.read` or `identity.roles.read`, the
users and the roles, where an administrator adds users, grants and
revokes roles, disables and enables users, and sets a password. Each
page calls the identity service in-process as the signed-in caller, so
the same permissions and the same coverage rule decide as on the
routes. Signing in, signing up and changing a password share the routes'
rate limits, and a sign-up page is served only when the API registers
users or the app's config asks for one. acme's console is at
`/console/users` and `/console/roles`, for Ada.

## API keys

A program that calls as a person, an agent over MCP or a script over
HTTP, should not hold that person's session: it ends in two weeks, an
idle timeout meant for a browser ends it sooner, and it carries
everything the person may do. An API key (D114) is a token a user makes
for it: named, long-lived, revocable, and held to a subset of the user's
permissions when the key names one.

Turn the routes on where the sessions are served:

```ts
@userSessions({ apiKeys: true })
export class Account {}

@userAdministration({ apiKeys: true })
export class Admin {}
```

| Operation | Route | Rule |
| --- | --- | --- |
| `createApiKey` | `POST auth/keys`, `{ name, expiresInSeconds?, permissions? }`, answers the key and its `token`, once | a caller signed in with a session; 10 a minute |
| `listApiKeys` | `GET auth/keys`, the caller's keys that are not revoked, newest first, never a token | a session |
| `revokeApiKey` | `DELETE auth/keys/{id}` | a session |
| `listUserApiKeys`, on `@userAdministration` | `GET auth/admin/users/{id}/keys` | `identity.users.read` |
| `revokeUserApiKey`, on `@userAdministration` | `DELETE auth/admin/users/{id}/keys/{keyId}` | `identity.users.write` |

```go
made, err := client.AccountNamespace.CreateApiKey(ctx, types.CreateApiKeyInput{
	Name:        "triage agent",
	Permissions: types.InputField[[]string]{Set: true, Value: []string{"issues.read", "issues.write"}},
})
agent.SetToken(made.Token) // key_..., shown this once
```

The token is `key_` and 43 characters, sent as a session's is,
`Authorization: Bearer key_...`, and never in the cookie. The database
keeps its SHA-256. Every server of an API over that `authDb` takes it,
whether or not it serves the routes. A TypeScript router whose options
carry the access log writes a row of it for each call a key makes
([The access log](/superschematic/guides/api-routes/#the-access-log)).

- **Its life.** A key ends at its `expiresAt`: `expiresInSeconds` after
  it was made, from 1 to the config's `apiKeyMaxTtlSeconds`, and that
  maximum, 365 days unless the config says otherwise, when the create
  names none. It has no idle timeout. It ends sooner when it is revoked,
  by its user or an administrator, and when its user is disabled, which
  revokes it for good; enabling the user brings no key back. A password
  change does not end it: revoke it from the list.
- **What it may do.** Without `permissions` a key holds what its user
  holds, as the user's roles change. With them it holds each permission
  it names while its user holds it, and the create is refused, 403, for
  a permission the caller lacks. A user who loses a role takes it from
  their keys. The subset narrows permissions, not routes: a route that
  asks only for a caller admits any key, and a row rule
  ([Row rules](/superschematic/guides/api-routes/#row-rules)) sees the
  key's user. An agent that should reach less gets a user of its own
  with a role of its own, or runs as an agent run, whose token is a
  grant on the rows of its task, in the TypeScript runtime
  ([Agent runs](/superschematic/guides/agent-runs/#the-runs-token)).
- **What it may not do.** A key does not act on its own account:
  `createApiKey`, `listApiKeys`, `revokeApiKey`, `logout` and
  `changePassword` need a session, and a key gets 403. A leaked key
  cannot make another, revoke the others or take the account. `me` and
  `capabilities` answer a key with the roles and permissions it holds.
- **An administrator** lists and revokes any user's keys, and makes none
  for another user: making one is signing in as them.

The table is added for every `User` table, so a project built before
this has one new table to migrate, an expand step with no hazard
([Migrations](/superschematic/reference/migrations/)). Migrate
before the new server runs, as for any expand step: a server ahead of its
migration serves sessions as before, and a bearer key, and the disabling
of a user, which revokes their keys, fail until the table is there.

## OAuth: connecting Claude and other clients

An API key is pasted into a program by hand. Claude's connectors, on
claude.ai, Desktop, mobile and Cowork, connect a remote MCP server only by
OAuth, from Anthropic's side, so they cannot take one. With `oauth` the
API is its own OAuth 2.1 authorization server
([#695](https://github.com/parable-work/superschematic/issues/695)): a
client sends the person to the API's own sign-in and consent page, and
holds a grant that narrows the person's permissions as an API key does.

```ts
@userSessions({ oauth: true })
export class Account {}

// Optional: an administrator lists and revokes any user's grants.
@userAdministration({ oauth: true })
export class Admin {}
```

`oauth` needs the login and an API that serves MCP (`outputs.api.mcp`).
The TypeScript server serves it; `check` refuses it on a Go or a Rust
server, which do not serve it yet. `oauth: true` takes every default; an
object sets them:

| Member | Default | Meaning |
| --- | --- | --- |
| `accessTokenTtlSeconds` | 3600 (1 h) | How long an access token lasts. |
| `refreshTokenTtlSeconds` | 2592000 (30 d) | How long a refresh token lasts, renewed on each rotation. |
| `grantMaxTtlSeconds` | 31536000 (365 d) | The longest a grant lasts, however often it refreshes. |
| `clients` | both | `metadataDocuments`: a client may name itself by a Client ID Metadata Document's URL, as Claude does. `registration`: a client may register (RFC 7591). |
| `consentPath` | the runtime's page | The project's own consent page, a path from the site's origin or a URL, which takes `?request=<id>`. |

The identity config, the API's `<API>_IDENTITY` field, takes the
deployment's part: `oauth.publicBaseUrl`, the URL the API is reached at
from outside, such as `https://app.example.com/api/notes`. The protected
resource is its `/api/mcp` and the issuer is it, so a client sees the URL
the person typed, not the one the server sees behind a site's proxy.
Without it the server answers for the request's own host and the
`X-Forwarded-Prefix` a site's proxy sends.

### What the server serves

| Route | What it is |
| --- | --- |
| `GET /.well-known/oauth-protected-resource`, and with the MCP endpoint's path after it | The protected resource metadata (RFC 9728). |
| `GET /.well-known/oauth-authorization-server`, `/.well-known/openid-configuration`, and each with the issuer's path after it | The authorization server metadata (RFC 8414): S256 alone, public clients alone (`none`), `client_id_metadata_document_supported`, and `registration_endpoint` when registration is on. |
| `GET` and `POST /oauth/authorize` | Stores the request and sends the browser to the consent page. A client it cannot read, or a redirect that is not the client's, is an error page; any other refusal goes back to the client's redirect. |
| `GET /oauth/consent` | The runtime's consent page, unless `consentPath` names one. |
| `POST /oauth/token` | `authorization_code` with its PKCE verifier, or `refresh_token`; form-encoded, RFC 6749's errors. |
| `POST /oauth/register` | Dynamic Client Registration, public clients with https or loopback redirects. |
| `POST /oauth/revoke` | RFC 7009. A refresh token revokes its grant. |
| `getOAuthRequest`, `approveOAuthRequest`, `denyOAuthRequest` | `auth/oauth/requests/{id}[/approve\|/deny]`, the JSON routes the consent page drives, with a session. |
| `listOAuthGrants`, `revokeOAuthGrant` | `auth/oauth/grants[/{id}]`, the person's connected apps. |
| `listUserOAuthGrants`, `revokeUserOAuthGrant` | `auth/admin/users/{id}/oauth/grants[/{grantId}]`, with `@userAdministration({ oauth: true })`. |

The MCP endpoint's 401 carries `WWW-Authenticate: Bearer
resource_metadata="..."`, with `error="invalid_token"` when a token was
refused, so a client finds the server from the endpoint's URL alone. The
OAuth operations are hidden from the tools: a person consents in their
own browser. The protocol routes run through the router's pipeline,
rate-limited per client by the router's key (the transport's peer
address unless `rateLimit.keyOf` names another), in its store.

### How a grant behaves

- **Consent.** The page names the client, who vouches for it (the host
  of a metadata document's URL; a registered client's name is its own
  claim), the host the request's redirect goes to (and warns when it is
  the person's own machine, as a command-line client's is), and the
  permissions it asks for, which are
  the API's permission names as scopes. The person may untick any. A
  request that names no scope asks for every permission the person
  holds.
- **Its tokens.** An access token is `oat_` and 43 characters, sent as
  `Authorization: Bearer`, never in a query string. A refresh token is
  `ort_...`, which only the token endpoint takes. The database keeps the
  SHA-256 of each.
- **Its audience.** An access token is held to the resource it was
  given for, the API's MCP endpoint under its public base: another API
  over the same `authDb` refuses it.
- **What it may do.** On every request the grant's permissions are
  narrowed against the person's current ones, as an API key's are, so a
  role taken away, a disabled user or a pending one counts on the next
  call. A token does not act on the person's account: the API key and
  OAuth routes, `logout` and `changePassword` need a session.
- **Once and bound.** A code works once, for 60 seconds, bound to its
  client, redirect, PKCE challenge (S256) and resource, each checked
  before the code is spent. A refresh token
  rotates on every use; using one twice, or redeeming a code twice,
  revokes the grant. Disabling a user revokes their grants.
- **Its record.** With the access log in the identity service's options,
  a grant given and one revoked are rows of it (`oauthGrant`,
  `oauthRevoke`), and a router whose options carry the log records each
  call a token makes (`oauthCall`).
- **Clients.** A metadata document is fetched over https alone, from a
  name that resolves to no private, loopback or link-local address, in
  5 seconds and 16 KB at most, with no redirect to another host, and
  kept as its cache headers say, a day at most. The fetch resolves the
  name again, so a name whose answer changes between the check and the
  fetch is not held; route the server's egress through a proxy where
  that matters. A registered client unused for 90 days that holds no
  live grant is pruned at the next registration, and the requests,
  codes and tokens that ended a day ago at the next authorization.

The four tables, `OAuthClient`, `OAuthGrant`, `OAuthCode` and
`OAuthToken`, are added beside every `User` table, as the API key's is,
whether or not an API turns `oauth` on: a project built before them has
four new tables to migrate, an expand step with no hazard.

Not built yet: the stack filling `publicBaseUrl` from the site's origin
and routing the site's root `/.well-known` paths to the API on the
Cloudflare and GCP sites, `stack dev` serving them for Claude Code, and
the Go and Rust servers. Until the site routes them, an API behind a site
serves discovery on its own origin alone. Claude reaches the server from
`160.79.104.0/21`, discovery included: no WAF rule may block it.

## What it does not do

The core model has no organizations or tenancy, single sign-on, second
factors or passkeys, email verification, password reset or account
lockout; login's rate limit and the hash's cost bound guessing instead. A
deployment that needs its own identity model registers its own auth
provider, as `examples/acme-schematic` does for its own keys.

A person or an organisation who never signs in, a contractor who texts a
photo, is no user: they are a party, a row of an app's own table that
acts through grants. Parties are built in the TypeScript runtime
([Outside parties](/superschematic/guides/parties/),
[Per-record access](/superschematic/guides/api-routes/#per-record-access)).
