A schema file imports decorators and type wrappers from the core authoring
packages. The package decides which kinds of schema may use them:
`@superschematic/schema` everywhere, `@superschematic/db` in DB schemas,
`@superschematic/api` in API schemas, `@superschematic/stack` in Stack
schemas, `@superschematic/memory-store` in MemoryStore schemas and
`@superschematic/tasks` in Tasks schemas. An extension adds its own from its own package. This page lists every decorator of the core packages and the type wrappers
these docs cover. [`superschematic catalog decorators`](/superschematic/reference/cli/#catalog-scalarsdecoratorsbehaviorscapabilities)
prints each one's TypeScript declaration and comment, the nodes it may sit
on and the kinds it is limited to, from the binary you run, an
extension's among them.

| `@stateMachine<T>({ field, transitions, terminal, fromNull? })` | class | the moves an enum field of the class may make (D118), one declaration per field: `field` is a field typed `E`, `Nullable<E>` or `Default<E, V>`, `transitions` maps a state to the states it may move to, `terminal` lists the states no update leaves, and on a `Nullable` field `fromNull` lists the states a null may take, `null` in a state's list returning the field to null. The build checks the graph: no transition leaves a terminal state, and every state is reached from the field's default, or from null. A write that keeps the value is no move, and an insert is not held. On a table of a DB service a trigger, on Postgres and SQLite, refuses every other move with `check_violation`, whatever writes the row, and a migration plan creates it in `contract`; on a class of any kind the Go, TypeScript, Python and Rust types get the terminal states and a function that says whether a move is listed. Refused on a `@queue` class and a field a behavior owns: a table's `Workflow` field is the other way to hold a status, moved by the behaviors' core with a permission | [Database tables](/superschematic/guides/database-tables/#state-machines), [Schema migrations](/superschematic/reference/migrations/#triggers-that-refuse-a-write) |
| `@fenced<T>({ field, covers? })` | class (a table of a DB schema) | names an integer field of the table, the fence, that every write it covers advances by one (D119), so a writer that compares it in its `WHERE` clause knows no covered write came between its read and its write. Without `covers`, every update of a row sets the fence to the stored value plus one; with `covers`, a list of the class's fields, an update that changes one of them does, and any other keeps the fence or adds one. A class has several fences when each lists its `covers` and no field is in two lists. A trigger, on Postgres and SQLite, refuses a write that does not, whatever writes the row, a migration plan creates it in `contract`, and the generated repositories advance the fence themselves. An insert is not fenced. The fence is a required field whose column is `SMALLINT`, `INTEGER` or `BIGINT` and that no `@stateMachine` governs. Refused on a `@queue` class, a version graph's member and a table that composes a behavior, whose rows the behaviors' core writes with statements that advance no fence; on an `@optimistic` table of a service that lists `sqlite`, a fence lists its `covers`. A fence counts no relation whose `onDelete` is `SET NULL`, a column the database itself sets when the row it names is deleted, with an update that advances no fence: the build refuses one that covers such a relation, and one without `covers` on a table that has one | [Database tables](/superschematic/guides/database-tables/#fences), [Schema migrations](/superschematic/reference/migrations/#triggers-that-refuse-a-write) |

## Stacks: `@superschematic/stack`

A Stack service (`kind: SchemaKind.Stack`) declares what runs where over
the services it names by their handles. Its build writes each
environment, resolved, to `stack/<service>/<environment>/environment.json`,
each Go server's entrypoint and Dockerfile to
`server/<service>/<server>/`, and with `outputs.ci` its CI workflow to
`ci/<service>/<renderer>/`. The stack takes its service's name. Each
class of its schema carries one of these decorators and no fields.

| Name | On | What it does | Covered in |

## Memory stores: `@superschematic/memory-store`

A MemoryStore schema declares each channel and key its store carries,
and nothing else (D75). The class is a declaration, not a type: no type
library emits it. Its fields, in order, are the parts of the
declaration's name, each a required string, integer, boolean, enum, or
superscalar scalar whose wire form is a string or an integer. A
declaration's name is its class's in kebab case unless `name` sets it,
one segment of lowercase letters, digits, `.`, `_` and `-`; `rate-limit`
is the core's.

| Name | On | What it does | Covered in |
| --- | --- | --- | --- |
| `@channel({ payload?, name? })` | abstract class | a channel: a wake-up or a sample every replica can lose. `payload` is the object type of each message, from a dependency of the store's schema and never `@strictJSON`; without it the channel is a signal, whose name is the whole message. A channel takes no TTL | [Memory stores](/superschematic/guides/memory-stores/#declare-a-store) |
| `@key({ use, ttlSeconds \| maxTtlSeconds, name? })` | abstract class | a key, which always expires: `use` is `"counter"`, which counts, or `"claim"`, which lets one caller do a piece of work once. It sets exactly one of `ttlSeconds`, its TTL from the write that creates it, and `maxTtlSeconds`, the longest TTL a call gives it; both are 1 to 604800 seconds | [Memory stores](/superschematic/guides/memory-stores/#declare-a-store) |
