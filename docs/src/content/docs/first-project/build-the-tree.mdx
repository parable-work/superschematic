So far each part built one service. `build-all` builds every service under
a directory in one process, in dependency order, and is what a project runs
in CI and before a release.

## Build every service

```sh
superschematic build-all schemas/services
```

```
Discovered 4 schema services: shop-db, shop-api, shop-common, shop-storefront (mode: sequential)
  Shared TypeScript program: 4 service(s)
  ...
  OK: shop-db (built)
  ...
  OK: shop-api (built)
  ...
  OK: shop-common (built)
  ...
  OK: shop-storefront (built)
  Wrote .../schemas/dist/.deps.json

All 4 schema services built successfully
```

The order comes from the configs: `shop-api` names `shop-db` as its
`authDb`, and `shop-storefront` lists `shop-common` in its `dependencies`,
so each builds after the service it needs. All four load through one
TypeScript program, which is faster than four separate builds.
`--parallel` builds services that do not depend on each other at the same
time.

`build --with-deps <service>` builds one service and everything it depends
on, and nothing else:

```sh
superschematic build --with-deps schemas/services/shop-storefront
```

```
Resolved 2 schema services for shop-storefront: shop-common, shop-storefront
...
Built 2 schema services for shop-storefront
```

## The package graph

`build-all` also writes `dist/.deps.json`, the graph of the generated
packages: each package's language, kind, name, the service that produced
it, and the packages it depends on. `shop-api`'s Go server depends on its
own types and on `shop-db`'s ORM:

<Snippet file="testdata/generated/deps.json" title="schemas/dist/.deps.json" from='"id": "shop-api-api"' to="]" />

A release script can publish the packages in this order, and a CI job can
build only what a change touched. `dist/` is usually ignored by version
control; `[deps] copy = "<path>"` in `superschematic.toml` writes a copy
you can commit.

## Reuse outputs with the cache

With `--cache`, `build-all` keeps each service's output in a
content-addressed cache, keyed by a hash of the service's inputs and of
the binary. A service whose inputs have not changed is skipped, and one
whose outputs are missing is restored:

```sh
superschematic build-all --cache schemas/services
```

```
  OK: shop-db (up to date)
  OK: shop-api (up to date)
  OK: shop-common (up to date)
  OK: shop-storefront (up to date)
```

After `rm -rf schemas/dist`, the same command answers
`restored from cache` for each service. The cache lives in your XDG cache
directory; `--cache-root`, `SUPERSCHEMATIC_BUILD_CACHE_DIR` or
`[cache] root` in the naming file move it. Because the key covers the
binary, build the CLI with `make build`, which strips the checkout's paths
and revision, so the key survives a commit that changes no Go code.

## Check it in CI

`examples/acme-shop/scripts/check.sh` is a complete CI script for a
project like this one:

1. `build-all` with the core binary;
2. `go build` and `go vet` on every generated Go module;
3. the Go service's tests, which call the generated server through the
   generated Go SDK;
4. `tsc` on the generated router and the TypeScript service, and its
   tests, which call the router through the generated TypeScript SDK;
5. a byte comparison of the generated files these pages quote against
   their committed copies under `testdata/generated/`.

It runs on every pull request to this repository, so the pages of this
tutorial stay true.
