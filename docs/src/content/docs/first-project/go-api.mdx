Shop staff add products and shoppers browse them. `shop-api` declares
those routes over the `Product` table. superschematic generates the Go
server, which routes, decodes, validates and checks permissions, its
`main`, and a Go SDK to call it. You write the business logic and say who
the caller is.

## Declare the API

<Snippet file="schemas/services/shop-api/src/products.schema.ts" />

- `ProductView` is what a caller sees of a product. `@source(Product)`
  makes it a view of the table, and the loader checks that each field
  matches a field of the table with a compatible type. It lists only the
  columns a caller may see.
- `CreateProductInput` is a plain type. `Validate<Generic.Int64, { min: 0 }>`
  adds a constraint that the generated Go types enforce, so the Go SDK
  refuses to send a negative price and the Go server refuses to accept one.
- A class of methods is an operation set. `@rest` gives each method its
  HTTP method and path, and the server mounts the paths under `/api`. The
  method bodies never run.
- `extends Authenticated` puts every route of the set behind the auth
  middleware. `@requirePermission` lists the permissions that let a caller
  in; a granted permission covers the ones nested under it, so `products`
  covers `products.read` and `products.write`.
- `QueryParam<boolean>` reads `inStock` from the query string.

## Configure it

<Snippet file="schemas/services/shop-api/schema.config.ts" />

- `api: { enabled: true }` generates the Go server, the default language.
  The server decodes requests into the Go types, so `types` lists Go.
- `public: true` marks an API whose callers the Go server authenticates. It
  turns on the auth provider's middleware and stores in the Go server.
  Without it, a `@requirePermission` route answers 401 unless the
  service's own middleware puts the caller on the context. The SDKs send
  a token either way, since those routes need a caller.
- `authDb` names the DB schema the auth provider reads its stores from,
  by `shop-db`'s handle, `ShopDb`, imported from `@acme/shop-db`.
  The core provider, `session`, finds `shop-db`'s `Session` and `User`
  tables and generates stores over the ORM for them.
- `sdk` lists the SDK languages. Any API can have an SDK in Go, TypeScript,
  Python or Rust, whatever language serves it. An SDK decodes and validates
  with the types package of its own language, so `types` lists every SDK
  language too.

## Implement the routes

`ProductQueries` and `ProductMutations` share the `product` namespace, so
the server asks for one implementation with all three methods:

<Snippet file="testdata/generated/api/shop-api/interfaces.go" symbol="ProductImplementation" />

The implementation of an API is a Go package at a path the naming file's
`[implementation_paths]` table gives, `go/{service}` from the parent of
the schemas root by default, so `shop-api`'s is `examples/acme-shop/go/shop-api`.
A stack's build writes a scaffold there when the package is missing, each
method answering 501, and never touches it again. The example implements
it over the ORM:

<Snippet file="go/shop-api/products.go" symbol={['Products', 'Products.GetProduct', 'Products.ListProducts']} />

The server has already decoded and validated the arguments, so a method
only does the work. The implementation imports the generated package as
`api`. An error from `api.NotFoundError` answers 404, and the other
constructors in `errors.go` (`BadRequestError`, `ConflictError`,
`ForbiddenError` and more) answer their own statuses. Any other error is
logged and answers 500 with a generic message, so no internal detail
reaches the caller.

The build also writes what the implementation is built from. `Deps`
holds the API's configuration, the ORM of its `authDb` and a logger, and
`Constructor` is the signature of the package's `New`:

<Snippet file="testdata/generated/api/shop-api/deps.go" symbol={['Deps', 'Constructor']} />

<Snippet file="go/shop-api/implementation.go" symbol="New" />

The example writes its implementation and wires its server by hand. To
start one, `superschematic build --scaffold schemas/services/shop-api`
writes `go/shop-api/implementation.go`, whose `New(deps Deps)` builds
every namespace from the generated `Deps` (here a `Config` with the
connection to `shop-db`, the `shop-db` ORM and a logger) and whose methods
answer 501 until you write them. A stack's build scaffolds it with no flag
and writes the server's entrypoint, which calls `New`
([Start an implementation](/superschematic/guides/api-routes/#start-an-implementation)).

## Say who the caller is

You write no auth code. `shop-db`'s `User` table has the core `User`
trait, signing in with its email, and its `Role` table the `UserRole`
trait. The build adds the tables the core owns beside them, `Session`,
`UserCredential` and `UserRoleGrant`, and every API whose `authDb` is
`shop-db` authenticates its callers with the identity runtime:

<Snippet file="schemas/services/shop-db/src/shop.schema.ts" symbol={['User', 'Role']} />

`shop-api` also serves the routes a user signs in and out with, and staff
manage users and roles with:

<Snippet file="schemas/services/shop-api/src/account.schema.ts" />

The generated `Config` takes the identity service, which the generated
`NewIdentity` builds over a store of `shop-db`'s tables. Its middleware
reads the session the request carries and puts the caller and their roles
on the request context. Each route then checks its `@requirePermission`
list against the roles and answers 403 when none covers it.
[Auth and permissions](/superschematic/guides/auth-and-permissions/#turn-it-on-the-user-model)
has the rest.

## Run it

You write no `main`. A stack, a service of the kind `Stack`, says what
runs and where. `shop-stack` deploys `shop-api` and `shop-orders`, each on
a server of its own, and its `Dev` environment runs them on the `local`
target:

<Snippet file="schemas/services/shop-stack/src/stack.schema.ts" />

With Docker running and the migration runner, `superschematic-migrate`, on
your `PATH` (see [the runner](/superschematic/reference/migrations/#the-runner)),
run it from `examples/acme-shop`:

```sh
superschematic stack dev
```

`stack dev` builds the stack and each service it deploys, with their
dependencies, then:

- writes each server's entrypoint, a Go module under
  `schemas/dist/server/shop-stack/`, whose `main` reads its configuration
  from the environment, connects to the database, calls `New` with the
  server's `Deps`, builds the API's identity service over `shop-db`, and
  serves the routes beside `/healthz` and `/readyz`;
- starts Postgres in a container, with a database for `shop-db` migrated
  to its schema;
- builds each server and starts it, waiting until it answers `/readyz`,
  then prints where each one is reached.

Nothing in the project names a port or a connection string. The build
derives them and writes the environment it resolved to
`schemas/dist/stack/shop-stack/Dev/environment.json`, where each server's
bindings are the configuration it is started with:

<Snippet file="testdata/generated/stack/shop-stack/Dev/environment.json" from={'"name": "shop-api",'} to={'"edge": "sql:shop-api->shop-db"'} />

Ctrl-C stops the servers and the container, which keeps its data for the
next run; `--remove-database` removes it too. The routes answer a caller
with a session in `shop-db`. `TestStackDevRunsTheShop`, in
`examples/acme-shop/go/stack_dev_test.go`, runs `stack dev`, creates a
user with the identity runtime's store, signs them in through `shop-api`'s
login, and calls both APIs through their SDKs. The
[CLI reference](/superschematic/reference/cli/#stack-dev-stack-service-dir)
lists the flags.

## Call it from Go

The generated SDK is the module `example.com/acme/sdk/go/shop-api`. Its
client has one field per namespace, and each method takes the same
arguments as the route. The example's tests serve the API in-process, as
the entrypoint does, with the ORM's no-op database in place of Postgres
and the identity service over a store in memory, sign in through the
SDK's `Login`, and drive it through the SDK:

<Snippet file="go/server_test.go" symbol={['productsServer', 'signIn', 'TestTheSDKCallsTheGeneratedServer']} />

- `AuthConfig.Token` sends `Authorization: Bearer <token>`. `GetToken`
  resolves a token per request, with the request's context, when no static
  token is set, and `RefreshToken` is called after a 401.
- `SDKConfig.ServiceCredential` sends a calling service's own credential in
  `Service-Authorization` and asks its `Token` for a fresh one once after a
  401 with the code `service_unauthorized`
  ([D37](https://github.com/parable-work/superschematic/blob/main/docs/DECISIONS.md#d37-a-service-caller-beside-the-end-user-admitted-per-operation)).
  A server forwards its own caller by setting `GetToken` to
  `serviceauth.ForwardedToken`, which reads the token of the request on the
  call's context.
- The SDK validates an input before it sends it and returns a
  `*sdk.ValidationError` without a request.
- A response outside 2xx returns an `*sdk.APIError`, or a type that embeds
  one: `*sdk.AuthenticationError` for 401, `*sdk.AuthorizationError` for
  403.

Run the tests from `examples/acme-shop/go` after building the schemas,
with the flags from
[Prerequisites](/superschematic/start/prerequisites/#compile-generated-go-code)
exported:

```sh
go test ./...
```

`examples/acme-shop/go/go.mod` requires each generated module and points a
`replace` line at `schemas/dist`, until the modules are published.

## Call it from TypeScript

The same build wrote a TypeScript SDK for this API, `@acme/shop-api-sdk`.
Its client is `ShopApiSDK`, with a `product` namespace:
`new ShopApiSDK({ baseUrl, auth: { token } })`, then
`await sdk.product.getProduct(id)`. The
[TypeScript path](/superschematic/first-project/typescript-api/) shows a
TypeScript SDK at work.
